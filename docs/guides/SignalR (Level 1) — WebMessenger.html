SignalR (Level 1) — WebMessenger

Подробный практический гайд по базовым навыкам SignalR с учетом текущей реализации WebMessenger после рефакторинга 2026 года.

Проект: ASP.NET Core 8 + SignalR + Next.js client (@microsoft/signalr)

1. Где SignalR живет в проекте сейчас

  • Hub endpoint: /hubs/chat (регистрация в Program.cs)
  • Hub: ChatHub : Hub<IChatClient>
  • Server push из сервисов: ChatEvents через IHubContext<ChatHub, IChatClient>
  • Группы: SignalRGroups.User/Chat/Direct
  • Клиентское соединение: singleton в chatHubClient.ts с reconnect и guard от гонок старта
// Program.cs (актуальное состояние)
builder.Services.AddSignalR(options =>
{
    options.EnableDetailedErrors = builder.Environment.IsDevelopment();
    options.KeepAliveInterval = TimeSpan.FromSeconds(15);
    options.ClientTimeoutInterval = TimeSpan.FromSeconds(30);
    options.MaximumReceiveMessageSize = 32 * 1024;
});

app.MapHub<ChatHub>("/hubs/chat").RequireCors("Front");
В WebMessenger SignalR это realtime-канал поверх REST: REST подтверждает и хранит данные, SignalR доставляет события клиентам быстро и адресно.

2. Declared Contracts: что нужно объявлять явно

Даже на Level 1 важно не оставлять "неявные" контракты. В проекте должны быть явно объявлены:

  • Hub-методы, которые вызывает клиент;
  • server-to-client события;
  • типы payload;
  • правила именования групп;
  • параметры транспорта и reconnect.

Как это реализовано в WebMessenger

  • Клиентские константы: ChatHubEvents и ChatHubMethods
  • Серверный клиентский контракт: IChatClient
  • Payload модели: MessageCreatedPayload, ReadReceiptPayload, TypingPayload
  • Группы: user:{id}, chat:{id}, dm:{a}:{b}
// Пример client-side контрактов
export const ChatHubEvents = {
  MessageCreated: 'MessageCreated',
  Typing: 'Typing',
  ReadReceipt: 'ReadReceipt',
} as const;

export const ChatHubMethods = {
  JoinChat: 'JoinChat',
  JoinDirect: 'JoinDirect',
  LeaveChat: 'LeaveChat',
  LeaveDirect: 'LeaveDirect',
  Typing: 'Typing',
  MarkRead: 'MarkRead',
} as const;
Когда контракты не объявлены явно, ошибка обычно не компилируется заранее, а проявляется только в рантайме: "подключено, но событие не приходит".

4. Users, Connections, Groups: базовая модель адресации

Один пользователь может иметь несколько активных подключений (вкладки, устройства). SignalR адресует события не только пользователю, но и конкретным группам подключений.

Сущности

  • User: доменный пользователь из JWT (Guid).
  • Connection: конкретная физическая сессия (ConnectionId).
  • Group: множество ConnectionId, объединенных логикой маршрутизации.

Паттерны WebMessenger

  • user-group: для событий "на все устройства пользователя".
  • chat-group: для room/группового чата.
  • dm-group: для direct-пары пользователей.
// ChatHub.OnConnectedAsync
await Groups.AddToGroupAsync(Context.ConnectionId, SignalRGroups.User(userId.Value));

// Join в конкретный контекст
await Groups.AddToGroupAsync(Context.ConnectionId, SignalRGroups.Chat(chatId), ct);
await Groups.AddToGroupAsync(Context.ConnectionId, SignalRGroups.Direct(me, otherUserId), ct);
Группа это не хранилище состояния, а routing-структура. Источник истины о правах доступа остается в бизнес-сервисах и БД.

Хорошая базовая дисциплина: бизнес-операции живут в сервисах, а отправка realtime-событий инкапсулирована в одном месте.

6. Strongly Typed Hub в WebMessenger

В проекте уже включен typed-подход: ChatHub : Hub<IChatClient>. Это важный шаг зрелости даже для Level 1.

Что это дает

  • События становятся методами интерфейса, а не строками.
  • Ошибки имен ловятся на этапе компиляции.
  • Проще поддерживать контракт между backend и frontend.
public interface IChatClient
{
    Task MessageCreated(MessageCreatedPayload payload, CancellationToken ct = default);
    Task ReadReceipt(ReadReceiptPayload payload, CancellationToken ct = default);
    Task Typing(TypingPayload payload, CancellationToken ct = default);
}

public class ChatHub : Hub<IChatClient> { ... }
Typed hub не отменяет необходимость в строгой версии payload-контрактов. Если поле удалено/переименовано, клиент также нужно обновлять согласованно.

7. Lifetime в SignalR: максимально простое объяснение

Базовые lifetimes в DI

  • Transient: новый объект при каждом запросе зависимости.
  • Scoped: один объект на scope (обычно HTTP-запрос).
  • Singleton: один объект на весь жизненный цикл приложения.

Ключевая мысль про Hub

Экземпляр Hub не живет как "сессия пользователя". Он создается для обработки вызовов и не должен хранить долгоживущее изменяемое состояние.

Что хранить где

Тип данныхГде хранить правильноПочему
Права доступа, членство в чатахБД/сервисыНужно консистентное правило на всех инстансах
Временные routing-связиSignalR GroupsЭто нативный механизм маршрутизации
Кэш, общий для всех запросовThread-safe singleton cache/RedisИзбегаем дублирования и race-condition
Per-request контекстScoped сервисИзолирует состояние конкретного запроса

Как сейчас в WebMessenger

  • IChatService - Scoped (корректно для бизнес-операций).
  • IChatEvents - Singleton (допустимо, потому что класс stateless и работает через IHubContext).
  • ChatHub не хранит собственный mutable state между вызовами.

Почему Singleton для ChatEvents сейчас нормален

  • Внутри нет mutable shared state вроде Dictionary без синхронизации.
  • Нет прямой зависимости на scoped-сервисы в полях singleton.
  • Используется IHubContext, который безопасно инжектится в singleton-слой отправки.

Где чаще ломают lifetime (и как не ломать)

ОшибкаПочему плохоКак исправить
Singleton инжектит DbContext/Scoped сервисНарушение DI boundary, runtime ошибки/утечкиИспользовать IServiceScopeFactory и создавать scope в момент вызова
Хранить user state в полях HubПотеря состояния после reconnect/redeployХранить в БД/Redis и вычислять заново
Shared mutable список подключений без lockRace-condition под нагрузкойConcurrent коллекции или внешнее хранилище
// Если singleton все же должен обратиться к scoped-сервису
public sealed class MySingleton(IServiceScopeFactory scopeFactory)
{
    public async Task DoWorkAsync()
    {
        using var scope = scopeFactory.CreateScope();
        var svc = scope.ServiceProvider.GetRequiredService<IMyScopedService>();
        await svc.RunAsync();
    }
}
Простое правило: singleton может быть stateful только если этот state thread-safe, ограничен по памяти, и действительно должен быть общим для всего приложения.

8. Filters (IHubFilter) и их lifetime: подробно

IHubFilter это middleware-подобный слой для Hub-методов: валидация, аудит, rate-limit, метрики, корреляция логов.

Что фильтр перехватывает

  • вызов hub-метода до выполнения;
  • исключение, если оно выброшено;
  • результат после выполнения;
  • события connect/disconnect (если реализованы соответствующие методы фильтра).

Где в WebMessenger сейчас

На текущий момент фильтры не зарегистрированы, но проект уже зрел для их добавления.

Какой lifetime выбрать для фильтра

Lifetime фильтраКогда уместноНа что смотреть
SingletonФильтр stateless, только логирует/метрикиНикаких mutable полей без thread-safety, не инжектить scoped напрямую
ScopedНужен scoped-контекст, например current user/request servicesБольше allocations, но проще безопасно работать с scoped зависимостями
TransientРедко, если фильтр легкий и без состоянияНа практике обычно singleton/scoped удобнее

Безопасный singleton filter пример

public sealed class HubLoggingFilter(ILogger<HubLoggingFilter> log) : IHubFilter
{
    public async ValueTask<object?> InvokeMethodAsync(
        HubInvocationContext invocationContext,
        Func<HubInvocationContext, ValueTask<object?>> next)
    {
        var sw = System.Diagnostics.Stopwatch.StartNew();
        try
        {
            var result = await next(invocationContext);
            sw.Stop();
            log.LogInformation("Hub {Hub} method {Method} ok in {Ms}ms",
                invocationContext.Hub.GetType().Name,
                invocationContext.HubMethodName,
                sw.ElapsedMilliseconds);
            return result;
        }
        catch (Exception ex)
        {
            sw.Stop();
            log.LogWarning(ex, "Hub {Hub} method {Method} failed in {Ms}ms",
                invocationContext.Hub.GetType().Name,
                invocationContext.HubMethodName,
                sw.ElapsedMilliseconds);
            throw;
        }
    }
}
// Регистрация
builder.Services.AddSingleton<HubLoggingFilter>();
builder.Services.AddSignalR().AddHubOptions<ChatHub>(opts =>
{
    opts.AddFilter<HubLoggingFilter>();
});

Scoped filter пример

public sealed class HubValidationFilter(IMyScopedValidator validator) : IHubFilter
{
    public async ValueTask<object?> InvokeMethodAsync(
        HubInvocationContext ctx,
        Func<HubInvocationContext, ValueTask<object?>> next)
    {
        validator.Validate(ctx.HubMethodArguments);
        return await next(ctx);
    }
}

builder.Services.AddScoped<HubValidationFilter>();
Главный practical check: если фильтр singleton и в нем есть mutable поля (счетчики, списки, кэш), они обязаны быть потокобезопасными, иначе под нагрузкой получите нестабильные баги.

9. Клиентский lifetime connection: почему singleton connection правильный

  • Один HubConnection на приложение снижает число лишних сокетов и гонок подписок.
  • startPromise guard защищает от параллельных start().
  • subscribeChatReconnected с unsubscribe предотвращает накопление обработчиков.
  • Явные serverTimeoutInMilliseconds и keepAliveIntervalInMilliseconds синхронизированы с сервером (30с/15с).
// Ключевая идея
if (!startPromise) {
  startPromise = conn.start().finally(() => { startPromise = null; });
}
await startPromise;
Для SPA это стандартный надежный шаблон: singleton connection + явный reconnect lifecycle + аккуратная подписка/отписка в хуках.

10. Мини-сценарий end-to-end в текущей архитектуре

  1. Пользователь открывает чат, клиент вызывает JoinChat.
  2. Hub валидирует membership через IChatService и добавляет connection в chat:{id}.
  3. При отправке сообщения сервис вызывает IChatEvents.MessageCreatedAsync.
  4. ChatEvents отправляет typed payload в нужные группы.
  5. Клиентские хуки получают событие MessageCreated и обновляют UI списка и активного чата.
  6. При reconnect клиент автоматически переподключается и пере-join-ит целевую группу.
