.NET Deployment Guide — WebMessenger

Practical deployment handbook for ASP.NET Core API and monorepo Docker stack.

Project: WebMessenger.Api + Client + MySQL · .NET 8 · Next.js 15 · Docker Compose

1. Deployment Architecture Overview

This repository uses a split architecture:

  • Client: Next.js app in Client/
  • Server: ASP.NET Core API in Server/WebMessenger.Api/
  • Database: MySQL (Docker container in the local workflow)

Runtime topology in Docker

Browser
  -> http://localhost:3000 (Client)
  -> Client server routes call http://api:8080 (internal docker network)
  -> API exposed externally on http://localhost:5227
  -> API uses MySQL at host name db:3306 (internal docker network)
  -> MySQL also exposed to host on 127.0.0.1:3307 (for tools like Workbench)
Why two API URLs exist:
PUBLIC_API_URL is used by browser-side code.
API_BASE_URL is used by server-side Next.js routes inside the compose network.

5. IIS vs Kestrel

Kestrel only

API runs directly with dotnet WebMessenger.Api.dll. Reverse proxy is optional.

IIS hosting in this project

Server/WebMessenger.Api/web.config configures AspNetCoreModuleV2 and launches the API process.

Your IIS using localhost:8080 does not conflict with Docker API in this setup because Docker publishes API on localhost:5227.

6. Secrets and Connection Strings

Development secrets with user-secrets

cd Server/WebMessenger.Api
dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Server=localhost;Port=3306;Database=WebMessenger;Uid=root;Pwd=***;"
dotnet user-secrets set "Jwt:Key" "***"
dotnet user-secrets set "Dropbox:AccessToken" "***"

Docker local secrets

Values are loaded from .env.docker by compose.

Production secrets

  • Use host environment variables or secret store
  • Do not commit real keys to repository
  • Rotate keys after accidental exposure

7. Docker Configuration from Scratch

7.1 Files required

  • Dockerfile.api - builds and runs ASP.NET Core API
  • Dockerfile.client - builds and runs Next.js app
  • docker-compose.yml - orchestrates db/api/client
  • .env.docker.example - committed template for local env values
  • .env.docker - local runtime values (created from template, not committed)
  • .dockerignore - reduces build context
  • docker/mysql/init/00-import-optional-dump.sh - optional dump import on first db init
  • docker/mysql/dumps/ - local dump files directory

7.2 Compose service map

services:
  db      -> mysql:8.0
             command: mysqld --lower_case_table_names=1
             ports: 3307:3306
             mounts optional init script + dumps directory
  api     -> build from Dockerfile.api
             applies EF Core migrations on startup
  client  -> build from Dockerfile.client

volumes:
  mysql_data

7.3 Deterministic env names

Database variables use WM_ prefix to avoid collision with machine-wide vars.

WM_MYSQL_ROOT_PASSWORD
WM_MYSQL_DATABASE
WM_MYSQL_USER
WM_MYSQL_PASSWORD
WM_DB_DUMP_FILE

Optional dump import behavior

The db init script imports a dump file only when all conditions are true:

  • WM_DB_DUMP_FILE is set
  • The file exists inside container path
  • The file is non-empty

Recommended value when file exists in docker/mysql/dumps:

WM_DB_DUMP_FILE=/docker-entrypoint-initdb.d/dumps/webmessenger-dump-20260502.sql
Generic variable names like MYSQL_USER can be overridden by host environment unexpectedly.

8. First Run Checklist

Step A: Prepare env file

# macOS / Linux
cp .env.docker.example .env.docker

# Windows
copy .env.docker.example .env.docker

Fill all required values
Set WM_DB_DUMP_FILE to a file in docker/mysql/dumps, or keep optional placeholder

Step B: If you need first-time dump import, reset DB volume

docker compose --env-file .env.docker down -v

Init scripts in /docker-entrypoint-initdb.d run only during first database initialization.

Step C: Build and start

docker compose --env-file .env.docker up -d --build

Step D: Validate

  • Client: http://localhost:3000
  • API Swagger: http://localhost:5227/swagger
  • MySQL host access: 127.0.0.1:3307
  • Containers: all services Up, db Healthy

Step E: Confirm dump import in db logs

docker compose --env-file .env.docker logs --tail=200 db

Expected lines include Optional dump import step and Dump import completed successfully.

Step F: Stop

docker compose --env-file .env.docker down

9. Troubleshooting Playbook

SymptomLikely causeFix
POST /api/auth/login returns 500Database schema not appliedEnsure startup migration is enabled and api logs show "Database migration completed"
Table 'WebMessenger.Users' doesn't existFresh DB volume without migrationsUse fresh init + verify API migration step is active
Both users and Users tables existCase-sensitive MySQL table behaviorRun db with --lower_case_table_names=1, then recreate volume with down -v
Dump file did not importNo first init, wrong path, missing file, or empty fileCheck WM_DB_DUMP_FILE, file location in dumps folder, and rerun with down -v
Connection refused to dbMySQL not healthy yetWait for db health, inspect db logs
Client cannot call APIWrong PUBLIC_API_URL/API_BASE_URLCorrect .env.docker values and recreate containers
Port already in useHost port conflictChange published host port in compose file

Useful diagnostics

docker compose --env-file .env.docker ps
docker compose --env-file .env.docker logs --tail=200 api
docker compose --env-file .env.docker logs --tail=200 db
docker compose --env-file .env.docker config
docker exec -i webmessenger-db mysql -uroot -p*** -e "SELECT @@lower_case_table_names;"
docker exec -i webmessenger-db mysql -uroot -p*** -e "USE WebMessenger; SELECT table_name FROM information_schema.tables WHERE table_schema='WebMessenger' AND LOWER(table_name)='users';"

10. Change Management: Rebuild vs Restart

What changedAction
Only runtime env valuesRecreate/restart service
Source code in API/ClientRebuild image for changed service
DockerfileRebuild required
Compose ports/volumes/networkRecreate compose stack

Current setup does not hot-reload source code by default because code is copied into image during build.

11. Docker Desktop Workflow (UI-first)

  1. Open Docker Desktop -> Containers
  2. Find compose app webmessenger
  3. Use Start / Stop / Restart at app or service level
  4. Open service logs directly in UI
  5. Use Exec tab to inspect container internals
  6. Use Volumes tab for DB data lifecycle management

External DB tools (MySQL Workbench)

  • Host: 127.0.0.1
  • Port: 3307
  • User: root
  • Password: from WM_MYSQL_ROOT_PASSWORD
  • Schema: WebMessenger
If your Docker Desktop version does not show a dedicated compose create button, start once via CLI, then manage everything through UI.
