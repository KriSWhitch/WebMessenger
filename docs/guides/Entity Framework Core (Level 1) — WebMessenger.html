1. Setup and Configuration — Настройка и конфигурация

1.1 Пакеты и провайдеры

EF Core (Entity Framework Core) — это ORM (Object-Relational Mapper) от Microsoft: он позволяет работать с реляционной базой данных через обычные C#-классы и LINQ-запросы, не писать SQL вручную. Сам по себе Microsoft.EntityFrameworkCore не умеет разговаривать ни с одной конкретной СУБД — для этого нужен провайдер. Провайдер транслирует LINQ-дерево выражений в SQL нужного диалекта и передаёт команды низкоуровневому ADO.NET-драйверу базы данных.

В WebMessenger используется MySQL 8 через community-провайдер Pomelo.EntityFrameworkCore.MySql — наиболее популярный и активно поддерживаемый вариант для MySQL / MariaDB.

1.2 Code-First vs Database-First

EF Core поддерживает два основных подхода к работе со схемой базы данных. Выбор определяет, что является источником истины: C#-классы или существующая БД.

Code-First (WebMessenger)Database-First
Источник истины C#-классы сущностей + конфигурация в OnModelCreating Существующая структура таблиц в БД
Рабочий процесс Пишешь классы → dotnet ef migrations add → database update dotnet ef dbcontext scaffold → EF генерирует классы по схеме БД
История изменений Файлы миграций в git — видно кто, когда и что изменил в схеме Только в БД или отдельных SQL DDL-скриптах вне системы контроля версий
Когда выбирать Новый проект — полный контроль над схемой, команда работает через код Есть legacy БД которую нельзя менять; DBA контролирует схему вручную
Риски Нужна дисциплина с миграциями: нельзя терять или редактировать применённые файлы Регенерация классов затирает ручные правки; схема и код могут разойтись

В WebMessenger используется Code-First: классы User, Chat, Message, ChatMember, Contact в папке WebMessenger.DAL/Entities/ — источник истины схемы. Папка Migrations/ хранит полную историю изменений в виде C#-файлов, коммитируемых вместе с остальным кодом.

1.3 DbContext — Unit of Work и Identity Map

DbContext — центральный класс EF Core, реализующий два классических паттерна:

  • Unit of Work — отслеживает все изменения сущностей с момента создания контекста и сбрасывает их в БД единой транзакцией при вызове SaveChangesAsync. Не нужно вручную писать BEGIN / COMMIT для каждой операции.
  • Identity Map — гарантирует, что один и тот же ряд таблицы (по PK) представлен ровно одним объектом в памяти. Два запроса с одинаковым Guid вернут один и тот же экземпляр — не дубликат.

Каждый DbSet<T> — это репозиторий для конкретной сущности: через него строятся LINQ-запросы и выполняются Add / Remove. 

// WebMessenger.DAL/Data/ApplicationDbContext.cs
// Primary constructor C# 12 — DbContextOptions содержит строку подключения,
// провайдер и все опции, заданные в Program.cs через AddDbContext.
public class ApplicationDbContext(DbContextOptions<ApplicationDbContext> options)
    : DbContext(options)
{
    // DbSet<T> — одна таблица = один DbSet.
    // Имя свойства — имя таблицы по умолчанию (EF плюрализует: User → Users).
    // EF Core сам инициализирует свойства при создании контекста через рефлексию.
    public DbSet<User>       Users       { get; set; }
    public DbSet<Chat>       Chats       { get; set; }
    public DbSet<Message>    Messages    { get; set; }
    public DbSet<ChatMember> ChatMembers { get; set; }
    public DbSet<Contact>    Contacts    { get; set; }

    // OnModelCreating — вызывается один раз при первой инициализации модели.
    // Здесь задаётся то, что нельзя выразить Data Annotations:
    // составные индексы, SQL-дефолты, поведение при удалении (Cascade / Restrict).
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        var ts = "CURRENT_TIMESTAMP(6)";  // MySQL: точность до микросекунды

        modelBuilder.Entity<Message>(entity =>
        {
            entity.Property(m => m.SentAt)
                  .HasColumnType("datetime(6)")
                  .HasDefaultValueSql(ts)   // БД проставит метку времени при INSERT
                  .ValueGeneratedOnAdd();    // EF знает: значение генерирует БД, не C#

            // Составной индекс — критичен для курсорной пагинации истории чата:
            // WHERE ChatId = ? AND SentAt < ? ORDER BY SentAt DESC LIMIT ?
            entity.HasIndex(m => new { m.ChatId, m.SentAt });
        });

        modelBuilder.Entity<ChatMember>(entity =>
        {
            // Уникальный составной индекс: один пользователь — один раз в чате
            entity.HasIndex(cm => new { cm.UserId, cm.ChatId }).IsUnique();
        });

        modelBuilder.Entity<Contact>(entity =>
        {
            // Restrict — нельзя удалить User, если у него есть Contact-записи.
            // Без явного OnDelete Pomelo/MySQL выбрал бы CASCADE или NO ACTION.
            entity.HasOne(c => c.OwnerUser)
                  .WithMany(u => u.Contacts)
                  .HasForeignKey(c => c.OwnerUserId)
                  .OnDelete(DeleteBehavior.Restrict);

            entity.HasOne(c => c.ContactUser)
                  .WithMany()
                  .HasForeignKey(c => c.ContactUserId)
                  .OnDelete(DeleteBehavior.Restrict);
        });
    }
}
DbContext не является потокобезопасным — нельзя использовать один экземпляр из нескольких потоков одновременно. Именно поэтому он регистрируется как Scoped: один экземпляр на один HTTP-запрос. Singleton-использование DbContext — распространённая ошибка, ведущая к гонкам данных и InvalidOperationException вида "A second operation was started on this context before a previous operation completed".

1.4 Регистрация DbContext в DI-контейнере

AddDbContext<T> регистрирует ApplicationDbContext как Scoped-сервис. В конце каждого HTTP-запроса DI-контейнер автоматически вызовет Dispose(), закрыв контекст и вернув соединение в connection pool. 

// Program.cs — полная регистрация из WebMessenger с разбором каждой строки
builder.Services.AddDbContext<ApplicationDbContext>((sp, options) =>
{
    // UseMySql — метод расширения из Pomelo.
    // MySqlServerVersion нужен чтобы Pomelo генерировал SQL под нужную версию MySQL:
    // JSON-функции, точность datetime, LIMIT/OFFSET и т.д.
    options.UseMySql(
        builder.Configuration.GetConnectionString("DefaultConnection"),
        new MySqlServerVersion(new Version(8, 0, 42)),
        mysqlOptions =>
        {
            // Автоматически повторять запрос при transient-ошибках:
            // обрыв сети, временная недоступность БД, таймаут соединения.
            // По умолчанию — до 6 попыток с экспоненциальной задержкой.
            // Особенно важно в Docker и облаке при перезапуске контейнера БД.
            mysqlOptions.EnableRetryOnFailure();
        }
    );

    // Диагностические опции включаем только в Development
    if (sp.GetRequiredService<IHostEnvironment>().IsDevelopment())
    {
        // Показывать фактические значения параметров SQL в логах.
        // Без этого: Executed ... WHERE UserId = @p0
        // С этим:    Executed ... WHERE UserId = '3fa85f64-5717-4562-b3fc-2c963f66afa6'
        // ЗАПРЕЩЕНО в продакшне — пароли и персональные данные попадут в лог-файлы.
        options.EnableSensitiveDataLogging();

        // Расширенные сообщения об ошибках трансляции LINQ → SQL.
        // Помогает понять почему конкретный LINQ-запрос не транслируется в SQL
        // и выполняется in-memory (что может вызвать загрузку всей таблицы).
        options.EnableDetailedErrors();
    }
});

Форма (sp, options) vs просто (options)

Обычно пишут AddDbContext<T>(options => ...). Форма с двумя параметрами (sp, options) предоставляет доступ к уже зарегистрированным сервисам внутри конфигурационной лямбды. В WebMessenger это нужно для IHostEnvironment — чтобы включать детальное логирование только в Development без хардкода имени окружения.

2. DbContext & Entities — Контекст и сущности

2.1 DbContext как Unit of Work и Identity Map

DbContext одновременно выполняет роль трёх вещей:

  • Unit of Work — отслеживает все изменения сущностей (добавление, изменение, удаление) с момента своего создания. Вызов SaveChangesAsync() транслирует накопленные изменения в минимально необходимый набор SQL-команд и выполняет их в одной транзакции.
  • Identity Map — гарантирует, что один и тот же первичный ключ всегда соответствует одному объекту в памяти. Два последовательных запроса одного User по Id вернут один и тот же экземпляр, а не два независимых объекта с одинаковыми данными.
  • Change Tracker — внутренний реестр состояний сущностей. Каждая отслеживаемая сущность имеет одно из состояний: Detached, Unchanged, Added, Modified, Deleted.

Состояния Change Tracker

СостояниеЧто означаетЧто сделает SaveChanges
DetachedОбъект создан, но контекст его не отслеживает (AsNoTracking или новый объект до Add)Ничего
UnchangedЗагружен из БД, свойства не изменилисьНичего
AddedДобавлен через Add() / InsertAsyncINSERT
ModifiedСвойство изменено или Attach + EntityState.ModifiedUPDATE (только изменённые столбцы)
DeletedПомечен через Remove()DELETE
// WebMessenger.DAL/Repository.cs — UpdateAsync: Attach + EntityState.Modified
// Attach говорит трекеру "начни следить за этим объектом",
// EntityState.Modified — "считай все поля изменёнными" → UPDATE всех колонок.
public async Task UpdateAsync(T entity, CancellationToken ct = default)
{
    _context.Set<T>().Attach(entity);
    _context.Entry(entity).State = EntityState.Modified;
}

// WebMessenger.DAL/UnitOfWork.cs — CommitAsync: единственная точка вызова SaveChangesAsync.
// Все накопленные Add/Update/Remove из ВСЕХ репозиториев записываются в БД разом.
public async Task<int> CommitAsync(CancellationToken ct = default)
    => await _context.SaveChangesAsync(ct);
UpdateAsync и полный UPDATE: подход Attach + EntityState.Modified помечает все столбцы как изменённые — EF отправит UPDATE для каждого поля. Если нужно обновлять только конкретные поля, загружают сущность из БД, меняют нужные свойства, и вызывают SaveChangesAsync(). Change Tracker сам определит что изменилось и сгенерирует минимальный SQL с только изменёнными столбцами.

2.2 DbSet<T> как репозиторий

DbSet<T> — это представление таблицы в C#. Он одновременно является:

  • IQueryable<T> — позволяет строить отложенные LINQ-запросы, которые транслируются в SQL только при материализации (ToListAsync, FirstOrDefaultAsync и т.п.).
  • Точкой входа для Add / AddRange / Remove / RemoveRange — регистрирует изменения в Change Tracker.
  • Источником для Find / FindAsync — сначала ищет в кеше Change Tracker, только потом обращается к БД (оптимально при повторных обращениях к одной сущности в рамках одного запроса). 
// ApplicationDbContext.cs — каждый DbSet<T> соответствует одной таблице.
// Имя свойства = имя таблицы по умолчанию (плюрализация встроена в EF Core).
public DbSet<User>       Users       { get; set; }  // → таблица Users
public DbSet<Chat>       Chats       { get; set; }  // → таблица Chats
public DbSet<Message>    Messages    { get; set; }  // → таблица Messages
public DbSet<ChatMember> ChatMembers { get; set; }  // → таблица ChatMembers
public DbSet<Contact>    Contacts    { get; set; }  // → таблица Contacts

// Repository<T> оборачивает DbSet, добавляя eager-loading и async CRUD
public class Repository<T> : IRepository<T> where T : class
{
    private readonly ApplicationDbContext _context;
    private DbSet<T> _dbSet => _context.Set<T>();

    // AsNoTracking — объекты не попадают в Change Tracker: экономия памяти и CPU
    // при запросах "только на чтение". Include по именам строит JOIN-ы.
    public IQueryable<T> GetAll(params string[] navigationProperties)
    {
        var query = _dbSet.AsNoTracking();
        foreach (var nav in navigationProperties)
            query = query.Include(nav);
        return query;
    }

    // FindAsync ищет сначала в кеше Change Tracker, потом в БД —
    // оптимально когда сущность уже могла быть загружена ранее в том же запросе.
    public async Task<T?> GetAsync(Guid id, CancellationToken ct = default)
        => await _dbSet.FindAsync(new object[] { id }, ct);

    // AddAsync помечает сущность как Added → SaveChanges сделает INSERT
    public async Task InsertAsync(T entity, CancellationToken ct = default)
        => await _dbSet.AddAsync(entity, ct);
}

2.3 Конвенции EF Core — что работает без явной настройки

EF Core содержит набор встроенных конвенций, которые автоматически определяют структуру схемы по именам классов и свойств. Это главное преимущество Code-First: минимум явной конфигурации для большинства случаев.

Первичный ключ Свойство Id или {ClassName}Id Message.Id → PRIMARY KEY автоматически

// WebMessenger.DAL/Entities/Message.cs — конвенции в действии
public class Message
{
    [Key]                              // явно, хотя конвенция нашла бы Id сама
    public Guid      Id        { get; set; }

    [MaxLength(5000)]
    public required string Content  { get; set; }  // required + non-nullable → NOT NULL

    public Guid      SenderId  { get; set; }  // FK на Users.Id — конвенция по имени
    public Guid      ChatId    { get; set; }  // FK на Chats.Id — конвенция по имени

    public DateTime  SentAt    { get; set; } = DateTime.UtcNow;
    public DateTime? EditedAt  { get; set; }  // nullable → NULL в БД

    // [ForeignKey] явно — при двух FK на одну таблицу EF не может выбрать сам
    [ForeignKey(nameof(SenderId))]
    public virtual User Sender { get; set; } = null!;

    [ForeignKey(nameof(ChatId))]
    public virtual Chat Chat   { get; set; } = null!;
}

2.4 Навигационные свойства

Навигационные свойства — C#-свойства сущности, ссылающиеся на связанные сущности вместо хранения только FK-значения. EF Core использует их для построения JOIN в SQL и для заполнения объектного графа при загрузке.

Reference-навигация (сторона «один»)

Ссылка на единственную связанную сущность. Пример: Message.Sender — ровно один User, отправивший сообщение. Инициализируется null! (null-forgiving operator): компилятор не предупреждает о null, реальное значение будет заполнено EF при загрузке с Include.

Collection-навигация (сторона «много»)

Коллекция связанных сущностей. Пример: User.Messages — все сообщения пользователя. Инициализируется [] (C# 12 collection expression): защита от NullReferenceException, когда EF не подгружал коллекцию — итерация вернёт пустой список вместо исключения. 

// WebMessenger.DAL/Entities/User.cs — оба вида навигационных свойств
public class User
{
    [Key]
    public Guid   Id           { get; set; }
    public required string Username     { get; set; }
    public required string PasswordHash { get; set; }
    public string? Bio          { get; set; }  // nullable → NULL
    public string? AvatarUrl    { get; set; }  // nullable → NULL

    // Collection-навигации, инициализированы пустой коллекцией (C# 12).
    // virtual — зарезервировано для lazy loading.
    // Без Include — коллекция пустая, но не null.
    public virtual ICollection<Contact>    Contacts        { get; set; } = [];
    public virtual ICollection<ChatMember> ChatMemberships { get; set; } = [];
    public virtual ICollection<Message>   Messages        { get; set; } = [];

// WebMessenger.DAL/Entities/Contact.cs — две reference-навигации на одну таблицу.
// EF не может автоматически определить какой FK к какому свойству —
// [ForeignKey] обязателен при нескольких FK на одну сущность.
public class Contact
{
    public Guid OwnerUserId   { get; set; }
    public Guid ContactUserId { get; set; }

    [ForeignKey(nameof(OwnerUserId))]
    public required virtual User OwnerUser   { get; set; }

    [ForeignKey(nameof(ContactUserId))]
    public required virtual User ContactUser { get; set; }

virtual и lazy loading: ключевое слово virtual на навигационных свойствах нужно для ленивой загрузки через прокси-классы (требует пакет Microsoft.EntityFrameworkCore.Proxies и вызов UseLazyLoadingProxies()). В WebMessenger lazy loading не включён, поэтому virtual не оказывает никакого эффекта на производительность и поведение — это хорошая практика, зарезервированная на будущее.

2.5 Паттерн Repository + Unit of Work поверх DbContext

В WebMessenger DbContext не используется напрямую в сервисах API. Вместо этого применяется двухуровневая обёртка:

  • Repository<T> — инкапсулирует доступ к конкретному DbSet<T>. Сервисы работают через IRepository<T> не зная об EF Core.
  • UnitOfWork — агрегирует все репозитории и единственный ApplicationDbContext. CommitAsync() вызывает SaveChangesAsync(), сохраняя изменения из всех репозиториев разом. Поддерживает явные транзакции. 
// WebMessenger.DAL/UnitOfWork.cs — ленивая инициализация через ??=
public class UnitOfWork(ApplicationDbContext context) : IUnitOfWork
{
    private readonly ApplicationDbContext _context = context;

    // Все репозитории разделяют один _context — один Change Tracker,
    // один набор отслеживаемых объектов, одна транзакция в CommitAsync.
    private IRepository<User>?       _users;
    public  IRepository<User>        Users       => _users       ??= new Repository<User>(_context);

    private IRepository<Chat>?       _chats;
    public  IRepository<Chat>        Chats       => _chats       ??= new Repository<Chat>(_context);

    private IRepository<Message>?    _messages;
    public  IRepository<Message>     Messages    => _messages    ??= new Repository<Message>(_context);

    private IRepository<ChatMember>? _chatMembers;
    public  IRepository<ChatMember>  ChatMembers => _chatMembers ??= new Repository<ChatMember>(_context);

    private IRepository<Contact>?    _contacts;
    public  IRepository<Contact>     Contacts    => _contacts    ??= new Repository<Contact>(_context);

    // Единственная точка сохранения — все изменения из всех репозиториев разом
    public async Task<int> CommitAsync(CancellationToken ct = default)
        => await _context.SaveChangesAsync(ct);

    // Явные транзакции — для атомарности нескольких SaveChangesAsync
    public async Task BeginTransactionAsync(CancellationToken ct = default)
        => _transaction = await _context.Database.BeginTransactionAsync(ct);

    public async Task CommitTransactionAsync(CancellationToken ct = default)
    {
        await _context.SaveChangesAsync(ct);
        await _transaction!.CommitAsync(ct);
    }

    public void Dispose() => _context.Dispose();
}
Один контекст — один Change Tracker: все пять репозиториев получают один и тот же _context. Это значит, что CommitAsync() запишет в БД изменения из любого репозитория, накопленные с начала HTTP-запроса. Разные экземпляры контекста имеют разные Change Tracker — изменения одного не видны другому.

3. Data Modeling — Моделирование данных

3.1 Convention-based mapping — маппинг по соглашениям

EF Core строит модель базы данных автоматически, анализируя классы C# по набору встроенных правил-конвенций. Большинство решений принимается без явной конфигурации: нужно лишь следовать соглашениям об именах и типах.

Как EF Core строит модель при старте

  1. Сканирует все DbSet<T>-свойства контекста.
  2. Для каждого типа T определяет: имя таблицы, первичный ключ, столбцы, типы данных.
  3. Анализирует навигационные свойства и автоматически добавляет обнаруженные связанные типы в модель.
  4. Применяет атрибуты Data Annotations (если есть).
  5. Применяет Fluent API из OnModelCreating (наивысший приоритет).

3.3 Data Annotations vs Fluent API

EF Core поддерживает два способа явной конфигурации модели помимо конвенций: Data Annotations (атрибуты прямо на классах/свойствах) и Fluent API (цепочки вызовов в OnModelCreating). В WebMessenger используются оба — в зависимости от сложности конфигурации.

// Fluent API — WebMessenger.DAL/Data/ApplicationDbContext.cs
// Используется для того что Data Annotations не умеют:
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    // HasColumnType — явный тип колонки (без этого Pomelo выберет datetime без дробных секунд)
    // HasDefaultValueSql — SQL-выражение как DEFAULT: БД сама проставит метку времени
    // ValueGeneratedOnAdd — EF знает: значение генерирует БД, не читать C#-свойство при INSERT
    modelBuilder.Entity<Message>(entity =>
    {
        entity.Property(m => m.SentAt)
              .HasColumnType("datetime(6)")
              .HasDefaultValueSql("CURRENT_TIMESTAMP(6)")
              .ValueGeneratedOnAdd();

        // Составной индекс (ChatId, SentAt) — критичен для пагинации истории чата:
        // WHERE ChatId = ? ORDER BY SentAt DESC LIMIT ?
        // Без него — полный скан таблицы Messages на каждый запрос истории.
        entity.HasIndex(m => new { m.ChatId, m.SentAt });
    });

    // Уникальный составной индекс — один пользователь не может войти в чат дважды
    modelBuilder.Entity<ChatMember>(entity =>
    {
        entity.HasIndex(cm => new { cm.UserId, cm.ChatId }).IsUnique();
    });

    // DeleteBehavior.Restrict — нельзя удалить User у которого есть контакты.
    // Без явного OnDelete Pomelo выбрал бы CASCADE — удаление User удалило бы все его контакты.
    modelBuilder.Entity<Contact>(entity =>
    {
        entity.HasOne(c => c.OwnerUser)
              .WithMany(u => u.Contacts)
              .HasForeignKey(c => c.OwnerUserId)
              .OnDelete(DeleteBehavior.Restrict);

        entity.HasOne(c => c.ContactUser)
              .WithMany()
              .HasForeignKey(c => c.ContactUserId)
              .OnDelete(DeleteBehavior.Restrict);
    });
}

// Self-referencing — Contact: User владеет списком контактов (других User).

modelBuilder.Entity<Contact>(entity =>

          .WithMany(u => u.Contacts)       // User.Contacts — обратная коллекция

          .OnDelete(DeleteBehavior.Restrict); // запрет каскадного удаления

          .OnDelete(DeleteBehavior.Restrict);

3.5 Value Conversions — конвертация значений

Value Conversion (HasConversion) позволяет хранить в БД одно значение, а в C#-модели работать с другим типом. Типичные применения: enum → string, кастомные типы → примитивы, зашифрованные строки.

Enum → string (абстрактный пример, расширение для WebMessenger)

// Допустим, в WebMessenger добавляется статус сообщения
public enum MessageStatus { Sent, Delivered, Read }

public class Message
{
    public MessageStatus Status { get; set; } = MessageStatus.Sent;
    // Без конвертации: хранится как int (0, 1, 2) — трудно читать в БД напрямую.
    // С конвертацией: хранится как "Sent", "Delivered", "Read" — читаемо.
}

// OnModelCreating — HasConversion<string> — встроенный конвертер EF Core
modelBuilder.Entity<Message>()
    .Property(m => m.Status)
    .HasConversion<string>()  // enum.ToString() при записи, Enum.Parse при чтении
    .HasMaxLength(20);        // varchar(20) вместо longtext

Кастомный конвертер

// Хранить список тегов как JSON-строку в одном столбце
modelBuilder.Entity<Chat>()
    .Property(c => c.Tags)
    .HasConversion(
        tags => JsonSerializer.Serialize(tags, (JsonSerializerOptions?)null),
        json => JsonSerializer.Deserialize<List<string>>(json, (JsonSerializerOptions?)null)!
    );
// Внимание: EF Core не умеет строить WHERE-условия внутри JSON-строки через LINQ без JSON-функций провайдера.
Встроенные конвертеры EF Core 8: HasConversion<string>() для enum, HasConversion<int>() для enum-как-int (явно), DateTimeOffsetToBinaryConverter, BoolToZeroOneConverter<T> и другие из пространства имён Microsoft.EntityFrameworkCore.Storage.ValueConversion.

3.6 DateTime vs DateTimeOffset

Выбор между DateTime и DateTimeOffset имеет значение как для логики приложения, так и для хранения в БД.

DateTimeDateTimeOffset
Хранит часовой пояс? Нет. Kind: Unspecified / Local / Utc Да. Хранит смещение от UTC (например +03:00)
В MySQL через Pomelo datetime(6) datetime(6) (смещение теряется!) или varchar с кастомным конвертером
Рекомендация Хранить только UTC (всегда использовать DateTime.UtcNow) Использовать когда важно сохранить исходный часовой пояс пользователя
Пример в WebMessenger Все временные метки: SentAt, CreatedAt, JoinedAt Не используется — все операции в UTC 
// WebMessenger: всегда DateTime.UtcNow — явное UTC, без риска путаницы часовых поясов
public DateTime CreatedAt  { get; set; } = DateTime.UtcNow;
public DateTime JoinedAt   { get; set; } = DateTime.UtcNow;
public DateTime SentAt     { get; set; } = DateTime.UtcNow;

// В ApplicationDbContext — явный HasColumnType("datetime(6)") для точности до микросекунды.
// Без этого Pomelo может выбрать datetime без дробной части → потеря точности при сравнении.
entity.Property(m => m.SentAt).HasColumnType("datetime(6)");

// HasDefaultValueSql — БД проставляет метку времени при INSERT, не C#.
// Это гарантирует согласованность: даже если C# не задал значение — БД запишет правильное время.
entity.Property(m => m.SentAt).HasDefaultValueSql("CURRENT_TIMESTAMP(6)").ValueGeneratedOnAdd();
Ловушка DateTime.Now vs DateTime.UtcNow: при использовании DateTime.Now значение зависит от часового пояса сервера. Если сервер переедет в другой дата-центр — все временные метки сдвинутся. В WebMessenger везде используется DateTime.UtcNow: хранение в UTC и конвертация в локальное время на клиенте — правильный подход для распределённых систем.

3.7 Индексы

Индексы критичны для производительности. В WebMessenger они сконфигурированы как через Data Annotations, так и через Fluent API, в зависимости от сложности. 

// Data Annotations — одиночные индексы на уровне класса
[Index(nameof(Username), IsUnique = true)]  // CREATE UNIQUE INDEX ON Users(Username)
[Index(nameof(IsOnline))]                    // CREATE INDEX ON Users(IsOnline)
[Index(nameof(IsGroup))]                     // CREATE INDEX ON Chats(IsGroup)

// Fluent API — составные и уникальные составные индексы

// Составной индекс (ChatId, SentAt): покрывает запрос истории чата
// SELECT * FROM Messages WHERE ChatId = ? ORDER BY SentAt DESC LIMIT ?
// Без индекса — полный скан Messages. С индексом — поиск за O(log n).
entity.HasIndex(m => new { m.ChatId, m.SentAt });

// Уникальный составной индекс: гарантирует что (UserId, ChatId) уникально в ChatMembers.
// Дублирует бизнес-правило "один пользователь = один раз в чате" на уровне БД.
entity.HasIndex(cm => new { cm.UserId, cm.ChatId }).IsUnique();
Порядок полей в составном индексе важен: индекс (ChatId, SentAt) эффективен для запросов WHERE ChatId = ? и WHERE ChatId = ? AND SentAt < ?. Но не эффективен для запросов только по SentAt без ChatId. Поле с высокой селективностью (ChatId) ставится первым.

4. Querying — Запросы к базе данных

4.1 LINQ-запросы в EF Core — принцип работы

EF Core транслирует LINQ-выражения в SQL через Expression Tree — дерево выражений, которое компилятор C# строит из лямбды и передаёт провайдеру как данные (не код). Провайдер анализирует это дерево и генерирует SQL-команду. Ключевое отличие от обычных делегатов: лямбда в Where на IQueryable<T> не выполняется в C# — она описывает условие, которое будет исполнено в базе данных.

IQueryable vs IEnumerable

IQueryable<T>IEnumerable<T>
Где работает фильтр На сервере БД (SQL WHERE) В памяти C# (после загрузки всех строк)
Когда идёт запрос в БД При материализации: ToListAsync, FirstOrDefaultAsync и т.п. При первой итерации — уже вся таблица в памяти
Тип в EF Core DbSet<T> и Repository.GetAll() После ToList() / AsEnumerable()
Риск Не все LINQ-операции транслируемы — часть выполняется in-memory молча Загрузка всей таблицы при добавлении .Where() после ToList() 
// Правильно — фильтр транслируется в SQL WHERE:
// SELECT * FROM Messages WHERE ChatId = '...' ORDER BY SentAt DESC LIMIT 50
var items = await _uow.MessageRepository
    .GetAll()
    .Where(m => m.ChatId == chatId)        // → WHERE ChatId = @p0
    .OrderByDescending(m => m.SentAt)       // → ORDER BY SentAt DESC
    .Take(take)                              // → LIMIT @p1
    .Select(MessageProjections.ToChatMessageDto) // → SELECT только нужных полей
    .ToListAsync();                          // ← здесь SQL отправляется в БД

// Опасно — ToList() материализует ВСЕ строки Messages, потом фильтр в C#:
var all  = await _uow.MessageRepository.GetAll().ToListAsync(); // вся таблица в память!
var bad  = all.Where(m => m.ChatId == chatId).ToList();        // фильтр в C#

// AnyAsync — проверка членства: SELECT COUNT(*) = 0 или EXISTS — без загрузки данных
var isMember = await _uow.ChatMemberRepository.GetAll()
    .AnyAsync(cm => cm.ChatId == chatId && cm.UserId == me);
if (!isMember) throw new UnauthorizedAccessException("Not a member of this chat");

// FirstOrDefaultAsync — один результат или null; генерирует LIMIT 1
var myLastReadAt = await _uow.ChatMemberRepository.GetAll()
    .Where(cm => cm.ChatId == chatId && cm.UserId == me)
    .Select(cm => cm.LastReadAt)
    .FirstOrDefaultAsync() ?? DateTime.MinValue;

// ToDictionaryAsync — батч-загрузка данных для N чатов одним запросом
// SELECT ChatId, LastReadAt FROM ChatMembers WHERE UserId = ? AND ChatId IN (...)
// Потом словарь для O(1) поиска вместо N отдельных запросов.
var lastReadMap = await _uow.ChatMemberRepository.GetAll()
    .Where(cm => cm.UserId == me && chatIds.Contains(cm.ChatId))
    .Select(cm => new { cm.ChatId, cm.LastReadAt })
    .ToDictionaryAsync(x => x.ChatId, x => x.LastReadAt);

4.3 Find vs FirstOrDefault — критерии выбора

Оба метода возвращают одну сущность или null, но работают принципиально по-разному:

FindAsync(id)FirstOrDefaultAsync(predicate)
Поиск в кеше Сначала в Change Tracker — возможно без SQL Всегда идёт в БД, кеш не проверяется
Только по PK? Да — только по первичному ключу Любое условие, любые поля
Поддержка Include Нет — не поддерживает Include / проекции Да — полная поддержка Include, Select, OrderBy
Когда использовать Нужна сущность по PK и она может быть уже загружена в контекст Нужен гибкий поиск или Include связей 
// WebMessenger.DAL/Repository.cs — FindAsync: кеш Change Tracker → потом БД
public async Task<T?> GetAsync(Guid id, CancellationToken ct = default)
    => await _dbSet.FindAsync(new object[] { id }, ct);
// Хорошо: GetAsync используется когда сущность точно могла быть загружена ранее
// в том же HTTP-запросе — например при update после проверки существования.

// FirstOrDefaultAsync: всегда SQL, поддерживает Include и Select — для read-запросов
var chat = await _uow.ChatRepository
    .GetAll(nameof(Chat.Members))         // Include Members → JOIN
    .FirstOrDefaultAsync(c => c.Id == chatId);
if (chat == null) return null;

4.4 Проекции (Select) — запрашивать только нужные поля

Проекция — трансформация результата запроса в другой тип прямо в SQL через SELECT. Вместо загрузки всей сущности (SELECT *) EF Core генерирует SELECT col1, col2, ... только для нужных полей. Это снижает нагрузку на сеть и память.

В WebMessenger для проекций используется паттерн Expression<Func<T, TDto>> в классе MessageProjections: выражение объявляется один раз и переиспользуется во всех запросах. 

// WebMessenger.Api/Projections/Messages/MessageProjections.cs

// Expression<Func> — EF Core может транслировать в SQL (дерево выражений).
// Используется в .Select(MessageProjections.ToChatMessageDto) в LINQ-запросах.
public static readonly Expression<Func<Message, ChatMessageDto>> ToChatMessageDto =
    m => new ChatMessageDto
    {
        Id       = m.Id,
        ChatId   = m.ChatId,
        SenderId = m.SenderId,
        Content  = m.Content,
        SentAt   = m.SentAt,
        EditedAt = m.EditedAt
    };
// EF генерирует: SELECT Id, ChatId, SenderId, Content, SentAt, EditedAt FROM Messages WHERE ...

// Func<> — скомпилированный делегат для маппинга в памяти.
// Compile() один раз при старте, используется для свежесозданных сущностей
// которые ещё не прошли через БД и не могут быть запрошены через IQueryable.
public static readonly Func<Message, ChatMessageDto> ToChatMessageDtoFunc =
    ToChatMessageDto.Compile();
// Использование в ChatService.GetMessagesAsync — проекция прямо в SQL
var items = await q
    .OrderByDescending(m => m.SentAt)
    .Take(take)
    .Select(MessageProjections.ToChatMessageDto)  // SELECT только 6 полей
    .ToListAsync();

// Inline-проекция через анонимный тип — для разовых запросов без переиспользования
var peerMap = (await _uow.UserRepository.GetAll()
    .Where(u => peerIds.Contains(u.Id))
    .Select(u => new { u.Id, u.Username, u.AvatarUrl })  // только 3 поля
    .ToListAsync())
    .ToDictionary(u => u.Id, u => (u.Username, u.AvatarUrl));
Expression vs Func: ключевое различие в том, что Expression<Func<T, TDto>> передаётся как данные (дерево выражений) и транслируется EF Core в SQL. Обычный Func<T, TDto> — это скомпилированный делегат, который выполняется в C# только после загрузки данных из БД. Передача Func вместо Expression в .Select() приведёт к загрузке всех столбцов сущности и маппингу в памяти.

4.5 Пагинация

В WebMessenger используется курсорная пагинация (keyset/cursor pagination) по полю DateTime? before — в отличие от классической офсетной пагинации через Skip(page * size).

Офсетная пагинация (Skip/Take)Курсорная пагинация (WebMessenger)
SQL LIMIT 50 OFFSET 1000 WHERE SentAt < @cursor ORDER BY SentAt DESC LIMIT 50
Производительность Деградирует с ростом OFFSET — БД читает и выбрасывает N строк Константная — индекс используется полностью
Проблема сдвига При добавлении новых записей страницы сдвигаются — дубли или пропуски Стабильно — курсор всегда указывает на конкретную точку
Навигация Можно перейти на любую страницу произвольно Только вперёд/назад по курсору 
// WebMessenger.Api/Services/ChatService.cs — GetMessagesAsync: курсорная пагинация
public async Task<PagedResult<ChatMessageDto>> GetMessagesAsync(
    Guid me, Guid chatId, int limit, DateTime? before)
{
    // Clamp защищает от limit=0 или limit=999999 от клиента
    var take = Math.Clamp(limit, 1, 200);

    var q = _uow.MessageRepository.GetAll()
        .Where(m => m.ChatId == chatId);   // база фильтра

    // Курсор: загрузить сообщения старше указанной метки времени
    // WHERE ChatId = ? AND SentAt < @before ORDER BY SentAt DESC LIMIT ?
    if (before.HasValue)
        q = q.Where(m => m.SentAt < before.Value);

    var items = await q
        .OrderByDescending(m => m.SentAt)  // DESC: сначала новые
        .Take(take)
        .Select(MessageProjections.ToChatMessageDto)
        .ToListAsync();

    items.Reverse();  // вернуть в хронологическом порядке клиенту

    return new PagedResult<ChatMessageDto>
    {
        Items   = items,
        HasMore = items.Count == take,          // если вернули take — значит есть ещё
        NextBefore = items.Count > 0
            ? items.First().SentAt            // курсор = SentAt самого старого в выборке
            : before
    };
}

4.6 Batch-запросы — избегаем N+1

N+1 проблема — антипаттерн: один запрос возвращает N записей, затем для каждой из них выполняется ещё один отдельный запрос. Итого N+1 круговых обращений к БД вместо одного. 

// Антипаттерн N+1 — НЕ делайте так
var chats = await _uow.ChatRepository.GetAll().ToListAsync(); // 1 запрос
foreach (var chat in chats)
{
    // N запросов — по одному на каждый чат!
    var lastMsg = await _uow.MessageRepository.GetAll()
        .Where(m => m.ChatId == chat.Id)
        .OrderByDescending(m => m.SentAt)
        .FirstOrDefaultAsync();
}
// Решение из WebMessenger — всё в одном LINQ-запросе с подзапросами,
// потом отдельный batch для счётчиков непрочитанных по всем chatIds разом.

// Шаг 1: один запрос — чаты + последнее сообщение через подзапрос
var baseQuery =
    from c in _uow.ChatRepository.GetAll(nameof(Chat.Members))
    where c.Members.Any(m => m.UserId == me)
    select new
    {
        Chat = c,
        LastMessage = _uow.MessageRepository.GetAll()
            .Where(m => m.ChatId == c.Id)
            .OrderByDescending(m => m.SentAt)
            .Select(m => new { m.Id, m.SenderId, m.Content, m.SentAt })
            .FirstOrDefault()  // коррелированный подзапрос в SQL
    };

// Шаг 2: batch-fetch LastReadAt для всех чатов — один запрос вместо N
var lastReadMap = await _uow.ChatMemberRepository.GetAll()
    .Where(cm => cm.UserId == me && chatIds.Contains(cm.ChatId))
    .ToDictionaryAsync(x => x.ChatId, x => x.LastReadAt);
// SELECT ChatId, LastReadAt FROM ChatMembers WHERE UserId=? AND ChatId IN (id1, id2, ...)

// Шаг 3: batch-fetch непрочитанных — GroupBy в SQL, один запрос
var unreadCounts = await _uow.MessageRepository.GetAll()
    .Where(m => chatIds.Contains(m.ChatId) && m.SenderId != me)
    .GroupBy(m => m.ChatId)
    .Select(g => new { ChatId = g.Key, Count = g.Count() })
    .ToListAsync();
// SELECT ChatId, COUNT(*) FROM Messages WHERE ChatId IN (...) AND SenderId != ? GROUP BY ChatId

4.7 Хранимые процедуры и сырой SQL

Иногда LINQ не позволяет выразить нужный запрос эффективно — например при сложных рекурсивных CTE или специфичных для MySQL функциях. EF Core предоставляет механизмы для сырого SQL. 

// FromSqlRaw — запрос возвращает сущности типа T, маппится EF Core.
// Безопасно: параметры передаются как параметры SQL (не конкатенация строк).
var users = await context.Users
    .FromSqlRaw("SELECT * FROM Users WHERE Username = {0}", username)
    .ToListAsync();

// FromSqlInterpolated — C# интерполированная строка: EF Core автоматически
// превращает {username} в параметр @p0. Предпочтительнее FromSqlRaw.
var users = await context.Users
    .FromSqlInterpolated($"SELECT * FROM Users WHERE Username = {username}")
    .ToListAsync();

// ExecuteSqlRawAsync — для команд без возвращаемых данных (UPDATE, DELETE, CALL).
// Возвращает количество затронутых строк.
await context.Database
    .ExecuteSqlRawAsync("CALL archive_old_messages({0})", cutoffDate);

// ВНИМАНИЕ: никогда не конкатенируйте пользовательский ввод в строку запроса!
// SQL-инъекция:
var bad = await context.Users
    .FromSqlRaw("SELECT * FROM Users WHERE Username = '" + username + "'") // ОПАСНО!
    .ToListAsync();
В WebMessenger сырой SQL не используется — все запросы выражены через LINQ. Это оптимально для большинства случаев: LINQ читаем, безопасен, и EF Core генерирует эффективный SQL с индексами. Сырой SQL нужен для исключительных случаев: рекурсивные CTE, полнотекстовый поиск, специфичные функции СУБД.

5. Loading Related Data — Загрузка связанных данных

5.1 Три стратегии загрузки

EF Core предоставляет три стратегии для загрузки навигационных свойств (связанных сущностей). Выбор определяет: когда и как связанные данные попадают в память.

СтратегияКогда загружаетсяКак активируетсяSQL-запросов

Explicit Loading По требованию вручную Entry(entity).Collection(...).LoadAsync() Отдельный запрос при вызове

5.2 Eager Loading — Include и ThenInclude

Eager Loading — основной и рекомендуемый подход в WebMessenger. Include() добавляет JOIN в SQL-запрос и загружает навигационные свойства вместе с основной сущностью за один обход к БД. 

// WebMessenger.DAL/Repository.cs — GetAll принимает имена навигационных свойств.
// Include добавляется через string-имя: не требует знать тип на уровне репозитория.
public IQueryable<T> GetAll(params string[] navigationProperties)
{
    var query = _dbSet.AsNoTracking();
    foreach (var nav in navigationProperties)
        query = query.Include(nav);   // → LEFT JOIN на каждый nav
    return query;
}

// ChatService.cs — Include(nameof(Chat.Members)):
// SELECT Chats.*, ChatMembers.* FROM Chats
// LEFT JOIN ChatMembers ON ChatMembers.ChatId = Chats.Id
// WHERE ChatMembers.UserId = @me
var chat = await _uow.ChatRepository
    .GetAll(nameof(Chat.Members))
    .FirstOrDefaultAsync(c => c.Id == chatId);

// ContactsService.cs — сначала Where с фильтром, потом Include.
// EF Core оптимизирует порядок: Where применяется до JOIN в SQL.
// Важно: Include указывается ПОСЛЕ Where — EF всё равно сгенерирует правильный SQL.
return await _unitOfWork.ContactRepository
    .GetAll()
    .Where(x => x.OwnerUserId == currentUserId
        && x.ContactUser!.Username.ToLower().Contains(query.ToLower()))
    .Include(x => x.ContactUser)   // строготипизированный Include с лямбдой
    .ToListAsync();

ThenInclude — загрузка вложенных навигаций

// ThenInclude загружает навигацию у уже включённой навигации.
// Пример (абстрактный — WebMessenger не требует такой глубины):
// Загрузить чаты → участников → пользователей участников
var chats = await context.Chats
    .Include(c => c.Members)               // загрузить ChatMember[]
        .ThenInclude(m => m.User)           // для каждого ChatMember загрузить User
    .Include(c => c.Messages)              // отдельная ветка Include
        .ThenInclude(msg => msg.Sender)     // для каждого Message загрузить User-отправителя
    .ToListAsync();
// Генерирует несколько JOIN или split query в зависимости от настроек.
// Для больших коллекций может привести к "картезианскому взрыву" строк —
// в этом случае используют AsSplitQuery().

5.3 Explicit Loading — явная загрузка по требованию

Explicit Loading позволяет загружать навигационное свойство отдельным запросом в любой момент после того, как основная сущность уже загружена в контекст. Полезно когда навигация нужна только в части кода и заранее неизвестно — понадобится она или нет. 

// Сущность уже в контексте (не AsNoTracking!)
// Явно загружаем коллекцию Messages только когда она нужна
var chat = await context.Chats.FindAsync(chatId);  // загружен без навигаций

// LoadAsync — отдельный SELECT FROM Messages WHERE ChatId = @chatId
await context.Entry(chat!)
    .Collection(c => c.Messages)
    .LoadAsync();

// Для reference-навигации (один объект) — Reference вместо Collection
var message = await context.Messages.FindAsync(msgId);
await context.Entry(message!)
    .Reference(m => m.Sender)
    .LoadAsync();

// Query() — добавить фильтр к явной загрузке
await context.Entry(chat!)
    .Collection(c => c.Messages)
    .Query()
    .Where(m => m.SentAt > cutoff)   // фильтровать при загрузке
    .LoadAsync();
Explicit Loading требует отслеживаемой сущности: нельзя использовать с AsNoTracking(). Сущность должна быть загружена через обычный запрос (без AsNoTracking) и находиться в Change Tracker. В WebMessenger Repository.GetAll() всегда использует AsNoTracking — поэтому Explicit Loading не применяется. Для подобных сценариев используется Eager Loading или отдельный запрос.

5.4 Lazy Loading — ленивая загрузка

Lazy Loading — навигационное свойство загружается автоматически при первом обращении к нему. EF Core подменяет сущность прокси-объектом, который перехватывает обращение и выполняет SQL-запрос незаметно.

Как включить

// 1. Установить пакет прокси
// dotnet add package Microsoft.EntityFrameworkCore.Proxies

// 2. Включить в AddDbContext
options.UseLazyLoadingProxies().UseMySql(...);

// 3. Все навигационные свойства должны быть virtual
public virtual ICollection<Message> Messages { get; set; } = [];

В WebMessenger lazy loading не включён. Ключевое слово virtual на навигационных свойствах присутствует по соглашению, но прокси-пакет не установлен и UseLazyLoadingProxies() не вызывается.

Почему lazy loading опасен

// При включённом lazy loading — этот код делает N+1 запросов незаметно!
var chats = await context.Chats.ToListAsync();  // 1 запрос
foreach (var chat in chats)
{
    // При первом обращении к Members — EF тихо делает SELECT по каждому Chat!
    // N чатов = N дополнительных запросов. Итого N+1.
    var count = chat.Members.Count;
}

// С Eager Loading тот же результат за 1 запрос:
var chats = await context.Chats
    .Include(c => c.Members)
    .ToListAsync();
foreach (var chat in chats)
{
    var count = chat.Members.Count;  // данные уже в памяти — нет запросов
}

5.5 Проблема N+1 — диагностика и решение

N+1 — один из самых распространённых и незаметных дефектов производительности в EF Core. Один запрос возвращает N записей, и для каждой из них выполняется ещё по одному запросу. При N=100 это 101 обращение к БД вместо одного.

Как обнаружить

  • LogTo / EnableSensitiveDataLogging — включить логирование SQL в Development и посмотреть сколько запросов выполняется на один HTTP-запрос.
  • EnableDetailedErrors — подробные сообщения при ошибках трансляции.
  • MiniProfiler / Application Insights — сторонние инструменты для анализа запросов в реальном времени.

Три сценария N+1 и их решения

СценарийПричинаРешение
Обращение к навигации в цикле без Include Lazy loading или не загруженное свойство Eager Loading через Include()
GetAsync в цикле по коллекции ID Один FindAsync на итерацию Batch-загрузка: Where(x => ids.Contains(x.Id)).ToListAsync()
Проверка существования в цикле Any() вызывается для каждого элемента Загрузить всё за один запрос, проверять в памяти через HashSet 
// Антипаттерн: GetAsync в цикле — N SELECT по PK
var memberIds = new List<Guid> { id1, id2, id3 };
var users = new List<User>();
foreach (var id in memberIds)
    users.Add((await _uow.Users.GetAsync(id))!);  // N запросов!

// Решение: один запрос с Contains
var users = await _uow.UserRepository.GetAll()
    .Where(u => memberIds.Contains(u.Id))   // WHERE Id IN (id1, id2, id3)
    .ToListAsync();                           // 1 запрос

// WebMessenger — ContactsService: HashSet для проверки без лишних запросов
public async Task<HashSet<Guid>> GetContactIdsAsync(Guid currentUserId)
{
    // Один запрос — SELECT ContactUserId FROM Contacts WHERE OwnerUserId = ?
    return (await _unitOfWork.ContactRepository.GetAll()
        .Where(c => c.OwnerUserId == currentUserId)
        .Select(c => c.ContactUserId)
        .ToListAsync())
        .ToHashSet();  // O(1) проверки в памяти вместо AnyAsync в цикле
}

5.6 Ограничения трансляции LINQ — реальный пример из проекта

Не все C#-методы транслируются EF Core в SQL. Некоторые конструкции EF Core не умеет перевести и либо выбрасывает исключение, либо молча переключается на вычисление в памяти (с загрузкой лишних данных). Один из таких случаев задокументирован в ContactsService.cs. 

// ContactsService.cs — реальный комментарий из кода проекта

// CA1862: Do not replace ToLower().Contains() with Contains(StringComparison) here.
// EF Core cannot translate the Contains(string, StringComparison) overload to SQL
// and will throw at runtime.
#pragma warning disable CA1862
return await _unitOfWork.ContactRepository.GetAll()
    .Where(x => x.OwnerUserId == currentUserId
        && x.ContactUser!.Username.ToLower().Contains(query.ToLower()))
    .Include(x => x.ContactUser)
    .ToListAsync();
#pragma warning restore CA1862

// Почему не работает "правильный" вариант:
// .Where(x => x.ContactUser!.Username.Contains(query, StringComparison.OrdinalIgnoreCase))
// → InvalidOperationException: The LINQ expression ... could not be translated.
// Pomelo/MySQL не поддерживает StringComparison.OrdinalIgnoreCase в WHERE.
//
// Рабочий вариант — ToLower().Contains() транслируется в:
// WHERE LOWER(ContactUser.Username) LIKE LOWER('%query%')
// Это работает, но не использует индекс на Username (функциональный вызов обёртывает поле).
Правило: если EF Core не может транслировать часть LINQ-выражения в SQL, он может либо бросить исключение InvalidOperationException с сообщением "could not be translated", либо (в некоторых версиях) тихо переключиться на вычисление в памяти после загрузки всей таблицы. Второй вариант особенно опасен — внешне всё работает, но на большой таблице запрос грузит миллионы строк в память. При включённом EnableDetailedErrors() EF Core всегда явно сообщает о нетранслируемых выражениях.

// Все три INSERT выполняются в одной транзакции.
await _uow.CommitAsync(ct);

6.3 UpdateAsync — обновление записи

В WebMessenger применяются два подхода к обновлению, в зависимости от ситуации:

Подход 1: загрузить → изменить → SaveChanges (точечный UPDATE)

// ChatService.cs — MarkChatReadAsync
// Загружаем ChatMember из БД (FirstOrDefaultAsync — GetAll использует AsNoTracking!).
// Внимание: GetAll возвращает AsNoTracking-объект — он НЕ отслеживается Change Tracker.
// Поэтому UpdateAsync явно аттачит и помечает Modified.
var cm = await _uow.ChatMemberRepository
    .GetAll()
    .FirstOrDefaultAsync(x => x.ChatId == chatId && x.UserId == me)
    ?? throw new UnauthorizedAccessException("Not a member of this chat");

// Изменяем поле — но объект не отслеживается (AsNoTracking)!
var now = atUtc?.ToUniversalTime() ?? DateTime.UtcNow;
cm.LastReadAt = cm.LastReadAt.HasValue && cm.LastReadAt.Value > now
    ? cm.LastReadAt : now;

// UpdateAsync: Attach + EntityState.Modified → UPDATE всех колонок ChatMember
// (не только LastReadAt — т.к. EntityState.Modified = все поля изменены)
await _uow.ChatMemberRepository.UpdateAsync(cm);
await _uow.CommitAsync();

Подход 2: загрузить с трекингом → изменить → SaveChanges (минимальный UPDATE)

// Если загрузить БЕЗ AsNoTracking — Change Tracker отслеживает изменения сам.
// EF Core генерирует UPDATE только для изменённых столбцов.
var cm = await context.ChatMembers  // напрямую через DbSet, без AsNoTracking
    .FirstOrDefaultAsync(x => x.ChatId == chatId && x.UserId == me);

cm!.LastReadAt = DateTime.UtcNow;  // Change Tracker видит изменение

await context.SaveChangesAsync();
// → UPDATE ChatMembers SET LastReadAt = @p0 WHERE Id = @p1
//   Только LastReadAt — EF знает что остальные поля не менялись.

ExecuteUpdateAsync — UPDATE без загрузки (EF Core 7+)

// Массовое обновление без загрузки сущностей в память — EF Core 7+
// UPDATE Messages SET EditedAt = @now WHERE ChatId = @chatId AND SenderId = @me
await context.Messages
    .Where(m => m.ChatId == chatId && m.SenderId == me)
    .ExecuteUpdateAsync(s => s.SetProperty(m => m.EditedAt, DateTime.UtcNow));
// Не использует Change Tracker — минимальный overhead, эффективно для батч-обновлений.

6.5 SaveChanges и транзакции

SaveChangesAsync() по умолчанию оборачивает все изменения в одну транзакцию. Если хотя бы одна SQL-команда завершается ошибкой — транзакция откатывается полностью и ни одно изменение не сохраняется. 

// WebMessenger.DAL/UnitOfWork.cs — CommitAsync: одна транзакция для всех изменений
public async Task<int> CommitAsync(CancellationToken ct = default)
    => await _context.SaveChangesAsync(ct);

// Явная транзакция — нужна когда несколько CommitAsync должны быть атомарными.
// Пример: создать чат И перевести средства — либо оба, либо ни одного.
await _uow.BeginTransactionAsync(ct);
try
{
    await _uow.ChatRepository.InsertAsync(chat, ct);
    await _uow.CommitAsync(ct);           // SaveChanges #1

    await _uow.ChatMemberRepository.CreateRangeAsync(members, ct);
    await _uow.CommitTransactionAsync(ct);  // SaveChanges #2 + COMMIT
}
catch
{
    await _uow._transaction!.RollbackAsync(ct);  // ROLLBACK обоих
    throw;
}

6.6 DbUpdateException и DbUpdateConcurrencyException

При вызове SaveChangesAsync() могут возникнуть два характерных исключения EF Core:

DbUpdateException

Базовый класс для всех ошибок при сохранении изменений в БД. Оборачивает исключение от ADO.NET/провайдера. Типичные причины:

  • Нарушение уникального ограничения (UNIQUE constraint) — например, попытка добавить Username который уже существует.
  • Нарушение NOT NULL — поле обязательно, но передан null.
  • Нарушение внешнего ключа — FK ссылается на несуществующую запись.
  • Превышение максимальной длины строки — MaxLength нарушен.
// Обработка DbUpdateException — например при регистрации пользователя
try
{
    await _uow.UserRepository.InsertAsync(newUser);
    await _uow.CommitAsync();
}
catch (DbUpdateException ex)
{
    // InnerException — конкретная ошибка провайдера (MySqlException, SqlException и т.п.)
    // Проверяем код ошибки чтобы дать понятное сообщение клиенту
    if (ex.InnerException?.Message.Contains("Duplicate entry") == true)
        throw new InvalidOperationException("Username already taken");
    throw;  // прочие ошибки БД — пробрасываем
}

DbUpdateConcurrencyException

Возникает при конкурентном обновлении: EF Core обнаруживает, что строка в БД изменилась с момента её загрузки. Требует настройки оптимистичной блокировки через токен параллелизма ([ConcurrencyCheck] или [Timestamp]). 

// Настройка токена параллелизма (абстрактный пример — расширение для WebMessenger)
public class Message
{
    public Guid Id { get; set; }
    public required string Content { get; set; }

    // [Timestamp] — RowVersion: БД автоматически обновляет поле при каждом UPDATE.
    // EF добавляет WHERE RowVersion = @original в UPDATE — если значение изменилось,
    // значит кто-то другой обновил запись → DbUpdateConcurrencyException.
    [Timestamp]
    public byte[] RowVersion { get; set; } = [];
}

// Обработка конкурентного обновления
try
{
    await _uow.CommitAsync();
}
catch (DbUpdateConcurrencyException ex)
{
    foreach (var entry in ex.Entries)
    {
        var dbValues    = await entry.GetDatabaseValuesAsync();
        var clientValues = entry.CurrentValues;
        // Стратегия "database wins": перезаписать изменения клиента значениями из БД
        entry.OriginalValues.SetValues(dbValues!);
        // Или "client wins": entry.CurrentValues остаётся — сохранить изменения клиента
    }
    await _uow.CommitAsync();  // повторить попытку
}

// ChatService.cs — SendMessageToUserAsync: создать чат если нет, отправить сообщение
public async Task<SendMessageResponse> SendMessageToUserAsync(
    Guid me, Guid other, string content, CancellationToken ct)
{
    if (string.IsNullOrWhiteSpace(content))
        throw new ArgumentException("Content is required");

    // 1. Поиск существующего личного чата — SELECT с JOIN по Members
    var chatId = await GetDirectChatIdAsync(me, other);

    if (!chatId.HasValue)
    {
        // 2a. Чата нет — создаём: Chat + 2 × ChatMember за один CommitAsync
        var chat = new Chat { IsGroup = false };
        await _uow.ChatRepository.InsertAsync(chat, ct);         // Added

        var cm1 = new ChatMember { Chat = chat, UserId = me };
        var cm2 = new ChatMember { Chat = chat, UserId = other };
        await _uow.ChatMemberRepository.CreateRangeAsync([cm1, cm2], ct); // Added x2

        await _uow.CommitAsync(ct);  // INSERT Chat + INSERT ChatMember x2 (транзакция)
        chatId = chat.Id;
    }

    // 2b. Чат нашёлся или только что создан — добавляем Message
    var message = new Message
    {
        ChatId   = chatId.Value,
        SenderId = me,
        Content  = content,
        SentAt   = DateTime.UtcNow
    };
    await _uow.MessageRepository.InsertAsync(message, ct);   // Added
    await _uow.CommitAsync(ct);  // INSERT Message

    // 3. Маппинг через скомпилированный Func (не Expression!) —
    //    сущность только что создана и не прошла через IQueryable,
    //    поэтому Expression<Func> нельзя использовать как Select.
    var dto = MessageProjections.ToChatMessageDtoFunc(message);

    // 4. Уведомление SignalR подписчиков через события
    await _events.MessageCreatedAsync(chatId.Value, dto, other, ct);

    return new SendMessageResponse(chatId.Value, dto);
}

7. Migrations — Миграции

7.1 Что такое миграция

Миграция — это C#-класс, который описывает инкрементальное изменение схемы БД: что добавить, что удалить, что изменить. EF Core генерирует этот класс автоматически, сравнивая текущую модель C# с последним известным снапшотом схемы (ApplicationDbContextModelSnapshot).

Миграция решает ключевую проблему Code-First: C#-модель меняется в процессе разработки, а схема БД должна за ней следовать — на всех средах (dev, staging, production) воспроизводимо и без потери данных.

7.3 Анатомия файла миграции

Каждый файл миграции содержит два метода: Up() применяет изменения вперёд, Down() откатывает их назад. EF Core использует Down() при команде database update {предыдущая_миграция}. 

// WebMessenger.DAL/Migrations/20250721190131_RemoveUniqueIndexFromEmail.cs
// Хороший пример минимальной миграции: одно точечное изменение
public partial class RemoveUniqueIndexFromEmail : Migration
{
    // Up() — применяется при database update: снять UNIQUE, создать обычный индекс
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropIndex(
            name: "IX_Users_Email",
            table: "Users");

        migrationBuilder.CreateIndex(
            name: "IX_Users_Email",
            table: "Users",
            column: "Email");   // без unique: true → обычный индекс
    }

    // Down() — откат: вернуть уникальный индекс
    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropIndex(
            name: "IX_Users_Email",
            table: "Users");

        migrationBuilder.CreateIndex(
            name: "IX_Users_Email",
            table: "Users",
            column: "Email",
            unique: true);    // UNIQUE восстановлен
    }
}
// WebMessenger.DAL/Migrations/20251123161128_RemoveMessageIsRead.cs
// Пример удаления столбца — Up убирает колонку, Down восстанавливает с default
public partial class RemoveMessageIsRead : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropColumn(
            name: "IsRead",
            table: "Messages");
        // Деструктивная операция — данные в колонке IsRead потеряны безвозвратно.
        // Down() может восстановить колонку, но не данные.
    }

    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.AddColumn<bool>(
            name: "IsRead",
            table: "Messages",
            type: "tinyint(1)",
            nullable: false,
            defaultValue: false);   // все строки получат false — исторические данные потеряны
    }
}

7.4 Что генерирует AddBasicModels — разбор крупной миграции

Миграция AddBasicModels — самая крупная в проекте: добавляет четыре новых таблицы и расширяет Users. По ней хорошо видно как EF Core транслирует C#-модель в DDL. 

// Фрагменты из 20250717131146_AddBasicModels.cs

// AlterColumn — изменение существующего столбца: добавлен DEFAULT CURRENT_TIMESTAMP(6)
// oldClrType / oldType — состояние до миграции (для Down())
migrationBuilder.AlterColumn<DateTime>(
    name: "CreatedAt", table: "Users",
    type: "datetime(6)",
    defaultValueSql: "CURRENT_TIMESTAMP(6)",
    oldClrType: typeof(DateTime), oldType: "datetime(6)");

// AddColumn — новое nullable поле: AvatarUrl string? → longtext NULL
migrationBuilder.AddColumn<string>(
    name: "AvatarUrl", table: "Users",
    type: "longtext", nullable: true);

// AddColumn — NOT NULL поле с defaultValue для существующих строк:
// при добавлении NOT NULL колонки в непустую таблицу нужен DEFAULT или defaultValue,
// иначе БД откажет — существующие строки не знают что поставить.
migrationBuilder.AddColumn<bool>(
    name: "IsOnline", table: "Users",
    type: "tinyint(1)", nullable: false,
    defaultValue: false);  // существующие пользователи → IsOnline = false

// CreateTable — новая таблица Chats с PK, столбцами, индексами
migrationBuilder.CreateTable(
    name: "Chats",
    columns: table => new
    {
        Id        = table.Column<Guid>(type: "char(36)", nullable: false),
        Name      = table.Column<string>(type: "varchar(100)", maxLength: 100, nullable: true),
        IsGroup   = table.Column<bool>(type: "tinyint(1)", nullable: false),
        CreatedAt = table.Column<DateTime>(type: "datetime(6)",
            defaultValueSql: "CURRENT_TIMESTAMP(6)"),
    },
    constraints: table => table.PrimaryKey("PK_Chats", x => x.Id));

// AddForeignKey — явная FK с именованием и OnDelete: Restrict
// EF Core автоматически добавляет FK после CreateTable для всех связанных таблиц
migrationBuilder.AddForeignKey(
    name: "FK_Contacts_Users_ContactUserId",
    table: "Contacts",
    column: "ContactUserId",
    principalTable: "Users",
    principalColumn: "Id",
    onDelete: ReferentialAction.Restrict);  // → ON DELETE RESTRICT

Стратегия поэтапного удаления столбца (без потери данных при откате):
  1. Миграция 1: сделать столбец nullable (AlterColumn nullable: true) — данные сохранены, код может читать null.
  2. Миграция 2: убрать использование столбца в C#-коде и деплой.
  3. Миграция 3: DropColumn — только теперь данные удаляются, и приложение уже не зависит от этого столбца.
В WebMessenger RemoveMessageIsRead применена напрямую — допустимо когда столбец использовался только внутри и резервная копия сделана.

8.4 TagWith — маркировка запросов

TagWith() добавляет SQL-комментарий к запросу, генерируемому EF Core. Это позволяет связать медленный запрос в логах базы данных (slow query log, Performance Insights, pg_stat_statements) с конкретным местом в C#-коде. 

// TagWith — добавляет комментарий в SQL: /* tag text */
var messages = await _uow.MessageRepository
    .GetAll()
    .TagWith("ChatService.GetMessagesAsync — history page")
    .Where(m => m.ChatId == chatId)
    .OrderByDescending(m => m.SentAt)
    .Take(take)
    .ToListAsync();

// Итоговый SQL в БД:
// -- ChatService.GetMessagesAsync — history page
// SELECT m.Id, m.ChatId, m.SenderId, m.Content, m.SentAt, m.EditedAt
// FROM Messages AS m
// WHERE m.ChatId = @p0
// ORDER BY m.SentAt DESC
// LIMIT @p1

// TagWithCallSite() — автоматически добавляет файл и номер строки C#-кода
var chats = await _uow.ChatRepository
    .GetAll()
    .TagWithCallSite()   // → /* file: ChatService.cs line: 42 */
    .Where(c => c.Members.Any(m => m.UserId == me))
    .ToListAsync();
Когда использовать TagWith: при оптимизации производительности, когда MySQL Slow Query Log или APM-система показывает медленный запрос, но непонятно откуда он пришёл. С тегом сразу видно: метод, назначение запроса. В WebMessenger теги не добавлены в продакшн-код, но это хорошая практика для высоконагруженных эндпоинтов.

9. Performance — Производительность

9.1 Сокращение числа round-trip к БД

Каждое обращение к базе данных включает сетевую задержку, разбор SQL, планирование запроса и передачу данных. В облачных и контейнерных средах latency одного round-trip может составлять 1–10 мс. При 100 запросах это 100–1000 мс — только на overhead. Главный принцип: меньше запросов к БД — быстрее ответ.

9.2 Async-операции с БД

Все методы материализации в WebMessenger используют async-варианты. Синхронные вызовы (ToList(), First(), Any()) блокируют поток ThreadPool на время ожидания ответа от БД — это критично для ASP.NET Core, где каждый заблокированный поток не может обрабатывать другие запросы.

СинхронныйAsync-аналогРекомендация

// Синхронный — блокирует поток на время IO (плохо в ASP.NET Core):
var items = _uow.MessageRepository.GetAll().ToList();  // ❌

// Async — освобождает поток пока БД обрабатывает запрос (правильно):
var items = await _uow.MessageRepository.GetAll().ToListAsync(ct);  // ✓

// SingleAsync vs FirstOrDefaultAsync:
// SingleAsync — генерирует исключение если записей 0 или >1. Использовать когда
// бизнес-логика гарантирует ровно одну запись (например PK-поиск).
// FirstOrDefaultAsync — безопасен: возвращает null если не найдено.
// В WebMessenger везде FirstOrDefaultAsync — защита от неожиданных данных.
var user = await _uow.UserRepository.GetAll()
    .FirstOrDefaultAsync(u => u.Username == username);
if (user == null) throw new KeyNotFoundException();

9.3 AsAsyncEnumerable — потоковая обработка

ToListAsync() загружает весь результат в память перед обработкой. При больших выборках (тысячи строк) это создаёт пиковое потребление памяти. AsAsyncEnumerable() позволяет обрабатывать строки по одной по мере их получения от БД. 

// ToListAsync — всё в памяти сразу. Хорошо для небольших выборок (≤1000 строк).
var all = await _uow.MessageRepository.GetAll()
    .Where(m => m.ChatId == chatId)
    .ToListAsync();  // например 50 000 сообщений → ~50 MB в памяти

// AsAsyncEnumerable — строки обрабатываются потоком, не накапливаются.
// Используется для экспорта, аналитики, батч-обработки больших объёмов данных.
await foreach (var message in _uow.MessageRepository.GetAll()
    .Where(m => m.ChatId == chatId)
    .OrderBy(m => m.SentAt)
    .AsAsyncEnumerable())
{
    await ProcessMessageAsync(message);  // обработка по одному
    // GC может собрать предыдущий объект пока идёт следующий
}

// В WebMessenger AsAsyncEnumerable не используется: все выборки ограничены
// пагинацией (limit ≤ 200 записей) — ToListAsync достаточно и проще.

9.4 Избегать избыточного Eager Loading

Include() добавляет JOIN и загружает дополнительные данные. Каждый Include увеличивает объём данных, передаваемых по сети, и нагрузку на БД. Загружать навигации нужно только когда они действительно используются. 

// Плохо: Include всего подряд, но реально нужен только Username участников
var chat = await _uow.ChatRepository
    .GetAll(
        nameof(Chat.Members),   // нужны
        nameof(Chat.Messages)   // не нужны для заголовка чата — лишний JOIN
    )
    .FirstOrDefaultAsync(c => c.Id == chatId);

// Хорошо: Include только Members + проекция только нужных полей User
var memberNames = await _uow.ChatMemberRepository
    .GetAll()
    .Where(cm => cm.ChatId == chatId)
    .Select(cm => cm.User!.Username)   // только Username — без Join на всю таблицу
    .ToListAsync();

// WebMessenger — ChatService.GetChatHeaderByChatIdAsync:
// Include только Members (нужен UserId), потом отдельный точечный запрос
// для одного User через FirstOrDefaultAsync + Select проекция.
var chat = await _uow.ChatRepository
    .GetAll(nameof(Chat.Members))   // только нужная навигация
    .FirstOrDefaultAsync(c => c.Id == chatId);

var other = await _uow.UserRepository.GetAll()
    .Where(u => u.Id == otherId)
    .Select(UserProjections.ToProfileDto)  // SELECT только нужных полей User
    .FirstOrDefaultAsync();

Признаки избыточного eager loading

  • Include-навигация присутствует, но в коде обращений к ней нет
  • Include коллекции с сотнями строк для операции, которой нужен только Count
  • ThenInclude глубиной 3+ уровня — почти всегда картезианский взрыв строк

9.5 Select только нужных полей — проекции

SELECT * загружает все столбцы сущности, включая большие поля (longtext, blob). Проекция через Select() точно указывает EF Core какие столбцы нужны — генерируется минимальный SELECT. 

// SELECT * — все поля User (включая PasswordHash, Bio, AvatarUrl и т.д.)
var users = await _uow.UserRepository.GetAll()
    .Where(u => peerIds.Contains(u.Id))
    .ToListAsync();  // тянем всё — нужны только Id, Username, AvatarUrl

// SELECT Id, Username, AvatarUrl — минимальный трафик
var peers = await _uow.UserRepository.GetAll()
    .Where(u => peerIds.Contains(u.Id))
    .Select(u => new { u.Id, u.Username, u.AvatarUrl })  // только 3 поля
    .ToListAsync();

// Переиспользуемая Expression-проекция (WebMessenger pattern):
// объявить один раз в MessageProjections / UserProjections,
// использовать во всех запросах — DRY + гарантия консистентности набора полей.
public static readonly Expression<Func<Message, ChatMessageDto>> ToChatMessageDto =
    m => new ChatMessageDto { Id = m.Id, ChatId = m.ChatId, /* ... */ };
// → SELECT Id, ChatId, SenderId, Content, SentAt, EditedAt FROM Messages

10. Security — Безопасность

10.1 SQL-параметризация в EF Core

EF Core всегда параметризует значения в LINQ-запросах. Любое значение C#-переменной в Where(), Select() или другом операторе передаётся в БД как параметр (@p0, @p1), а не вставляется в строку SQL напрямую. Это делает LINQ-запросы иммунными к SQL-инъекции по умолчанию. 

// Любое значение из C# → параметр в SQL. Внедрить SQL через LINQ невозможно.
var username = request.Username;  // может быть "admin' OR '1'='1" — не важно

var user = await _uow.UserRepository.GetAll()
    .FirstOrDefaultAsync(u => u.Username == username);

// EF Core генерирует:
// SELECT u.Id, u.Username, ... FROM Users AS u
// WHERE u.Username = @p0          ← @p0 = "admin' OR '1'='1"
// LIMIT 1
//
// БД получает СТРОКУ как данные, а не как SQL-код.
// Инъекция невозможна независимо от содержимого username.
// WebMessenger — ContactsService.GetUserContactsAsync: параметр query тоже безопасен
return await _unitOfWork.ContactRepository.GetAll()
    .Where(x => x.OwnerUserId == currentUserId
        && x.ContactUser!.Username.ToLower().Contains(query.ToLower()))
    .Include(x => x.ContactUser)
    .ToListAsync();
// query — строка поиска от пользователя. EF транслирует в:
// WHERE LOWER(u.Username) LIKE LOWER(CONCAT('%', @p1, '%'))
// @p1 получает значение query как параметр — инъекция невозможна.

10.2 Риски сырого SQL — конкатенация строк

FromSqlRaw() и ExecuteSqlRawAsync() позволяют выполнять произвольный SQL. При конкатенации пользовательского ввода в строку запроса возникает классическая SQL-инъекция. 

// ОПАСНО: конкатенация пользовательского ввода → SQL-инъекция
var username = request.Username;  // "'; DROP TABLE Users; --"

// ❌ Итоговый SQL: SELECT * FROM Users WHERE Username = ''; DROP TABLE Users; --'
// БД выполнит DROP TABLE!
var users = await context.Users
    .FromSqlRaw("SELECT * FROM Users WHERE Username = '" + username + "'")
    .ToListAsync();
// БЕЗОПАСНО: параметры через placeholders в FromSqlRaw
var users = await context.Users
    .FromSqlRaw("SELECT * FROM Users WHERE Username = {0}", username)
    .ToListAsync();
// {0} → @p0 = username. БД получает значение как данные, не как код.

// БЕЗОПАСНО: интерполированная строка в FromSqlInterpolated
// EF Core распознаёт C#-интерполяцию и автоматически превращает {username} в @p0
var users = await context.Users
    .FromSqlInterpolated($"SELECT * FROM Users WHERE Username = {username}")
    .ToListAsync();
// ВНИМАНИЕ: FormattableString, не обычная string!
// Если передать обычную интерполированную string — это конкатенация → инъекция:
string sql = $"SELECT * FROM Users WHERE Username = {username}";
var bad = await context.Users.FromSqlRaw(sql).ToListAsync();  // ❌ инъекция!

FromSqlRaw vs FromSqlInterpolated

FromSqlRawFromSqlInterpolated
Тип аргумента string + params object[] FormattableString (только C# $-interpolation)
Параметризация Вручную через {0}, {1} Автоматически из {переменная}
Риск инъекции Высокий при конкатенации; безопасен при {0} Безопасен — невозможно передать строку напрямую
Когда использовать Динамические части SQL (имена таблиц, ORDER BY), которые нельзя параметризовать Запросы с условиями по значениям — предпочтительный выбор

10.3 Правило минимума данных

Безопасность включает не только защиту от инъекций, но и минимизацию передаваемых данных: не возвращать клиенту поля, которые он не должен видеть. 

// Плохо: возвращаем всю сущность User, включая PasswordHash
var user = await _uow.UserRepository.GetAll()
    .FirstOrDefaultAsync(u => u.Id == userId);
return user;  // PasswordHash утечёт в ответ API если нет явного маппинга

// Хорошо: проекция через Expression — только безопасные поля
// WebMessenger.Api/Projections/Users/UserProjections.cs
public static readonly Expression<Func<User, UserProfileDto>> ToProfileDto =
    u => new UserProfileDto
    {
        Id        = u.Id,
        Username  = u.Username,
        FirstName = u.FirstName,
        LastName  = u.LastName,
        AvatarUrl = u.AvatarUrl,
        IsOnline  = u.IsOnline
        // PasswordHash не включён — никогда не уходит клиенту
    };

// Проекция применяется прямо в SQL:
// SELECT Id, Username, FirstName, LastName, AvatarUrl, IsOnline FROM Users WHERE ...
var profile = await _uow.UserRepository.GetAll()
    .Where(u => u.Id == userId)
    .Select(UserProjections.ToProfileDto)
    .FirstOrDefaultAsync();
