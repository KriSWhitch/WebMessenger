Entity Framework Core (Level 1) — WebMessenger

Practical skill guide to EF Core patterns, based on the current WebMessenger implementation.

Project: ASP.NET Core 8 + EF Core 8 + MySQL + Pomelo.EntityFrameworkCore.MySql 8.0.3 + Code-First approach

1. Environment and Tooling

Current setup in WebMessenger

  • Provider: Pomelo.EntityFrameworkCore.MySql v8.0.3 (MySQL 8.0+)
  • DbContext registration: in Program.cs with options builder
  • Approach: Code-first (entities define schema, migrations follow)
  • Connection string: from appsettings.json section ConnectionStrings:DefaultConnection
  • Migration strategy: Applied at startup in retry loop
// Program.cs
builder.Services.AddDbContext<ApplicationDbContext>((sp, options) =>
{
  options.UseMySql(
    builder.Configuration.GetConnectionString("DefaultConnection"),
    new MySqlServerVersion(new Version(8, 0, 42)),
    mysqlOptions => { mysqlOptions.EnableRetryOnFailure(); }
  );

  if (sp.GetRequiredService<IHostEnvironment>().IsDevelopment())
  {
    options.EnableSensitiveDataLogging();
    options.EnableDetailedErrors();
  }
});

Key concepts

  • DbContext lifetime: scoped per request (best practice for web)
  • Connection pooling: Pomelo handles this automatically
  • Retry on failure: enabled for transient network issues
  • Dev diagnostics: detailed EF errors and sensitive SQL parameter logging enabled only in Development
  • Migrations in git: all migrations tracked and applied deterministically

2. DbContext and Entities

DbContext as unit of work pattern

The ApplicationDbContext serves as both:

  • Gateway to query and save entities
  • Unit of Work for coordinated SaveChangesAsync across multiple operations
// ApplicationDbContext.cs
public class ApplicationDbContext(DbContextOptions options) : DbContext(options)
{
    public DbSet<User> Users { get; set; }
    public DbSet<Chat> Chats { get; set; }
    public DbSet<Message> Messages { get; set; }
    public DbSet<ChatMember> ChatMembers { get; set; }
    public DbSet<Contact> Contacts { get; set; }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // Fluent API configuration
    }
}

DbSet semantics

  • DbSet<T> represents a table mapped to entity type T
  • LINQ queries on DbSet are compiled to SQL and executed on the database
  • Navigation properties create relationships without explicit joins in code

Key conventions

Id property = Primary KeyAutomaticAll entities have Guid Id

3. Basic Modeling (Fluent API + Annotations)

Modeling approach in WebMessenger

This project uses Fluent API in OnModelCreating for database configuration and Data Annotations on entities for constraints.

Examples from ApplicationDbContext

// Timestamps with server-side defaults
modelBuilder.Entity(entity =>
{
    entity.Property(u => u.CreatedAt)
        .HasColumnType("datetime(6)")
        .HasDefaultValueSql("CURRENT_TIMESTAMP(6)")
        .ValueGeneratedOnAdd();

    entity.Property(u => u.LastSeenAt)
        .HasColumnType("datetime(6)")
        .HasDefaultValueSql("CURRENT_TIMESTAMP(6)")
        .ValueGeneratedOnAddOrUpdate();
});

// Composite unique index (user can only add another user as contact once)
modelBuilder.Entity(entity =>
{
    entity.HasIndex(c => new { c.OwnerUserId, c.ContactUserId }).IsUnique();

    // Relationship with Restrict behavior (no cascading deletes of users)
    entity.HasOne(c => c.OwnerUser)
        .WithMany(u => u.Contacts)
        .HasForeignKey(c => c.OwnerUserId)
        .OnDelete(DeleteBehavior.Restrict);
});

Simple vs complex relationships

RelationshipTypeExample in WebMessenger
One-to-ManyUser has many ContactsUser.Contacts → Contact[].OwnerUserId
Many-to-Many (via join table)User has many Chats (through ChatMember)User → ChatMember → Chat
One-to-One implicitMessage.Sender → UserEach Message has one Sender

Required vs Optional

  • Required (not nullable): Message.Content (enforced by [Required] annotation and non-null C# property)
  • Optional (nullable): Message.EditedAt (nullable C# property maps to NULL column)
  • Foreign keys: always required (if relationship is required)

4. Basic Querying

LINQ basics and materialization

Query that returns a list:

// From Repository.cs
public IQueryable GetAll(params string[] navigationProperties)
{
    var query = _dbSet.AsNoTracking();
    foreach (var navProp in navigationProperties)
    {
        query = query.Include(navProp);
    }
    return query;  // Not materialized yet — still IQueryable
}

// Service layer — materialization
var users = await _unitOfWork.UserRepository.GetAll()
    .Where(x => x.Username.ToLower().Contains(queryLower))
    .OrderBy(u => u.Username)
    .Take(limit)
    .ToListAsync();  // Materialization happens here

Find by primary key:

// Fast lookup by ID
var user = await _dbSet.FindAsync(new object[] { id }, ct);
// FindAsync checks local cache first, then database

FirstOrDefault and SingleOrDefault:

// FirstOrDefault — first match, or null
var chat = await _uow.ChatRepository.GetAll()
    .FirstOrDefaultAsync(c => c.Id == chatId);

// SingleOrDefault — exactly one match, or null (throws if >1)
var chatInfo = await _uow.ChatRepository.GetAll()
    .AsNoTracking()
    .Where(c => c.Id == chatId)
    .SingleOrDefaultAsync(ct);

Projections (select specific columns):

// UserService.cs — EF-translatable projection to DTO
var profile = await _unitOfWork.UserRepository.GetAll()
  .Where(u => u.Id == userId)
  .Select(UserProjections.ToProfileDto)
  .FirstOrDefaultAsync();

// ChatService.cs — centralized message projection
var items = await q
  .OrderByDescending(m => m.SentAt)
  .Take(take)
  .Select(MessageProjections.ToChatMessageDto)
  .ToListAsync();

Pagination:

// Cursor-based pagination (used in chats/messages listing)
var baseQuery = _uow.MessageRepository.GetAll();

if (before.HasValue)
    baseQuery = baseQuery.Where(m => m.SentAt < before.Value);

var items = await baseQuery
    .OrderByDescending(m => m.SentAt)
    .Take(limit)
    .ToListAsync();

5. Loading Related Data (Include/ThenInclude)

Eager loading with Include

// From ContactsService.cs
var contacts = await _unitOfWork.ContactRepository.GetAll()
    .Where(x => x.OwnerUserId == currentUserId && x.ContactUser!.Username.ToLower().Contains(query.ToLower()))
    .Include(x => x.ContactUser)  // Eager load the related user
    .ToListAsync();
// Single query with JOIN instead of N+1 problem

Multi-level loading with ThenInclude

Currently not used in this project, but recommended: 
// Example (not yet in WebMessenger):
var chats = await _dbContext.Chats
    .Include(c => c.Members)
        .ThenInclude(cm => cm.User)  // Load users within members
    .Where(c => c.Id == chatId)
    .ToListAsync();
// Loads: Chat → ChatMembers → Users in a single query

AsNoTracking for read-only queries

Used throughout the repository to improve performance on queries that don't modify entities:

var query = _dbSet.AsNoTracking();  // Skip change tracking overhead

Avoiding N+1 queries

PatternProblemSolution
Loop + separate query per itemN+1 queries (1 + N)Use Include before the loop
foreach (var item in list) { db.Get(item.Id) }If list has 100 items: 101 queriesMaterialize all first, then reference in memory
Per-chat unread count queryN queries for N chatsUse grouped batch query + dictionary map (implemented in ChatService)
Implemented optimization: ChatService.GetUserChatsAsync now batch-loads chat read states, unread counts, and DM peer info, then builds maps in memory instead of querying per chat.

6. Saving Data (Add/Update/Remove + SaveChanges)

Change tracking and state management

Adding:

// From Repository.cs
public async Task InsertAsync(T entity, CancellationToken ct = default)
{
    if (entity == null) throw new ArgumentNullException(nameof(entity));
    await _dbSet.AddAsync(entity, ct);  // Entity state = Added
    // Not committed yet — waiting for SaveChangesAsync
}

Updating:

// From Repository.cs
public Task UpdateAsync(T entity, CancellationToken ct = default)
{
    if (entity == null) throw new ArgumentNullException(nameof(entity));
    _dbSet.Attach(entity);
    _context.Entry(entity).State = EntityState.Modified;  // Mark as modified
    return Task.CompletedTask;
}

Removing:

// From Repository.cs
public async Task DeleteAsync(Guid id, CancellationToken ct = default)
{
    var entity = await _dbSet.FindAsync(new object[] { id }, ct);
    if (entity == null) throw new KeyNotFoundException($"Entity not found");
    _dbSet.Remove(entity);  // Entity state = Deleted
}

SaveChanges (Unit of Work pattern):

// From UnitOfWork.cs
public async Task CommitAsync(CancellationToken ct = default)
{
    await _context.SaveChangesAsync(ct);
    // All tracked changes (Add/Update/Remove) are batched and sent in single transaction
}

Common exceptions

ExceptionWhen it occursHow to handle
DbUpdateExceptionFK violation, unique constraint failure, or other DB errorCatch and log; return 400 or 409 to client
DbUpdateConcurrencyExceptionOptimistic concurrency conflict (rare without explicit concurrency tokens)Reload entity and retry or return conflict response
OperationCanceledExceptionQuery/save cancelled via CancellationTokenHandle gracefully in middleware

7. Basic Migrations

Creating migrations

// CLI command
dotnet ef migrations add AddBasicModels -p Server/WebMessenger.DAL -s Server/WebMessenger.Api

// Creates two files:
// - 20250717131146_AddBasicModels.cs (Up/Down methods)
// - 20250717131146_AddBasicModels.Designer.cs (snapshot, auto-generated)

Migration structure

// AddBasicModels.cs — Up method (schema changes to apply)
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.CreateTable(
        name: "Chats",
        columns: table => new
        {
            Id = table.Column(type: "char(36)", nullable: false),
            Name = table.Column(type: "varchar(100)", maxLength: 100, nullable: true),
            IsGroup = table.Column(type: "tinyint(1)", nullable: false),
            CreatedAt = table.Column(type: "datetime(6)", nullable: false, 
                defaultValueSql: "CURRENT_TIMESTAMP(6)")
        },
        constraints: table =>
        {
            table.PrimaryKey("PK_Chats", x => x.Id);
        });
}

// Down method (undo the changes — for rollback)
protected override void Down(MigrationBuilder migrationBuilder)
{
    migrationBuilder.DropTable(name: "Chats");
}

Applying migrations

// At startup (Program.cs)
var db = scope.ServiceProvider.GetRequiredService();
db.Database.Migrate();  // Applies all pending migrations

Reverting migrations

Only for development — in production, always create new migrations to undo changes. 
// CLI
dotnet ef database update RemoveUniqueIndexFromEmail  // Revert to specific migration
dotnet ef database update 0                           // Remove all migrations

8. Value Conversions

When to use value converters

Value converters transform property values between CLR type and database representation.

Common scenarios

CLR TypeDatabase TypeUse Case
enumint or stringStore enum as integer or name
boolbit or char(1)Database-specific boolean
DateTimeVARCHAR + timezone conversionUTC storage with local display
List<T>JSON stringStore collection as JSON column
Not currently used in WebMessenger, but a recommended next step for handling enum status fields or JSON arrays in future features.

Theoretical example

// Example: store enum as string in database
public enum MessageStatus { Sent, Delivered, Read }

modelBuilder.Entity()
    .Property(m => m.Status)
    .HasConversion(
        v => v.ToString(),                    // To database
        v => Enum.Parse(v)     // From database
    );

10. Performance Fundamentals

Reducing round trips

  • Batch operations: use AddRangeAsync instead of loop + Add
  • Include related data: load chats + members in one query vs separate queries
  • Use pagination: don't load all 10K messages at once

Async database operations

All DAL queries use async operators to avoid blocking:

Sync (avoid)Async (use)
.ToList().ToListAsync()
.FirstOrDefault().FirstOrDefaultAsync()
.Count().CountAsync()
.Any().AnyAsync()
.Single().SingleAsync()

Projection for memory efficiency

// Centralized projection expressions (implemented)
// Server/WebMessenger.Api/Projections/Users/UserProjections.cs
public static readonly Expression<Func<User, UserProfileDto>> ToProfileDto = ...;

// Usage from UserService.cs
return await _unitOfWork.UserRepository.GetAll()
    .Where(u => u.Id == userId)
    .Select(UserProjections.ToProfileDto)
    .FirstOrDefaultAsync();
This pattern is now used in UserService, ChatService, and ContactsService through UserProjections, MessageProjections, and ContactProjections.

Avoiding heavy eager loading

  • Don't include all related collections by default
  • Use AsNoTracking() for read-only queries
  • Explicit loading when needed, not automatic

11. Security Fundamentals

SQL parameterization

LINQ to Entities automatically parameterizes all queries — no manual escaping needed:

// SAFE — parameters are automatically bound
var username = userInput;  // Could contain ' or malicious SQL
var user = await _userRepository.GetAll()
    .FirstOrDefaultAsync(u => u.Username == username);
// EF Core sends: SELECT ... WHERE Username = @p0, with value as separate parameter

What NOT to do — raw SQL concatenation

// DANGEROUS — never do this
string sql = $"SELECT * FROM Users WHERE Username = '{userInput}'";  // SQL injection risk
var users = await _dbContext.Users.FromSqlRaw(sql).ToListAsync();

// SAFE — use parameterization
var users = await _dbContext.Users
    .FromSqlInterpolated($"SELECT * FROM Users WHERE Username = {userInput}")
    .ToListAsync();

Permission boundaries

In WebMessenger, business logic enforces:

  • Users can only view chats they're members of
  • Users can only update their own profile
  • Contacts can only be managed by the owner
// Service-level check (required + contact ownership)
if (!isMember)
    throw new UnauthorizedAccessException("Not a member of this chat");

var cm = await _uow.ChatMemberRepository.GetAll()
    .FirstOrDefaultAsync(x => x.ChatId == chatId && x.UserId == me);
// Only the current user can fetch their own read state
