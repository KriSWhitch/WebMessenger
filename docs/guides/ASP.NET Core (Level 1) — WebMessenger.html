ASP.NET Core (Level 1) — WebMessenger

Практический гайд по ASP.NET Core 8 с разбором концепций фреймворка на примерах из реального проекта WebMessenger. Каждый раздел объясняет: что это, как работает, зачем нужно и когда применять.

Проект: ASP.NET Core 8 Web API + EF Core + SignalR + Serilog + JWT

1. Structure of an ASP.NET Project

Понимание структуры проекта — это фундамент. Прежде чем писать логику, нужно знать, что за файлы лежат рядом, что они делают и что происходит после сборки.

1.1 Solution и Projects — организация кода

Что это. В экосистеме .NET код организован на двух уровнях: solution (.sln) и project (.csproj). Solution — это контейнер, который объединяет несколько проектов под одним «зонтиком» для совместной сборки и навигации в IDE. Каждый проект — это отдельная единица компиляции со своими зависимостями, типом выходного артефакта и настройками.

Зачем делить на проекты. Разбиение на проекты даёт:

  • Изоляцию зависимостей — проект WebMessenger.Contracts не тащит за собой EF Core, потому что он ему не нужен.
  • Переиспользование — любой другой проект (тесты, другой сервис) может подключить только нужный слой.
  • Контроль видимости — типы с модификатором internal не выходят за границы проекта.
  • Параллельную сборку — MSBuild строит независимые проекты одновременно.

Структура WebMessenger. Solution состоит из четырёх проектов, каждый из которых реализует отдельный слой архитектуры:

Проект SDK Роль
WebMessenger.Api Microsoft.NET.Sdk.Web Точка входа. HTTP-контроллеры, SignalR-хабы, Middleware, DI-конфигурация, Program.cs
WebMessenger.DAL Microsoft.NET.Sdk Data Access Layer. DbContext, сущности, репозитории, миграции EF Core
WebMessenger.Contracts Microsoft.NET.Sdk Общие контракты. DTO, вспомогательные модели, не зависит от инфраструктуры
WebMessenger.Api.Tests Microsoft.NET.Sdk Тесты для API-слоя. Зависит от WebMessenger.Api
Правило зависимостей: Api → DAL и Contracts; DAL → Contracts; Contracts ни от кого не зависит. Если Contracts начнёт зависеть от DAL — это сигнал о нарушении архитектуры.

1.2 Файл .csproj — сердце проекта

Что это. Файл .csproj — это XML-манифест проекта в формате MSBuild. Он описывает: на каком SDK основан проект, какой фреймворк таргетируется, какие NuGet-пакеты нужны, ссылки на другие проекты и любые дополнительные инструкции для сборщика.

SDK-стиль (.NET Core+). Современные проекты используют SDK-стиль (SDK-style project): большинство файлов (*.cs) подключаются автоматически — их не надо явно прописывать. Это резко сокращает объём XML по сравнению с legacy .csproj из .NET Framework.

// WebMessenger.Api/WebMessenger.Api.csproj — разбор по строкам
<Project Sdk="Microsoft.NET.Sdk.Web">
  // ↑ SDK определяет тип проекта.
  //   .Sdk.Web добавляет зависимость на Microsoft.AspNetCore.App framework reference,
  //   Register'ит Kestrel, Middleware-инфраструктуру и пр. автоматически.
  //   Для библиотек используют Microsoft.NET.Sdk (без .Web).

  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    // ↑ Монитор версии runtime. net8.0 = .NET 8. Можно указать несколько через ;

    <Nullable>enable</Nullable>
    // ↑ Включает Nullable Reference Types (NRT) для всего проекта.
    //   Компилятор выдаёт предупреждения CS8600-CS8604 при небезопасной работе с null.

    <ImplicitUsings>enable</ImplicitUsings>
    // ↑ Автоматически добавляет популярные using'и (System, System.Linq и др.)
    //   через сгенерированный файл в obj/. Не надо писать "using System;" в каждом файле.

    <UserSecretsId>webmessenger-api-secrets</UserSecretsId>
    // ↑ ID для хранилища секретов (dotnet user-secrets).
    //   Секреты хранятся вне репозитория: %APPDATA%/Microsoft/UserSecrets/{id}/secrets.json
  </PropertyGroup>

  <ItemGroup>
    // Явное исключение папки logs/ из компиляции и контента.
    // Без этого MSBuild может включать .txt-файлы в артефакты.
    <Compile Remove="logs\**" />
    <Content Remove="logs\**" />
  </ItemGroup>

  <ItemGroup>
    // NuGet-пакеты. Version — фиксированная или диапазон.
    <PackageReference Include="Swashbuckle.AspNetCore" Version="6.6.2" />
    <PackageReference Include="Serilog.AspNetCore" Version="8.0.3" />

    // Design-time only зависимости (генерация кода, тулинг, анализаторы).
    // PrivateAssets=all означает: пакет не транзитивно переходит к зависимым проектам.
    <PackageReference Include="Microsoft.EntityFrameworkCore.Design" Version="8.0.18">
      <PrivateAssets>all</PrivateAssets>
      <IncludeAssets>runtime; build; native; contentfiles; analyzers; buildtransitive</IncludeAssets>
    </PackageReference>
  </ItemGroup>

  <ItemGroup>
    // Ссылки на другие проекты внутри solution.
    // MSBuild знает: сначала собрать эти, потом текущий.
    <ProjectReference Include="..\WebMessenger.Contracts\WebMessenger.Contracts.csproj" />
    <ProjectReference Include="..\WebMessenger.DAL\WebMessenger.DAL.csproj" />
  </ItemGroup>

</Project>

1.3 Файл Program.cs — точка входа приложения

Что это. Начиная с .NET 6, точка входа приложения — это файл Program.cs с использованием top-level statements. Вся конфигурация приложения (DI-контейнер, middleware-пайплайн, хосты) живёт здесь. Main() более не нужен явно — компилятор генерирует его автоматически.

Структура Program.cs. Условно делится на два этапа:

  1. Фаза конфигурации (builder phase) — создаётся WebApplicationBuilder, регистрируются сервисы в DI-контейнере.
  2. Фаза запуска (app phase) — создаётся WebApplication, настраивается HTTP-пайплайн (middleware), маппируются эндпоинты, вызывается app.Run().
// WebMessenger.Api/Program.cs — аннотированный разбор

// --- ФАЗА КОНФИГУРАЦИИ ---

var builder = WebApplication.CreateBuilder(args);
// ↑ Создаёт WebApplicationBuilder — «строитель» приложения.
//   Внутри уже настроен: Kestrel, конфигурация из appsettings.json,
//   переменные окружения, ILogger, IHostEnvironment.

builder.Host.UseSerilog(...);
// ↑ Заменяет встроенный Microsoft.Extensions.Logging на Serilog.
//   builder.Host даёт доступ к IHostBuilder для настройки хоста.

builder.Services.AddControllers();
builder.Services.AddSwaggerGen();
// ↑ builder.Services — это IServiceCollection.
//   Все вызовы .Add* здесь регистрируют сервисы в DI-контейнере.
//   AddControllers() регистрирует инфраструктуру MVC-контроллеров.

builder.Services.AddScoped<IUnitOfWork, UnitOfWork>();
builder.Services.AddSingleton<IChatEvents, ChatEvents>();
// ↑ Регистрация собственных сервисов.

// --- ПЕРЕХОД ---

var app = builder.Build();
// ↑ Финализирует DI-контейнер и создаёт WebApplication.
//   После этой строки добавлять сервисы в builder.Services бессмысленно —
//   контейнер уже заморожен.

// --- ФАЗА ЗАПУСКА ---

if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
}

app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseCors(FrontCors);
app.UseAuthentication();
app.UseAuthorization();
// ↑ Настройка HTTP middleware-пайплайна. ПОРЯДОК КРИТИЧЕН.
//   Каждый .Use* добавляет звено в цепочку обработки запроса.

app.MapControllers();
app.MapHub<ChatHub>("/hubs/chat");
// ↑ Маппинг эндпоинтов: контроллеры и SignalR-хабы.

app.Run();
// ↑ Запускает Kestrel и блокирует поток до завершения приложения.

1.4 Файлы конфигурации — appsettings.json

Что это. ASP.NET Core имеет встроенную систему конфигурации (IConfiguration), которая агрегирует настройки из нескольких источников. Главный файл — appsettings.json. Дополнительно поддерживаются: переменные окружения, командная строка, User Secrets, Azure Key Vault и другие провайдеры.

Принцип слоёв. Каждый следующий источник конфигурации перекрывает значения предыдущего. Это позволяет иметь безопасные дефолты в appsettings.json и переопределять их в окружениях.

Источник Приоритет Назначение
appsettings.json Низкий (база) Дефолтные настройки. Коммитится в git. Секреты не хранить!
appsettings.{Environment}.json Средний Переопределения для конкретного окружения (Development, Production)
User Secrets Высокий (Development) Локальные секреты разработчика (вне репозитория)
Environment Variables Очень высокий Настройки в Docker/CI/Production
Command-line arguments Наивысший Временные переопределения при запуске 
// appsettings.json — базовая конфигурация WebMessenger
{
    "ConnectionStrings": {
        "DefaultConnection": ""     // пустая строка — будет переопределена
    },
    "Jwt": {
        "Key": "",                  // секрет — пустой в базовом файле
        "Issuer": "WebMessenger",
        "Audience": "WebMessengerClients",
        "ExpireDays": 1
    },
    "Serilog": {
        "MinimumLevel": {
            "Default": "Information",
            "Override": {
                "Microsoft": "Warning",
                "Microsoft.EntityFrameworkCore": "Warning"
            }
        }
    }
}

// appsettings.Development.json — переопределение только нужных полей
{
    "Serilog": {
        "MinimumLevel": {
            "Default": "Debug",         // в Development хотим видеть Debug-логи
            "Override": {
                "Microsoft": "Information"
            }
        }
    }
}
// Итог: в Development MinimumLevel.Default = "Debug",
// а остальные секции из appsettings.json остаются без изменений.

Доступ к конфигурации в коде

// Способ 1: прямое чтение через IConfiguration (не рекомендуется для сложных секций)
var connStr = builder.Configuration.GetConnectionString("DefaultConnection");

// Способ 2: Options Pattern — типизированное связывание (рекомендуется)
// WebMessenger.Api/Options/JwtOptions.cs
public class JwtOptions
{
    public const string SectionName = "Jwt";

    [Required]
    public required string Key { get; init; }

    [Required]
    public required string Issuer { get; init; }

    [Required]
    public required string Audience { get; init; }

    public int ExpireDays { get; init; } = 1;
}

// Регистрация в Program.cs с валидацией при старте:
builder.Services
    .AddOptions<JwtOptions>()
    .BindConfiguration(JwtOptions.SectionName)   // секция "Jwt" из appsettings
    .ValidateDataAnnotations()                    // проверяет [Required] и др.
    .ValidateOnStart();                           // падает при старте, не при первом обращении

// Использование в сервисе через IOptions<T>:
public class AuthService(IOptions<JwtOptions> jwtOptions)
{
    private readonly JwtOptions _jwt = jwtOptions.Value;
    // _jwt.Key, _jwt.Issuer и т.д.
}
Никогда не храните секреты (пароли, ключи, токены) в appsettings.json! Этот файл попадает в git. Используйте User Secrets локально и переменные окружения в production.

1.5 launchSettings.json — настройки запуска

Что это. Файл Properties/launchSettings.json описывает профили запуска для IDE (Visual Studio, Rider) и dotnet run. Это исключительно dev-файл — он не используется в production и не должен влиять на поведение приложения в реальных окружениях.

Что задаёт. Каждый профиль может задать: URL-адрес для прослушивания (applicationUrl), переменные окружения (ASPNETCORE_ENVIRONMENT), команду запуска (commandName: Project, IISExpress, Executable).

// Properties/launchSettings.json
{
    "profiles": {
        "http": {
            "commandName": "Project",
            // ↑ "Project" = запустить как dotnet-процесс (Kestrel).
            //   "IISExpress" = запустить через IIS Express.

            "applicationUrl": "http://localhost:5227",
            // ↑ Адрес, на котором слушает Kestrel при запуске этого профиля.

            "launchBrowser": true,
            "launchUrl": "swagger",
            // ↑ IDE откроет браузер на /swagger после запуска.

            "environmentVariables": {
                "ASPNETCORE_ENVIRONMENT": "Development"
                // ↑ Устанавливает переменную окружения для этого запуска.
                //   Приложение читает её через IHostEnvironment.EnvironmentName.
                //   Это активирует appsettings.Development.json и IsDevelopment() = true.
            }
        }
    }
}
ASPNETCORE_ENVIRONMENT — ключевая переменная. Её значение определяет: какой appsettings.{Environment}.json загрузится, что вернёт IHostEnvironment.IsDevelopment(), и какие middleware активируются условно.

1.6 Артефакты сборки — папки bin/ и obj/

Что это. При компиляции проекта MSBuild создаёт две служебные папки: obj/ и bin/. Их содержимое генерируется автоматически — они никогда не коммитятся в git (.gitignore исключает их по умолчанию).

Папка obj/ — промежуточные артефакты

Используется MSBuild в процессе компиляции. Содержит:

  • *.g.cs — сгенерированный код (например, файл глобальных using от ImplicitUsings)
  • project.assets.json — граф всех NuGet-зависимостей (транзитивных включительно)
  • *.csproj.nuget.g.props — импортированные MSBuild-свойства из NuGet-пакетов
  • *.dll — промежуточные скомпилированные файлы до линковки

Папка bin/ — финальные артефакты

Содержит готовый к запуску результат сборки. Структура:

2. Servers, Host and Publishing

Прежде чем запрос дойдёт до вашего контроллера, он должен быть принят HTTP-сервером, передан хосту, который управляет жизненным циклом приложения, и весь этот процесс должен быть упакован в артефакт публикации. Этот раздел объясняет инфраструктуру запуска ASP.NET Core «от сети до кода».

2.1 IHost и IHostBuilder — общая модель хоста

Что это. IHost — это абстракция «хоста» в .NET: долгоживущий объект, который управляет временем жизни приложения, DI-контейнером, конфигурацией и набором hosted services (IHostedService). Он появился в .NET Core 2.1 как обобщённый хост — Generic Host, — чтобы одна и та же инфраструктура работала и для Web API, и для консольных приложений, и для фоновых Worker-сервисов.

Иерархия.

  • IHostBuilder — строитель хоста. Настраивает конфигурацию, DI, логирование. Метод .Build() возвращает IHost.
  • IHost — запущенный хост. Методы StartAsync() / StopAsync() / RunAsync() управляют временем жизни. Предоставляет IServiceProvider.
  • IHostedService — интерфейс для фоновых сервисов, которые запускает и останавливает хост.
// Концептуальная схема Generic Host (упрощённо)
// IHostBuilder настраивает хост ДО запуска
IHostBuilder builder = Host.CreateDefaultBuilder(args)
    .ConfigureAppConfiguration((context, config) =>
    {
        // Добавление источников конфигурации
        config.AddJsonFile("appsettings.json");
        config.AddEnvironmentVariables();
    })
    .ConfigureServices((context, services) =>
    {
        // Регистрация сервисов в DI
        services.AddHostedService<MyBackgroundWorker>();
    })
    .ConfigureLogging(logging =>
    {
        logging.AddConsole();
    });

// Build() фиксирует всё, запускает IHost
IHost host = builder.Build();

// Run() запускает все IHostedService и блокирует поток
// до получения сигнала остановки (Ctrl+C, SIGTERM и т.д.)
await host.RunAsync();

Что делает Host.CreateDefaultBuilder(). Этот статический метод — удобная точка старта. Он автоматически настраивает:

  • Загрузку конфигурации из appsettings.json, appsettings.{Environment}.json, переменных окружения и аргументов командной строки
  • Логирование через Microsoft.Extensions.Logging (Console, Debug, EventSource)
  • Установку корневой директории как ContentRootPath
  • Поддержку User Secrets в Development-окружении

2.2 WebApplication и WebApplicationBuilder — Web-специфичный хост

Что это. Начиная с .NET 6, для веб-приложений появился упрощённый API поверх Generic Host: WebApplicationBuilder и WebApplication. Это не замена IHost — под капотом всё равно работает тот же IHost. Это синтаксическое упрощение, которое убирает шаблонный код и позволяет настроить всё в одном файле Program.cs.

WebApplicationBuilder

Создаётся через WebApplication.CreateBuilder(args). Предоставляет единую точку доступа ко всем подсистемам конфигурации хоста:

Свойство Тип Что настраивает
builder.Services IServiceCollection DI-контейнер: регистрация сервисов
builder.Configuration ConfigurationManager Конфигурация: чтение и добавление источников
builder.Environment IWebHostEnvironment Окружение: имя, ContentRoot, WebRoot
builder.Host IHostBuilder Настройки Generic Host: Serilog, Windows Service и пр.
builder.WebHost IWebHostBuilder Настройки web-хоста: Kestrel, IIS, URL-адреса
builder.Logging ILoggingBuilder Логирование: провайдеры, фильтрация 
// WebMessenger.Api/Program.cs — разбор WebApplicationBuilder
var builder = WebApplication.CreateBuilder(args);
// ↑ Внутри: создаёт IHostBuilder, WebHostBuilder, загружает конфигурацию,
//   настраивает Kestrel как сервер по умолчанию.

// builder.Host даёт доступ к IHostBuilder
// Здесь мы заменяем стандартный провайдер логирования на Serilog:
builder.Host.UseSerilog((context, services, configuration) =>
    configuration.ReadFrom.Configuration(context.Configuration)
                 .ReadFrom.Services(services)
                 .Enrich.FromLogContext());
// context.Configuration — это уже загруженная конфигурация из appsettings.json
// ReadFrom.Services — позволяет инжектировать ILogEventSink через DI

// builder.Services — регистрация всех сервисов
builder.Services.AddControllers();
builder.Services.AddSignalR(options =>
{
    options.EnableDetailedErrors = builder.Environment.IsDevelopment();
    // ↑ builder.Environment доступен на этапе конфигурации,
    //   можно ветвиться по окружению прямо здесь
});

WebApplication

Создаётся через builder.Build(). Реализует сразу несколько интерфейсов:

  • IHost — управление временем жизни
  • IApplicationBuilder — настройка middleware-пайплайна через .Use*()
  • IEndpointRouteBuilder — маппинг эндпоинтов через .Map*()
// WebMessenger.Api/Program.cs — разбор WebApplication
var app = builder.Build();
// ↑ После этой строки DI-контейнер заморожен.
//   Нельзя добавить новые сервисы. Можно только читать.

// app реализует IApplicationBuilder → настройка пайплайна:
app.UseExceptionHandler();
app.UseCors(FrontCors);
app.UseAuthentication();
app.UseAuthorization();

// app реализует IEndpointRouteBuilder → маппинг:
app.MapControllers();
app.MapHub<ChatHub>("/hubs/chat");

// app.Run() = host.RunAsync() + блокировка текущего потока
app.Run();

2.3 Application Lifetime Events

Что это. IHostApplicationLifetime — сервис, который позволяет реагировать на события жизненного цикла хоста и программно инициировать остановку. Доступен через DI.

Токен / Метод Когда срабатывает
ApplicationStarted Хост полностью запустился и готов обрабатывать запросы
ApplicationStopping Получен сигнал остановки (Ctrl+C, SIGTERM, StopApplication()). Запросы ещё принимаются
ApplicationStopped Хост полностью остановлен. Все IHostedService.StopAsync() завершены
StopApplication() Программно инициирует graceful shutdown 
// Регистрация обработчиков событий жизненного цикла
// (абстрактный пример — в WebMessenger не используется напрямую,
//  т.к. Serilog и EF управляют своими ресурсами самостоятельно)

var app = builder.Build();

var lifetime = app.Services.GetRequiredService<IHostApplicationLifetime>();

lifetime.ApplicationStarted.Register(() =>
{
    Console.WriteLine("Application is ready to handle requests");
    // Здесь можно: прогреть кэш, отправить уведомление о запуске,
    // зарегистрировать сервис в Service Discovery и т.д.
});

lifetime.ApplicationStopping.Register(() =>
{
    Console.WriteLine("Application is shutting down gracefully...");
    // Здесь можно: остановить прием новых задач,
    // дождаться завершения in-flight операций
});

lifetime.ApplicationStopped.Register(() =>
{
    Console.WriteLine("Application has stopped");
    // Здесь можно: закрыть соединения с внешними системами,
    // сбросить кэш на диск
});

app.Run();

// -------------------------------------------------------
// IHostedService — фоновый сервис, который хост запускает/останавливает
public class MyWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        // stoppingToken отменяется при ApplicationStopping.
        // Именно через него реализуется graceful shutdown фоновых задач.
        while (!stoppingToken.IsCancellationRequested)
        {
            await DoWorkAsync();
            await Task.Delay(TimeSpan.FromSeconds(10), stoppingToken);
        }
    }
}

Graceful shutdown в WebMessenger. В проекте Bootstrap-логгер Serilog оборачивает весь запуск в try/catch/finally — это ручная реализация graceful shutdown для логгера. Log.CloseAndFlush() в блоке finally гарантирует сброс буферов логов даже при аварийном завершении.

// WebMessenger.Api/Program.cs — обёртка graceful shutdown
try
{
    Log.Information("Starting WebMessenger API");
    var builder = WebApplication.CreateBuilder(args);
    // ... конфигурация ...
    var app = builder.Build();
    // ... пайплайн ...
    app.Run();
    // ↑ Блокирует до сигнала остановки (Ctrl+C / SIGTERM / docker stop)
}
catch (Exception ex) when (ex is not HostAbortedException)
{
    // HostAbortedException — нормальный сигнал от инструментов (dotnet watch и т.д.)
    // Его не логируем как fatal
    Log.Fatal(ex, "Application terminated unexpectedly");
}
finally
{
    // Выполняется всегда: и при нормальной остановке, и при краше
    Log.CloseAndFlush(); // сброс всех буферов Serilog
}

2.4 Kestrel — встроенный HTTP-сервер

Что это. Kestrel — это кроссплатформенный HTTP-сервер, встроенный в ASP.NET Core. Он написан на управляемом C# поверх libuv/Socket API и является сервером по умолчанию для всех ASP.NET Core приложений. Kestrel не зависит от операционной системы — одинаково работает на Windows, Linux и macOS.

Роль Kestrel. Kestrel принимает TCP-соединения, разбирает HTTP/1.1, HTTP/2 и HTTP/3, и передаёт объекты HttpContext в ASP.NET Core пайплайн. Это «нижний уровень» — он не знает ничего о контроллерах или middleware.

Конфигурация Kestrel

// Способ 1: через переменную окружения (используется в WebMessenger Docker)
// docker-compose.yml:
// environment:
//   ASPNETCORE_URLS: http://+:8080
//   ↑ http://+:8080 означает: слушать на порту 8080 на всех сетевых интерфейсах
//   Dockerfile.api:
//   ENV ASPNETCORE_URLS=http://+:8080

// Способ 2: через appsettings.json (рекомендуется для сложных настроек)
{
    "Kestrel": {
        "Endpoints": {
            "Http": {
                "Url": "http://+:8080"
            },
            "Https": {
                "Url": "https://+:8443",
                "Certificate": {
                    "Path": "/certs/cert.pfx",
                    "Password": "password"
                }
            }
        },
        "Limits": {
            "MaxConcurrentConnections": 100,
            "MaxRequestBodySize": 10485760,   // 10 MB
            "KeepAliveTimeout": "00:02:00"
        }
    }
}

// Способ 3: программная настройка через builder.WebHost
builder.WebHost.ConfigureKestrel(options =>
{
    options.ListenAnyIP(8080);                  // HTTP
    options.ListenAnyIP(8443, listenOptions =>  // HTTPS
    {
        listenOptions.UseHttps("/certs/cert.pfx", "password");
        listenOptions.Protocols = HttpProtocols.Http1AndHttp2;
    });

    options.Limits.MaxRequestBodySize = 10 * 1024 * 1024; // 10 MB
    options.Limits.RequestHeadersTimeout = TimeSpan.FromSeconds(15);
});
В WebMessenger: Kestrel настроен через переменную окружения ASPNETCORE_URLS=http://+:8080. Это самый простой способ для Docker-развёртывания. HTTPS-терминация вынесена на уровень реверс-прокси (nginx), поэтому внутри контейнера используется только HTTP.

2.5 IIS как реверс-прокси для ASP.NET Core

Что это. IIS (Internet Information Services) в контексте ASP.NET Core играет роль реверс-прокси, а не самостоятельного HTTP-сервера. Запросы принимает IIS, а затем перенаправляет их в Kestrel через модуль ASP.NET Core Module (ANCM).

Два режима ANCM:

Режим Как работает Плюсы Минусы
In-Process (рекомендуется) ASP.NET Core запускается прямо внутри рабочего процесса IIS (w3wp.exe). Нет сетевого проксирования. Минимальная latency, меньше ресурсов Один AppPool — одно приложение
Out-of-Process IIS проксирует запросы в отдельный Kestrel-процесс по loopback Изоляция процессов, независимые перезапуски Дополнительный hop, чуть выше latency 
// web.config — конфигурация ANCM для WebMessenger
// hostingModel="inprocess" — рекомендуемый режим
<aspNetCore processPath="dotnet"
            arguments=".\WebMessenger.Api.dll"
            stdoutLogEnabled="false"
            hostingModel="inprocess" />

// Для Out-of-Process:
// <aspNetCore hostingModel="outofprocess" ... />

Когда использовать IIS. IIS актуален при хостинге на Windows Server: он обеспечивает управление процессами (автоперезапуск), интеграцию с Windows Authentication, централизованное управление сертификатами и application pools. В Linux/Docker-окружениях IIS не используется — там Kestrel работает напрямую или за nginx/Caddy.

Сценарий Рекомендуемая схема
Windows Server (корпоративная среда) IIS → ANCM → Kestrel (In-Process)
Linux / Docker nginx/Caddy → Kestrel (реверс-прокси + TLS-терминация)
Разработка Kestrel напрямую (через launchSettings.json)
WebMessenger в Docker docker-compose → Kestrel на порту 8080, снаружи маппится на 5227

2.6 Publishing Process — dotnet publish

Что это. dotnet publish — команда CLI, которая подготавливает приложение к развёртыванию. В отличие от dotnet build, которая просто компилирует, publish копирует в выходную папку всё необходимое для запуска: скомпилированные сборки, зависимости, конфигурационные файлы, статические файлы.

Основные флаги команды

// Базовый вызов — Release-конфигурация, framework-dependent deployment:
dotnet publish Server/WebMessenger.Api/WebMessenger.Api.csproj -c Release -o /app/publish

// Флаги:
// -c Release            — конфигурация сборки (Debug / Release)
//                         Release включает оптимизации и убирает отладочный код
// -o /app/publish       — выходная папка
// --no-restore          — пропустить dotnet restore (уже выполнен ранее)
// -r linux-x64          — Runtime Identifier (RID) для self-contained
// --self-contained      — включить runtime в артефакт
// --self-contained false— framework-dependent (runtime на хосте)
// -p:PublishSingleFile=true — упаковать всё в один .exe / бинарник
// -p:PublishTrimmed=true    — обрезать неиспользуемые части runtime (уменьшает размер)

Framework-Dependent vs Self-Contained

Тип Что включает Размер Требования к хосту Когда использовать
Framework-Dependent (FDD) Только код приложения и NuGet-зависимости ~5–20 MB Установленный .NET runtime нужной версии Docker (базовый образ dotnet/aspnet), корпоративные серверы
Self-Contained (SCD) Код + весь .NET runtime ~80–200 MB Ничего не нужно устанавливать Дистрибуция как standalone-приложение, нестандартные окружения

Многоэтапная Docker-сборка в WebMessenger

// Dockerfile.api — классический multi-stage build
// ЭТАП 1: сборка (используем полный SDK-образ ~800 MB)
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

# Сначала копируем только .csproj для кэширования слоёв Docker.
# Если исходный код изменился, но зависимости нет — restore берётся из кэша.
COPY Server/WebMessenger.Api/WebMessenger.Api.csproj Server/WebMessenger.Api/
COPY Server/WebMessenger.DAL/WebMessenger.DAL.csproj Server/WebMessenger.DAL/
COPY Server/WebMessenger.Contracts/WebMessenger.Contracts.csproj Server/WebMessenger.Contracts/

RUN dotnet restore Server/WebMessenger.Api/WebMessenger.Api.csproj

# Теперь копируем весь код (этот слой инвалидируется при изменении кода)
COPY Server/ Server/

RUN dotnet publish Server/WebMessenger.Api/WebMessenger.Api.csproj \
    -c Release \          # Release-оптимизации
    -o /app/publish \     # выходная директория внутри контейнера
    --no-restore          # restore уже был выше

# ЭТАП 2: runtime-образ (лёгкий ~200 MB, без SDK)
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app

RUN mkdir -p logs

# Копируем только артефакты publish из build-этапа
# В финальный образ SDK не попадает — это ключевое преимущество multi-stage
COPY --from=build /app/publish .

ENV ASPNETCORE_URLS=http://+:8080
EXPOSE 8080

# Точка входа: запуск через dotnet (Framework-Dependent Deployment)
ENTRYPOINT ["dotnet", "WebMessenger.Api.dll"]
Почему multi-stage? SDK-образ включает компилятор, NuGet, инструменты и весит ~800 MB. Runtime-образ содержит только то, что нужно для запуска — ~200 MB. Multi-stage позволяет собрать код в тяжёлом SDK-образе, а в production отправить только лёгкий runtime-образ.

2.7 Итоговая схема: от кода до запроса

Понимание того, как все эти компоненты связаны, можно выразить в виде последовательности:

Шаг Что происходит Компонент
1. Сборка dotnet build компилирует IL-код в bin/ MSBuild / Roslyn
2. Публикация dotnet publish собирает артефакты в одну папку MSBuild
3. Запуск хоста WebApplication.CreateBuilder() + Build() — создаёт IHost Generic Host
4. Старт сервера app.Run() запускает Kestrel, начинает слушать порт Kestrel
5. Входящий запрос Kestrel принимает TCP, парсит HTTP, создаёт HttpContext Kestrel
6. Пайплайн HttpContext проходит через цепочку middleware ASP.NET Core Pipeline
7. Обработка Роутер находит контроллер/хаб, вызывает action-метод Routing / MVC
8. Остановка SIGTERM/Ctrl+C → ApplicationStopping → drain → ApplicationStopped IHostApplicationLifetime

3. HTTP Pipeline

HTTP Pipeline — это сердце ASP.NET Core. Каждый входящий запрос проходит сквозь цепочку middleware-компонентов, прежде чем попасть к контроллеру. Понимание того, как устроен этот конвейер и как в него встраиваются фильтры, позволяет писать предсказуемый, хорошо структурированный код.

3.1 HttpContext — контекст запроса

Что это. HttpContext — главный объект в ASP.NET Core. Он создаётся Kestrel'ом для каждого входящего HTTP-запроса и живёт ровно столько, сколько обрабатывается запрос. Это единый контейнер, содержащий всё: данные запроса, объект ответа, информацию о пользователе, DI-скоуп и многое другое.

Ключевые свойства HttpContext

Свойство Тип Назначение
Request HttpRequest Данные входящего запроса: метод, URL, заголовки, тело, cookies
Response HttpResponse Исходящий ответ: статус-код, заголовки, тело, cookies
User ClaimsPrincipal Аутентифицированный пользователь и его claims
Items IDictionary<object, object?> Словарь для передачи данных между middleware в рамках одного запроса
RequestServices IServiceProvider DI-скоуп запроса — все Scoped-сервисы живут пока жив HttpContext
Connection ConnectionInfo IP-адрес клиента и сервера, порт, ID соединения
TraceIdentifier string Уникальный ID запроса для трейсинга (используется в ProblemDetails)
WebSockets WebSocketManager Управление WebSocket-апгрейдом (использует SignalR внутри)
Session ISession Сессионное хранилище (требует AddSession())
Abort() — Немедленно разрывает соединение

HttpRequest — ключевые свойства

// Пример доступа к HttpRequest в middleware или контроллере

// Метод запроса (GET, POST, PUT, DELETE...)
string method = context.Request.Method;

// Путь: /api/chats
PathString path = context.Request.Path;

// Query string: ?limit=20&before=2024-01-01
IQueryCollection query = context.Request.Query;
string? limit = query["limit"];  // "20"

// Заголовки
IHeaderDictionary headers = context.Request.Headers;
string? contentType = headers.ContentType;
string? authHeader = headers.Authorization;  // "Bearer eyJ..."

// Cookies
IRequestCookieCollection cookies = context.Request.Cookies;
string? token = cookies["auth-token"];

// Тело запроса (Stream — читается только один раз!)
Stream body = context.Request.Body;
// Для повторного чтения: context.Request.EnableBuffering()

// Является ли запрос HTTPS
bool isHttps = context.Request.IsHttps;

// Определение пути для SignalR в WebMessenger:
var path = context.HttpContext.Request.Path;
if (path.StartsWithSegments("/hubs/chat"))
{
    // JWT читается из query string для SignalR (браузерский WebSocket
    // не поддерживает заголовок Authorization)
    if (context.Request.Query.TryGetValue("access_token", out var token))
        context.Token = token;
}

// Статус-код (устанавливать ДО отправки заголовков)

IHttpContextAccessor — доступ к HttpContext из сервисов

В контроллере HttpContext доступен напрямую через this.HttpContext. Но в сервисах и репозиториях его нет — там нужен IHttpContextAccessor. WebMessenger активно использует этот паттерн в CurrentUser:

// WebMessenger.Api/Infrastructure/CurrentUser.cs
// ICurrentUser — абстракция для получения данных текущего пользователя из JWT

public class CurrentUser(IHttpContextAccessor accessor) : ICurrentUser
{
    private readonly IHttpContextAccessor _accessor = accessor;

    // Проверка через ClaimsPrincipal, а не через базу данных — быстро и без лишних запросов
    public bool IsAuthenticated =>
        _accessor.HttpContext?.User?.Identity?.IsAuthenticated == true;

    public Guid Id
    {
        get
        {
            if (!IsAuthenticated)
                throw new InvalidOperationException("User is not authenticated");

            // Claim NameIdentifier содержит userId (задаётся при генерации JWT)
            var claim = _accessor.HttpContext!.User.FindFirst(ClaimTypes.NameIdentifier)
                        ?? throw new InvalidOperationException("NameIdentifier claim not found");

            return Guid.Parse(claim.Value);
        }
    }

    public string? Username =>
        _accessor.HttpContext?.User?.FindFirst(ClaimTypes.Name)?.Value;
}

// Регистрация в Program.cs:
builder.Services.AddHttpContextAccessor();  // регистрирует IHttpContextAccessor
builder.Services.AddScoped<ICurrentUser, CurrentUser>();

// Использование в ChatController:
// var userId = _currentUser.Id;  // получает Id из JWT без прямого доступа к HttpContext
Почему не инжектировать IHttpContextAccessor везде. IHttpContextAccessor хранит HttpContext в AsyncLocal<T> — это поточно-безопасно, но добавляет неявную зависимость от инфраструктуры. Лучше инкапсулировать его в сервис (как ICurrentUser) и инжектировать только этот сервис.

3.2 Middleware — концепция, порядок и настройка

Что это. Middleware — это компоненты обработки HTTP-запроса, выстроенные в цепочку (pipeline). Каждый компонент получает HttpContext и функцию-делегат next, указывающую на следующее звено. Компонент может:

  • Обработать запрос и вызвать next() — передать управление дальше
  • Остановить цепочку, не вызывая next() — короткое замыкание (short-circuit)
  • Выполнить действия до и после вызова next() — оборачивание
// Концептуальная модель middleware

// Схема пайплайна:
// Request  →  [MW1] → [MW2] → [MW3] → endpoint (контроллер)
// Response ←  [MW1] ← [MW2] ← [MW3] ← endpoint

// Каждое middleware — это функция вида:
// (HttpContext context, RequestDelegate next) => Task

// Три способа добавить middleware через IApplicationBuilder:

// 1. app.Use() — полноценное middleware с доступом к next
app.Use(async (context, next) =>
{
    // Код ДО следующего middleware (на пути запроса)
    var sw = Stopwatch.StartNew();

    await next(context);  // передаём управление следующему звену

    // Код ПОСЛЕ (на пути ответа)
    sw.Stop();
    context.Response.Headers.Append("X-Response-Time", $"{sw.ElapsedMilliseconds}ms");
});

// 2. app.Run() — терминальное middleware (не вызывает next, всегда замыкает цепочку)
app.Run(async context =>
{
    await context.Response.WriteAsync("This is the end of the pipeline");
    // next не вызывается — дальше ничего не выполнится
});

// 3. app.Map() — условное ветвление по пути
app.Map("/health", healthApp =>
{
    healthApp.Run(async context =>
    {
        await context.Response.WriteAsync("Healthy");
    });
});
// Запросы на /health уходят в отдельную ветку, остальные идут дальше

Порядок middleware — КРИТИЧНО

Порядок вызова .Use*() в Program.cs определяет порядок выполнения middleware. Это один из самых частых источников ошибок в ASP.NET Core.

// WebMessenger.Api/Program.cs — порядок middleware и почему он именно такой

app.UseSerilogRequestLogging();
// ↑ 1. Логирование запросов — первым, чтобы логировать ВСЕ запросы,
//      включая те, что будут отклонены позже

app.UseExceptionHandler();
// ↑ 2. Обработчик исключений — очень рано, чтобы перехватить исключения
//      из ЛЮБОГО последующего middleware

if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
}
// ↑ 3. Swagger — только в Development, до редиректа на HTTPS

if (!app.Environment.IsDevelopment())
{
    app.UseHttpsRedirection();
}
// ↑ 4. Редирект HTTP → HTTPS — до CORS и аутентификации.
//      В Development и Docker отключён (TLS терминируется снаружи)

app.UseCors(FrontCors);
// ↑ 5. CORS — ПЕРЕД аутентификацией. Preflight OPTIONS-запросы (браузер
//      отправляет их автоматически) не несут Authorization-заголовок.
//      Если поставить CORS после Auth — preflight получит 401.

app.UseAuthentication();
// ↑ 6. Аутентификация — читает JWT из заголовка/cookie, заполняет
//      context.User (ClaimsPrincipal). Не отклоняет запрос сама.

app.UseAuthorization();
// ↑ 7. Авторизация — проверяет [Authorize] атрибуты. ОБЯЗАНА идти
//      ПОСЛЕ UseAuthentication(), иначе context.User пуст.

app.MapControllers();
app.MapHub<ChatHub>("/hubs/chat").RequireCors(FrontCors);
// ↑ 8. Эндпоинты — терминальный шаг. Запрос достигает контроллера
//      или хаба только если все предыдущие middleware пропустили его.
Типичные ошибки порядка:
  • UseAuthorization() перед UseAuthentication() → context.User всегда пуст, авторизация не работает
  • UseCors() после UseAuthentication() → Preflight OPTIONS получает 401
  • UseExceptionHandler() в середине → исключения из ранних middleware не перехватываются

Написание собственного middleware

// Способ 1: класс с соглашением (Convention-based) — рекомендуется для сложных middleware
public class RequestTimingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTimingMiddleware> _logger;

    // ILogger инжектируется через конструктор (Singleton-lifetime)
    public RequestTimingMiddleware(RequestDelegate next, ILogger<RequestTimingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    // Метод ОБЯЗАН называться InvokeAsync или Invoke
    // Scoped-сервисы инжектируются сюда (не в конструктор — middleware Singleton)
    public async Task InvokeAsync(HttpContext context)
    {
        var sw = Stopwatch.StartNew();
        await _next(context);
        sw.Stop();

        _logger.LogInformation("{Method} {Path} completed in {Ms}ms",
            context.Request.Method,
            context.Request.Path,
            sw.ElapsedMilliseconds);
    }
}

// Расширение для удобной регистрации:
public static class RequestTimingMiddlewareExtensions
{
    public static IApplicationBuilder UseRequestTiming(this IApplicationBuilder app)
        => app.UseMiddleware<RequestTimingMiddleware>();
}

// Использование:
app.UseRequestTiming();

// Способ 2: inline через app.Use() — для простых однострочных случаев
app.Use(async (context, next) =>
{
    context.Response.Headers.Append("X-Frame-Options", "DENY");
    await next(context);
});

3.4 Filters — фильтры MVC

Что это. Filters (фильтры) — механизм перехвата в MVC/Web API пайплайне, который работает после роутинга, но до/после выполнения action-метода. Ключевое отличие от middleware: фильтры работают в контексте MVC и имеют доступ к ActionContext, параметрам метода, результату и типизированным объектам MVC.

Типы фильтров по роли

Тип фильтра Интерфейс Когда срабатывает Типичное использование
Authorization Filter IAuthorizationFilter Первым, до всех остальных Кастомная авторизация, проверка ролей/claims
Resource Filter IResourceFilter После авторизации, до model binding Кэширование, короткое замыкание запроса
Action Filter IActionFilter До и после выполнения action Логирование, трансформация аргументов и результата
Exception Filter IExceptionFilter При необработанном исключении в action Централизованная обработка ошибок MVC-уровня
Result Filter IResultFilter До и после выполнения IActionResult Изменение/обёртывание ответа, добавление заголовков

Порядок выполнения фильтров

// Полный порядок выполнения при обработке запроса:
//
// [Authorization Filters]       → могут short-circuit, возвращая 401/403
//   ↓
// [Resource Filters] OnExecuting
//   ↓
// [Model Binding]               → заполнение параметров action-метода
//   ↓
// [Action Filters] OnActionExecuting
//   ↓
// ACTION METHOD выполняется     → возвращает IActionResult
//   ↓
// [Action Filters] OnActionExecuted
//   ↓
// [Exception Filters]           → срабатывают при исключении
//   ↓
// [Result Filters] OnResultExecuting
//   ↓
// IActionResult.ExecuteResultAsync() → формирование HTTP-ответа
//   ↓
// [Result Filters] OnResultExecuted
//   ↓
// [Resource Filters] OnExecuted

Типы фильтров по области применения (Scope)

Scope Как задать На что действует
Action-level Атрибут на конкретном action-методе Только на один метод
Controller-level Атрибут на классе контроллера Все action-методы контроллера
Global Регистрация через AddControllers(o => o.Filters.Add(...)) Все контроллеры и действия приложения 
// Примеры использования фильтров

// ─── Action Filter — логирование времени выполнения ───
public class LogExecutionTimeAttribute : ActionFilterAttribute
{
    // ActionFilterAttribute реализует IActionFilter и IResultFilter одновременно,
    // что удобно для простых случаев.

    public override void OnActionExecuting(ActionExecutingContext context)
    {
        // Сохраняем момент начала в Items — передача данных внутри запроса
        context.HttpContext.Items["_start"] = Stopwatch.GetTimestamp();
    }

    public override void OnActionExecuted(ActionExecutedContext context)
    {
        var start = (long)context.HttpContext.Items["_start"]!;
        var elapsed = Stopwatch.GetElapsedTime(start);

        var logger = context.HttpContext.RequestServices
            .GetRequiredService<ILogger<LogExecutionTimeAttribute>>();

        logger.LogInformation("{Action} executed in {Ms}ms",
            context.ActionDescriptor.DisplayName, elapsed.TotalMilliseconds);
    }
}

// ─── Authorization Filter — пример кастомной проверки ───
public class ApiKeyAttribute : Attribute, IAuthorizationFilter
{
    public void OnAuthorization(AuthorizationFilterContext context)
    {
        var apiKey = context.HttpContext.Request.Headers["X-Api-Key"].FirstOrDefault();
        if (apiKey != "expected-key")
        {
            // Short-circuit: устанавливаем Result — дальнейшие фильтры не выполняются
            context.Result = new UnauthorizedResult();
        }
    }
}

// ─── Exception Filter — перехват NotFoundException ───
public class NotFoundExceptionFilter : IExceptionFilter
{
    public void OnException(ExceptionContext context)
    {
        if (context.Exception is KeyNotFoundException ex)
        {
            context.Result = new NotFoundObjectResult(new { message = ex.Message });
            context.ExceptionHandled = true;  // помечаем: исключение обработано
        }
        // Если ExceptionHandled = false — исключение идёт дальше (к UseExceptionHandler)
    }
}

// ─── Применение по scope ───

// Action-level: только для метода GetUserProfile
[HttpGet("profile")]
[LogExecutionTime]
public async Task<IActionResult> GetUserProfile() { ... }

// Controller-level: для всего UserController
[ApiKey]
[Authorize]
[ApiController]
[Route("api/users")]
public class UserController : ControllerBase { ... }

// Global: для всего приложения
builder.Services.AddControllers(options =>
{
    options.Filters.Add<NotFoundExceptionFilter>();
    options.Filters.Add(new LogExecutionTimeAttribute());
    // Порядок: Action-level → Controller-level → Global (при выполнении)
    // При OnActionExecuting: Global → Controller → Action
    // При OnActionExecuted: Action → Controller → Global (обратный)
});

Middleware vs Filters — когда что использовать

Аспект Middleware Filters
Область действия Весь HTTP-пайплайн, включая статику, SignalR, Minimal API Только MVC/Web API контроллеры
Контекст HttpContext ActionContext, параметры action, IActionResult
DI-lifetime Сам middleware — Singleton; Scoped через InvokeAsync Transient или Scoped через ServiceFilter / TypeFilter
Типичные задачи CORS, Auth, Logging, HTTPS Redirect, Compression Валидация модели, трансформация ответа, exception handling в MVC

3.5 WebApplicationFactory — тестирование пайплайна

Что это. WebApplicationFactory<TProgram> — класс из пакета Microsoft.AspNetCore.Mvc.Testing, позволяющий поднять реальный HTTP-пайплайн приложения в памяти для интеграционных тестов. Никакого реального сетевого соединения не создаётся — TestServer работает через in-memory транспорт.

Зачем. Интеграционные тесты с WebApplicationFactory проверяют весь стек: роутинг, middleware, авторизацию, DI, контроллеры и сериализацию. Это принципиально отличается от unit-тестов контроллеров с Moq, где тестируется только логика метода.

4. Routing

Routing (маршрутизация) — механизм, который сопоставляет входящий HTTP-запрос с конкретным action-методом контроллера. ASP.NET Core предоставляет два стиля маршрутизации: Convention-based и Attribute-based. В Web API почти всегда используется атрибутный стиль.

4.1 UseRouting и UseEndpoints

Как работает routing внутри пайплайна. Маршрутизация в ASP.NET Core разделена на два этапа, выполняемых разными middleware:

  1. UseRouting() — анализирует URL входящего запроса и определяет, какой эндпоинт ему соответствует. Записывает результат в HttpContext (через IEndpointFeature). Не выполняет сам эндпоинт.
  2. UseEndpoints() / MapControllers() — выполняет найденный эндпоинт (вызывает action-метод контроллера).

Такое разделение позволяет middleware между этими двумя шагами (например, UseAuthentication, UseAuthorization) знать, какой эндпоинт будет вызван, и принимать решения на основе этой информации.

// Современный подход (.NET 6+): UseRouting() неявно добавляется
// при вызове MapControllers() / MapHub() и т.д.
// Явный вызов UseRouting() нужен только если между ним и UseEndpoints()
// нужно поставить middleware, зависящий от информации о маршруте.

// WebMessenger.Api/Program.cs — эндпоинты:
app.UseAuthentication();
app.UseAuthorization();
// ↑ Стоят ДО MapControllers(). Благодаря неявному UseRouting() в начале пайплайна,
//   middleware авторизации уже знает, что [Authorize] задан на целевом эндпоинте,
//   и проверяет наличие аутентификации до выполнения action.

app.MapControllers();
// ↑ Регистрирует ВСЕ контроллеры как эндпоинты.
//   Эквивалентно UseEndpoints(e => e.MapControllers()) из старого API.

app.MapHub<ChatHub>("/hubs/chat").RequireCors(FrontCors);
// ↑ SignalR-хаб — отдельный эндпоинт с явным указанием пути и CORS-политики.

// Явное использование UseRouting / UseEndpoints (старый стиль, до .NET 6):
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.UseEndpoints(endpoints =>
{
    endpoints.MapControllers();
    endpoints.MapHub<ChatHub>("/hubs/chat");
});
// Оба стиля эквивалентны по поведению.

4.2 Convention Routing vs Attribute Routing

Convention Routing (конвенциональная маршрутизация)

Маршруты задаются централизованно — один шаблон покрывает множество контроллеров. Используется в MVC-приложениях с Razor Views. В Web API практически не применяется.

// Convention routing — централизованное задание шаблонов (MVC-стиль)
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");
// Шаблон означает:
// GET /Products/List    → ProductsController.List()
// GET /Products/Edit/5  → ProductsController.Edit(id: 5)
// GET /                 → HomeController.Index()

// Проблемы с Convention Routing для API:
// 1. Неочевидно: маршруты контроллера разбросаны по Program.cs и по классу
// 2. Нет поддержки HTTP-методов в шаблоне (GET vs POST vs PUT)
// 3. Путь привязан к имени класса — рефакторинг класса = изменение URL

Attribute Routing (атрибутная маршрутизация)

Маршруты объявляются прямо на контроллерах и action-методах через атрибуты. Стандарт для Web API. WebMessenger использует исключительно атрибутный стиль.

// WebMessenger.Api/Controllers/ChatController.cs — атрибутный роутинг

[ApiController]
[Route("api/chats")]          // ← базовый маршрут контроллера
public class ChatController : ControllerBase
{
    // GET  /api/chats  ← [Route("api/chats")] + [HttpGet] без суффикса
    [HttpGet]
    public async Task<ActionResult<PagedResult<ChatListItemDto>>> Index(...) { }

    // GET  /api/chats/{chatId}/header
    // {chatId:guid} — параметр с ограничением типа (только GUID)
    [HttpGet("{chatId:guid}/header")]
    public async Task<IActionResult> GetChatHeader(Guid chatId) { }

    // GET  /api/chats/direct/{userId}/header
    // Сегмент "direct" — статическая часть пути
    [HttpGet("direct/{userId:guid}/header")]
    public async Task<IActionResult> GetDirectHeader(Guid userId) { }

    // GET  /api/chats/{chatId}/messages
    [HttpGet("{chatId:guid}/messages")]
    public async Task<ActionResult<PagedResult<ChatMessageDto>>> GetMessages(Guid chatId, ...) { }

В WebMessenger все 4 контроллера используют атрибутный роутинг: AuthController → api/auth, ChatController → api/chats, ContactController → api/contacts, UserController → api/users. Это стандартная практика для REST API.

4.3 Route Templates и их конфигурация

Что это. Route template (шаблон маршрута) — строка, описывающая структуру URL. Состоит из литеральных сегментов, параметров и специальных символов.

Синтаксис шаблонов

// Литеральный сегмент — совпадает буквально
[Route("api/contacts")]           // → /api/contacts

// Параметр — {name}
[Route("users/{id}")]             // → /users/123, /users/abc

// Необязательный параметр — {name?}
[Route("users/{id?}")]            // → /users  или  /users/123

// Параметр с дефолтным значением — {name=default}
[Route("users/{page=1}")]         // → /users  (page=1)  или  /users/3

// Catch-all параметр — {**name}
[Route("files/{**path}")]         // → /files/a/b/c/d.txt (path = "a/b/c/d.txt")

// Ограничения типа (route constraints) — {name:constraint}
[Route("{id:int}")]               // только целые числа: /42, /0
[Route("{id:guid}")]              // только GUID: /3fa85f64-...
[Route("{id:minlength(3)}")]      // строки длиной ≥ 3
[Route("{id:alpha}")]             // только буквы
[Route("{id:range(1,100)}")]      // целые числа от 1 до 100
[Route("{id:datetime}")]          // DateTime

// Комбинация нескольких ограничений через двоеточие:
[Route("{id:int:min(1)}")]        // int И min=1

Все route constraints

Ограничение Пример Совпадает
int {id:int} Только 32-битные целые числа
long {id:long} 64-битные целые числа
guid {id:guid} GUID в любом стандартном формате
bool {flag:bool} true или false
datetime {date:datetime} Дата/время в invariant culture
decimal {price:decimal} Десятичное число
double {val:double} Число с плавающей точкой
float {val:float} Float
alpha {name:alpha} Только буквы (a-z, A-Z)
minlength(n) {s:minlength(3)} Строка длиной ≥ n
maxlength(n) {s:maxlength(10)} Строка длиной ≤ n
length(n) / length(min,max) {s:length(4,8)} Строка длиной ровно n или в диапазоне
min(n) {age:min(18)} Целое ≥ n
max(n) {age:max(150)} Целое ≤ n
range(min,max) {page:range(1,100)} Целое в диапазоне

Route constraints — это не валидация. Они только определяют, совпадает ли URL с маршрутом. Если ограничение не выполнено, роутер переходит к следующему маршруту (или возвращает 404). Для бизнес-валидации значений используйте Data Annotations или FluentValidation.

4.4 Route Values

Что это. Route values — это словарь пар ключ/значение, который роутер извлекает из URL после сопоставления с шаблоном. Они автоматически подставляются в параметры action-метода через Model Binding.

// Как работают route values

// Шаблон контроллера: "api/chats"
// Шаблон action:     "{chatId:guid}/messages"
// Итоговый шаблон:   "api/chats/{chatId:guid}/messages"

// Запрос: GET /api/chats/3fa85f64-5717-4562-b3fc-2c963f66afa6/messages?limit=50

// Route values (из пути URL):
// { "chatId": "3fa85f64-5717-4562-b3fc-2c963f66afa6" }

// Query string values (из ?limit=50):
// { "limit": "50" }

// Model Binding автоматически сопоставит:
[HttpGet("{chatId:guid}/messages")]
public async Task<IActionResult> GetMessages(
    Guid chatId,          // ← из route values: "3fa85f64-..."  → Guid
    int limit = 50,       // ← из query string: "50" → int  (дефолт 50 если нет)
    DateTime? before = null) // ← из query string: отсутствует → null
{ }

// Доступ к route values напрямую (если не используете параметры):
var chatId = HttpContext.GetRouteValue("chatId"); // object?
// или через RouteData:
var chatId2 = RouteData.Values["chatId"];

4.6 Разрешение конфликтов маршрутов

Если два маршрута могут совпасть с одним URL, ASP.NET Core пытается выбрать наиболее специфичный. Если оба одинаково специфичны — бросает AmbiguousMatchException.

// Пример конфликта:
[HttpGet("{chatId:guid}/header")]        // (1)
[HttpGet("direct/{userId:guid}/header")] // (2)
// GET /api/chats/direct/3fa85f64.../header
//   → роутер сначала пробует (1): "direct" не является GUID → не совпадает
//   → переходит к (2): "direct" = литерал → совпадает ✓

// Почему это работает:
// Constraint :guid на {chatId} делает маршрут (1) более строгим.
// "direct" не является валидным GUID, значит (1) не совпадает — нет конфликта.

// Потенциальный конфликт (если убрать :guid):
[HttpGet("{chatId}/header")]          // (1) без ограничения
[HttpGet("direct/{userId}/header")]   // (2)
// GET /api/chats/direct/abc/header — AmbiguousMatchException!
// Оба подходят: в (1) chatId="direct", userId="abc" — нет.
// На самом деле (2) победит как более специфичный (литерал "direct").
// Но это неявно — всегда используйте :guid / :int для большей ясности.

4.7 URL Generation — генерация URL

Что это. ASP.NET Core позволяет программно генерировать URL по имени маршрута или ссылке на action. Это избавляет от хардкода строк URL и обеспечивает согласованность при изменении маршрутов.

// Три способа генерации URL:

// ─── 1. IUrlHelper (в контроллере: this.Url) ───
// Генерация URL к конкретному action:
string? url = Url.Action(
    action: "GetChatHeader",
    controller: "Chat",
    values: new { chatId = Guid.NewGuid() });
// Результат: "/api/chats/3fa85f64-.../header"

// Генерация абсолютного URL:
string? absUrl = Url.Action("GetChatHeader", "Chat",
    new { chatId = id }, Request.Scheme);
// Результат: "https://localhost:5227/api/chats/.../header"

// ─── 2. LinkGenerator (из DI — работает вне контроллера) ───
public class NotificationService(LinkGenerator linkGenerator)
{
    public string GetChatUrl(Guid chatId)
    {
        // GetPathByAction — генерирует относительный путь
        return linkGenerator.GetPathByAction(
            action: "GetChatHeader",
            controller: "Chat",
            values: new { chatId })
            ?? throw new InvalidOperationException("Cannot generate URL");
    }

    public string GetAbsoluteChatUrl(HttpContext ctx, Guid chatId)
    {
        // GetUriByAction — генерирует абсолютный URI
        return linkGenerator.GetUriByAction(ctx,
            action: "GetChatHeader",
            controller: "Chat",
            values: new { chatId })!;
    }
}

// ─── 3. CreatedAtAction / CreatedAtRoute (в контроллере) ───
// Используется при POST-создании ресурса: возвращает 201 Created
// с заголовком Location, указывающим на новый ресурс.
[HttpPost]
public async Task<IActionResult> CreateChat([FromBody] CreateChatDto dto)
{
    var chat = await _chatService.CreateChatAsync(dto);

    return CreatedAtAction(
        actionName: nameof(GetChatHeader),  // ссылка на action для Location header
        routeValues: new { chatId = chat.Id },
        value: chat);
    // HTTP 201 Created
    // Location: /api/chats/3fa85f64-.../header
}

5. Validation

Валидация входящих данных — обязательная граница безопасности и корректности любого API. ASP.NET Core предоставляет встроенную систему Model Validation на основе Data Annotations, которая при наличии [ApiController] работает полностью автоматически.

5.1 Model Validation — когда и как происходит

Что это. Model Validation — процесс проверки объекта, полученного из тела запроса (или других источников), на соответствие правилам, заданным атрибутами. Выполняется автоматически после Model Binding — то есть после того, как ASP.NET Core десериализовал тело запроса в объект параметра action-метода.

Порядок выполнения при входящем запросе:

  1. Kestrel принимает HTTP-запрос и создаёт HttpContext
  2. Middleware пайплайн (Auth, CORS и т.д.)
  3. Роутер определяет action-метод
  4. Model Binding — читает тело запроса, заголовки, query string и создаёт объекты параметров
  5. Model Validation — проверяет созданные объекты по атрибутам, заполняет ModelState
  6. При [ApiController]: если ModelState.IsValid == false → автоматический ответ 400, action не вызывается
  7. Выполняется action-метод
// Без [ApiController] — ручная проверка ModelState
[HttpPost("register")]
public async Task<IActionResult> Register([FromBody] RegisterDto dto)
{
    if (!ModelState.IsValid)
        return BadRequest(ModelState);  // нужно явно проверять

    // ... логика
}

// С [ApiController] — автоматически (WebMessenger использует этот вариант)
[ApiController]
[Route("api/auth")]
public class AuthController : ControllerBase
{
    [HttpPost("register")]
    public async Task<IActionResult> Register([FromBody] RegisterDto dto)
    {
        // Если RegisterDto невалиден — этот код НИКОГДА не выполнится.
        // [ApiController] перехватывает запрос раньше и возвращает 400.
        await _userService.RegisterUserAsync(dto);
        return Ok(new { message = "Registration successful" });
    }
}

ModelState — словарь состояния валидации

// ModelState — IDictionary<string, ModelStateEntry>
// Каждый ключ = имя поля, значение = список ошибок для этого поля

// Пример ответа при автоматической валидации [ApiController]:
// POST /api/auth/register с телом: { "username": "", "password": "12" }
//
// HTTP 400 Bad Request
// {
//   "type": "https://tools.ietf.org/html/rfc7807",
//   "title": "One or more validation errors occurred.",
//   "status": 400,
//   "errors": {
//     "Username": ["The Username field is required."],
//     "Password": ["The field Password must be a string with a minimum length of 6."]
//   }
// }

// Ручная работа с ModelState (когда нужна кастомная логика):
if (!ModelState.IsValid)
{
    var errors = ModelState
        .Where(e => e.Value?.Errors.Count > 0)
        .ToDictionary(
            kvp => kvp.Key,
            kvp => kvp.Value!.Errors.Select(e => e.ErrorMessage).ToArray()
        );
    return BadRequest(new { errors });
}

// Добавление ошибки вручную (бизнес-логика, не атрибутная):
if (await _userService.IsUsernameExistsAsync(dto.Username))
{
    ModelState.AddModelError("Username", "Username already exists");
    return BadRequest(ModelState);
}

Кастомный атрибут валидации

// Когда встроенных атрибутов недостаточно — создаём свой,
// наследуясь от ValidationAttribute

// Абстрактный пример: проверка что username не содержит запрещённых слов
public class NoProhibitedWordsAttribute : ValidationAttribute
{
    private static readonly string[] _prohibited = ["admin", "root", "system"];

    protected override ValidationResult? IsValid(object? value, ValidationContext ctx)
    {
        if (value is string str)
        {
            var lower = str.ToLowerInvariant();
            foreach (var word in _prohibited)
            {
                if (lower.Contains(word))
                {
                    return new ValidationResult(
                        $"Username cannot contain '{word}'",
                        new[] { ctx.MemberName! });
                }
            }
        }
        return ValidationResult.Success;
    }
}

// Применение:
public sealed record RegisterDto
{
    [Required]
    [MaxLength(50)]
    [NoProhibitedWords]   // ← наш кастомный атрибут
    public required string Username { get; init; }
    // ...
}

IValidatableObject — кросс-польная валидация

// Когда валидация зависит от нескольких полей одновременно:
public sealed record CreateChatDto : IValidatableObject
{
    [Required]
    [MaxLength(100)]
    public required string Name { get; init; }

    public bool IsDirect { get; init; }

    public IEnumerable<Guid> ParticipantIds { get; init; } = [];

    public IEnumerable<ValidationResult> Validate(ValidationContext context)
    {
        // Кросс-польная логика: прямой чат должен иметь ровно одного участника
        if (IsDirect && ParticipantIds.Count() != 1)
        {
            yield return new ValidationResult(
                "Direct chat must have exactly one participant",
                new[] { nameof(ParticipantIds) });
        }

        // Групповой чат должен иметь название
        if (!IsDirect && string.IsNullOrWhiteSpace(Name))
        {
            yield return new ValidationResult(
                "Group chat must have a name",
                new[] { nameof(Name) });
        }
    }
}
// IValidatableObject.Validate() вызывается ПОСЛЕ всех атрибутов прошли проверку.
// Если атрибуты уже нашли ошибки — Validate() по умолчанию не вызывается.

5.3 API Auto-Validation с [ApiController]

Что происходит автоматически. Атрибут [ApiController] регистрирует в пайплайне MVC фильтр ModelStateInvalidFilter, который выполняется до вызова action-метода. Если ModelState.IsValid == false — фильтр формирует ответ ValidationProblemDetails (HTTP 400) и короткозамкает цепочку.

// Поведение [ApiController] + [Required]:
// POST /api/auth/register
// Body: { "password": "abc" }  — нет поля username
//
// Model Binding: username = null (поле отсутствует в JSON)
// Validation: [Required] на Username → ошибка
// ModelStateInvalidFilter: ModelState.IsValid = false → 400

// Автоматический ответ (ValidationProblemDetails):
// {
//   "type": "https://tools.ietf.org/html/rfc7807",
//   "title": "One or more validation errors occurred.",
//   "status": 400,
//   "traceId": "00-abc123...",
//   "errors": {
//     "Username": [ "The Username field is required." ]
//   }
// }
// ↑ traceId добавляется через builder.Services.AddProblemDetails()
//   в Program.cs WebMessenger (ProblemDetails.Extensions["traceId"])

// Кастомизация автоматического ответа:
builder.Services.AddControllers()
    .ConfigureApiBehaviorOptions(options =>
    {
        options.InvalidModelStateResponseFactory = context =>
        {
            var errors = context.ModelState
                .Where(e => e.Value?.Errors.Count > 0)
                .ToDictionary(
                    kvp => kvp.Key,
                    kvp => kvp.Value!.Errors.Select(e => e.ErrorMessage).ToArray()
                );

            return new BadRequestObjectResult(new
            {
                type = "validation_error",
                errors
            });
        };

        // Отключить автовалидацию (если нужно делать вручную):
        // options.SuppressModelStateInvalidFilter = true;
    });
В WebMessenger все контроллеры используют [ApiController], поэтому автовалидация активна по умолчанию. Дополнительная ручная бизнес-логика (например, проверка уникальности username) делается явно внутри action-метода после прохождения автовалидации.

5.4 Валидация вне Model Binding — ручной вызов Validator

Иногда нужно провалидировать объект вне HTTP-запроса — в тестах, в фоновых сервисах или при ручном создании объекта. Для этого используется System.ComponentModel.DataAnnotations.Validator.

// WebMessenger.Contracts.Tests/Unit/Validation/LoginDtoValidationTests.cs
// Именно так устроены тесты валидации DTO в проекте:

private static List<ValidationResult> Validate(object model)
{
    var results = new List<ValidationResult>();
    var ctx     = new ValidationContext(model);

    // validateAllProperties: true — проверять ВСЕ свойства, не только [Required]
    Validator.TryValidateObject(model, ctx, results, validateAllProperties: true);
    return results;
}

5.5 Тонкости и подводные камни

required vs [Required]

// C# 11 ввёл ключевое слово required для свойств и полей.
// Это НЕ то же самое, что [Required] атрибут.

public sealed record RegisterDto
{
    // required (C# keyword) — compile-time: свойство обязательно задать
    // при инициализации объекта. Нарушение → ошибка компилятора.
    public required string Username { get; init; }

    // [Required] (Data Annotation) — runtime: значение не должно быть null/"".
    // Нарушение → ошибка в ModelState при валидации HTTP-запроса.
    [Required]
    public string Username2 { get; init; } = "";
}

// В WebMessenger оба используются вместе:
public sealed record RegisterDto
{
    [Required]          // ← runtime: ASP.NET Core ModelState валидация
    [MaxLength(50)]
    public required string Username { get; init; }  // ← compile-time: нельзя забыть задать
}
// required гарантирует что объект создан корректно в коде (тесты, сервисы).
// [Required] гарантирует что данные из HTTP-запроса не пустые.

[Required] и null vs пустая строка

// [Required] по умолчанию не считает пустую строку ошибкой!
// Пустая строка и null — разные вещи для [Required].

// Чтобы запретить и null, и "":
[Required]
public string Name { get; set; } = "";
// По умолчанию "" проходит Required. Чтобы запретить:

// Вариант 1: MinLength(1)
[Required]
[MinLength(1)]

// Вариант 2: AllowEmptyStrings = false (явно)

    // При Nullable enable — non-nullable string? автоматически получает [Required]
});

Валидация вложенных объектов

// В WebMessenger вложенная валидация не нужна — все DTO «плоские».

Client-Side Validation

В Web API (JSON) клиентская валидация полностью реализуется на стороне фронтенда — ASP.NET Core не генерирует JavaScript для валидации (это функция Razor Pages / MVC с Unobtrusive Validation). Однако контракт Data Annotations можно переиспользовать:

  • Swagger/OpenAPI — аннотации автоматически отражаются в OpenAPI-схеме: [MaxLength(50)] → maxLength: 50, [Required] → поле попадает в required: [...]. Клиент может генерировать типизированный код с учётом этих ограничений.
  • Ранняя валидация на клиенте — в Next.js (WebMessenger Client) формы используют собственную клиентскую валидацию через state/библиотеки, зеркалируя правила, заданные в DTO.
  • Двойная валидация — клиентская валидация улучшает UX, серверная — обязательна для безопасности. Никогда нельзя полагаться только на клиентскую сторону.

// RegisterDto.Username:
//   [Required] [MaxLength(50)]
//   →
// "Username": {
//   "type": "string",
//   "maxLength": 50,
//   "minLength": 0
// }
// "required": ["Username", "Password"]

// Что Swashbuckle (Swagger) распознаёт автоматически:
// [Required]        → поле в секции required
// [MinLength(n)]    → minLength
// [MaxLength(n)]    → maxLength
// [Range(min,max)]  → minimum + maximum
// [EmailAddress]    → format: email
// [Url]             → format: uri
// [RegularExpression] → pattern

6. Exception Handling

Необработанные исключения — неизбежная часть любого приложения. ASP.NET Core предоставляет несколько уровней их перехвата: от страницы с деталями исключения для разработчика до глобального обработчика с форматированием ответа по RFC 7807 (ProblemDetails). WebMessenger использует оба подхода согласованно.

6.1 Что происходит без обработчика исключений

Если в action-методе или middleware выбрасывается исключение, которое никто не перехватил — Kestrel возвращает пустой ответ с кодом 500 Internal Server Error без тела. Клиент получает бесполезный пустой ответ, а информация об ошибке теряется. Именно для этого настраивают обработчики исключений.

6.2 Developer Exception Page

Что это. UseDeveloperExceptionPage() — middleware, которое перехватывает необработанные исключения и возвращает HTML-страницу с полным стеком вызовов, информацией о запросе, переменными окружения и query string. Предназначено исключительно для разработки.

// Явная активация (исторический стиль, до .NET 6):
if (app.Environment.IsDevelopment())
{
    app.UseDeveloperExceptionPage();
}

// Начиная с .NET 6: Developer Exception Page активируется АВТОМАТИЧЕСКИ
// в Development-окружении — явно писать не надо.
// Это поведение встроено в WebApplication.

// Чтобы ОТКЛЮЧИТЬ автоматическую Developer Exception Page:
app.UseDeveloperExceptionPage(); // вызов вне if(IsDevelopment()) НЕ рекомендуется!
// или через настройку:
builder.WebHost.UseSetting("detailedErrors", "false");

Что показывает Developer Exception Page:

  • Тип исключения и сообщение
  • Полный стек вызовов с кликабельными ссылками на файлы исходного кода
  • Информацию о запросе: метод, путь, заголовки, cookies, query string
  • Переменные окружения (ASPNETCORE_ENVIRONMENT и др.)
Никогда не включайте Developer Exception Page в production! Стек вызовов раскрывает внутреннее устройство приложения, пути к файлам, версии библиотек — это ценная информация для злоумышленника.

6.3 Global Exception Handling — UseExceptionHandler

Что это. UseExceptionHandler() — production-ready middleware для глобальной обработки необработанных исключений. Перехватывает любое исключение из последующих middleware и action-методов, формирует структурированный ответ и предотвращает утечку деталей реализации.

Как работает. При вызове без аргументов (app.UseExceptionHandler()) ASP.NET Core использует ProblemDetails-ответ, который настраивается через AddProblemDetails() в DI-контейнере.

// WebMessenger.Api/Program.cs — реальная конфигурация:

// 1. Регистрация ProblemDetails-сервиса с кастомизацией
builder.Services.AddProblemDetails(options =>
{
    options.CustomizeProblemDetails = context =>
    {
        // Добавляем traceId в каждый ProblemDetails-ответ.
        // TraceIdentifier — уникальный ID запроса от Kestrel.
        // Позволяет сопоставить ответ клиента с записью в логах.
        context.ProblemDetails.Extensions["traceId"] =
            context.HttpContext.TraceIdentifier;
    };
});

// 2. Использование обработчика в пайплайне
app.UseExceptionHandler();
// ↑ Без аргументов: использует встроенный ProblemDetails handler.
//   Перехватывает ВСЕ необработанные исключения.
//   Должен стоять как можно раньше в пайплайне — до всех остальных middleware,
//   которые могут выбросить исключение.

Что возвращает UseExceptionHandler при необработанном исключении

// Пример: в action-методе выбросилось исключение, не пойманное try/catch

UseExceptionHandler с явным путём (старый стиль)

6.5 Обработка исключений в контроллерах WebMessenger

В текущей реализации WebMessenger контроллеры используют ручной подход: каждый action-метод оборачивает логику в try/catch. Это явная стратегия — понять её плюсы и минусы важно.

// WebMessenger.Api/Controllers/ChatController.cs — типичный паттерн
[HttpGet("{chatId:guid}/messages")]
public async Task<ActionResult<PagedResult<ChatMessageDto>>> GetMessages(
    Guid chatId, int limit = 50, DateTime? before = null)
{
    try
    {
        var page = await _chatService.GetMessagesAsync(_currentUser.Id, chatId, limit, before);
        return Ok(page);
    }
    catch (UnauthorizedAccessException ex)
    {
        // Бизнес-исключение: попытка доступа к чужому чату
        // Логируем как Warning (не ошибка системы — ошибка пользователя)
        _logger.LogWarning(ex, "User {UserId} attempted to access messages in chat {ChatId} without membership",
            _currentUser.Id, chatId);
        return Forbid(); // 403
    }
    catch (Exception ex)
    {
        // Непредвиденная ошибка: логируем как Error
        _logger.LogError(ex, "Error fetching messages for chat {ChatId}, user {UserId}",
            chatId, _currentUser.Id);
        return StatusCode(500, new { message = "An error occurred while fetching messages" });
    }
}

Плюсы и минусы ручного try/catch в каждом action

Плюсы Минусы
Ручной try/catch Явный контроль над каждым исключением, гранулярное логирование с контекстом (UserId, ChatId) Дублирование кода, легко забыть оборачивать, inconsistency форматов ответов между контроллерами
Глобальный обработчик Нет дублирования, единый формат ответа, контроллеры чище Меньше контекста в логах (нет userId/chatId), сложнее дифференцировать типы ошибок
Exception Filter (MVC) Работает в MVC-контексте, есть доступ к ActionContext, можно задать по scope Не перехватывает ошибки в middleware

Альтернатива: централизованная обработка через Exception Filter

// Пример глобального Exception Filter, который можно добавить в WebMessenger
// для замены повторяющихся try/catch блоков:

public class GlobalApiExceptionFilter : IExceptionFilter
{
    private readonly ILogger<GlobalApiExceptionFilter> _logger;

    public GlobalApiExceptionFilter(ILogger<GlobalApiExceptionFilter> logger)
    {
        _logger = logger;
    }

    public void OnException(ExceptionContext context)
    {
        // Логируем с контекстом из ActionContext
        var actionName = context.ActionDescriptor.DisplayName;
        _logger.LogError(context.Exception, "Unhandled exception in {Action}", actionName);

        // Дифференцируем ответ по типу исключения
        var (statusCode, title) = context.Exception switch
        {
            UnauthorizedAccessException => (403, "Access denied"),
            KeyNotFoundException        => (404, "Resource not found"),
            ArgumentException           => (400, "Invalid argument"),
            _                           => (500, "Internal server error")
        };

        context.Result = new ObjectResult(new ProblemDetails
        {
            Status = statusCode,
            Title  = title
        })
        { StatusCode = statusCode };

        context.ExceptionHandled = true;
    }
}

// Регистрация глобально:
builder.Services.AddControllers(options =>
{
    options.Filters.Add<GlobalApiExceptionFilter>();
});
В WebMessenger применяется комбинированный подход: UseExceptionHandler() как последний рубеж обороны для действительно непойманных исключений + ручные try/catch в контроллерах для явного контекстного логирования. AddProblemDetails() с traceId обеспечивает прослеживаемость ошибок между клиентом и логами.

7.2 Model Binding

Что это. Model Binding — процесс автоматического извлечения данных из HTTP-запроса и преобразования их в параметры action-метода. ASP.NET Core умеет читать данные из нескольких источников и приводить их к нужным типам.

Источники привязки (Binding Sources)

Атрибут Источник Когда использовать
[FromBody] Тело запроса (JSON, XML) Сложные объекты в POST/PUT/PATCH. Только один раз на метод.
[FromRoute] Параметры маршрута ({id}) Идентификаторы ресурсов в URL-пути
[FromQuery] Query string (?key=value) Фильтрация, пагинация, поиск
[FromHeader] HTTP-заголовки API-ключи, версионирование, кастомные метаданные
[FromForm] Form data (multipart/form-data, x-www-form-urlencoded) Загрузка файлов (IFormFile), HTML-формы
[FromServices] DI-контейнер Инжекция сервиса прямо в параметр action (без конструктора)

Inference правила с [ApiController]

При наличии [ApiController] источник привязки выводится автоматически:

Тип параметра Выводится как
Сложный тип (class/record), не IFormFile [FromBody]
Примитив/string и имя совпадает с маршрутным параметром [FromRoute]
Примитив/string, не совпадает с маршрутом [FromQuery]
IFormFile / IFormFileCollection [FromForm]
CancellationToken Из HttpContext.RequestAborted (не из запроса)

Кастомный Model Binder

// Когда стандартного биндинга недостаточно — создаём кастомный.
// Пример: автоматическое приведение строки к нормализованному username

public class NormalizedUsernameModelBinder : IModelBinder
{
    public Task BindModelAsync(ModelBindingContext bindingContext)
    {
        var value = bindingContext.ValueProvider
            .GetValue(bindingContext.ModelName).FirstValue;

        if (string.IsNullOrEmpty(value))
        {
            bindingContext.Result = ModelBindingResult.Failed();
            return Task.CompletedTask;
        }

        // Нормализация: lowercase + trim
        var normalized = value.Trim().ToLowerInvariant();
        bindingContext.Result = ModelBindingResult.Success(normalized);
        return Task.CompletedTask;
    }
}

// Провайдер для биндера:
public class NormalizedUsernameModelBinderProvider : IModelBinderProvider
{
    public IModelBinder? GetBinder(ModelBinderProviderContext context)
    {
        // Применять только к параметрам с атрибутом [NormalizedUsername]
        if (context.Metadata.ModelType == typeof(string) &&
            context.Metadata.ContainerType != null)
        {
            var attr = context.Metadata.ContainerType
                .GetProperty(context.Metadata.PropertyName ?? "")
                ?.GetCustomAttribute<NormalizedUsernameAttribute>();

            if (attr != null)
                return new NormalizedUsernameModelBinder();
        }
        return null;
    }
}

// Регистрация:
builder.Services.AddControllers(options =>
{
    options.ModelBinderProviders.Insert(0, new NormalizedUsernameModelBinderProvider());
});

// IActionResult — не типизировано, Swagger не может вывести схему тела ответа

}

// ActionResult<T> — типизировано, Swagger генерирует точную схему

}

// Оба типа применяются в WebMessenger:
// IActionResult — там где разные пути возвращают разные типы данных (204 vs объект)

8. Security

Безопасность — не отдельная фича, а сквозная характеристика всего приложения. Этот раздел охватывает три практические области: защиту чувствительных данных через Data Protection API, управление кросс-доменными запросами через CORS, и защитные HTTP-заголовки.

8.1 Data Protection API

Что это. ASP.NET Core Data Protection — встроенный API для криптографической защиты данных: шифрования и верификации произвольных байт/строк. Это низкоуровневая альтернатива ручной работе с AES/HMAC — фреймворк сам управляет ключами, их ротацией и хранением.

Типичные применения:

  • Защита cookies (ASP.NET Core сам использует Data Protection для cookie-аутентификации)
  • Токены для сброса пароля, подтверждения email (ограниченное время жизни)
  • Защита состояния Anti-Forgery (CSRF-токены)
  • Шифрование чувствительных данных перед сохранением в БД
  • Защита параметров в URL (например, идентификаторов, которые нельзя угадать)

Базовая регистрация и использование

// Регистрация в Program.cs
builder.Services.AddDataProtection();
// ↑ Регистрирует IDataProtectionProvider.
//   По умолчанию ключи хранятся в памяти (не переживают рестарт) или
//   в %LOCALAPPDATA%/ASP.NET/DataProtection-Keys/ на Windows.

// Для production необходимо явное хранилище ключей:
builder.Services.AddDataProtection()
    .PersistKeysToFileSystem(new DirectoryInfo("/app/data-protection-keys"))
    // Шифрование ключей (опционально, но рекомендуется):
    .ProtectKeysWithCertificate(cert)
    // Имя приложения — ключи разных приложений несовместимы:
    .SetApplicationName("WebMessenger");

// ─── Использование IDataProtector ───
public class TokenService(IDataProtectionProvider provider)
{
    // Создаём протектор с purpose-строкой.
    // Purpose — изоляция: протектор "PasswordReset" не расшифрует
    // данные, зашифрованные протектором "EmailConfirm".
    private readonly IDataProtector _protector =
        provider.CreateProtector("WebMessenger.PasswordReset");

    public string GenerateResetToken(Guid userId)
    {
        var payload = $"{userId}:{DateTimeOffset.UtcNow.AddHours(1).ToUnixTimeSeconds()}";
        return _protector.Protect(payload);
        // Результат: Base64Url-строка — безопасно вставить в URL или email-ссылку
    }

    public (Guid userId, bool valid) ValidateResetToken(string token)
    {
        try
        {
            var payload = _protector.Unprotect(token);
            var parts = payload.Split(':');
            var userId = Guid.Parse(parts[0]);
            var expiry = DateTimeOffset.FromUnixTimeSeconds(long.Parse(parts[1]));

            return (userId, expiry > DateTimeOffset.UtcNow);
        }
        catch (CryptographicException)
        {
            // Токен подделан, истёк или принадлежит другому purpose
            return (Guid.Empty, false);
        }
    }
}

        provider.CreateProtector("WebMessenger.EmailConfirm")
                .ToTimeLimitedDataProtector(); // ← конвертация

    public string GenerateConfirmToken(string email)
    {
        // Защищаем с явным временем жизни — не нужно вручную хранить expiry
        return _protector.Protect(email, lifetime: TimeSpan.FromHours(24));
    }

    public string? ValidateConfirmToken(string token)
    {
        try
        {
            return _protector.Unprotect(token); // бросает если истёк
        }
        catch (SecurityTokenExpiredException)
        {
            return null; // токен истёк
        }
        catch (CryptographicException)
        {
            return null; // токен недействителен
        }
    }
}

8.2 CORS — Cross-Origin Resource Sharing

Что это. CORS — механизм браузерной безопасности, который ограничивает JavaScript-запросы к другим источникам (origin = схема + домен + порт). Браузер блокирует кросс-доменные запросы по умолчанию. Сервер сигнализирует о разрешении через HTTP-заголовки Access-Control-*.

Как работает Preflight. Для «небезопасных» запросов (не-GET/HEAD/POST, или POST с нестандартным Content-Type, или запросы с кастомными заголовками) браузер сначала отправляет OPTIONS-запрос — preflight. Сервер должен ответить разрешающими заголовками, иначе браузер не отправит основной запрос.

// Preflight запрос (браузер отправляет автоматически перед POST /api/chats):
// OPTIONS /api/chats/direct/{userId}/messages HTTP/1.1
// Origin: http://localhost:3000
// Access-Control-Request-Method: POST
// Access-Control-Request-Headers: content-type, authorization

// Ответ сервера при корректной CORS-политике:
// HTTP/1.1 204 No Content
// Access-Control-Allow-Origin: http://localhost:3000
// Access-Control-Allow-Methods: POST
// Access-Control-Allow-Headers: content-type, authorization
// Access-Control-Allow-Credentials: true
// Vary: Origin

Конфигурация в WebMessenger

// WebMessenger.Api/Program.cs

const string FrontCors = "Front";  // имя политики — строка-ключ

builder.Services.AddCors(opts =>
{
    opts.AddPolicy(name: FrontCors, policy =>
    {
        policy
            .WithOrigins(
                "http://localhost:3000",   // Next.js в Development
                "https://localhost:3000"   // Next.js по HTTPS в Development
            )
            // AllowAnyHeader() — разрешить любые заголовки запроса
            // (Authorization, Content-Type, X-Custom и т.д.)
            .AllowAnyHeader()
            // AllowAnyMethod() — разрешить все HTTP-методы (GET, POST, PUT, DELETE...)
            .AllowAnyMethod()
            // AllowCredentials() — разрешить отправку cookies и Authorization заголовка.
            // ОБЯЗАТЕЛЬНО для JWT в Authorization + cookie "auth-token".
            // При AllowCredentials() нельзя использовать AllowAnyOrigin()!
            .AllowCredentials();
    });
});

// Применение в пайплайне — ПЕРЕД Authentication:
app.UseCors(FrontCors);

// Для SignalR-хаба — явное указание политики через RequireCors:
app.MapHub<ChatHub>("/hubs/chat").RequireCors(FrontCors);
// ↑ SignalR требует явного CORS — общий UseCors() к хабам не применяется автоматически.

Все методы конфигурации политики

AllowAnyOrigin() Любой Origin (*) Несовместимо с AllowCredentials()
WithOrigins("https://*.example.com") Wildcard поддомены Только один уровень wildcard
AllowAnyHeader() Любые заголовки запроса Добавляет Access-Control-Allow-Headers: *

WithMethods("GET", "POST") Конкретные методы Явный список

Множественные политики и применение по контроллеру

// Несколько именованных политик для разных нужд:
builder.Services.AddCors(opts =>
{
    // Политика для основного фронтенда
    opts.AddPolicy("Front", policy =>
        policy.WithOrigins("http://localhost:3000")
              .AllowAnyHeader().AllowAnyMethod().AllowCredentials());

    // Политика для публичного API (без credentials, широкий доступ)
    opts.AddPolicy("PublicApi", policy =>
        policy.AllowAnyOrigin().AllowAnyHeader().WithMethods("GET"));

    // Политика по умолчанию (fallback)
    opts.AddDefaultPolicy(policy =>
        policy.WithOrigins("https://app.example.com")
              .AllowAnyHeader().AllowAnyMethod());
});

// Применение по контроллеру или action через атрибут:
[ApiController]
[Route("api/public")]
[EnableCors("PublicApi")]     // ← применить конкретную политику к контроллеру
public class PublicController : ControllerBase { }

[HttpGet("open-data")]
[EnableCors("PublicApi")]     // ← или к конкретному action
public IActionResult GetOpenData() => Ok();

// Явный запрет CORS для action:
[HttpGet("internal")]
[DisableCors]                 // ← никакая CORS-политика не применяется
public IActionResult InternalOnly() => Ok();
Критичная ошибка: AllowCredentials() + AllowAnyOrigin() = исключение при старте. Браузер запрещает Access-Control-Allow-Credentials: true при Access-Control-Allow-Origin: *. При включённых credentials всегда указывайте конкретные Origin.

8.3 Security Headers — защитные HTTP-заголовки

Что это. Security Headers — HTTP-заголовки ответа, которые инструктируют браузер о политиках безопасности. Они защищают от XSS, clickjacking, MIME-sniffing, man-in-the-middle и других классических атак. ASP.NET Core не добавляет большинство из них по умолчанию — нужно настраивать явно.

Ключевые заголовки безопасности

Заголовок Защита от Рекомендуемое значение
Strict-Transport-Security Downgrade-атаки, MITM max-age=31536000; includeSubDomains
X-Content-Type-Options MIME-type sniffing nosniff
X-Frame-Options Clickjacking (устарел, заменён CSP) DENY или SAMEORIGIN
Content-Security-Policy XSS, data injection Зависит от приложения (см. ниже)
Referrer-Policy Утечка URL в Referer-заголовке strict-origin-when-cross-origin
Permissions-Policy Неавторизованный доступ к API браузера camera=(), microphone=(), geolocation=()
X-XSS-Protection XSS (устарел в пользу CSP) 0 (отключить — CSP надёжнее)
Cache-Control Кэширование чувствительных данных no-store для API с персональными данными

Добавление заголовков через Middleware

// Способ 1: inline middleware в Program.cs (простой вариант)
app.Use(async (context, next) =>
{
    // Запрет фреймирования сайта в iframe — защита от clickjacking
    context.Response.Headers.Append("X-Frame-Options", "DENY");

    // Запрет MIME-sniffing — браузер не должен угадывать Content-Type
    context.Response.Headers.Append("X-Content-Type-Options", "nosniff");

    // Политика Referrer — не отправлять полный URL в Referer при кросс-доменных переходах
    context.Response.Headers.Append("Referrer-Policy", "strict-origin-when-cross-origin");

    // Запрет устаревшей XSS-фильтрации браузера (CSP надёжнее)
    context.Response.Headers.Append("X-XSS-Protection", "0");

    // Permissions-Policy — ограничение доступа к API браузера
    context.Response.Headers.Append("Permissions-Policy",
        "camera=(), microphone=(), geolocation=(), payment=()");

    await next(context);
});

// Способ 2: отдельный класс SecurityHeadersMiddleware (рекомендуется для production)
public class SecurityHeadersMiddleware(RequestDelegate next)
{
    public async Task InvokeAsync(HttpContext context)
    {
        context.Response.Headers.Append("X-Frame-Options", "DENY");
        context.Response.Headers.Append("X-Content-Type-Options", "nosniff");
        context.Response.Headers.Append("Referrer-Policy", "strict-origin-when-cross-origin");
        context.Response.Headers.Append("X-XSS-Protection", "0");
        context.Response.Headers.Append("Permissions-Policy",
            "camera=(), microphone=(), geolocation=()");

        await next(context);
    }
}

app.UseMiddleware<SecurityHeadersMiddleware>();

HSTS — HTTP Strict Transport Security

// HSTS инструктирует браузер всегда использовать HTTPS для данного домена.
// После первого посещения браузер кэширует политику на max-age секунд.

// Встроенная поддержка в ASP.NET Core:
builder.Services.AddHsts(options =>
{
    options.MaxAge           = TimeSpan.FromDays(365);
    options.IncludeSubDomains = true;   // применять к поддоменам
    options.Preload          = true;    // заявка на включение в HSTS Preload List
    // options.ExcludedHosts.Add("api.example.com"); // исключение конкретных хостов
});

// Применение — только в production (в Development HTTPS необязателен):
if (!app.Environment.IsDevelopment())
{
    app.UseHsts();
    // ↑ Добавляет заголовок: Strict-Transport-Security: max-age=31536000; includeSubDomains
    app.UseHttpsRedirection();
    // ↑ Редиректит HTTP → HTTPS (301/307)
}

// В WebMessenger HSTS отключён — HTTPS-терминация на уровне реверс-прокси
// (nginx/Caddy снаружи контейнера), Kestrel работает только на HTTP.

Content-Security-Policy

// CSP — мощный механизм: указывает браузеру, откуда можно загружать ресурсы.
// Главная защита от XSS: даже если атакующий вставил скрипт,
// браузер не выполнит его, если он не из разрешённого источника.

// Для чистого REST API (без HTML, только JSON):
context.Response.Headers.Append("Content-Security-Policy", "default-src 'none'");
// ↑ Ничего нельзя загружать — API возвращает только JSON, нет необходимости в ресурсах.

// Для приложения с Swagger UI (нужны inline-стили и скрипты):
context.Response.Headers.Append("Content-Security-Policy",
    "default-src 'self'; " +
    "script-src 'self' 'unsafe-inline'; " +  // Swagger требует inline JS
    "style-src 'self' 'unsafe-inline'; " +   // Swagger требует inline CSS
    "img-src 'self' data:;");

// Директивы CSP:
// default-src  — источник по умолчанию для всех типов ресурсов
// script-src   — JavaScript
// style-src    — CSS
// img-src      — изображения
// font-src     — шрифты
// connect-src  — XHR/fetch/WebSocket
// frame-src    — iframe
// 'self'       — только тот же origin
// 'none'       — ничего
// 'unsafe-inline' — разрешить inline скрипты (избегать в продакшене!)
// https:       — только HTTPS ресурсы

8.4 Secure Cookies — разбор кода WebMessenger

Cookie с JWT-токеном в WebMessenger настроена с учётом всех важных security-опций. Разберём каждую:

// WebMessenger.Api/Controllers/AuthController.cs — Login
Response.Cookies.Append("auth-token", token, new CookieOptions
{
    HttpOnly = true,
    // ↑ КРИТИЧНО: JavaScript не может прочитать эту cookie (document.cookie).
    //   Защищает от XSS-атаки: даже если XSS есть — токен не украсть через JS.

    Secure = Request.IsHttps,
    // ↑ Cookie отправляется только по HTTPS-соединению.
    //   В Development (HTTP) = false, в Production (HTTPS через nginx) = true.
    //   Без этого токен может утечь через незашифрованный HTTP.

    SameSite = SameSiteMode.Lax,
    // ↑ Политика отправки cookie при кросс-доменных запросах:
    //   Strict — cookie не отправляется ни при каких кросс-доменных запросах
    //   Lax    — cookie отправляется при top-level навигации (переход по ссылке),
    //            но не при AJAX/fetch кросс-доменных запросах (защита от CSRF)
    //   None   — всегда отправляется (требует Secure=true)
    //
    //   Lax — хороший баланс: защита от CSRF + работает при переходе по ссылкам.

    Expires = DateTimeOffset.UtcNow.AddDays(1)
    // ↑ Время жизни cookie — 1 день (совпадает с ExpireDays в JwtOptions).
    //   Persistent cookie (с Expires) vs Session cookie (без Expires — живёт до закрытия вкладки).
});
