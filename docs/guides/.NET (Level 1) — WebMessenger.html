1. Environment and Tooling — Окружение и инструменты

1.1 SDK-style csproj — формат проектного файла

Каждый .NET-проект описывается файлом .csproj. До .NET Core этот файл был громоздким XML, который перечислял каждый .cs-файл вручную. Начиная с .NET Core 2.0 появился SDK-style формат: компилятор сам находит все .cs-файлы в папке проекта, а в .csproj остаётся только то, что отличает проект от умолчания.

Зачем это важно: SDK-style файл читается и редактируется руками без IDE, хорошо работает с git (нет случайных merge-конфликтов из-за списков файлов), а также поддерживает все современные возможности — nullable, implicit usings, публикацию. 

<!-- WebMessenger.Api/WebMessenger.Api.csproj -->
<Project Sdk="Microsoft.NET.Sdk.Web">
  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <UserSecretsId>webmessenger-api-secrets</UserSecretsId>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Serilog.AspNetCore" Version="9.0.0" />
    <PackageReference Include="BCrypt.Net-Next" Version="4.0.3" />
  </ItemGroup>

  <ItemGroup>
    <ProjectReference Include="..\WebMessenger.DAL\WebMessenger.DAL.csproj" />
    <ProjectReference Include="..\WebMessenger.Contracts\WebMessenger.Contracts.csproj" />
  </ItemGroup>
</Project>

1.3 Отладка в Visual Studio

Отладчик — главный инструмент понимания того, что происходит в программе в реальном времени. Он позволяет остановить выполнение в любой точке, посмотреть значения переменных, пройти код пошагово и понять, почему поведение не совпадает с ожидаемым.

Базовый цикл отладки

  1. F9 — поставить / снять точку останова (breakpoint) на строке
  2. F5 — запустить с отладчиком (или продолжить выполнение до следующего breakpoint)
  3. F10 — Step Over: выполнить текущую строку, не заходя внутрь метода
  4. F11 — Step Into: войти внутрь вызываемого метода
  5. Shift+F11 — Step Out: выйти из текущего метода и вернуться в вызывающий
  6. Shift+F5 — остановить отладку

Условные breakpoints — мощный инструмент

Обычный breakpoint останавливается каждый раз. Условный — только когда выполняется условие. Это незаменимо при отладке циклов или потоков запросов (например, остановиться только для конкретного userId). 

// Пример: остановиться только когда обрабатывается конкретный чат
// ПКМ по breakpoint → Conditions → добавить условие:
chatId == new Guid("3fa85f64-5717-4562-b3fc-2c963f66afa6")

// Или: остановиться только после N-го срабатывания (Hit Count)
Горячая перезагрузка (.NET Hot Reload): dotnet watch и Visual Studio поддерживают Hot Reload — изменения в методах применяются без перезапуска процесса. Работает для большинства изменений внутри тел методов, но не для изменений в сигнатурах или структуре классов.

2. Language Fundamentals — Основы языка

2.1 Top-level statements, file-scoped namespaces, global usings

C# 9–12 убрали много обязательного boilerplate. Три главных упрощения — top-level statements, file-scoped namespaces и global usings — используются во всём проекте WebMessenger.

Top-level statements — зачем и когда

До C# 9 каждая точка входа требовала явного класса Program и метода static void Main. Top-level statements позволяют писать код прямо в файле — компилятор сам генерирует обёртку. Используй для точки входа приложения (Program.cs) — это стандарт в .NET 6+. Не используй в обычных классах библиотеки — там нужна явная структура. 

// До C# 9 — обязательный шаблон
public class Program
{
    public static void Main(string[] args)
    {
        var builder = WebApplication.CreateBuilder(args);
        ...
    }
}

// C# 9+ — top-level statements. Компилятор генерирует Program и Main сам
// Program.cs в WebMessenger.Api:
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllers();
var app = builder.Build();
app.Run();

File-scoped namespaces — зачем и когда

Обычный namespace добавляет уровень отступа ко всему файлу. File-scoped namespace (C# 10) объявляется одной строкой с точкой с запятой и применяется ко всему файлу автоматически — экономит один уровень вложенности. Используй всегда в новых проектах, когда в файле ровно один namespace (стандартная ситуация). Не используй, если в одном файле несколько namespace (редкий случай). 

// Старый стиль — лишний уровень отступа для всего содержимого файла
namespace WebMessenger.Api.Services
{
    public class AuthService { ... }
}

// File-scoped namespace — используется во всём WebMessenger
namespace WebMessenger.Api.Services;   // точка с запятой вместо { }

public class AuthService { ... }      // код не сдвигается вправо

Global usings — зачем и когда

global using (C# 10) добавляет using сразу во все файлы проекта. При включённом ImplicitUsings SDK генерирует стандартный набор автоматически. Используй для namespace, которые нужны повсюду: System, System.Linq, доменные типы проекта. Не используй для специфичных зависимостей — это скрывает реальные зависимости файла и усложняет навигацию. 

// Что ImplicitUsings автоматически добавляет для Microsoft.NET.Sdk.Web:
global using System;
global using System.Collections.Generic;
global using System.Linq;
global using System.Threading.Tasks;
global using Microsoft.AspNetCore.Builder;
global using Microsoft.AspNetCore.Http;
global using Microsoft.Extensions.DependencyInjection;
global using Microsoft.Extensions.Logging;

// Найти сгенерированный файл можно здесь:
// obj/Debug/net8.0/WebMessenger.Api.GlobalUsings.g.cs

2.2 Встроенные типы: value vs reference, nullable

Value types vs reference types — в чём разница и почему это важно

Это одно из фундаментальных различий C#, которое влияет на производительность, поведение при копировании и равенство объектов.

Value type (структура, enum): хранится на стеке или встроенно в объект. При присваивании создаётся полная независимая копия. Изменение копии не влияет на оригинал. Примеры: int, bool, Guid, DateTime, struct.

Reference type (класс, массив, строка): хранится в куче (heap), переменная содержит только ссылку на объект. При присваивании копируется ссылка — обе переменные указывают на один объект. Примеры: class, string, array, List<T>. 

// Value type — копирование создаёт независимый объект
Guid id1 = Guid.NewGuid();
Guid id2 = id1;  // независимая копия, изменение id2 не затронет id1

// Reference type — копируется ссылка, не объект
var user1 = new User { Username = "alice" };
var user2 = user1;        // обе переменные указывают на один User
user2.Username = "bob";  // user1.Username тоже стал "bob"!

// Из User.cs — поля с разными типами
public Guid Id { get; set; }                        // value type
public required string Username { get; set; }        // reference type (immutable)
public DateTime LastSeenAt { get; set; } = DateTime.UtcNow; // value type

Nullable — аннотации для безопасной работы с null

Nullable value type (int?, DateTime?) — это структура Nullable<T>, которая хранит значение и флаг HasValue. Единственный способ сделать value type null-совместимым. Используй, когда значение может отсутствовать: EditedAt (сообщение может не редактироваться), LastLoginAt (пользователь ещё не логинился).

Nullable reference type (string?, User?) — это аннотация компилятору при включённом Nullable enable. Сам тип не меняется, но компилятор предупреждает, если ты обращаешься к nullable-ссылке без проверки. Используй, чтобы явно показать: это поле может быть null. Не используй string?, если поле всегда заполнено. 

// Nullable value type — HasValue + Value
DateTime? editedAt = null;           // сообщение не редактировалось
if (editedAt.HasValue)
    Console.WriteLine(editedAt.Value); // безопасное обращение

// Из Message.cs — опциональная дата редактирования
public DateTime? EditedAt { get; init; }  // null = не редактировалось

// Null-conditional ?. — не вызывает исключение если левая часть null
var username = user?.Username;  // null если user == null, иначе user.Username

// Null-coalescing ?? — значение по умолчанию если левая часть null
var display = user?.Username ?? "anonymous";

// Цепочка ?. — из CurrentUser.cs
bool isAuth = _accessor.HttpContext?.User?.Identity?.IsAuthenticated == true;
// Если любое звено null — выражение вернёт null, а не бросит NullReferenceException

// Null-forgiving ! — говоришь компилятору "я знаю, что это не null"
// Используй только когда уверен — подавляет предупреждение, но не даёт защиты в runtime
var ctx = _accessor.HttpContext!; // "доверяю, что HttpContext есть"

2.3 Операторы, type tests, TryParse

Pattern matching — is и switch expression

Оператор is проверяет тип объекта в runtime и одновременно объявляет переменную нужного типа. Это безопаснее и лаконичнее, чем сначала проверить тип, а потом явно кастовать. Используй, когда нужно проверить тип перед использованием.

Switch expression (C# 8) — функциональная альтернатива switch-statement. Возвращает значение, поддерживает паттерны. Используй вместо длинных if-else цепочек, когда из набора условий нужно выбрать одно значение. 

// is — type test + объявление переменной в одном выражении
if (ex is InvalidOperationException ioe)
    Console.WriteLine(ioe.Message);   // ioe уже типизирована как InvalidOperationException

// is not — отрицание (используется в ChatHub.cs)
catch (Exception ex) when (ex is not OperationCanceledException) { ... }

// switch expression — DateTime.Kind в ChatController.cs
DateTime? at = body?.At?.Kind switch
{
    DateTimeKind.Utc       => body.At,
    DateTimeKind.Local     => body.At?.ToUniversalTime(),
    DateTimeKind.Unspecified => body.At.HasValue
        ? DateTime.SpecifyKind(body.At.Value, DateTimeKind.Utc) : null,
    _                      => null   // _ — дефолтная ветка (discard)
};

TryParse — безопасный разбор строк

Методы Parse бросают исключение при неверном формате. TryParse возвращает bool и передаёт результат через out-параметр — никаких исключений. Используй TryParse всегда, когда входная строка приходит от пользователя или внешней системы и её формат не гарантирован. Parse используй только когда данные заведомо корректны (например, константы в коде). 

// Из CurrentUser.cs — разбор Guid из JWT-клейма
var claim = _accessor.HttpContext!.User.FindFirst(ClaimTypes.NameIdentifier)
    ?? throw new InvalidOperationException("NameIdentifier claim not found");

return Guid.Parse(claim.Value); // здесь Parse OK — мы сами генерировали JWT

// Но если данные приходят снаружи — используй TryParse
if (!Guid.TryParse(externalId, out var userId))
    return BadRequest("Invalid user id format");

// TryParse для int — параметр пагинации из query string
if (!int.TryParse(Request.Query["limit"], out var limit))
    limit = 20; // значение по умолчанию если параметр не число

2.4 Дата и время: DateTime, DateTimeOffset, TimeSpan

DateTime и проблема часовых поясов

DateTime хранит дату и время, но не информацию о часовом поясе — только Kind: Utc, Local или Unspecified. Ключевое правило: в серверном коде, БД и API всегда используй DateTime.UtcNow и храни всё в UTC. Конвертацию в локальное время делай только на клиенте при отображении. Если смешать Local и Utc, получишь ошибки пагинации, неверные сортировки и баги с дедлайнами. 

// ПРАВИЛЬНО — все поля в сущностях WebMessenger инициализируются UtcNow
public DateTime SentAt { get; init; } = DateTime.UtcNow;    // Message.cs

3. Object-Oriented Programming — ООП

3.1 Классы, конструкторы, свойства, инкапсуляция

Класс — базовая единица структуры кода

Класс объединяет данные (поля, свойства) и поведение (методы) в одну сущность. Инкапсуляция — принцип, при котором внутреннее состояние скрыто от внешнего кода: поля приватные, доступ только через публичные методы или свойства. Это защищает инвариант объекта — гарантию, что он всегда находится в корректном состоянии.

Конструкторы: обычный vs primary constructor (C# 12)

Primary constructor (C# 12) — параметры объявляются прямо в скобках после имени класса. Это синтаксический сахар: компилятор создаёт поля из параметров автоматически или позволяет явно присвоить их в теле. Используй primary constructor в сервисах и контроллерах — это стандарт в .NET 8. Не используй, если в конструкторе нужна сложная логика инициализации — тогда обычный конструктор читается лучше. 

// Обычный конструктор — явные поля и присваивание
public class AuthService : IAuthService
{
    private readonly JwtOptions _jwt;
    private readonly ILogger<AuthService> _logger;

    public AuthService(IOptions<JwtOptions> jwtOptions, ILogger<AuthService> logger)
    {
        _jwt = jwtOptions.Value;
        _logger = logger;
    }
}

// Primary constructor (C# 12) — то же самое, но короче.
// Используется во всех сервисах и контроллерах WebMessenger.
public class AuthService(IOptions<JwtOptions> jwtOptions, ILogger<AuthService> logger) : IAuthService
{
    private readonly JwtOptions _jwt = jwtOptions.Value;   // параметр используется для инициализации поля
    private readonly ILogger<AuthService> _logger = logger; // поле readonly — нельзя переприсвоить
}

readonly — защита от случайного переприсваивания

Поле readonly можно присвоить только в объявлении или конструкторе. После создания объекта оно не меняется. Используй для всех зависимостей, получаемых через конструктор — это явно документирует, что зависимость стабильна на весь жизненный цикл объекта.

3.2 struct — value type с семантикой значения

struct — пользовательский value type. В отличие от class, экземпляр struct живёт на стеке (если не захвачен heap-объектом) и копируется при присваивании и передаче в метод. Нет наследования, нет виртуальных методов. GC не отслеживает структуры — нет давления на сборщик мусора.

Когда использовать struct: маленькие, неизменяемые, логически цельные значения — координаты, цвета, диапазоны, money-объекты. Практическое правило: размер ≤ 16 байт, преимущественно readonly, нет полиморфизма.

// readonly struct — неизменяемый value type. Компилятор запрещает мутацию.
// Пример: диапазон времени для фильтрации сообщений
public readonly struct DateRange
{
    public DateTime From { get; }
    public DateTime To   { get; }

    public DateRange(DateTime from, DateTime to)
    {
        if (to < from) throw new ArgumentException("To must be >= From");
        From = from;
        To   = to;
    }

    // Метод — не мутирует, возвращает новый экземпляр
    public bool Contains(DateTime dt) => dt >= From && dt <= To;

    public override string ToString() => $"{From:yyyy-MM-dd} — {To:yyyy-MM-dd}";
}

3.3 Records — неизменяемые типы данных

Зачем нужны records

record (C# 9) — специальный вид класса, оптимизированный для хранения данных. В отличие от обычного класса, record из коробки предоставляет:

  • Структурное равенство — два record равны, если равны все их свойства (как у struct, а не как у class)
  • ToString — автоматически выводит все свойства с именами
  • Deconstruct — можно разобрать на переменные через деструктуризацию
  • with-выражение — создать копию с изменёнными полями без мутации оригинала

Используй record для DTO, request/response моделей, payload-ов SignalR — данных, которые передаются между слоями и не должны меняться после создания. Не используй для EF-сущностей — EF Core отслеживает изменения через change tracker, которому нужна мутируемость; record с init затруднит это.

Два синтаксиса record

// 1. Positional record — параметры = свойства. Компактно для 2–4 полей.
//    Используется в WebMessenger для простых payload-ов и response-ов

// SignalRPayloads.cs — три positional record
public sealed record MessageCreatedPayload(Guid ChatId, Guid? PeerUserId, ChatMessageDto Message);

//    Используется для DTO в WebMessenger.Contracts после рефакторинга

public sealed record ChatMessageDto

sealed — зачем запрещать наследование

Все DTO в WebMessenger объявлены sealed. Это значит, что от них нельзя наследоваться. Зачем: DTO — это контракт передачи данных, а не иерархия поведения. Наследование DTO ведёт к сложным зависимостям и неочевидным изменениям контракта. Кроме того, sealed record позволяет компилятору генерировать более эффективный код для equality и ToString.

3.4 Перегрузка операторов

C# позволяет определить поведение стандартных операторов (+, -, ==, <, > и др.) для своих типов. Это делает код с value-объектами более читаемым — price1 + price2 понятнее, чем price1.Add(price2).

Когда стоит перегружать: тип представляет математическое или физическое значение (деньги, координаты, интервалы), и операция семантически очевидна. Когда не стоит: если смысл оператора неочевиден для читателя — перегрузка становится ловушкой. 

// Пример: тип Money с перегруженными операторами
public readonly struct Money
{
    public decimal Amount   { get; }
    public string  Currency { get; }

    public Money(decimal amount, string currency)
    {
        Amount   = amount;
        Currency = currency;
    }

    // operator + — сложение двух сумм в одной валюте
    public static Money operator +(Money a, Money b)
    {
        if (a.Currency != b.Currency)
            throw new InvalidOperationException("Cannot add different currencies");
        return new Money(a.Amount + b.Amount, a.Currency);
    }

    // operator == и != — обязательно в паре
    public static bool operator ==(Money a, Money b)
        => a.Amount == b.Amount && a.Currency == b.Currency;

    public static bool operator !=(Money a, Money b) => !(a == b);

    // При перегрузке == обязательно переопределить Equals и GetHashCode
    public override bool Equals(object? obj) => obj is Money m && this == m;
    public override int  GetHashCode() => HashCode.Combine(Amount, Currency);

    // operator < и > — для сортировки
    public static bool operator <(Money a, Money b) => a.Amount < b.Amount;
    public static bool operator >(Money a, Money b) => a.Amount > b.Amount;

    public override string ToString() => $"{Amount:N2} {Currency}";
}

// Использование — читается как математика
var price    = new Money(100, "USD");
var discount = new Money(20,  "USD");
var total    = price + discount;   // Money(120, "USD")
bool isEqual = price == discount;  // false
bool cheaper = discount < price;   // true
// Операторы неявного/явного приведения типов (implicit/explicit conversion)
public readonly struct Celsius
{
    public double Value { get; }
    public Celsius(double value) => Value = value;

    // implicit — автоматическое приведение double → Celsius без каста
    public static implicit operator Celsius(double value) => new(value);

    // explicit — явный каст Celsius → double (может потерять информацию о типе)
    public static explicit operator double(Celsius c) => c.Value;
}

Celsius temp = 36.6;           // implicit: double → Celsius автоматически
double  val  = (double)temp;   // explicit: требует явного каста

// В WebMessenger перегрузка операторов не используется — доменные типы представлены
// через record и class. Понимать важно для чтения библиотечного кода (NodaTime,
// System.Numerics.Vector, BigInteger и др.), которые активно применяют операторы.
Правило: перегружай операторы только для value-типов (struct, record struct) с очевидной математической семантикой. Для reference types — почти никогда (если только это не специализированный тип вроде матрицы). При перегрузке == — обязательно переопределить Equals и GetHashCode, а != всегда в паре с ==.

3.5 Generics и constraints

Зачем нужны generics

Generics позволяют написать один класс или метод, который работает с любым типом, сохраняя типобезопасность. Без generics пришлось бы писать UserRepository, MessageRepository, ChatRepository с дублирующимся кодом. С generics — один Repository<T> покрывает всё.

Используй generics, когда логика одинакова для разных типов: репозитории, обёртки ответов (PagedResult<T>), утилиты. Не увлекайся — если логика для каждого типа разная, лучше явные классы.

Constraints — ограничения на тип T

where T : constraint говорит компилятору, какие операции допустимы с T внутри класса. Без ограничения T — полностью непрозрачный тип, у него нет никаких известных методов. 

// Repository.cs — where T : class обязателен для DbSet<T>
public class Repository<T> : IRepository<T> where T : class
// "T должен быть reference type" — EF Core не работает со struct в DbSet
{
    private readonly DbSet<T> _dbSet;

    public IQueryable<T> GetAll(params string[] navigationProperties)
    {
        var query = _dbSet.AsNoTracking(); // AsNoTracking — не отслеживать, быстрее для чтения
        foreach (var nav in navigationProperties)
            query = query.Include(nav);   // Include — загрузить связанные сущности (JOIN)
        return query;
    }

    public async Task<T?> GetAsync(Guid id, CancellationToken ct = default)
        => await _dbSet.FindAsync(new object[] { id }, ct);
    // FindAsync — ищет по primary key; сначала смотрит в change tracker, потом в БД
}
// PagedResult<T> — generic wrapper для пагинированных ответов API
// Один тип работает и для чатов, и для сообщений, и для контактов
public sealed record PagedResult<T>
{
    public IReadOnlyList<T> Items { get; init; } = [];
    public bool HasMore { get; init; }
    public DateTime? NextBefore { get; init; }  // курсор для следующей страницы
}

// Использование в ChatService.cs
return new PagedResult<ChatListItemDto>
{
    Items = result,
    HasMore = rows.Count == take,
    NextBefore = rows.LastOrDefault()?.Chat.LastActivityAt
};

Lazy initialization — ??= в UnitOfWork

Оператор ??= присваивает значение только если переменная равна null. В UnitOfWork это используется для ленивой инициализации репозиториев: объект создаётся не при старте UnitOfWork, а только при первом обращении. Это экономит ресурсы — если запрос не затрагивает, например, чаты, ChatRepository не создаётся. 

// UnitOfWork.cs — lazy init через ??=
private IRepository<User>? _userRepository;
private IRepository<Message>? _messageRepository;

public IRepository<User> UserRepository
    => _userRepository ??= new Repository<User>(_context);
// Первый вызов: _userRepository == null → создаём и сохраняем
// Второй вызов: _userRepository уже есть → просто возвращаем

public IRepository<Message> MessageRepository
    => _messageRepository ??= new Repository<Message>(_context);

3.6 Интерфейсы vs базовые классы

Интерфейсы — контракт без реализации

Интерфейс описывает что умеет объект, не говоря как он это делает. Класс, реализующий интерфейс, обязан предоставить все объявленные методы и свойства. В WebMessenger каждый сервис скрыт за интерфейсом — это даёт три преимущества:

  • Тестируемость — в юнит-тестах реальный сервис заменяется Mock-объектом того же интерфейса
  • Заменяемость — можно сменить реализацию (например, Dropbox → S3) без изменения кода, который её использует
  • Явный контракт — интерфейс показывает, что именно публично доступно, а не весь класс целиком
// IFileStorage.cs — контракт хранилища файлов
public interface IFileStorage

    Task<bool>   DeleteAsync(string fileUrl, CancellationToken ct = default);
    bool         ValidateFile(IFormFile file, long maxSizeBytes, string[] allowedMimeTypes);
}

// DropboxFileStorage.cs — одна из возможных реализаций
public class DropboxFileStorage : IFileStorage
{
    public async Task<string?> UploadAsync(Stream fileStream, string fileName, CancellationToken ct = default)
    { /* Dropbox SDK */ }

4. Exceptions — Исключения

4.1 Что такое исключение и зачем оно нужно

Исключение — это механизм сигнализации о том, что в программе произошло что-то, с чем текущий код не может справиться самостоятельно. В отличие от возврата кода ошибки (return -1), исключение разматывает стек вызовов вверх до ближайшего catch, который умеет его обработать. Это позволяет писать «счастливый путь» без проверок на каждом уровне и централизованно обрабатывать ошибки.

Когда бросать исключение: входные данные некорректны, операция невозможна в текущем состоянии, внешний ресурс недоступен. Когда НЕ бросать: «не найдено» — ожидаемый результат (лучше вернуть null или false); управление потоком выполнения — исключения дороги и не предназначены для этого.

4.2 try / catch / finally — структура обработки

Блок try содержит код, который может бросить исключение. Блок catch перехватывает его и обрабатывает — логирует, преобразует в ответ API, возвращает безопасное значение. Блок finally выполняется всегда, независимо от того, было исключение или нет — используется для освобождения ресурсов (хотя в современном C# для этого чаще используют using). 

// AuthService.cs — try/catch вокруг внешней библиотеки BCrypt.
// BCrypt.Verify может бросить исключение при повреждённом хеше — мы это обрабатываем.
public bool ValidateUserCredentials(User? user, string password)
{
    // Guard-проверки ДО try — не нужно ловить то, что можно предотвратить
    if (user == null || string.IsNullOrWhiteSpace(password))
    {
        _logger.LogWarning("Attempt to validate null user or empty password");
        return false;
    }

    try
    {
        return BCrypt.Net.BCrypt.Verify(password, user.PasswordHash,
            enhancedEntropy: false, hashType: HashType.SHA256);
    }
    catch (Exception ex)
    {
        // Логируем с объектом исключения — Serilog запишет полный stack trace
        _logger.LogError(ex, "Error validating credentials for {Username}", user.Username);
        return false;  // безопасное значение вместо propagation
    }
}

4.3 Выбор правильного типа исключения

.NET предоставляет иерархию стандартных исключений. Выбор правильного типа помогает вызывающему коду точно понять, что пошло не так, и написать точный catch. Не бросай Exception напрямую — это лишает смысла всю типизацию.

Guard-методы — лаконичные проверки аргументов

Статические методы ArgumentNullException.ThrowIfNull, ArgumentException.ThrowIfNullOrWhiteSpace (C# 10+) заменяют шаблонный if (x == null) throw new .... Используй их в начале каждого публичного метода — это называется fail-fast: чем раньше обнаружена ошибка, тем легче её диагностировать. 

// AuthService.cs — guard в начале метода
public string GenerateJwtToken(User user)
{
    ArgumentNullException.ThrowIfNull(user);
    // Дальнейший код гарантированно работает с не-null user
    ...
}

4.4 Несколько catch, when-фильтры и rethrow

Несколько catch — от конкретного к общему

CLR проверяет блоки catch сверху вниз и выполняет первый подходящий. Поэтому всегда размещай более конкретные типы выше, общие — ниже. Если поставить catch (Exception) первым, до остальных блоков никогда не дойдёт. 

// ChatController.cs — два catch: бизнес-ошибка → 404, всё остальное → 500
catch (InvalidOperationException ex)         // конкретный тип — идёт первым
{
    _logger.LogWarning(ex, "Business rule violated for user {UserId}", userId);
    return NotFound(new { message = ex.Message });      // HTTP 404
}
catch (UnauthorizedAccessException ex)
{
    _logger.LogWarning(ex, "Unauthorized access for user {UserId}", userId);
    return StatusCode(403, new { message = ex.Message });  // HTTP 403
}
catch (Exception ex)                          // общий — идёт последним
{
    _logger.LogError(ex, "Unexpected error");
    return StatusCode(500, new { message = "An error occurred" }); // HTTP 500
}

when — фильтр исключений

Ключевое слово when добавляет условие к catch: блок выполнится только если условие истинно. Главное преимущество перед if внутри catch: фильтр вычисляется до разматывания стека, что сохраняет полный stack trace для диагностики и не влияет на производительность при несрабатывании. 

// Пропустить отмену операции — она не является ошибкой
catch (Exception ex) when (ex is not OperationCanceledException)
{
    _logger.LogError(ex, "Unexpected error processing request");
    throw;
}
// OperationCanceledException не поймается этим блоком — продолжит разматывание стека

// when с проверкой свойства исключения
catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.TooManyRequests)
{
    await Task.Delay(TimeSpan.FromSeconds(5));  // retry-логика при rate limit
}

throw vs throw ex — сохранение stack trace

Это одна из самых распространённых ошибок начинающих. throw ex сбрасывает оригинальный stack trace и заменяет его текущей позицией — ты теряешь информацию о том, где именно возникло исключение. throw (без аргумента) пробрасывает исключение с сохранением полного стека. 

// ПЛОХО — stack trace потерян, диагностика затруднена
catch (Exception ex)
{
    _logger.LogError(ex, "Error");
    throw ex;  // ← stack trace перезаписан текущей строкой
}

// ХОРОШО — throw без аргумента сохраняет оригинальный stack trace
catch (Exception ex)
{
    _logger.LogError(ex, "Error");
    throw;     // ← стек сохранён, диагностика полная
}

// ExceptionDispatchInfo — сохранить и пробросить из другого места (advanced)
var edi = ExceptionDispatchInfo.Capture(ex);
// ... позже ...
edi.Throw();  // стек сохранён, даже если бросаем из другого потока
Никогда не пиши catch (Exception ex) { } (пустой catch) — это «глотает» исключение, программа продолжает работать в некорректном состоянии, а ты никогда не узнаешь о проблеме. Как минимум залогируй.

4.5 Исключения в async-коде

В асинхронном коде исключения ведут себя чуть иначе: они захватываются внутри Task и пробрасываются при await. Это значит, что try/catch вокруг await работает ожидаемо — так же, как синхронный код. 

// try/catch вокруг await — стандартный паттерн во всех контроллерах
try
{
    var result = await _chatService.SendMessageToUserAsync(me, other, content, ct);
    return Ok(result);
}
catch (InvalidOperationException ex)
{
    return BadRequest(new { message = ex.Message });
}

// OperationCanceledException — особый случай: клиент отключился.
// Это НЕ ошибка — просто прекращаем работу без логирования как Error.
catch (OperationCanceledException)
{
    return StatusCode(499);  // 499 Client Closed Request (nginx convention)
}
AggregateException — при использовании Task.WhenAll все исключения оборачиваются в AggregateException. При await Task.WhenAll(...) первое исключение разворачивается автоматически. Для доступа ко всем — используй Task.WhenAll(...).ContinueWith или проверяй AggregateException.InnerExceptions.

5. Interfaces — Интерфейсы

5.1 Что такое интерфейс и зачем он нужен

Интерфейс — это контракт: набор методов и свойств, которые класс обязуется реализовать. Сам интерфейс не содержит логики — только сигнатуры. Это разделение между что делает (интерфейс) и как делает (реализация).

Главная ценность интерфейсов в WebMessenger — любой компонент, зависящий от IChatService, не знает ничего про ChatService. Он знает только, какие методы существуют. Это позволяет: тестировать компоненты изолированно, менять реализацию без касания зависимых классов, явно документировать публичный контракт сервиса.

5.2 Контракты: методы, свойства, async

Интерфейс может объявлять методы (синхронные и async), свойства (только геттер или с сеттером) и события. Async-методы в интерфейсе объявляются через возвращаемый тип Task/Task<T> — ключевое слово async в интерфейс не пишется, оно только в реализации. 

// ICurrentUser.cs — свойства-контракты (только get — реализация сама решает как получить)
public interface ICurrentUser
{
    bool IsAuthenticated { get; }   // реализация читает из HttpContext
    Guid Id { get; }               // реализация парсит JWT-клейм
    string? Username { get; }      // nullable — пользователь может быть анонимным
}

// IRepository.cs — generic CRUD-контракт.
// async в интерфейсе НЕ пишется — только Task/Task<T> как возвращаемый тип
public interface IRepository<T> where T : class
{
    IQueryable<T> GetAll(params string[] navigationProperties);
    Task<T?>      GetAsync(Guid id, CancellationToken ct = default);
    Task          InsertAsync(T entity, CancellationToken ct = default);
    Task          UpdateAsync(T entity, CancellationToken ct = default);
    Task          DeleteAsync(Guid id, CancellationToken ct = default);
}

// IContactsService.cs — бизнес-контракт сервиса контактов
public interface IContactsService
{
    Task<AddContactResponse>  AddContactAsync(Guid currentUserId, AddContactRequest request, CancellationToken ct = default);
    Task<PagedResult<ContactDto>> GetContactsAsync(Guid currentUserId, int limit, DateTime? before, CancellationToken ct = default);
    Task                       RemoveContactAsync(Guid currentUserId, Guid contactId, CancellationToken ct = default);
}

5.3 Реализация интерфейса

Класс реализует интерфейс через : IInterfaceName. Он обязан предоставить все объявленные члены — компилятор выдаст ошибку при пропуске любого. Один класс может реализовывать несколько интерфейсов через запятую. Реализация может добавлять дополнительные публичные методы — они не нарушают контракт, но не видны через переменную типа интерфейса. 

// ContactsService.cs — реализует IContactsService.

5.4 Явная реализация интерфейса

Если класс реализует два интерфейса с методами одного имени, или нужно скрыть метод от прямого вызова через экземпляр класса — используется явная реализация. Метод доступен только через переменную типа интерфейса. 

// Явная реализация — метод виден только через IDisposable, не через UnitOfWork напрямую
public class UnitOfWork : IUnitOfWork
{
    private readonly ApplicationDbContext _context;

    // Неявная (обычная) реализация — доступна и через UnitOfWork, и через IUnitOfWork
    public async Task SaveAsync(CancellationToken ct = default)
        => await _context.SaveChangesAsync(ct);

    // Dispose вызывается DI-контейнером автоматически — нет смысла звать вручную
    public void Dispose() => _context.Dispose();
}

5.6 IComparable<T> и IEquatable<T> — сортировка и равенство

Два ключевых стандартных интерфейса для типов, которые нужно сортировать или сравнивать. IComparable<T> определяет порядок объектов — используется в List.Sort(), SortedSet<T>, OrderBy(). IEquatable<T> определяет равенство — используется в Contains(), Distinct(), HashSet<T>, Dictionary.

Зачем реализовывать явно, если есть == и Equals? Для reference types Equals по умолчанию сравнивает ссылки, а не значения. Если нужно чтобы два разных объекта с одинаковыми полями считались равными — необходимо переопределить Equals и реализовать IEquatable<T>. 

// IComparable<T> — реализовать чтобы объекты можно было сортировать напрямую.
// CompareTo должен возвращать: отрицательное число (this < other), 0 (равны), положительное (this > other)
public class ChatPreview : IComparable<ChatPreview>
{
    public DateTime LastActivityAt { get; init; }
    public string   ChatName        { get; init; } = "";

    // Сортировка по убыванию активности (самые свежие чаты — первыми)
    public int CompareTo(ChatPreview? other)
    {
        if (other is null) return 1;  // null всегда меньше
        return other.LastActivityAt.CompareTo(this.LastActivityAt); // обратный порядок
    }
}

var chats = new List<ChatPreview> { ... };
chats.Sort();  // использует IComparable<T>.CompareTo — самые активные первыми

var sorted = new SortedSet<ChatPreview>(chats);  // автоматически отсортирован при добавлении
// IEquatable<T> — реализовать чтобы объекты сравнивались по значению, а не по ссылке.
// ОБЯЗАТЕЛЬНО: при реализации IEquatable<T> также переопределить GetHashCode()
// Правило: если Equals(x, y) == true, то GetHashCode(x) == GetHashCode(y)
public class UserId : IEquatable<UserId>
{
    public Guid Value { get; }
    public UserId(Guid value) => Value = value;

    public bool Equals(UserId? other) => other is not null && Value == other.Value;

    // Переопределить object.Equals тоже — для использования в object-контексте
    public override bool Equals(object? obj) => Equals(obj as UserId);

    public override int GetHashCode() => Value.GetHashCode();

    // Опционально: перегрузить операторы для удобства
    public static bool operator ==(UserId? a, UserId? b) => EqualityComparer<UserId>.Default.Equals(a, b);
    public static bool operator !=(UserId? a, UserId? b) => !(a == b);
}

var id1 = new UserId(Guid.NewGuid());
var id2 = new UserId(id1.Value);  // разные объекты, одинаковые значения

Console.WriteLine(id1 == id2);            // true  — через перегруженный ==
Console.WriteLine(id1.Equals(id2));        // true  — через IEquatable<T>

var set = new HashSet<UserId> { id1 };
Console.WriteLine(set.Contains(id2));     // true  — HashSet использует GetHashCode + Equals

record как готовое решение для value equality

Если нужен тип с равенством по значению и не нужна мутабельность — используй record. Компилятор автоматически генерирует Equals, GetHashCode, оператор == и IEquatable<T> на основе всех свойств. 

// record — компилятор генерирует весь boilerplate автоматически
public record MessageKey(Guid ChatId, Guid MessageId);

var key1 = new MessageKey(chatId, msgId);
var key2 = new MessageKey(chatId, msgId);
Console.WriteLine(key1 == key2);  // true — record сравнивает по значению полей

var cache = new Dictionary<MessageKey, ChatMessageDto>();
cache[key1] = dto;

6.4 Dictionary — батч-маппинг в ChatService

Одна из самых частых операций в ChatService — взять массив ID чатов, сделать один SQL-запрос для получения связанных данных и быстро сопоставить их с нужными чатами. Для этого используется ToDictionaryAsync — LINQ-метод, материализующий запрос сразу в словарь. 

// ChatService.cs — три Dictionary для сборки списка чатов за 3 запроса вместо N
// Шаг 1: получить chatIds из результатов
var chatIds = rows.Select(r => r.Chat.Id).ToArray();

// Шаг 2: lastReadMap — когда каждый участник последний раз читал чат
var lastReadMap = await _uow.ChatMemberRepository.GetAll()
    .Where(cm => cm.UserId == me && chatIds.Contains(cm.ChatId))
    .Select(cm => new { cm.ChatId, cm.LastReadAt })
    .ToDictionaryAsync(x => x.ChatId, x => x.LastReadAt);  // ключ → значение

// Шаг 3: unreadMap — количество непрочитанных сообщений для каждого чата
var unreadMap = (await _uow.MessageRepository.GetAll()
    .Where(m => chatIds.Contains(m.ChatId) && m.SenderId != me)
    .GroupBy(m => m.ChatId)
    .Select(g => new { ChatId = g.Key, Count = g.Count() })
    .ToListAsync())
    .ToDictionary(x => x.ChatId, x => x.Count);  // in-memory после материализации

// Использование: TryGetValue безопаснее индексатора [] — не бросает KeyNotFoundException
var unread = unreadMap.TryGetValue(chatId, out var count) ? count : 0;
var lastRead = lastReadMap.TryGetValue(chatId, out var r) ? r ?? DateTime.MinValue : DateTime.MinValue;
Почему не N+1 запросов? Вместо того чтобы в цикле по чатам делать отдельный запрос на каждый (N+1 problem), сначала получаем все нужные чаты, потом одним запросом получаем связанные данные и сопоставляем через Dictionary. Итого 3 запроса вместо N+2.

6.5 IEqualityComparer<T> — кастомное равенство

По умолчанию Dictionary и HashSet используют Equals и GetHashCode объекта для определения равенства ключей. Иногда нужна другая логика: сравнение без учёта регистра, по одному полю объекта, или для типов без переопределённого Equals. IEqualityComparer<T> позволяет задать эту логику снаружи типа. 

// Пример 1: Dictionary с ключами-строками без учёта регистра
// По умолчанию "Alice" и "alice" — разные ключи
var users = new Dictionary<string, User>(StringComparer.OrdinalIgnoreCase);
users["Alice"] = aliceUser;
var found = users["alice"];  // работает! OrdinalIgnoreCase считает их равными

// StringComparer — встроенные компараторы для строк:
// StringComparer.Ordinal            — регистро-чувствительный
// StringComparer.OrdinalIgnoreCase  — без учёта регистра (использовать для username, email)
// StringComparer.CurrentCulture     — с учётом локали пользователя (для UI)

// Пример 2: HashSet с дедупликацией по одному полю объекта
// (когда User не переопределяет Equals/GetHashCode)
public class UserByUsernameComparer : IEqualityComparer<User>
{
    public bool Equals(User? x, User? y)
        => string.Equals(x?.Username, y?.Username, StringComparison.OrdinalIgnoreCase);

    public int GetHashCode(User obj)
        => obj.Username.ToUpperInvariant().GetHashCode();
    // Правило: если Equals(x, y) == true, то GetHashCode(x) == GetHashCode(y)
    // HashSet/Dictionary использует GetHashCode для разбивки по корзинам (buckets)
    // Если нарушить это правило — элементы не будут находиться
}

var uniqueUsers = new HashSet<User>(new UserByUsernameComparer());
uniqueUsers.Add(new User { Username = "Alice" });
uniqueUsers.Add(new User { Username = "alice" });  // не добавится — считается дубликатом
Console.WriteLine(uniqueUsers.Count);  // 1

// Передача компаратора в LINQ Distinct/GroupBy/Intersect/Except:
// (эти методы принимают IEqualityComparer<T> как второй аргумент)
var distinct = allUsers.Distinct(new UserByUsernameComparer()).ToList();
Правило: для строк используй готовые StringComparer.OrdinalIgnoreCase и аналоги — не пиши свой компаратор для строк. Кастомный IEqualityComparer<T> нужен когда: объект не переопределяет Equals, или нужна логика равенства отличная от встроенной (например, по одному полю из многих).

    Console.WriteLine($"Processing: {next}");

    Console.WriteLine($"Next up: {upcoming}");

var peek = history.Peek();   // "action 2" — посмотреть без извлечения
// LinkedList<T> — двусвязный список. Хранит узлы LinkedListNode<T>
// Важно: доступ к узлу делает вставку/удаление O(1), поиск по значению всё равно O(n)
var messages = new LinkedList<string>();

LinkedListNode<string> first  = messages.AddLast("msg-1");
LinkedListNode<string> second = messages.AddLast("msg-2");
LinkedListNode<string> third  = messages.AddLast("msg-3");

// Вставка перед конкретным узлом — O(1) (в отличие от List.Insert — O(n))
messages.AddBefore(second, "msg-1.5");  // список: msg-1 → msg-1.5 → msg-2 → msg-3

// Удаление узла — O(1) если есть ссылка на узел
messages.Remove(second);  // список: msg-1 → msg-1.5 → msg-3

// Перебор — как IEnumerable

    Console.WriteLine(m);

7.1 Строки — immutable reference type

7.3 Regex — валидация и парсинг

Regex — мощный инструмент для проверки формата строк и извлечения данных. Две формы использования: статические методы (удобно для разовых вызовов) и скомпилированный экземпляр (быстрее при многократном использовании, т.к. паттерн компилируется один раз). В .NET 7+ появился [GeneratedRegex] — компилятор генерирует оптимальный код на этапе сборки. 

// Статический вызов — удобно, но паттерн компилируется при каждом вызове
if (!Regex.IsMatch(username, @"^[a-zA-Z0-9_]{3,50}$"))
    throw new ArgumentException("Invalid username format");

// Скомпилированный экземпляр — паттерн компилируется один раз при загрузке класса
private static readonly Regex _usernameRegex =
    new(@"^[a-zA-Z0-9_]{3,50}$", RegexOptions.Compiled);

public bool IsValid(string username) => _usernameRegex.IsMatch(username);

// [GeneratedRegex] (.NET 7+) — компилятор генерирует оптимальный код, нет накладных расходов runtime
public partial class Validator
{
    [GeneratedRegex(@"^[a-zA-Z0-9_]{3,50}$")]
    private static partial Regex UsernameRegex();

    public bool IsValid(string s) => UsernameRegex().IsMatch(s);
}

// Извлечение групп — парсинг Bearer-токена из заголовка

if (match.Success)
    token = match.Groups["token"].Value;  // именованная группа

8.2 Expression<Func<T,TResult>> — лямбда как данные

Обычная лямбда (Func<T, bool>) — это скомпилированный метод, который выполняется в памяти. Expression<Func<T, bool>> — это описание лямбды в виде дерева объектов. EF Core читает это дерево и транслирует в SQL. Если передать EF обычную Func вместо Expression, вся таблица загрузится в память и фильтрация произойдёт на стороне C# — это N-кратно медленнее. 

// MessageProjections.cs — Expression: EF Core транслирует в SQL SELECT
public static readonly Expression<Func<Message, ChatMessageDto>> ToDto =
    m => new ChatMessageDto
    {
        Id       = m.Id,
        ChatId   = m.ChatId,
        SenderId = m.SenderId,
        Content  = m.Content,
        SentAt   = m.SentAt,
        EditedAt = m.EditedAt
    };

// Используется в запросе — EF видит Expression и генерирует оптимальный SQL
var messages = await _uow.MessageRepository.GetAll()
    .Where(m => m.ChatId == chatId)
    .Select(MessageProjections.ToDto)   // Expression → SELECT конкретных колонок
    .ToListAsync(ct);

// Func<T, TResult> — скомпилированная версия для in-memory маппинга после материализации
public static readonly Func<Message, ChatMessageDto> ToDtoFunc = ToDto.Compile();
// ToDto.Compile() — одноразовая операция (дорогая), результат кешируется в static поле
Expression vs Func в Where/Select: передавай Expression<Func<...>> в IQueryable-методы (EF Core), Func<...> — в IEnumerable-методы (in-memory). Если перепутаешь — код скомпилируется, но EF выполнит запрос неправильно.

8.3 Захват переменных (closures)

Лямбда может ссылаться на переменные из внешнего scope — это называется замыкание (closure). Компилятор создаёт скрытый класс, который хранит захваченные переменные. Важно понимать: захватывается переменная (ссылка на ячейку памяти), а не её значение в момент создания. 

// ChatService.cs — лямбда захватывает me из внешнего scope.
// EF Core транслирует me в параметр SQL-запроса (@p0)
var me = _currentUser.Id;
var query = _uow.ChatRepository.GetAll()
    .Where(c => c.Members.Any(m => m.UserId == me));
// SQL: WHERE EXISTS (SELECT 1 FROM ChatMembers WHERE UserId = @p0)

// ЛОВУШКА: захват loop-переменной — все лямбды ссылаются на одну и ту же i
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
    actions.Add(() => Console.WriteLine(i));  // ПЛОХО: все выведут 3

// ПРАВИЛЬНО: захватить копию через локальную переменную
for (int i = 0; i < 3; i++)
{
    int copy = i;
    actions.Add(() => Console.WriteLine(copy));  // каждая лямбда держит свой copy
}
// foreach в C# 5+ делает это автоматически — захватывает копию итерационной переменной

9. LINQ

9.1 Что такое LINQ и как он работает

LINQ (Language Integrated Query) — набор методов расширения для работы с последовательностями данных. Одни и те же операторы (Where, Select, OrderBy) работают с разными источниками: IEnumerable<T> (коллекции в памяти) и IQueryable<T> (EF Core — переводит в SQL).

Ключевое понятие — отложенное выполнение: методы LINQ строят описание запроса, но не выполняют его. Реальное выполнение происходит только при материализации — вызове ToListAsync(), ToArrayAsync(), ToDictionaryAsync(), FirstOrDefaultAsync(), CountAsync() или итерации в foreach.

9.2 Отложенное vs немедленное выполнение

// IQueryable<T> — запрос строится, но SQL не выполняется
IQueryable<Message> query = _uow.MessageRepository.GetAll()  // нет обращения к БД
    .Where(m => m.ChatId == chatId)                            // добавляет WHERE к запросу
    .OrderByDescending(m => m.SentAt);                        // добавляет ORDER BY

// Добавляй фильтры ДО материализации
if (before.HasValue)
    query = query.Where(m => m.SentAt < before.Value);  // всё ещё IQueryable, SQL не выполнен

// Материализация — здесь уходит SELECT в БД
var messages = await query.Take(limit).ToListAsync(ct);

// IEnumerable — после материализации, выполнение в памяти
var filtered = messages.Where(m => m.Content.Contains("hello")); // in-memory, нет SQL
Ловушка IEnumerable vs IQueryable: если промежуточный метод возвращает IEnumerable<T> вместо IQueryable<T>, дальнейшие .Where() и .Select() выполняются в памяти — вся таблица уже загружена. Всегда материализуй ПОСЛЕ всех фильтров.

9.4 Query syntax vs Method syntax

Оба синтаксиса полностью эквивалентны — компилятор переводит query syntax в method syntax. Method syntax используется чаще: короче, хорошо сочетается с цепочками. Query syntax удобен для сложных join-ов с let — читается ближе к SQL. 

// ChatService.cs — query syntax с let для промежуточной переменной
var baseQuery =
    from c in _uow.ChatRepository.GetAll(nameof(Chat.Members))
    where c.Members.Any(m => m.UserId == me)
    let lastMsg = _uow.MessageRepository.GetAll()
                      .Where(m => m.ChatId == c.Id)
                      .OrderByDescending(m => m.SentAt)
                      .FirstOrDefault()
    orderby (lastMsg != null ? lastMsg.SentAt : c.CreatedAt) descending
    select new { Chat = c, LastMessage = lastMsg };

// Метод-синтаксис — тот же запрос, другой стиль записи
var baseQuery = _uow.ChatRepository.GetAll(nameof(Chat.Members))
    .Where(c => c.Members.Any(m => m.UserId == me))
    .Select(c => new
    {
        Chat = c,
        LastMessage = _uow.MessageRepository.GetAll()
            .Where(m => m.ChatId == c.Id)
            .OrderByDescending(m => m.SentAt)
            .FirstOrDefault()
    })
    .OrderByDescending(x => x.LastMessage != null ? x.LastMessage.SentAt : x.Chat.CreatedAt);

9.5 Паттерн limit+1 — пагинация без COUNT(*)

// ContactsService.cs — строим запрос, условно добавляем курсорный фильтр, материализуем один раз
var query = _uow.ContactRepository.GetAll()
    .Where(c => c.UserId == currentUserId);

if (before.HasValue)
    query = query.Where(c => c.CreatedAt < before.Value);

var rows = await query
    .OrderByDescending(c => c.CreatedAt)
    .Take(limit + 1)          // берём на 1 больше — чтобы проверить HasMore без COUNT(*)
    .Select(ContactProjections.ToDto)
    .ToListAsync(ct);          // ← единственный SQL-запрос

bool hasMore = rows.Count == limit + 1;
var items = hasMore ? rows.Take(limit).ToList() : rows;  // in-memory срез лишней записи

return new PagedResult<ContactDto>
{
    Items      = items,
    HasMore    = hasMore,
    NextBefore = items.LastOrDefault()?.CreatedAt
};
Правило "limit + 1": вместо отдельного SELECT COUNT(*) запрашиваем на одну запись больше нужного. Если вернулось limit + 1 записей — следующая страница есть, лишнюю отрезаем. Итого один SQL-запрос вместо двух. NextBefore — курсор для следующего запроса: клиент передаёт его в параметре before.

10. Async / Await

10.1 Зачем async/await и как это работает

ASP.NET Core обслуживает каждый HTTP-запрос на потоке из пула (thread pool). Пул ограничен — обычно несколько десятков потоков на ядро. Если поток синхронно ждёт ответа от БД или внешнего API, он заблокирован и не может взять новый запрос. При 50 одновременных «медленных» запросах пул исчерпан, новые запросы ждут в очереди — сервер деградирует.

await решает это: он возвращает поток в пул на время ожидания IO. Когда IO завершается, продолжение метода возобновляется на свободном потоке. Компилятор превращает async-метод в машину состояний — это происходит на этапе сборки, не в рантайме.

10.2 Task, async/await — базовый паттерн

// Любой метод с IO (БД, файлы, сеть, SignalR) — async Task
// async Task<T> — возвращает результат, async Task — аналог void для async
public async Task<PagedResult<ChatListItemDto>> GetUserChatsAsync(
    Guid me, int limit, DateTime? before, CancellationToken ct)
{
    var rows = await baseQuery.ToListAsync(ct);         // поток освобождён на время SQL
    var map  = await unreadQuery.ToDictionaryAsync(..., ct);  // снова await
    return BuildResult(rows, map);                        // нет await — синхронная сборка
}

// Вызов из контроллера — await пробрасывается наверх
var result = await _chatService.GetUserChatsAsync(me, limit, before, ct);
return Ok(result);

Правила async/await

10.3 CancellationToken — отмена операций

CancellationToken — механизм кооперативной отмены. Клиент (контроллер, SignalR-хаб) получает токен от фреймворка и передаёт его вниз по цепочке. Если клиент закрыл вкладку или соединение — токен отменяется, все awaited вызовы с этим токеном бросают OperationCanceledException. Сервер прекращает бесполезную работу. 

// Контроллер — токен приходит из ASP.NET Core автоматически через [FromServices] или параметр
[HttpGet]
public async Task<IActionResult> GetChats([FromQuery] GetChatsRequest req, CancellationToken ct)
{
    var result = await _chatService.GetUserChatsAsync(me, req.Limit, req.Before, ct);
    return Ok(result);
}

// Сервис — принимает ct и пробрасывает во все async-вызовы
public async Task<PagedResult<ChatListItemDto>> GetUserChatsAsync(
    Guid me, int limit, DateTime? before, CancellationToken ct = default)
{
    var rows = await baseQuery.ToListAsync(ct);         // ct прокидывается в EF
    var map  = await query.ToDictionaryAsync(..., ct);
    return ...;
}

// Repository — ct доходит до самого нижнего вызова
public async Task<T?> GetAsync(Guid id, CancellationToken ct = default)
    => await _dbSet.FindAsync(new object[] { id }, ct);

// ChatHub.cs — SignalR предоставляет свой токен через Context.ConnectionAborted
// Он срабатывает когда клиент отключается от WebSocket
var ct = Context.ConnectionAborted;
var messages = await _chatService.GetMessagesAsync(me, chatId, limit, before, ct);

// Обработка OperationCanceledException в контроллере — это не ошибка

{

}
Правило WebMessenger: каждый публичный async-метод принимает CancellationToken ct = default последним параметром и передаёт его во все вложенные async-вызовы. = default делает параметр необязательным — удобно для unit-тестов, где токен не нужен.

10.4 Task.WhenAll — параллельное выполнение

Последовательный await выполняет задачи одну за другой. Если задачи независимы, их можно запустить параллельно через Task.WhenAll — общее время ожидания равно времени самой медленной задачи, а не их сумме. 

// МЕДЛЕННО: последовательно — totalTime = t1 + t2
var profile = await _userService.GetProfileAsync(userId, ct);
var avatar  = await _fileStorage.GetDirectLinkAsync(avatarPath, ct);

// БЫСТРО: параллельно — totalTime = max(t1, t2)
// Запускаем обе задачи сразу (без await), затем ждём обе вместе
var profileTask = _userService.GetProfileAsync(userId, ct);
var avatarTask  = _fileStorage.GetDirectLinkAsync(avatarPath, ct);
await Task.WhenAll(profileTask, avatarTask);

var profile = profileTask.Result;   // уже завершён — .Result безопасен после WhenAll
var avatar  = avatarTask.Result;

// Альтернатива — await каждый после WhenAll (компилятор знает что Task уже завершён)
var profile = await profileTask;
var avatar  = await avatarTask;
Task.WhenAll и исключения: если несколько задач бросили исключения, WhenAll оборачивает их в AggregateException. При await Task.WhenAll(...) пробрасывается первое исключение. Для доступа ко всем — проверяй task.Exception?.InnerExceptions на каждой задаче отдельно.

10.5 ConfigureAwait и контекст синхронизации

В ASP.NET Core нет SynchronizationContext — после await продолжение выполняется на любом потоке пула. Поэтому ConfigureAwait(false) в серверном коде не нужен (в отличие от WPF/WinForms, где он обязателен в library-коде). В WebMessenger его нет нигде — это нормально. 

// В library-коде (NuGet пакеты, shared libraries) — принято писать ConfigureAwait(false)
// чтобы не захватывать UI-контекст у потребителей библиотеки
await someTask.ConfigureAwait(false);  // в ASP.NET Core не нужен, но не вреден

// В WebMessenger — просто await без ConfigureAwait
var result = await _uow.ChatRepository.GetAll().ToListAsync(ct);

10.6 Task.Delay vs Thread.Sleep, async void

// Task.Delay — async, НЕ блокирует поток. Использовать в async-коде.
await Task.Delay(TimeSpan.FromSeconds(5), ct);  // ct — отмена задержки

// Thread.Sleep — БЛОКИРУЕТ поток. Плохо в ASP.NET Core.
Thread.Sleep(5000);  // поток занят, не берёт новые запросы

// async void — только для event-handler (Window.Loaded, Button.Click)
// Исключение внутри async void НЕ поймать через try/catch снаружи — приложение упадёт
private async void OnButtonClick(object sender, EventArgs e)  // допустимо
{
    await DoSomethingAsync();
}

// В WebMessenger async void нет нигде — все методы возвращают Task
Три антипаттерна async: .Result / .Wait() — синхронная блокировка в async-контексте → deadlock; async void в обычном коде → непойманные исключения; new Thread(...) или Task.Run(...) для IO-операций — IO не требует нового потока, await достаточно.

11. Runtime Fundamentals — Основы CLR

11.1 CLR, IL, JIT — путь от C# до машинного кода

Когда ты нажимаешь «Build», компилятор C# (Roslyn) переводит код не в машинный код напрямую, а в IL (Intermediate Language) — платформенно-независимый байткод, который хранится в .dll/.exe. При первом вызове метода CLR запускает JIT-компилятор, который переводит IL в нативный машинный код конкретной платформы и кеширует его. Повторный вызов того же метода работает уже на нативном коде — без JIT.

11.2 Value types vs Reference types

Все типы C# делятся на две категории по способу хранения данных в памяти. Это влияет на поведение при копировании, производительность и способ сравнения.

// DateTime — value type. Сравнение == сравнивает значения
var t1 = DateTime.UtcNow;

// class — reference type. Переменная хранит ссылку

11.3 Boxing и Unboxing

Boxing — упаковка value type в объект на куче. Происходит неявно при присваивании value type переменной типа object или интерфейса. Создаёт heap allocation и давление на GC — избегай в hot path. 

// Boxing — неявная упаковка Guid в object[]
await _dbSet.FindAsync(new object[] { id }, ct);
// id (Guid, 16 байт на стеке) → упаковывается в object на куче

// Явный boxing / unboxing
object boxed   = 42;          // boxing: int → heap
int    unboxed = (int)boxed;  // unboxing: heap → stack, требует приведения типа

// Типичная ловушка: интерполяция/конкатенация DateTime — boxing
string s = "Time: " + DateTime.UtcNow;  // DateTime (struct) упаковывается для ToString()
// Лучше: string s = $"Time: {DateTime.UtcNow:O}";

// Обобщённые коллекции List<T>, Dictionary<K,V> — НЕ боксируют
// В отличие от ArrayList (устаревший) — там хранится object[]
var ids = new List<Guid>();   // нет boxing — Guid хранится as-is

11.4 Stack vs Heap — где живут данные

// Стек — быстрый, автоматически очищается при выходе из метода
// Хранит: локальные переменные value type, параметры методов, return address
void Process()
{
    int count = 0;       // на стеке
    Guid id = Guid.NewGuid();  // на стеке
    // при выходе из метода — всё сразу освобождается
}

// Куча — управляется GC, дольше аллоцировать, нет детерминированного времени освобождения
// Хранит: все объекты классов, массивы, строки, боксированные value types
var message = new Message();      // на куче
var list    = new List<Guid>();   // List-объект на куче, внутренний массив тоже

// Span<T> / stackalloc — выделение на стеке без GC (advanced, .NET 8)
Span<byte> buffer = stackalloc byte[256];  // 256 байт на стеке — нет heap allocation
В WebMessenger большинство кода работает с heap-объектами (DTO, EF-сущности, списки) — это нормально. Оптимизации на уровне Span/stackalloc применяются только там, где профилирование показало узкое место. Преждевременная оптимизация усложняет код без измеримой пользы.

12. Garbage Collector — Сборщик мусора

12.1 Как работает GC

CLR автоматически освобождает управляемые объекты (все классы C#) через Garbage Collector. GC работает по принципу поколений: объекты создаются в поколении 0 (Gen0), выжившие переходят в Gen1, затем в Gen2. Большинство временных объектов умирает в Gen0 — сборка Gen0 быстрая и частая. Gen2 собирается редко, но дольше (full GC).

ПоколениеЧто хранитКак часто собирается
Gen0Новые объекты (DTO, временные переменные)Часто, быстро (~мс)
Gen1Объекты, пережившие одну сборку Gen0Реже
Gen2Долгоживущие объекты (кеши, Singleton-сервисы)Редко, full GC (~десятки мс)
LOH (Large Object Heap)Объекты ≥ 85 000 байт (большие массивы, строки)Вместе с Gen2; не компактируется по умолчанию
// GC отслеживает корни (roots): локальные переменные, статические поля, GC handles
// Объект живёт, пока на него есть хоть одна ссылка из корня

// Большой список DTO — Gen0, быстро умрёт после запроса
var items = await query.ToListAsync(ct);   // создаётся в Gen0
return Ok(items);                           // после отправки — нет ссылок → GC соберёт

// Singleton с кешем — живёт в Gen2 всё время работы приложения
private static readonly ConcurrentDictionary<Guid, UserDto> _cache = new();
// Не забывай инвалидировать — иначе утечка памяти через Gen2

12.2 Управляемые vs неуправляемые ресурсы

GC освобождает только управляемую память. Для неуправляемых ресурсов (файловые дескрипторы, сетевые сокеты, нативные хэндлы, БД-соединения) нужен явный детерминированный сброс через IDisposable. Иначе ресурс «утечёт» до следующего GC. 

// UnitOfWork.cs — реализует IDisposable, чтобы явно закрыть DbContext
// DbContext держит открытое соединение с БД — его нельзя ждать GC
public class UnitOfWork : IUnitOfWork, IDisposable
{
    private readonly ApplicationDbContext _context;

    public void Dispose() => _context.Dispose();  // возвращает соединение в пул
}

// using declaration (C# 8) — Dispose вызывается при выходе из scope
// Гарантирует освобождение даже при исключении
using var stream = File.OpenRead(filePath);
var data = await JsonSerializer.DeserializeAsync<Config>(stream);
// ← здесь stream.Dispose() вызывается автоматически

// await using — для IAsyncDisposable
// DbTransaction, некоторые стримы требуют async-очистки
await using var tx = await _context.Database.BeginTransactionAsync(ct);
try
{
    await DoWorkAsync(ct);
    await tx.CommitAsync(ct);
}
catch
{
    await tx.RollbackAsync(ct);
    throw;
}
// await tx.DisposeAsync() вызывается автоматически
В WebMessenger UnitOfWork зарегистрирован как Scoped — DI-контейнер ASP.NET Core сам вызовет Dispose() в конце каждого HTTP-запроса. Явный using нужен только для объектов, создаваемых внутри метода (стримы, транзакции).

12.3 Финализаторы и WeakReference

// Финализатор (~ClassName) — вызывается GC перед сборкой объекта
// Нужен только если класс напрямую владеет неуправляемым ресурсом (нативный хэндл)
// В WebMessenger финализаторов нет — все ресурсы обёрнуты в SafeHandle / IDisposable
public class NativeWrapper : IDisposable
{
    private IntPtr _handle;
    private bool _disposed;

    ~NativeWrapper() => Dispose(false);       // финализатор — fallback

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);            // отменить финализатор — он уже не нужен
    }

    private void Dispose(bool disposing)
    {
        if (_disposed) return;
        // освободить нативный хэндл
        _disposed = true;
    }
}

// WeakReference<T> — ссылка, которая не мешает GC собрать объект
// Используется для кешей: если GC решил собрать — кеш просто промахнётся
var weakRef = new WeakReference<UserDto>(userDto);
if (weakRef.TryGetTarget(out var cached))
    return cached;   // объект ещё жив
// иначе — перезагрузить из БД
Правило: если класс реализует IDisposable — всегда используй его через using или убедись, что DI-контейнер сделает это за тебя (Scoped/Transient сервисы). Никогда не полагайся на финализатор как основной механизм освобождения.

13. I/O, File System, and Networking

13.1 Stream — абстракция потока данных

Stream — базовый класс для любого последовательного чтения/записи данных: файлы, сеть, память, сжатие. Ключевое свойство — данные читаются порциями, не целиком в память. Это критично для больших файлов (аватары, вложения): вместо загрузки всего файла в byte[] стрим передаёт данные «кусками» напрямую в HTTP-ответ. 

// AvatarController.cs — отдать файл клиенту через стрим, не загружая в память целиком
await using var stream = new FileStream(
    filePath,
    FileMode.Open,
    FileAccess.Read,
    FileShare.Read,
    bufferSize: 4096,
    useAsync: true);     // useAsync: true — OS-level async IO, не блокирует поток

await stream.CopyToAsync(Response.Body, ct);  // 4096 байт за раз → в HTTP-ответ

// IFormFile — загружаемый файл от клиента тоже приходит как Stream
await using var uploadStream = file.OpenReadStream();
await _fileStorage.UploadAsync(uploadStream, path, ct);

// MemoryStream — стрим в памяти. Удобен для тестов и промежуточных операций
await using var ms = new MemoryStream();
await originalStream.CopyToAsync(ms, ct);
ms.Position = 0;   // сброс позиции перед повторным чтением
var bytes = ms.ToArray();

13.3 ZIP-архивы — ZipArchive и ZipFile

System.IO.Compression содержит классы для работы с ZIP-архивами. Два основных инструмента: ZipFile — статические хелперы для простых операций (создать архив из папки, распаковать в папку), ZipArchive — полный контроль: читать/добавлять отдельные записи, работать через Stream без создания файлов на диске. 

// ZipFile — простые операции с файлами на диске
using System.IO.Compression;

// Создать ZIP из папки
ZipFile.CreateFromDirectory(
    sourceDirectoryName: @"uploads/user-123",
    destinationArchiveFileName: @"export/user-123.zip",
    compressionLevel: CompressionLevel.Optimal,
    includeBaseDirectory: false);   // false — не включать имя корневой папки

// Распаковать ZIP в папку
ZipFile.ExtractToDirectory(
    sourceArchiveFileName: "export/user-123.zip",
    destinationDirectoryName: "restored/user-123",
    overwriteFiles: true);

// Открыть существующий архив для чтения
using var zip = ZipFile.OpenRead("archive.zip");
foreach (var entry in zip.Entries)
    Console.WriteLine($"{entry.FullName}  {entry.Length:N0} bytes");
// ZipArchive — работа через Stream. Полезно для:
// - создания ZIP в памяти (без файла на диске) для HTTP-ответа
// - добавления отдельных записей по одной
// - чтения конкретной записи без распаковки всего архива

// Создать ZIP в памяти и вернуть как файл-ответ в контроллере
public async Task<IActionResult> DownloadUserFiles(Guid userId, CancellationToken ct)
{
    var ms = new MemoryStream();  // не using — поток должен жить до File()

    using (var archive = new ZipArchive(ms, ZipArchiveMode.Create, leaveOpen: true))
    // leaveOpen: true — не закрывать ms когда archive Dispose'ится
    {
        var files = await GetUserFilesAsync(userId, ct);

        foreach (var file in files)
        {
            // Добавить запись в архив
            var entry = archive.CreateEntry(file.Name, CompressionLevel.Optimal);
            await using var entryStream = entry.Open();
            await using var fileStream  = File.OpenRead(file.LocalPath);
            await fileStream.CopyToAsync(entryStream, ct);
        }
    }
    // После using-блока archive Disposed — данные записаны в ms

    ms.Position = 0;  // сброс позиции перед отдачей
    return File(ms, "application/zip", $"user-{userId}-files.zip");
}
// Читать конкретную запись из архива по имени — без распаковки всего
await using var fs      = File.OpenRead("archive.zip");

// Optimal    — баланс скорости и размера (по умолчанию для большинства случаев)

// NoCompression — только упаковка без сжатия (PDF, JPEG уже сжаты — сжатие не даст выигрыша)

13.4 HttpClient и HttpClientFactory

HttpClient — основной инструмент для HTTP-запросов к внешним API. Его нельзя создавать через new HttpClient() в каждом запросе: сокеты остаются в состоянии TIME_WAIT после закрытия и при интенсивной нагрузке порты исчерпываются (socket exhaustion). Правильное решение — IHttpClientFactory, который переиспользует соединения через пул. 

// Program.cs — регистрация именованного клиента
builder.Services.AddHttpClient("dropbox", client =>
{
    client.BaseAddress = new Uri("https://api.dropboxapi.com/");
    client.DefaultRequestHeaders.Add("User-Agent", "WebMessenger/1.0");
    client.Timeout = TimeSpan.FromSeconds(30);
});

// Сервис — получает фабрику, создаёт клиент по имени
public class DropboxFileStorage(IHttpClientFactory httpClientFactory, ...)
{
    public async Task UploadAsync(Stream stream, string path, CancellationToken ct)
    {
        using var client = _httpClientFactory.CreateClient("dropbox");
        using var content = new StreamContent(stream);
        var response = await client.PostAsync("2/files/upload", content, ct);
        response.EnsureSuccessStatusCode();
    }
}

// HttpResponseMessage — работа с ответом
var response = await client.GetAsync(url, ct);
response.EnsureSuccessStatusCode();                         // бросает при 4xx/5xx
var json = await response.Content.ReadAsStringAsync(ct);
var dto  = await response.Content.ReadFromJsonAsync<MyDto>(ct);  // авто-десериализация
Никогда не создавай new HttpClient() в методе — socket exhaustion. Никогда не делай using var client = new HttpClient() в Singleton-сервисе — клиент не увидит DNS-изменения. Всегда используй IHttpClientFactory.

13.5 WebSocket и SignalR — постоянное соединение

HTTP-запрос — это соединение «открыть → запрос → ответ → закрыть». WebSocket — двунаправленный постоянный канал: сервер может пушить данные клиенту в любой момент без нового запроса. SignalR — библиотека Microsoft, надстройка над WebSocket (с fallback на Server-Sent Events и Long Polling). 

// ChatHub.cs — SignalR Hub — точка подключения WebSocket-клиентов
// Каждое подключение = отдельный экземпляр Hub (Transient-like)
public class ChatHub(IChatService chatService, IChatEvents chatEvents, ...)
    : Hub<IChatHubClient>, IEventHandler
{
    // Клиент подключился — подписаться на события
    public override async Task OnConnectedAsync()
    {
        _chatEvents.Subscribe(me, this);
        await base.OnConnectedAsync();
    }

    // Клиент вызывает серверный метод (RPC через WebSocket)
    public async Task SendMessage(SendMessageRequest req)
    {
        var ct = Context.ConnectionAborted;   // токен отменяется при дисконнекте
        await _chatService.SendMessageAsync(me, req, ct);
    }

    // Сервер пушит событие клиенту (IChatHubClient — типизированный контракт)
    public async Task OnMessageCreatedAsync(ChatMessageDto message, CancellationToken ct)
        => await Clients.Caller.ReceiveMessage(message);
}

// Program.cs — регистрация SignalR и маппинг хаба
builder.Services.AddSignalR();
app.MapHub<ChatHub>("/hubs/chat");
Context.ConnectionAborted — CancellationToken, который срабатывает при разрыве WebSocket-соединения. Передавай его во все async-вызовы внутри Hub-методов — сервер прекратит работу, если клиент отключился до завершения запроса.

14.6 Base64 и UTF-8/BOM

Base64 — кодирование бинарных данных (байты) в ASCII-строку для передачи по каналам, где бинарные данные недопустимы: JSON-поля, HTTP-заголовки, email-вложения. Коэффициент разрастания ~1.33× (3 байта → 4 символа).

UTF-8 и BOM. UTF-8 — стандартная кодировка в .NET 8 для всех строк, файлов и JSON. BOM (Byte Order Mark, 0xEF 0xBB 0xBF) — необязательная метка в начале файла. Encoding.UTF8 (new UTF8Encoding(encoderShouldEmitUTF8Identifier: false)) — без BOM. new UTF8Encoding(true) — с BOM. JSON без BOM — стандарт RFC 8259. 

// Base64 — кодирование/декодирование

string base64 = Convert.ToBase64String(avatarBytes);
// "/9j/4AAQSkZJRgAB..." — ASCII-безопасная строка

// Decode: строка → байты (для сохранения файла)
byte[] decoded = Convert.FromBase64String(base64);
await File.WriteAllBytesAsync("restored.jpg", decoded);

// Data URL — распространённый формат для передачи изображений в браузер
string dataUrl = $"data:image/jpeg;base64,{base64}";

// TryFromBase64String — без исключения при неверном формате
byte[] buffer = new byte[Base64.GetMaxDecodedFromUtf8Length(base64.Length)];
if (Convert.TryFromBase64String(base64, buffer, out int bytesWritten))
    Console.WriteLine($"Decoded {bytesWritten} bytes");
else
    Console.WriteLine("Invalid Base64");
// Encoding.UTF8 — без BOM (стандарт для JSON, REST API, файлов)
// Это свойство System.Text.Encoding.UTF8, которое НЕ добавляет BOM
string json = """{"username":"alice"}""";
byte[] bytes = Encoding.UTF8.GetBytes(json);   // без BOM — RFC 8259

// new UTF8Encoding(encoderShouldEmitUTF8Identifier: true) — С BOM
// Нужно для Windows-инструментов которые требуют BOM (старый Excel, некоторые legacy системы)
var utf8WithBom = new System.Text.UTF8Encoding(encoderShouldEmitUTF8Identifier: true);
await File.WriteAllTextAsync("export.csv", csvContent, utf8WithBom);

// StreamWriter — явно указывать кодировку при записи текстовых файлов
await using var writer = new StreamWriter("log.txt", append: true, encoding: Encoding.UTF8);
await writer.WriteLineAsync("Entry");

// Определить кодировку файла — через BOM в первых байтах
byte[] header = new byte[3];
await using var fs = File.OpenRead("unknown.txt");

15.2 IOptions<T> — strongly typed конфигурация

Прямое чтение через configuration["Key"] возвращает строку — нет типобезопасности и нет валидации при старте. IOptions<T> привязывает секцию конфигурации к POCO-классу с DataAnnotations, и если что-то не так — приложение падает при старте, а не при первом запросе. 

// JwtOptions.cs — POCO с DataAnnotations
public class JwtOptions
{
    public const string SectionName = "Jwt";

    [Required][MinLength(32)]        // ключ ≥ 32 символа, иначе HMAC-SHA256 небезопасен
    public required string Key { get; init; }

    [Range(1, 365)]
    public int ExpireDays { get; init; } = 7;
}

// Program.cs — регистрация с валидацией при старте приложения

    .BindConfiguration(JwtOptions.SectionName)   // секция "Jwt" → JwtOptions
    .ValidateDataAnnotations()                     // проверить [Required], [MinLength], ...
    .ValidateOnStart();                            // если ошибка — не стартовать

16. Dependency Injection — Внедрение зависимостей

16.1 Зачем DI и как работает контейнер

Dependency Injection — паттерн, при котором объект не создаёт свои зависимости сам через new, а получает их снаружи. Это даёт:

  • Тестируемость — в тестах можно подменить реальный сервис на mock
  • Слабую связность — класс зависит от интерфейса, а не от конкретной реализации
  • Управление временем жизни — контейнер решает, когда создать и уничтожить объект

В ASP.NET Core DI-контейнер встроен. При каждом HTTP-запросе он строит граф зависимостей: видит, что ContactsController требует IContactsService, IContactsService требует IUnitOfWork, IUnitOfWork требует ApplicationDbContext — и создаёт всё автоматически.

16.2 Регистрация сервисов — Program.cs

builder.Services.AddScoped<IAuthService,     AuthService>();
