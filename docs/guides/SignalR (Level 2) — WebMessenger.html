SignalR (Level 2) — WebMessenger

Продвинутый практический гайд по SignalR с учетом текущего состояния WebMessenger: typed contracts, security, token lifecycle, observability, limits и производительность.

Проект: ASP.NET Core 8 + SignalR + Serilog + Next.js client

1. Auth Pipeline: от браузера до Hub метода

Как сейчас устроено в WebMessenger

  • Hub защищен [Authorize].
  • JWT достается в JwtBearerEvents.OnMessageReceived для пути /hubs/chat.
  • Источник токена: сначала access_token query, потом cookie auth-token.
// Program.cs
options.Events = new JwtBearerEvents
{
    OnMessageReceived = context =>
    {
        var path = context.HttpContext.Request.Path;
        if (path.StartsWithSegments("/hubs/chat"))
        {
            if (context.Request.Query.TryGetValue("access_token", out var tokenFromQuery))
            {
                context.Token = tokenFromQuery;
                return Task.CompletedTask;
            }
            if (context.Request.Cookies.TryGetValue("auth-token", out var tokenFromCookie))
            {
                context.Token = tokenFromCookie;
                return Task.CompletedTask;
            }
        }
        return Task.CompletedTask;
    }
};

End-to-end последовательность

  1. Клиент инициирует negotiate/connect к /hubs/chat.
  2. Токен попадает в pipeline через query/cookie.
  3. JWT middleware валидирует подпись, issuer, audience, lifetime.
  4. Если токен валиден, Hub методы получают доступ к Context.User.
  5. Если нет - подключение/вызовы завершаются 401/403.
Это хороший production pattern: единая auth-модель для REST и SignalR.

2. Types и contracts: что уже внедрено и зачем это важно

Текущее состояние

  • На сервере: typed hub ChatHub : Hub<IChatClient>.
  • На сервере: payload records (MessageCreatedPayload, ReadReceiptPayload, TypingPayload).
  • На клиенте: единые константы событий/методов + TS payload-типы.

Почему это Level 2

  • Снижается число runtime-ошибок из-за строковых опечаток.
  • Контракт становится "проверяемым" компилятором.
  • Проще делать постепенную эволюцию API событий.
// Серверный контракт клиента
public interface IChatClient
{
    Task MessageCreated(MessageCreatedPayload payload, CancellationToken ct = default);
    Task ReadReceipt(ReadReceiptPayload payload, CancellationToken ct = default);
    Task Typing(TypingPayload payload, CancellationToken ct = default);
}

Правила versioning для realtime payload

  • Добавление nullable-поля обычно безопасно.
  • Переименование/удаление поля требует синхронного релиза клиента.
  • Для несовместимых изменений лучше вводить новую версию события.

3. Access Token Storage: practical security trade-offs

Как сделано сейчас

  • Базовое хранение токена: HttpOnly cookie auth-token.
  • Для SignalR клиент получает токен через route /api/auth/token.
// route.ts
const jwt = jar.get('auth-token')?.value;
if (!jwt) return NextResponse.json({ error: 'No auth token' }, { status: 401 });
return NextResponse.json({ token: jwt });

Плюсы схемы

  • Основной auth не завязан на localStorage.
  • Cookie удобны для SSR/edge.

Риски, которые нельзя игнорировать

  • Токен все равно становится доступным JS после вызова /api/auth/token.
  • При XSS атаке attacker может использовать этот endpoint.

Минимальный hardening checklist

  • Строгая CSP без лишних inline/script-src wildcard.
  • Ограничение сторонних скриптов.
  • Редакция логов, чтобы токены не попадали в plain text.
  • Короткий lifetime access token + аккуратный re-auth UX.

4. Access Token Expiration и reconnect стратегия

Что важно понять

В SignalR проблема истечения токена проявляется не только при первом connect, но и в момент автоматического reconnect после разрыва канала.

Текущая основа в проекте

  • ValidateLifetime = true на сервере.
  • На клиенте включен withAutomaticReconnect.
  • Добавлен централизованный lifecycle reconnect-подписок.

Практический сценарий отказа

  1. Соединение было стабильно.
  2. Сеть временно пропала и запустился reconnect.
  3. К этому моменту JWT уже истек.
  4. Reconnect получает 401, пользователь "застревает" без realtime.

Что обязательно сделать на клиенте

  • Обработать onclose и классифицировать auth-failure.
  • Показывать пользователю понятное состояние: "сессия истекла".
  • Запускать controlled flow переавторизации.
// Идея обработки
connection.onclose((err) => {
  if (isAuthError(err)) {
    redirectToLogin();
    return;
  }
  scheduleReconnectUiState();
});
Automatic reconnect это не замена auth lifecycle. Это только транспортная устойчивость.

6. ConnectionId, ConnectionToken и identity boundary

Правильная модель

  • ConnectionId это технический ID канала, не user identity.
  • ConnectionToken это internal protocol artifact, не доменная сущность.
  • Источник прав всегда JWT claims + серверная проверка membership.

Где ConnectionId полезен

  • техническая диагностика connect/disconnect;
  • исключение текущего отправителя из broadcast (как в Typing через GroupExcept);
  • корреляция сетевых инцидентов в логах.
// Текущий паттерн Typing без echo отправителю
await _chatEvents.TypingAsync(chatId, me.Value, isTyping,
    excludeConnectionId: Context.ConnectionId, ct: ct);

7. Logging и observability для SignalR

Цель Level 2 наблюдаемости

Не просто "логировать побольше", а сделать систему, где можно быстро ответить на вопросы: кто отвалился, почему не пришло событие, где узкое место.

Что логировать

  • Lifecycle: connected/disconnected/reconnecting/reconnected.
  • Hub methods: имя метода, длительность, результат.
  • Broadcast: имя события, target type (chat/user/dm), размер payload bucket.
  • Auth failures: счетчик и контекст (без токенов).

Что не логировать

  • JWT целиком.
  • Полный текст сообщений в production логах.
  • Любые секреты/PII без redaction.

Операционные метрики, которые стоит завести

  • Reconnect success rate.
  • Hub invocation error rate по методам.
  • P95/P99 latency для JoinChat/Typing/MarkRead.
  • Distribution размера входящих payload.

8. Buffer Management и limits: текущие значения и смысл

Актуальные серверные настройки

options.KeepAliveInterval = TimeSpan.FromSeconds(15);
options.ClientTimeoutInterval = TimeSpan.FromSeconds(30);
options.MaximumReceiveMessageSize = 32 * 1024;

Почему это хороший базовый профиль для чата

  • 15с keepalive помогает быстрее обнаруживать обрыв.
  • 30с timeout не слишком агрессивен, но и не "вечный".
  • 32 KB защищают от случайного/вредоносного oversized input.

Client-side alignment

  • connection.serverTimeoutInMilliseconds = 30_000
  • connection.keepAliveIntervalInMilliseconds = 15_000
Когда сервер и клиент согласованы по таймингам, меньше ложных reconnect и сложных edge-cases в нестабильной сети.

9. Performance: что дает эффект в реальном чате

Приоритеты оптимизации

  1. Снизить частоту лишних событий (typing, read-receipt spam).
  2. Отправлять payload только нужным адресатам (минимальный fan-out).
  3. Сократить размер payload, не дублировать поля.
  4. Убрать лишние subscribe/unsubscribe churn на клиенте.
  5. Держать один стабильный singleton connection на приложение.

Что уже сделано в WebMessenger

  • start guard от гонок conn.start();
  • централизованные reconnect callbacks с unsubscribe;
  • константы событий/методов вместо строк;
  • очистка group membership при cleanup хука.

Следующий разумный шаг

  • добавить клиентский debounce/throttle для Typing (например, 250-400мс);
  • добавить серверный rate-limit на burst.

10. MessagePack: когда действительно стоит внедрять

Что дает MessagePack

  • более компактный формат по сравнению с JSON;
  • меньше network overhead на большом трафике.

Когда переход оправдан

  • метрики показывают, что именно размер/сериализация является bottleneck;
  • высокая частота событий и большой concurrent online;
  • ограниченные каналы (mobile/edge).

Когда лучше отложить

  • если основная проблема в неправильном fan-out или event flood;
  • если контракт payload пока нестабилен.

Безопасный rollout-подход

  1. Сначала стабилизировать и версионировать payload DTO.
  2. Ввести feature flag.
  3. Запустить canary на небольшой группе пользователей.
  4. Сравнить latency/error/CPU до и после.
  5. Только после этого масштабировать rollout.

13. Краткий итог

Текущий WebMessenger уже соответствует крепкому Level 2 фундаменту SignalR: типобезопасные контракты, корректная адресация, выровненные таймауты, управляемый reconnect и разумные ограничения сервера.
