.NET (Level 2) — WebMessenger

Продвинутый практический гайд по C# и .NET с объяснением концепций и примерами из реального проекта WebMessenger. Каждая конструкция разбирается: что это, зачем, когда применять и когда не стоит.

Проект: ASP.NET Core 8 + EF Core + SignalR + Serilog

1. Language Fundamentals

1.1 Nullable Reference Types (NRT)

Что это. Начиная с C# 8 компилятор может статически отслеживать, может ли переменная ссылочного типа принять null. При включённом режиме <Nullable>enable</Nullable> любой string, User, List<T> по умолчанию считается non-nullable. Чтобы явно разрешить null, нужно написать string?, User?.

Зачем. NullReferenceException — самое частое исключение в .NET. NRT переносит обнаружение проблемы с runtime на compile-time: компилятор выдаёт предупреждение (CS8602) там, где вы пытаетесь разыменовать потенциально нулевую ссылку без проверки.

Когда включать. Всегда в новом коде. В legacy-проектах — постепенно, файл за файлом через директиву #nullable enable.

Когда осторожно. NRT — только статические аннотации и предупреждения, они не дают гарантий в runtime. Данные из внешних источников (JSON, БД) могут прийти null даже если тип помечен non-nullable. Там нужна дополнительная runtime-валидация.

// WebMessenger.DAL/Entities/User.cs — NRT в действии
// Bio и AvatarUrl могут быть null — помечены "?"
public string? Bio { get; set; }
public string? AvatarUrl { get; set; }

// Username — обязательное поле, null недопустим.
// "required" + non-nullable = двойная защита:
// компилятор требует задать значение при инициализации объекта
[Required]
[MaxLength(50)]
public required string Username { get; set; }

// -------------------------------------------------------
// Использование в сервисе
// Возвращаем User? — явно сигнализируем: пользователь может не найтись
public async Task<User?> FindUserByUsernameAsync(string username)
{
    return await _unitOfWork.UserRepository.GetAll()
        .FirstOrDefaultAsync(u => u.Username == username);
}

// Без проверки — компилятор выдаст предупреждение CS8602:
// var name = user.Username; // WARN: user может быть null

// С проверкой — flow analysis: ниже user точно non-null
var user = await FindUserByUsernameAsync("alice");
if (user is null) return;
var name = user.Username; // OK

// Null-forgiving operator "!" — явное подавление предупреждения.
// Используйте только когда вы абсолютно уверены что null невозможен,
// а аннотации этого выразить не могут. Злоупотребление убивает смысл NRT.
var forced = user!.Username;
В WebMessenger: #nullable enable включён в ChatHub.cs. Рекомендуется включить во всех файлах через <Nullable>enable</Nullable> в .csproj.

1.2 Pattern Matching

Что это. Механизм для одновременной проверки типа/формы значения и извлечения из него данных в одном выражении. В C# 9–12 значительно расширен: type patterns, property patterns, relational patterns, logical patterns (and/or/not), list patterns.

Зачем. Заменяет цепочки if/else + кастов типов + null-проверок на компактные читаемые выражения. Компилятор умеет проверять exhaustiveness (полноту покрытия вариантов) для switch expressions — если забыл случай, будет предупреждение.

Когда использовать. Когда нужно ветвить логику по типу объекта, по структуре его свойств, по диапазонам значений. Особенно полезно в доменной логике, маппинге, обработке состояний.

Когда не стоит. Не нужно превращать в switch expression всё подряд — если у вас простая однострочная проверка, обычный if читается лучше.

// --- Type pattern ---
// Проверяет тип И приводит к нему одним действием, без явного каста
object result = GetSomeValue();
if (result is string text) // text уже типа string, не нужен (string)result
{
    Console.WriteLine(text.Length);
}

// --- Property pattern ---
// Проверяет значения свойств объекта без явного разворачивания
public string DescribeUser(User? user) => user switch
{
    null                                         => "anonymous",
    { IsOnline: true, Username: var u }          => $"{u} is online",       // онлайн
    { LastSeenAt: var t }
        when (DateTime.UtcNow - t).TotalMinutes < 5 => "just left",       // guard clause
    _                                            => "offline"               // wildcard — default
};
// switch expression (не switch statement) — это expression, у него есть значение
// _ — это wildcard, "всё остальное"

// --- Relational pattern ---
// Для числовых сравнений — короче серии if/else
public static string ClassifyLimit(int limit) => limit switch
{
    <= 0   => "invalid",
    <= 10  => "small",
    <= 200 => "normal",
    _      => "too large"
};

// --- Logical patterns: and / or / not ---
bool isValidPort = port is >= 1024 and <= 65535;
bool isEdgeCase  = limit is 0 or < 0;
bool isNotNull   = obj is not null;

// --- List pattern (C# 11) ---
int[] arr = { 1, 2, 3 };
bool isExactlyThree = arr is [_, _, _]; // ровно 3 элемента
bool startsWithOne  = arr is [1, ..];   // начинается с 1, ".." — остаток

// --- Реальный пример из ChatHub.cs ---
var userId = GetCurrentUserId(); // возвращает Guid?
if (!userId.HasValue)
{
    Context.Abort();
    return;
}
// Компилятор через flow analysis знает: ниже userId.Value безопасен

1.3 Records

Что это. Специальный тип (record class или record struct), для которого компилятор автоматически генерирует: конструктор из параметров, деконструктор, equals/hashcode по значениям полей, ToString, оператор with для создания копии с изменёнными полями.

Зачем. Устраняет boilerplate для иммутабельных объектов передачи данных. Вместо 30+ строк ручного кода — одна строка. Структурная (value) equality вместо reference equality "из коробки".

record class vs record struct. record class — ссылочный тип (heap, reference semantics, но value equality). record struct — значимый тип (stack, copy semantics, ещё меньше аллокаций). Для небольших DTO — record struct.

Когда использовать. DTO, payload для SignalR событий, результаты запросов, конфигурационные объекты — всё, что не меняется после создания.

Когда не стоит. Не для EF Core entity-классов — EF требует mutable properties и change tracking. Не для объектов со сложным жизненным циклом и богатым поведением.

// WebMessenger.Contracts/Models/SignalRPayloads.cs
// Три строки заменяют ~60 строк boilerplate:
public sealed record MessageCreatedPayload(Guid ChatId, Guid? PeerUserId, ChatMessageDto Message);
public sealed record ReadReceiptPayload(Guid ChatId, Guid UserId, DateTime LastReadAt);
public sealed record TypingPayload(Guid ChatId, Guid UserId, bool IsTyping);

// Что компилятор генерирует автоматически:
// 1. Конструктор: new MessageCreatedPayload(chatId, peerId, msg)
// 2. Деконструктор: var (chatId, peer, msg) = payload;
// 3. Equals: два payload равны если ВСЕ поля равны (value equality!)
//    Для class equality по умолчанию = сравнение ссылок (reference equality)
//    Records меняют это поведение
// 4. GetHashCode: по всем полям
// 5. ToString: "MessageCreatedPayload { ChatId = ..., ... }"

// WebMessenger.Contracts/Models/PagedResult.cs — record с init-only свойствами
public sealed record PagedResult<T>
{
    public IReadOnlyList<T> Items { get; init; } = [];
    public bool HasMore { get; init; }
    public DateTime? NextBefore { get; init; }
}

// Оператор "with" — создаёт КОПИЮ с изменёнными полями. Оригинал не тронут.
var page1 = new PagedResult<string> { Items = ["a", "b"], HasMore = true };
var page2 = page1 with { HasMore = false }; // Items те же, HasMore = false

// Value equality в действии:
var p1 = new ReadReceiptPayload(chatId, userId, dt);
var p2 = new ReadReceiptPayload(chatId, userId, dt);
Console.WriteLine(p1 == p2); // true — у обычных классов было бы false!

// Деконструкция позиционного record
var (chat, user, readAt) = payload; // работает автоматически

1.4 Primary Constructors

Что это. C# 12: параметры конструктора указываются прямо в заголовке класса/структуры/record. Компилятор делает их доступными во всём теле класса как captured variables.

Зачем. Убирает шаблонный код инициализации зависимостей. DI-конструкторы в сервисах сокращаются радикально — не нужно объявлять поля и присваивать в теле конструктора.

Нюанс. Для обычных классов primary constructor параметры не становятся автоматически свойствами — они просто захватываются. Если нужно свойство — придётся явно его объявить. Для records всё иначе: там параметры становятся свойствами автоматически.

Когда осторожно. Если параметр конструктора используется тяжело (например, дорогой сервис), лучше сохранить его в readonly поле явно для ясности.

// WebMessenger.Api/Services/AuthService.cs — Primary Constructor
public class AuthService(
    IOptions<JwtOptions> jwtOptions,
    ILogger<AuthService> logger) : IAuthService
{
    // Параметры используются прямо в инициализации полей
    private readonly JwtOptions _jwt = jwtOptions.Value;
    private readonly ILogger<AuthService> _logger = logger
        ?? throw new ArgumentNullException(nameof(logger));
    // jwtOptions и logger доступны в теле класса как captured переменные,
    // но сохранять в readonly поля — хорошая практика для читаемости и тестируемости

    public bool ValidateUserCredentials(User? user, string password)
    {
        // _jwt и _logger доступны здесь
        if (user == null) { _logger.LogWarning("..."); return false; }
        // ...
    }
}

// Сравнение: как это выглядело ДО primary constructors
public class AuthServiceOld : IAuthService
{
    private readonly JwtOptions _jwt;
    private readonly ILogger<AuthServiceOld> _logger;

    public AuthServiceOld(IOptions<JwtOptions> jwtOptions, ILogger<AuthServiceOld> logger)
    {
        _jwt = jwtOptions.Value;
        _logger = logger ?? throw new ArgumentNullException(nameof(logger));
    }
    // Те же 2 параметра, но 7 строк boilerplate вместо 3
}

// Для record — параметры СТАНОВЯТСЯ свойствами:
public record Point(double X, double Y); // X и Y — это свойства!
var p = new Point(1.0, 2.0);
Console.WriteLine(p.X); // OK — X это свойство

// Для class — параметры НЕ являются свойствами:
public class Box(int width, int height)
{
    public int Area => width * height; // width/height — captured vars, не свойства
    // box.Width — не существует снаружи!
}

1.5 Init-only Properties и Required Members

init — модификатор accessor, разрешающий установить свойство только в объектном инициализаторе или конструкторе. После создания объекта свойство становится de-facto readonly.

required (C# 11) — компилятор требует, чтобы свойство было задано при создании объекта. Если его пропустить — ошибка компиляции CS9035.

Зачем. Позволяют строить иммутабельные объекты через object initializer синтаксис — без конструктора с кучей параметров, но с гарантией, что нужные поля заданы.

// WebMessenger.Api/Options/JwtOptions.cs
public class JwtOptions
{
    public const string SectionName = "Jwt";

    [Required]
    [MinLength(32)]
    public required string Key { get; init; }    // обязательно задать, нельзя изменить после

    [Required]
    public required string Issuer { get; init; }

    [Required]
    public required string Audience { get; init; }

    [Range(1, 365)]
    public int ExpireDays { get; init; } = 1;    // необязательное, есть default
}

// При создании — компилятор проверяет наличие required свойств:
var opts = new JwtOptions
{
    Key = "my-super-secret-key-min-32-chars!!",
    Issuer = "WebMessenger",
    Audience = "WebMessenger-Client"
}; // OK

// opts.Key = "other"; // ОШИБКА компиляции: init-only property

// Попытка создать без Key:
// var bad = new JwtOptions { Issuer = "..." }; // ОШИБКА CS9035: required member 'Key' not set

// Разница init vs set:
// set: можно менять в любой момент — dto.Name = "new"
// init: только при создании — после объект "заморожен"
// Используйте init везде, где нет необходимости в мутабельности

1.6 Tuples и Deconstruction

Что это. ValueTuple — легковесный способ вернуть несколько значений из метода без создания отдельного класса. Deconstruction — разбор объекта на части через var (a, b) = obj. Кортежи в C# — value types (структуры), не heap allocation.

Когда использовать. Для внутренней логики, вспомогательных результатов внутри класса, временных промежуточных вычислений. Именованные кортежи — хорошо.

Когда не стоит. В public API — там лучше именованный record или class: документируется лучше, легче эволюционировать.

// Именованный кортеж — читабельнее безымянного
public (bool IsValid, string? Error) ValidateUsername(string username)
{
    if (string.IsNullOrWhiteSpace(username))
        return (false, "Username is required");      // позиционный синтаксис
    if (username.Length > 50)
        return (IsValid: false, Error: "Too long");  // именованный синтаксис
    return (true, null);
}

// Деконструкция результата при вызове
var (isValid, error) = ValidateUsername(dto.Username);
if (!isValid)
    throw new ArgumentException(error);

// Именованные поля кортежа доступны как свойства
var result = ValidateUsername("alice");
Console.WriteLine(result.IsValid);  // true
Console.WriteLine(result.Error);    // null

// Кортежи как составные ключи в словарях (часто удобнее отдельного ключ-класса)
var sessionMap = new Dictionary<(Guid userId, string connId), DateTime>();
sessionMap[(userId, Context.ConnectionId)] = DateTime.UtcNow;

// Деконструкция record — компилятор генерирует Deconstruct автоматически
var payload = new ReadReceiptPayload(chatId, userId, DateTime.UtcNow);
var (chat, user, readAt) = payload; // работает для позиционных record

// Игнорирование ненужных элементов через "_"
var (_, _, readAtOnly) = payload;

1.7 Extension Methods

Что это. Статические методы, которые синтаксически выглядят как методы экземпляра. Первый параметр с ключевым словом this — это объект, на котором метод "вызывается". Позволяют "добавить" методы к типу, который вы не можете модифицировать (sealed классы, интерфейсы из чужой библиотеки, примитивы).

Зачем. Fluent API, обогащение интерфейсов, чистый chain-вызов вместо вложенных функций. LINQ целиком построен на extension methods (Where, Select, ToList и т. д. — всё это extension methods на IEnumerable<T>).

Когда не стоит. Не добавляйте extension methods со сложной логикой или состоянием — это запутает читателя. Не обходите через extension методы OOP-иерархию.

// LINQ — это расширение над IEnumerable<T> через extension methods
// Что на самом деле вызывает компилятор:
users.Where(u => u.IsOnline).ToList();
// Эквивалентно:
Enumerable.ToList(Enumerable.Where(users, u => u.IsOnline));
// Extension method — синтаксический сахар для более читаемой записи

// Свой extension метод — пример для WebMessenger
public static class QueryableExtensions
{
    // "this IQueryable<T> query" — параметр, на котором вызывается метод
    public static IQueryable<T> BeforeDate<T>(
        this IQueryable<T> query,
        DateTime? before,
        Expression<Func<T, DateTime>> selector)
    {
        return before.HasValue
            ? query.Where(...)
            : query; // без фильтра если before == null
    }
}

// Использование — теперь это часть fluent-цепочки:
var messages = _repo.GetAll()
    .Where(m => m.ChatId == chatId)
    .BeforeDate(cursor, m => m.SentAt) // ← extension метод
    .OrderByDescending(m => m.SentAt)
    .Take(limit);

// Extension на string
public static class StringExtensions
{
    public static bool IsNullOrEmpty(this string? s) => string.IsNullOrEmpty(s);
    // Теперь можно: if (username.IsNullOrEmpty()) — вместо string.IsNullOrEmpty(username)
}

// Требования: класс static, метод static, первый параметр с "this"
// Класс обычно размещают в отдельном файле Extensions/ или Helpers/

1.8 Attributes

Что это. Декларативные метаданные, прикрепляемые к типам, методам, свойствам, параметрам. Читаются в runtime через Reflection, или в compile-time через Source Generators/Roslyn Analyzers. Сами по себе не исполняют никакой логики — они только хранят информацию.

Зачем. Управление поведением фреймворков (EF Core строит схему БД, ASP.NET валидирует модели, JSON сериализатор меняет имена) без изменения бизнес-логики. Аннотирование требований к данным. Кастомная метаинформация для своей инфраструктуры.

AttributeTargets — при создании своего атрибута указывается, к чему его можно применять: класс, метод, свойство, параметр и т. д.

// WebMessenger.DAL/Entities/User.cs — атрибуты в действии
[Index(nameof(Username), IsUnique = true)]   // EF Core: создать уникальный индекс в БД
[Index(nameof(Email))]                        // EF Core: обычный индекс для быстрого поиска
public class User
{
    [Key]                        // EF Core: это первичный ключ таблицы
    public Guid Id { get; set; }

    [Required]                   // EF Core: NOT NULL; DataAnnotations: обязательное поле
    [MaxLength(50)]              // EF Core: VARCHAR(50); DataAnnotations: максимум 50 символов
    public required string Username { get; set; }

    [EmailAddress]               // DataAnnotations: проверяет формат email-адреса
    public string Email { get; set; } = string.Empty;

    [Url]                        // DataAnnotations: проверяет формат URL
    [MaxLength(255)]
    public string? AvatarUrl { get; set; }
}

// WebMessenger.Api/Options/JwtOptions.cs — атрибуты для Options Validation
public class JwtOptions
{
    [Required]
    [MinLength(32)]              // ключ минимум 32 символа
    public required string Key { get; init; }

    [Range(1, 365)]              // допустимый диапазон
    public int ExpireDays { get; init; } = 1;
}

// Создание собственного атрибута
[AttributeUsage(
    AttributeTargets.Method,   // только для методов
    AllowMultiple = false,      // один раз на метод
    Inherited = true)]          // наследуется в подклассах
public class RequiresAdminAttribute : Attribute
{
    public string Reason { get; }
    public RequiresAdminAttribute(string reason) => Reason = reason;
}

[RequiresAdmin("Only admins can delete users")]
public async Task DeleteUserAsync(Guid id) { ... }

// Чтение атрибута в runtime через Reflection:
var method = typeof(UserService).GetMethod(nameof(UserService.DeleteUserAsync));
var attr = method?.GetCustomAttribute<RequiresAdminAttribute>();
if (attr is not null)
    logger.LogWarning("Admin-only: {Reason}", attr.Reason);

2. Exceptions & Error Handling

2.1 Иерархия исключений и когда создавать свои

Что это. В .NET все исключения наследуются от System.Exception. Встроенные: ArgumentNullException, InvalidOperationException, UnauthorizedAccessException и т. д. Собственные (custom exceptions) нужны, когда встроенные не выражают семантику вашего домена достаточно точно.

Когда создавать своё исключение. Если вызывающий код должен уметь отдельно ловить эту ситуацию — нужен свой тип. Например, UserNotFoundException vs ChatNotFoundException — разные ситуации, разные обработчики. Если вы просто хотите добавить сообщение — свой тип не нужен, хватит встроенного.

Когда не нужны свои исключения. Не создавайте исключение для каждого edge-case. Для ожидаемых ситуаций (пользователь не найден при поиске) лучше возвращать null или Result<T> — исключения дорогостоящи (захват стектрейса).

// Кастомное исключение — минимальный правильный шаблон.
// Три конструктора — это соглашение .NET, нужны для:
// 1. new UserNotFoundException("message")
// 2. new UserNotFoundException("message", innerException)  — для wrap-паттерна
// 3. Сериализация в некоторых сценариях (legacy, remoting)
public class UserNotFoundException : Exception
{
    public Guid UserId { get; }  // доменные данные — кто именно не найден

    public UserNotFoundException(Guid userId)
        : base($"User '{userId}' not found.")
    {
        UserId = userId;
    }

    public UserNotFoundException(Guid userId, Exception inner)
        : base($"User '{userId}' not found.", inner)
    {
        UserId = userId;
    }
}

// Использование:
public async Task<UserProfileDto> GetUserProfileAsync(Guid userId)
{
    var user = await _unitOfWork.UserRepository.GetAsync(userId);
    if (user is null)
        throw new UserNotFoundException(userId); // семантически точнее InvalidOperationException

    return MapToDto(user);
}

// В WebMessenger используется InvalidOperationException — это нормально
// для небольшого проекта. Свои исключения оправданы при росте и нескольких
// командах, когда разграничение ошибок критично.
public async Task<UserProfileDto> GetUserProfileAsync(Guid userId)
{
    return await _unitOfWork.UserRepository.GetAll()
        .Where(u => u.Id == userId)
        .Select(UserProjections.ToProfileDto)
        .FirstOrDefaultAsync()
        ?? throw new InvalidOperationException("User not found"); // оператор ?? throw
}

2.2 Guard Clauses

Что это. Паттерн раннего выхода: проверка предусловий в самом начале метода с немедленным throw/return, до основной логики. Альтернатива — вложенные if, которые растут вправо и затрудняют чтение.

Зачем. "Happy path" (основная логика) остаётся ненагромождённой и читается прямо. Все граничные случаи вынесены наверх.

ArgumentNullException.ThrowIfNull (C# 10+) и аналоги — статические guard-методы встроенные в BCL, заменяют ручные проверки.

// ПЛОХО — глубокая вложенность, основная логика в конце:
public async Task SendMessageAsync(Guid userId, Guid chatId, string content)
{
    if (userId != Guid.Empty)
    {
        if (chatId != Guid.Empty)
        {
            if (!string.IsNullOrWhiteSpace(content))
            {
                // основная логика здесь, на уровне 3 вложенности
            }
        }
    }
}

// ХОРОШО — guard clauses, основная логика на нулевом уровне:
public async Task SendMessageAsync(Guid userId, Guid chatId, string content)
{
    // Guard clauses — бросаем сразу при нарушении предусловия
    ArgumentNullException.ThrowIfNull(content);               // BCL-метод, C# 10+
    if (userId == Guid.Empty)
        throw new ArgumentException("UserId cannot be empty", nameof(userId));
    if (string.IsNullOrWhiteSpace(content))
        throw new ArgumentException("Content cannot be blank", nameof(content));
    if (content.Length > 4000)
        throw new ArgumentOutOfRangeException(nameof(content), "Message too long");

    // Основная логика — никакой вложенности
    var message = new Message { SenderId = userId, ChatId = chatId, Content = content };
    await _repo.InsertAsync(message);
}

// WebMessenger.Api/Services/UserService.cs — guard в реальном коде:
public async Task<IEnumerable<UserSearchResultDto>> SearchUsersAsync(
    Guid currentUserId, string query, int limit)
{
    if (string.IsNullOrWhiteSpace(query))
        throw new ArgumentException("Search query is required"); // guard clause

    // Далее основная логика — никаких else
    var queryLower = query.ToLower();
    // ...
}

// WebMessenger.Api/Services/AuthService.cs — guard через ?? throw:
private readonly ILogger<AuthService> _logger = logger
    ?? throw new ArgumentNullException(nameof(logger)); // инлайн guard при инициализации

// ArgumentNullException.ThrowIfNull(obj) — эквивалент:
// if (obj is null) throw new ArgumentNullException(nameof(obj));
ArgumentNullException.ThrowIfNull(user);
ArgumentException.ThrowIfNullOrWhiteSpace(username);

2.3 Exception Filters

Что это. Конструкция catch (Exception ex) when (условие) — фильтр, который решает, нужно ли войти в catch-блок. Условие вычисляется до того, как стек раскручивается, поэтому фильтры не мешают отладчику поймать исключение в точке бросания.

Зачем. Позволяет ловить только конкретные подтипы ошибок без отдельных типов исключений. Удобно для транзиентных ошибок (retry-логика), для условной обработки по коду статуса HTTP и т. д.

// Без фильтра — ловим ВСЕ HttpRequestException
try { await httpClient.GetAsync(url); }
catch (HttpRequestException ex)
{
    if (ex.StatusCode == HttpStatusCode.NotFound) { /* 404 */ }
    else if (ex.StatusCode == HttpStatusCode.Unauthorized) { /* 401 */ }
    else throw; // не наше — перебросить
}

// С фильтром — каждый catch ловит только свой случай, чище:
try { await httpClient.GetAsync(url); }
catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.NotFound)
{
    // 404 — ресурс не найден
}
catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.Unauthorized)
{
    // 401 — не авторизован
}
// Остальные HttpRequestException пробросятся дальше

// В WebMessenger — ChatHub.cs ловит по типу исключения (аналогичный паттерн):
try
{
    _ = await _chats.GetMessagesAsync(me, chatId, limit: 1, before: null);
}
catch (UnauthorizedAccessException)
{
    // Специфичный тип — конкретная обработка
    throw new HubException("You are not a member of this chat");
}
catch (Exception ex)
{
    // Всё остальное — логируем и оборачиваем
    _logger.LogError(ex, "Failed membership check for user {UserId}", me);
    throw new HubException("Failed to join chat");
}

// Фильтр для транзиентных ошибок (retry-паттерн)
static bool IsTransient(Exception ex) =>
    ex is TimeoutException or HttpRequestException { StatusCode: HttpStatusCode.ServiceUnavailable };

try { await CallExternalService(); }
catch (Exception ex) when (IsTransient(ex))
{
    await Task.Delay(1000);
    await CallExternalService(); // упрощённый retry
}

2.4 Rethrow vs Wrap (InnerException)

Rethrow — перебросить то же исключение выше. Wrap — создать новое исключение, завернув оригинальное в InnerException. Swallow — поймать и проглотить (почти всегда плохо).

Когда rethrow (throw; без аргумента): вы поймали исключение только чтобы залогировать или очистить ресурсы, но дальше его должен обработать вызывающий код. throw; сохраняет оригинальный стектрейс. throw ex; — сбрасывает стектрейс, не делайте так.

Когда wrap: вы хотите добавить контекст домена поверх технической ошибки, или изолировать вызывающий код от деталей реализации (например, DbException → DomainException).

Когда swallow: только для ожидаемых некритичных ситуаций (например, "не удалось покинуть группу — ничего страшного"). В WebMessenger это делается осознанно в ChatHub.

// ПРАВИЛЬНЫЙ rethrow — стектрейс сохранён
try { await _repo.SaveAsync(); }
catch (Exception ex)
{
    _logger.LogError(ex, "Save failed");
    throw;        // ← правильно: throw без аргумента
    // throw ex; // ← НЕПРАВИЛЬНО: сбрасывает стектрейс, теряем место ошибки
}

// WRAP — оборачиваем техническую ошибку в доменную
try
{
    await _dbContext.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException ex)
{
    // DbUpdateConcurrencyException — деталь EF Core, изолируем от вызывающего кода
    throw new MessageSendFailedException("Message was modified concurrently", ex);
    //                                                                          ↑
    //                                    original exception → InnerException
}

// Просмотр цепочки InnerException при диагностике:
catch (MessageSendFailedException ex)
{
    Console.WriteLine(ex.Message);            // "Message was modified concurrently"
    Console.WriteLine(ex.InnerException?.Message); // оригинальный DbUpdateConcurrencyException
}

// SWALLOW (осознанный) — в WebMessenger ChatHub.cs:
try
{
    var peer = await _chats.TryGetDirectPeerAsync(chatId, me, ct);
    if (peer.HasValue)
        await Groups.RemoveFromGroupAsync(Context.ConnectionId, ...);
}
catch (Exception ex)
{
    // Выход из DM-группы — некритичная операция,
    // провал не должен прервать основное подключение
    _logger.LogDebug(ex, "Auto-leave DM failed for chat {ChatId}", chatId);
    // исключение поглощено намеренно, без rethrow
}

// AuthService.cs — swallow с возвратом null вместо исключения:
try
{
    var jwtToken = handler.ReadJwtToken(token);
    return jwtToken.Claims.FirstOrDefault(...)?.Value;
}
catch (Exception ex)
{
    _logger.LogWarning(ex, UsernameClaimNotFound);
    return null; // ошибка парсинга токена — возвращаем null, не пробрасываем
}
Антипаттерн: catch (Exception) { } без логирования и без осознанного решения — "тихое" проглатывание ошибок, которое делает диагностику проблем невозможной.

3. Delegates, Lambdas & Events

3.1 Что такое делегат

Что это. Делегат — это типобезопасный указатель на метод (или группу методов). Он описывает сигнатуру: типы параметров и тип возвращаемого значения. Переменная делегатного типа может хранить ссылку на любой метод с подходящей сигнатурой и вызывать его позже.

Зачем. Делегаты — основа для колбэков, событий, LINQ, async и всего функционального стиля в C#. Func<T, TResult>, Action<T>, Predicate<T> — это готовые делегатные типы из BCL, их хватает в 95% случаев. Свои delegate-типы нужны только когда нужна специфичная семантика (например, для событий с EventArgs).

// Объявление своего делегата (нужно редко — обычно хватает Func/Action)
public delegate Task MessageHandler(MessageCreatedPayload payload, CancellationToken ct);

// Встроенные делегатные типы BCL — использовать их предпочтительно:
Func<int, int, int>  add    = (a, b) => a + b;       // есть возвращаемое значение
Action<string>       log    = msg => Console.WriteLine(msg); // нет возвращаемого значения
Predicate<User>      online = u => u.IsOnline;        // bool возвращаемое значение

// Method group conversion — компилятор сам создаёт делегат из имени метода
// Не нужно писать лямбду-обёртку если сигнатура совпадает
Action<string> logMethod = Console.WriteLine; // метод группа, не лямбда
// Эквивалентно: Action<string> logMethod = s => Console.WriteLine(s);

// В LINQ — делегаты передаются повсюду:
var onlineUsers = users.Where(u => u.IsOnline); // лямбда — это делегат Func<User, bool>
var names       = users.Select(u => u.Username); // Func<User, string>

3.2 Variance: ковариантность и контравариантность

Что это. Variance описывает, как соотносятся делегатные типы при наследовании параметров. Это позволяет передавать метод с "более широким" или "более узким" типом туда, где ожидается делегат с другим типом.

Ковариантность (out — возвращаемое значение). Если метод возвращает Dog, а делегат ожидает Animal — это ок. Подтип может стоять там, где ожидается надтип. Интуиция: возвращаемое значение "выходит" наружу, поэтому подтип безопасен.

Контравариантность (in — параметры). Если метод принимает Animal, а делегат ожидает метод принимающий Dog — это ок. Метод для Animal точно умеет обработать Dog. Интуиция: параметр "входит" внутрь, поэтому надтип безопасен.

class Animal { }
class Dog : Animal { }

// Ковариантность возвращаемого типа — Func<Dog> присваивается Func<Animal>
Func<Dog> getDog = () => new Dog();
Func<Animal> getAnimal = getDog; // OK — Dog IS-A Animal, возвращаемый тип ковариантен

// Контравариантность параметров — Action<Animal> присваивается Action<Dog>
Action<Animal> feedAnimal = a => Console.WriteLine($"Feed {a}");
Action<Dog> feedDog = feedAnimal; // OK — метод для Animal справится с Dog
// Интуиция: если умеешь кормить любое животное, умеешь кормить и собаку

// В generic интерфейсах: IEnumerable<out T> (ковариантен)
IEnumerable<Dog> dogs = new List<Dog>();
IEnumerable<Animal> animals = dogs; // OK — IEnumerable<T> ковариантен по T

// Но List<T> инвариантен — не работает:
// List<Animal> list = new List<Dog>(); // ОШИБКА

3.3 Multicast Delegates

Что это. Делегат в C# может хранить несколько методов (invocation list). При вызове делегата все методы вызываются по порядку. Это называется multicast. Операторы += и -= добавляют/удаляют методы из списка.

Нюансы. Если в multicast делегате у одного из методов выбросилось исключение — оставшиеся методы в цепочке не вызовутся. Возвращаемое значение — только от последнего метода в списке. Поэтому multicast делегаты хорошо работают с void (Action), но с возвращаемым значением — осторожно.

Action<string> logger = msg => Console.WriteLine($"[LOG]: {msg}");
Action<string> audit  = msg => Console.WriteLine($"[AUDIT]: {msg}");

// Объединяем — теперь оба метода в invocation list
Action<string> combined = logger + audit;
combined("User logged in"); // вызовет logger, потом audit

// += для подписки, -= для отписки
combined += msg => Console.WriteLine($"[TRACE]: {msg}");
combined -= audit; // удаляем конкретный метод

// Просмотр invocation list
var list = combined.GetInvocationList();
Console.WriteLine($"Subscribers: {list.Length}");

// Безопасный вызов multicast (защита от null)
combined?.Invoke("message"); // если combined == null (нет подписчиков) — не падает

// Проблема с возвращаемым значением:
Func<int> f1 = () => 1;
Func<int> f2 = () => 2;
Func<int> multi = f1 + f2;
int result = multi(); // result == 2, значение f1 потеряно!
// Поэтому Func-делегаты почти никогда не делают multicast

3.4 Closures

Что это. Лямбда "захватывает" переменные из окружающего scope. Компилятор генерирует скрытый класс, который хранит захваченную переменную. Лямбда работает с ссылкой на переменную, а не с её копией в момент захвата.

Классическая ловушка. Захват переменной цикла — лямбды в цикле все захватывают одну и ту же переменную, которая к моменту вызова уже равна конечному значению.

Аллокации. Каждый новый closure-объект — это heap allocation. В hot-path (часто вызываемый код) это может давить на GC. Решение: static lambda (C# 9) запрещает захват переменных — компилятор генерирует статический метод без closure-объекта.

// Захват переменной — лямбда работает с ССЫЛКОЙ, не с копией
int multiplier = 3;
Func<int, int> multiply = x => x * multiplier; // захватила ссылку на multiplier

Console.WriteLine(multiply(5)); // 15

multiplier = 10; // изменили внешнюю переменную
Console.WriteLine(multiply(5)); // 50 — лямбда видит НОВОЕ значение! Это closure.

// Ловушка цикла — классическая ошибка
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
{
    actions.Add(() => Console.WriteLine(i)); // захватывают ОДНУ переменную i
}
actions.ForEach(a => a()); // выведет 3, 3, 3 — не 0, 1, 2!

// Исправление — локальная копия внутри цикла
for (int i = 0; i < 3; i++)
{
    int local = i; // новая переменная на каждой итерации
    actions.Add(() => Console.WriteLine(local)); // захватывает свою копию
}
actions.ForEach(a => a()); // 0, 1, 2 — правильно

// Foreach не имеет этой проблемы в C# 5+ — переменная итерации новая на каждый шаг
foreach (var user in users)
{
    Task.Run(() => Process(user)); // user — отдельная переменная каждой итерации, OK
}

// Static lambda (C# 9) — запрещает захват, нет closure-объекта, нет аллокации
Func<int, int> square = static x => x * x; // не захватывает ничего
// static x => x * multiplier; // ОШИБКА: static lambda не может захватить внешнюю переменную

3.5 Events: дизайн и безопасность

Что это. Event — это обёртка над делегатом с ограниченным доступом: снаружи класса можно только подписаться (+=) или отписаться (-=), но нельзя напрямую вызвать или заменить. Это инкапсуляция паттерна "издатель–подписчик".

EventArgs. По соглашению .NET события используют сигнатуру void Handler(object sender, TEventArgs e). EventArgs должны быть иммутабельными — подписчик не должен иметь возможность испортить данные для других подписчиков.

Дублирование подписок. Если один и тот же метод подписан дважды через += — он вызовется дважды. Паттерн "отпишись перед подпиской" гарантирует единственность.

// Иммутабельный EventArgs — record идеален
public sealed record MessageEventArgs(Guid ChatId, string Content, DateTime SentAt);

// Класс-издатель
public class MessageBus
{
    // event — ограничивает доступ: снаружи только += и -=
    public event EventHandler<MessageEventArgs>? MessageReceived;

    // Метод вызова события — protected виртуальный по соглашению
    protected virtual void OnMessageReceived(MessageEventArgs e)
    {
        // Потокобезопасный вызов: копируем в локальную переменную
        // чтобы между null-проверкой и вызовом никто не отписался
        var handler = MessageReceived;
        handler?.Invoke(this, e);
    }

    public void Publish(Guid chatId, string content)
    {
        OnMessageReceived(new MessageEventArgs(chatId, content, DateTime.UtcNow));
    }
}

// Подписка — паттерн "unsubscribe first" гарантирует отсутствие дублей
public class NotificationService
{
    private readonly MessageBus _bus;

    public NotificationService(MessageBus bus)
    {
        _bus = bus;
        // Сначала отписываемся (на случай повторной инициализации),
        // потом подписываемся — гарантированно один раз
        _bus.MessageReceived -= OnMessageReceived;
        _bus.MessageReceived += OnMessageReceived;
    }

    private void OnMessageReceived(object? sender, MessageEventArgs e)
    {
        Console.WriteLine($"New message in chat {e.ChatId}: {e.Content}");
    }

    // Отписка при завершении работы — важно для предотвращения утечек памяти!
    // Пока подписчик жив в event — GC его не соберёт (издатель держит ссылку)
    public void Dispose()
    {
        _bus.MessageReceived -= OnMessageReceived;
    }
}

// Утечка памяти через события — типичная проблема:
// Если NotificationService подписался на MessageBus (который живёт долго),
// но сам NotificationService не отписался при уничтожении —
// GC не сможет его собрать, пока MessageBus жив.
В WebMessenger события между сервисами реализованы через SignalR (push к клиентам) и прямые вызовы методов между сервисами через DI, а не через C# events. C# events — паттерн для in-process pub/sub внутри одного приложения.

4. Interfaces & Contracts

4.1 Interface vs Abstract Class

Когда interface. Когда вы описываете контракт поведения — что умеет делать объект, независимо от его природы. Класс может реализовывать несколько интерфейсов. Интерфейс — про "умеет": IDisposable, IComparable, IRepository<T>.

Когда abstract class. Когда у вас есть общая реализация, которую подклассы должны наследовать и переопределять. Абстрактный класс — про "является": BaseController, BaseRepository. Только одно наследование.

Практическое правило. Предпочитайте интерфейс, если нет общей логики для переиспользования. Abstract class — когда хотите поделиться реализацией между подклассами одной иерархии.

4.2 Explicit Interface Implementation

Что это. Метод можно реализовать "явно" — тогда он доступен только через переменную типа интерфейса, но не через переменную конкретного класса. Синтаксис: void IDisposable.Dispose() { ... } без модификатора доступа.

Зачем. Скрыть методы интерфейса из публичного API класса, когда они не предназначены для прямого вызова пользователем. Разрешить конфликт имён при реализации двух интерфейсов с одинаковыми именами методов. Управлять формой публичного API.

// Класс реализует IDisposable, но не хочет "засорять" свой публичный API методом Dispose.
// Пользователи класса должны использовать using, а не вызывать Dispose() напрямую.
public class DatabaseContext : IDisposable, IAsyncDisposable
{
    // Явная реализация — не видна через переменную DatabaseContext

4.3 Default Interface Members

Что это. C# 8+: интерфейс может содержать методы с реализацией по умолчанию. Если класс не переопределяет метод — используется реализация из интерфейса.

Зачем. Эволюция API без breaking change. Если вы добавили новый метод в интерфейс — все существующие реализации "получают" его автоматически. Без default members добавление нового члена сломало бы всех реализаторов.

Когда осторожно. Default members могут запутать код — читатель не сразу понимает, где находится реализация. Не злоупотребляйте как заменой abstract class. Хорошее применение — версионирование библиотечных API.

// Версионирование: добавляем новый метод в интерфейс без поломки реализаций
public interface IChatService

}

// GetUnreadCountAsync вернёт 0 по умолчанию

4.4 Static Abstract Members (Generic Math)

Что это. C# 11+: интерфейс может объявлять статические абстрактные члены, в том числе операторы. Реализующий тип должен предоставить статическую реализацию. Это позволяет писать обобщённые алгоритмы, работающие с числовыми операциями (+, -, *) для любого типа.

Зачем. До C# 11 нельзя было написать обобщённый метод Sum<T> — компилятор не знал, есть ли у T оператор +. Теперь можно через INumber<T> или собственный интерфейс с static abstract.

// Интерфейс объявляет статический оператор как требование
public interface IAddable<T> where T : IAddable<T>
{
    static abstract T operator +(T left, T right); // статический абстрактный оператор
    static abstract T Zero { get; }                 // статическое абстрактное свойство
}

// Реализация
public readonly struct Money : IAddable<Money>
{
    public decimal Amount { get; }
    public Money(decimal amount) => Amount = amount;

    public static Money operator +(Money left, Money right) =>
        new(left.Amount + right.Amount);

    public static Money Zero => new(0);
}

// Обобщённый алгоритм — работает с любым типом, реализующим IAddable<T>
public static T Sum<T>(IEnumerable<T> items) where T : IAddable<T>
{
    T result = T.Zero;            // вызов статического члена через тип-параметр!
    foreach (var item in items)
        result = result + item;   // оператор + гарантирован интерфейсом
    return result;
}

4.5 Variance в Generic Interfaces

Ковариантность (out T). Интерфейс IEnumerable<out T> — ковариантен. Можно присвоить IEnumerable<Dog> переменной типа IEnumerable<Animal>. Работает потому что T используется только как возвращаемое значение (выходит наружу).

Контравариантность (in T). Интерфейс IComparer<in T> — контравариантен. Можно присвоить IComparer<Animal> переменной типа IComparer<Dog>. Работает потому что T используется только как входной параметр.

Инвариантность. IList<T> — инвариантен, потому что T используется и на входе (Add(T)), и на выходе (T this[int]).

// Ковариантность: out T — T только возвращается
interface IProducer<out T>
{

}

// Контравариантность: in T — T только принимается

{

}

// IList<T>             — инвариантен (читает И пишет)

// Практический пример: почему это важно

5.2 Iterators и yield return

Что это. Метод с yield return — это итератор. Вместо того чтобы создать коллекцию целиком и вернуть её, итератор генерирует элементы по одному при каждом следующем шаге перебора. Компилятор генерирует из такого метода конечный автомат (state machine).

Зачем. Ленивая (lazy) генерация: элементы создаются только когда нужны. Экономит память при работе с большими или потенциально бесконечными последовательностями. Упрощает код — вместо ручного накопления в список.

Ключевое. Тело итератора не выполняется при вызове метода — оно выполняется при итерации. Это называется deferred execution.

// Без yield — всё создаётся сразу, весь список в памяти
public IEnumerable<int> GetEvenNumbers(int max)
{
    var result = new List<int>();
    for (int i = 0; i <= max; i++)
        if (i % 2 == 0) result.Add(i);
    return result; // List уже полностью заполнен
}

// С yield — ленивая генерация, каждый элемент по требованию
public IEnumerable<int> GetEvenNumbersLazy(int max)
{
    for (int i = 0; i <= max; i++)
        if (i % 2 == 0)
            yield return i; // выдать элемент и ПРИОСТАНОВИТЬ выполнение
    // yield break; — явное завершение итератора (опционально)
}

// Вызывающий код — одинаков в обоих случаях
foreach (var n in GetEvenNumbersLazy(1_000_000))
{
    if (n > 100) break; // итератор остановится на 102, не вычислит 103..1_000_000
}

// Практический пример — потоковая обработка сообщений без загрузки всего в память
public async IAsyncEnumerable<ChatMessageDto> StreamMessagesAsync(
    Guid chatId,
    [EnumeratorCancellation] CancellationToken ct)
{
    int page = 0;
    PagedResult<ChatMessageDto> result;
    do
    {
        result = await _repo.GetPageAsync(chatId, page++, ct);
        foreach (var msg in result.Items)
            yield return msg; // каждое сообщение выдаётся как только страница загружена
    } while (result.HasMore);
}

// ВАЖНО: итератор не выполняется при вызове:

foreach (var n in seq) { }         // вот здесь начинается выполнение

5.3 Sorted, ReadOnly и Custom Comparers

SortedDictionary vs SortedList. Оба держат элементы в отсортированном порядке по ключу. SortedDictionary — на основе красно-чёрного дерева (O(log n) для всего). SortedList — на основе двух массивов (O(log n) поиск, но O(n) вставка/удаление), зато меньше памяти при плотном заполнении.

IComparer<T> позволяет задать кастомный порядок сортировки отдельно от самого типа. IComparable<T> — встроенный порядок прямо в тип.

ReadOnly-обёртки. AsReadOnly() / ReadOnlyCollection<T> — обёртка без копирования, изменения в исходном списке будут видны. ImmutableList<T> — настоящая неизменяемость, но с копированием при каждом изменении.

// Кастомный comparer — сортировка пользователей: онлайн первые, потом по имени
public class UserOnlineFirstComparer : IComparer<User>
{
    public int Compare(User? x, User? y)
    {
        if (x is null && y is null) return 0;
        if (x is null) return 1;
        if (y is null) return -1;

        // Онлайн-пользователи выше (меньше = раньше в сортировке)
        if (x.IsOnline != y.IsOnline)
            return x.IsOnline ? -1 : 1;

        // При равном статусе — по имени
        return string.Compare(x.Username, y.Username, StringComparison.OrdinalIgnoreCase);
    }
}

// SortedSet — отсортированное множество без дубликатов
var sortedUsers = new SortedSet<User>(new UserOnlineFirstComparer());
sortedUsers.Add(user1);
sortedUsers.Add(user2);
// Элементы всегда в порядке: онлайн первые, потом алфавит

// ReadOnly обёртка — без копирования данных
var list = new List<string> { "a", "b", "c" };
IReadOnlyList<string> readOnly = list.AsReadOnly();
// readOnly.Add("d"); // ОШИБКА компиляции: нет метода Add
list.Add("d"); // оригинал изменился
Console.WriteLine(readOnly.Count); // 4 — обёртка "видит" изменение!

// Immutable — настоящая неизменяемость (System.Collections.Immutable)
ImmutableList<string> immutable = ImmutableList.Create("a", "b");
ImmutableList<string> withC = immutable.Add("c"); // НОВЫЙ список, immutable не тронут
Console.WriteLine(immutable.Count); // 2 — не изменился

private readonly ConcurrentDictionary<Guid, HashSet<string>> _userConnections = new();

5.5 Capacity Planning

Что это. List<T> внутри — массив. Когда массив заполняется, List создаёт новый в 2 раза больший и копирует все элементы. Это O(n) операция при каждом удвоении. Если вы знаете примерный размер заранее — задайте capacity при создании.

Dictionary. Аналогичная история: при превышении load factor (~0.72) происходит rehash — создание нового массива buckets и перемещение всех записей.

// БЕЗ capacity — при 1000 элементах будет ~10 удвоений (1→2→4→8...→1024)
// каждый раз: new array + Array.Copy
var list = new List<int>();
for (int i = 0; i < 1000; i++) list.Add(i);

// С capacity — один array, ноль перевыделений
var list = new List<int>(capacity: 1000); // сразу резервируем место
for (int i = 0; i < 1000; i++) list.Add(i);

// В WebMessenger — ChatService.cs знает лимит пагинации заранее:
var take = Math.Clamp(limit, 1, 200); // максимум 200 элементов
// Здесь нет явного capacity, но ToListAsync() EF Core использует
// оценку из COUNT запроса если возможно

// Dictionary с capacity
var dict = new Dictionary<Guid, string>(capacity: users.Count);
foreach (var u in users)
    dict[u.Id] = u.Username; // ни одного rehash если Count не превышен

// CollectionsMarshal.SetCount — unsafe быстрое задание размера List
// (для performance-critical кода, не для обычного использования)

var span = CollectionsMarshal.AsSpan(fastList); // прямой доступ к внутреннему массиву

6. LINQ

6.1 Deferred Execution и ToList-границы

Что это. Большинство LINQ-операторов (Where, Select, OrderBy и т. д.) — ленивые: они не выполняют никакой работы при объявлении цепочки. Реальное выполнение происходит только при материализации: ToList(), ToArray(), FirstOrDefault(), foreach и т. п.

Почему это важно. Для IQueryable<T> (EF Core) это означает, что вся цепочка компилируется в один SQL-запрос. Каждый ToList() — это граница: после него работа продолжается в памяти (IEnumerable<T>), не в БД. Лишний ToList() в середине цепочки = лишний round-trip или загрузка лишних данных.

// IQueryable — всё до ToListAsync() компилируется в ОДИН SQL:
var query = _uow.MessageRepository.GetAll()     // SELECT * FROM Messages
    .Where(m => m.ChatId == chatId)              // WHERE ChatId = @chatId
    .Where(m => m.SenderId != me)                // AND SenderId != @me
    .OrderByDescending(m => m.SentAt)            // ORDER BY SentAt DESC
    .Take(50);                                   // LIMIT 50
// SQL ещё НЕ выполнен! query — это описание запроса

var messages = await query.ToListAsync();        // ЗДЕСЬ выполняется один SQL-запрос

// -------------------------------------------------------
// ОШИБКА: ToList() в середине — переключение на in-memory
var bad = _uow.MessageRepository.GetAll()
    .Where(m => m.ChatId == chatId)
    .ToList()                    // ← SQL выполнен, ВСЕ сообщения чата загружены в память
    .Where(m => m.SenderId != me)// ← фильтрация теперь в C# в памяти
    .OrderByDescending(m => m.SentAt)
    .Take(50);
// Загрузили тысячи сообщений, отфильтровали 50 — остальные выброшены

// -------------------------------------------------------
// Из WebMessenger.ChatService.cs — правильный подход:
// Весь запрос строится как IQueryable, ToListAsync только один раз в конце
var baseQuery =
    from c in _uow.ChatRepository.GetAll(nameof(Chat.Members))

6.2 GroupBy vs ToLookup

LINQ GroupBy (IQueryable). Компилируется в SQL GROUP BY. Выполняется на стороне БД. Возвращает IQueryable<IGrouping<K,T>>. Ленивый.

LINQ GroupBy (IEnumerable). Выполняется в памяти. Тоже ленивый — группы вычисляются при итерации. Если вы итерируете несколько раз — группировка происходит несколько раз.

ToLookup. Выполняется немедленно (eager), создаёт in-memory хэш-таблицу. Можно обращаться по ключу O(1) множество раз без повторного вычисления. Используйте когда нужно многократно искать группы по ключу.

// GroupBy на IQueryable — GROUP BY в SQL
var unreadCounts = await _uow.MessageRepository.GetAll()
    .Where(m => chatIds.Contains(m.ChatId) && m.SenderId != me)
    .GroupBy(m => m.ChatId)                         // GROUP BY ChatId в SQL
    .Select(g => new { ChatId = g.Key, Count = g.Count() }) // COUNT(*) в SQL
    .ToListAsync();
// Результат: список {ChatId, Count} — агрегация произошла на сервере БД

// GroupBy на IEnumerable — в памяти, ленивый
var groups = messages.GroupBy(m => m.SenderId);    // группы ещё не вычислены
foreach (var group in groups)                      // вычисляется здесь
{
    Console.WriteLine($"{group.Key}: {group.Count()} messages");
}
// Если итерировать groups ещё раз — группировка повторится! (deferred)

// ToLookup — eager, один раз, потом быстрый доступ
// Используем когда нужно многократно искать по ключу
var byChat = messages.ToLookup(m => m.ChatId);      // СРАЗУ строит таблицу

// Теперь O(1) доступ по ключу, сколько угодно раз
var chatMessages = byChat[chatId];                   // не пересчитывается
var otherMessages = byChat[otherChatId];             // не пересчитывается

// Отличие от Dictionary: ToLookup никогда не бросает KeyNotFoundException
// Если ключа нет — возвращает пустую последовательность
var missing = byChat[Guid.Empty]; // пустой IEnumerable, не исключение

6.3 Joins и Set Operations

Join. Объединение двух последовательностей по ключу. Для IQueryable компилируется в SQL INNER JOIN. В памяти — хэш-join.

Set operations. Union, Intersect, Except — операции над множествами. Используют Equals/GetHashCode для сравнения, или кастомный IEqualityComparer<T>.

// Join — объединение пользователей с их статусом прочтения
var result = users.Join(
    readStates,                         // вторая последовательность
    u => u.Id,                          // ключ из первой
    rs => rs.UserId,                    // ключ из второй
    (u, rs) => new { u.Username, rs.LastReadAt }  // проекция результата
);

// Query syntax — часто читабельнее для join
var result =
    from u in users
    join rs in readStates on u.Id equals rs.UserId
    select new { u.Username, rs.LastReadAt };

// GroupJoin — LEFT JOIN (включая пользователей без записей прочтения)
var result = users.GroupJoin(
    readStates,
    u => u.Id,
    rs => rs.UserId,
    (u, rsGroup) => new
    {
        u.Username,
        LastRead = rsGroup.FirstOrDefault()?.LastReadAt  // null если нет записи
    });

// Set operations — в WebMessenger: поиск контактов которые уже в чате
var contactIds  = new HashSet<Guid> { /* id контактов */ };
var memberIds   = chat.Members.Select(m => m.UserId);

var contactsInChat  = contactIds.Intersect(memberIds);   // пересечение
var contactsNotIn   = contactIds.Except(memberIds);      // разность: контакты не в чате
var allInvolved     = contactIds.Union(memberIds);        // объединение без дубликатов

// Distinct — убрать дубликаты (использует Equals/GetHashCode)
var uniqueSenders = messages.Select(m => m.SenderId).Distinct();

6.4 Многоуровневая сортировка

Стабильная сортировка. LINQ гарантирует стабильную сортировку: элементы с одинаковым ключом сохраняют исходный порядок. Это важно при многоуровневой сортировке.

ThenBy vs повторный OrderBy. Никогда не используйте два OrderBy подряд — второй полностью отменяет первый. Для многоуровневой сортировки используйте OrderBy(...).ThenBy(...).ThenByDescending(...).

// НЕПРАВИЛЬНО — второй OrderBy отменяет первый:
var bad = users
    .OrderByDescending(u => u.IsOnline)  // сортировка 1 — потеряна!
    .OrderBy(u => u.Username);           // сортировка 2 — только она действует

// ПРАВИЛЬНО — ThenBy добавляет уровень к существующей сортировке:
var sorted = users
    .OrderByDescending(u => u.IsOnline)  // сначала онлайн
    .ThenBy(u => u.Username);            // при равном IsOnline — по имени

// В WebMessenger — ChatService.cs:
var rows = await baseQuery
    .OrderByDescending(x => x.LastActivityAt)  // по активности
    .Take(take)
    .ToListAsync();

// Многоуровневая: чаты группы → DM, потом по активности, потом по имени
var ordered = chats
    .OrderByDescending(c => c.IsGroup)          // группы первыми
    .ThenByDescending(c => c.LastActivityAt)    // потом по активности
    .ThenBy(c => c.Title);                      // потом по алфавиту

// Сортировка по нескольким полям через анонимный тип в query syntax:
var q = from m in messages
        orderby m.ChatId ascending, m.SentAt descending
        select m;

6.5 Func<T> vs Expression<Func<T>> и IQueryable

Ключевое различие. Func<T, bool> — это скомпилированный делегат, исполняемый код в памяти. Expression<Func<T, bool>> — это дерево выражений, структура данных описывающая код. EF Core может прочитать это дерево и транслировать его в SQL. Обычный делегат EF Core транслировать не может.

Когда что использовать. Для EF Core Where, Select и т. д. — нужны Expression (и они туда попадают автоматически при записи лямбд на IQueryable). Если вы передаёте предикат как параметр метода и хотите чтобы он шёл в SQL — тип параметра должен быть Expression<Func<T, bool>>, не Func<T, bool>.

// IQueryable.Where принимает Expression<Func<T,bool>>
// IEnumerable.Where принимает Func<T,bool>
// Компилятор выбирает нужную перегрузку автоматически по типу переменной:

IQueryable<User> queryable = _repo.GetAll();
queryable.Where(u => u.IsOnline);    // компилятор создаёт Expression — уйдёт в SQL

IEnumerable<User> enumerable = users;
enumerable.Where(u => u.IsOnline);   // компилятор создаёт Func — выполнится в памяти

// Проблема: вызвали AsEnumerable() слишком рано
var bad = _repo.GetAll()
    .AsEnumerable()              // ← переключились на IEnumerable!
    .Where(u => u.IsOnline);     // фильтрация в памяти, все юзеры загружены из БД

// Передача предиката как параметра — тип важен!
// НЕПРАВИЛЬНО: фильтрация всегда в памяти, не в SQL
public IEnumerable<User> FindUsers(Func<User, bool> predicate)
{
    return _repo.GetAll()        // IQueryable
        .Where(predicate)        // AsEnumerable().Where(predicate) — EF Core материализует всё!
        .ToList();
}

// ПРАВИЛЬНО: предикат транслируется в SQL
public IEnumerable<User> FindUsers(Expression<Func<User, bool>> predicate)
{
    return _repo.GetAll()        // IQueryable
        .Where(predicate)        // остаётся IQueryable, уйдёт в SQL
        .ToList();
}

// Expression можно строить динамически (dynamic LINQ):
Expression<Func<User, bool>> expr = u => u.IsOnline; // базовое выражение
// Комбинирование через PredicateBuilder или AndAlso/OrElse Expression API
var body = Expression.AndAlso(
    expr.Body,
    Expression.Equal(
        Expression.Property(expr.Parameters[0], nameof(User.Username)),
        Expression.Constant("alice")));
var combined = Expression.Lambda<Func<User, bool>>(body, expr.Parameters);
Типичная ошибка: вызов .AsEnumerable() или .ToList() до фильтрации Where при работе с EF Core — вся таблица загружается в память.

7. Parallel LINQ (PLINQ)

7.1 Что такое PLINQ и когда его использовать

Что это. PLINQ (AsParallel()) — расширение LINQ, которое автоматически распараллеливает обработку последовательности на несколько потоков из ThreadPool. Компилятор разбивает источник на разделы (partitions), обрабатывает их параллельно и сливает результаты.

Когда стоит использовать. CPU-bound вычисления на больших коллекциях в памяти: обработка изображений, сложные расчёты, CPU-intensive трансформации данных. Выгода появляется когда работа каждого элемента занимает заметное время (несколько миллисекунд и более).

Когда НЕ стоит использовать.

  • I/O-bound операции — для них async/await + Task.WhenAll, PLINQ тут бесполезен и занимает потоки впустую.
  • Маленькие коллекции — накладные расходы на разбиение, синхронизацию и слияние могут превысить выигрыш.
  • Код с shared mutable state — параллельный доступ без синхронизации ведёт к гонкам данных.
  • ASP.NET Core request pipeline — потоки ThreadPool и так заняты обслуживанием запросов; PLINQ будет конкурировать с ними.
// Последовательный LINQ
var results = data.Where(x => IsExpensive(x)).Select(x => Transform(x)).ToList();

// PLINQ — добавляем AsParallel()
var results = data
    .AsParallel()
    .Where(x => IsExpensive(x))
    .Select(x => Transform(x))
    .ToList();
// Автоматически использует Environment.ProcessorCount потоков

// PLINQ НЕ подходит для async-операций:
// AsParallel().Select(async x => await FetchFromDb(x)) — ПЛОХО
// Правильно для I/O-bound:
var tasks = data.Select(x => FetchFromDbAsync(x));
var results = await Task.WhenAll(tasks);

7.2 Степень параллелизма и опции

WithDegreeOfParallelism(n). Ограничивает максимальное число потоков. По умолчанию PLINQ использует столько потоков, сколько логических процессоров. В ASP.NET Core полезно ограничить, чтобы не забирать все потоки у сервера.

WithExecutionMode. По умолчанию PLINQ сам решает, стоит ли параллелить (может упасть обратно на последовательное выполнение если посчитает невыгодным). ParallelExecutionMode.ForceParallelism заставляет всегда параллелить.

WithMergeOptions. Управляет тем, как результаты собираются в конечный поток. Влияет на задержку первого результата.

var results = data
    .AsParallel()
    .WithDegreeOfParallelism(4)                    // не более 4 потоков
    .WithExecutionMode(ParallelExecutionMode.ForceParallelism)  // всегда параллельно
    .WithMergeOptions(ParallelMergeOptions.NotBuffered) // выдавать результаты сразу
    .Where(x => HeavyFilter(x))
    .Select(x => HeavyTransform(x))
    .ToList();

// ParallelMergeOptions:
// Default         — буферизует, хорошая пропускная способность
// NotBuffered     — каждый результат выдаётся сразу, меньше задержка первого
// FullyBuffered   — всё буферизуется до конца, максимальная пропускная способность

7.3 Порядок результатов

Важно. PLINQ по умолчанию не сохраняет порядок элементов — потоки завершаются в произвольном порядке. Если порядок важен, используйте AsOrdered(), но это добавляет накладные расходы на синхронизацию.

// Без сохранения порядка — быстрее
var unordered = data.AsParallel()
    .Select(x => Transform(x))
    .ToList(); // порядок элементов может отличаться от исходного

// С сохранением порядка — чуть медленнее
var ordered = data.AsParallel()
    .AsOrdered()                   // сохранять порядок исходной последовательности
    .Select(x => Transform(x))
    .ToList(); // порядок как в data

// AsUnordered() — снять требование порядка если AsOrdered() был унаследован
var fast = orderedSource.AsParallel().AsOrdered()
    .Where(x => Filter(x))
    .AsUnordered()                 // дальше порядок не важен — быстрее
    .Select(x => Transform(x))
    .ToList();

7.4 Отмена с WithCancellation

Что это. PLINQ поддерживает CancellationToken через WithCancellation(ct). При отмене токена выбрасывается OperationCanceledException. Без этого PLINQ будет продолжать работу даже после отмены.

var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5)); // таймаут 5 сек

try
{
    var results = data
        .AsParallel()
        .WithCancellation(cts.Token)    // регистрируем токен отмены
        .WithDegreeOfParallelism(4)
        .Select(x => HeavyTransform(x))
        .ToList();
}
catch (OperationCanceledException)
{
    // Токен был отменён — нормальная ситуация, обрабатываем
    logger.LogWarning("Parallel processing was cancelled");
}

// Отмена из другого места:
cts.Cancel(); // все потоки PLINQ получат сигнал отмены и остановятся

7.5 Стратегии разделения (Partitioning)

Что это. Прежде чем распараллелить, PLINQ делит исходную коллекцию на части (partitions). Стратегия разделения влияет на эффективность параллелизма.

Range partitioning. Для массивов и List: делит на равные диапазоны [0..n/4], [n/4..n/2] и т. д. Хорошо когда работа одинаковая на каждый элемент.

Chunk partitioning. Потоки берут элементы динамически чанками. Лучше когда время обработки элементов сильно варьируется (load balancing).

ForAll. Специальный терминальный оператор вместо ToList() — потребляет результаты прямо в параллельных потоках без слияния. Подходит для side-effectful операций (запись в thread-safe коллекцию, логирование).

// Кастомный partitioner — chunk partitioning для неравномерной нагрузки
var partitioner = Partitioner.Create(data, loadBalance: true);
var results = partitioner
    .AsParallel()
    .Select(x => VariableHeavyWork(x))
    .ToList();

// ForAll — потребление без слияния, быстрее ToList() для side-effects
var bag = new ConcurrentBag<string>();
data.AsParallel()
    .Where(x => Filter(x))
    .ForAll(x => bag.Add(Transform(x))); // каждый поток пишет напрямую в ConcurrentBag
// bag.Add потокобезопасен — ConcurrentBag специально для этого

// ForAll vs ToList:
// ToList() — сливает все результаты, создаёт List в памяти, порядок через буфер
// ForAll()  — нет слияния, нет List, нет буфера — чисто параллельное потребление

7.6 Обработка исключений в PLINQ

AggregateException. Если несколько потоков бросили исключения, PLINQ оборачивает их все в AggregateException. Нужно явно обрабатывать каждое через InnerExceptions или Handle().

try
{
    var results = data
        .AsParallel()
        .Select(x =>
        {
            if (x < 0) throw new ArgumentOutOfRangeException(nameof(x), "Negative value");
            return x * 2;
        })
        .ToList();
}
catch (AggregateException ae)
{
    // ae.InnerExceptions — все исключения из всех потоков
    foreach (var ex in ae.InnerExceptions)
        logger.LogError(ex, "Error in parallel processing");

    // Handle() — обработать только известные типы, остальные перебросить
    ae.Handle(ex =>
    {
        if (ex is ArgumentOutOfRangeException)
        {
            logger.LogWarning(ex, "Skipping invalid item");
            return true;   // обработано — не перебрасывать
        }
        return false;      // не обработано — перебросить как AggregateException
    });
}

// Flatten() — разворачивает вложенные AggregateException в плоский список
catch (AggregateException ae)
{
    foreach (var inner in ae.Flatten().InnerExceptions)
        Console.WriteLine(inner.Message);
}
В WebMessenger PLINQ не применяется — проект I/O-bound (БД, сеть), а не CPU-bound. Для CPU-bound сценариев (например, батчевая обработка медиафайлов) PLINQ был бы уместен при соответствующей архитектуре.

8. Garbage Collector

8.1 Поколения: Gen 0, Gen 1, Gen 2

Принцип. GC в .NET делит heap на три поколения. Гипотеза: большинство объектов живут очень недолго. Поэтому GC сначала собирает только молодые объекты — это дёшево. Долгоживущие объекты переходят в старшие поколения и собираются реже.

Gen 0. Новые маленькие объекты. Размер ~256 KB. Сборка очень частая (может быть сотни раз в секунду) и очень быстрая (доли миллисекунды). Объекты выжившие после Gen 0 GC — перемещаются в Gen 1.

Gen 1. Буфер между Gen 0 и Gen 2. Объекты живут чуть дольше. Сборка реже. Выжившие — перемещаются в Gen 2.

Gen 2. Долгоживущие объекты: статические данные, кэши, объекты уровня приложения. Сборка редкая, но дорогая — GC приостанавливает все потоки (stop-the-world) на время полной сборки. Именно Gen 2 GC вызывает заметные паузы в приложении.

Promotion. Объект "повышается" в поколение если пережил сборку своего поколения. Цель: не создавать объекты, которые живут "чуть дольше Gen 0" — они попадут в Gen 1, а потом в Gen 2, раздувая старый heap.

// Диагностика поколений
var obj = new User(); // создан в Gen 0
Console.WriteLine(GC.GetGeneration(obj)); // 0

GC.Collect(0); // принудительная сборка Gen 0 (в production НЕ делайте!)
Console.WriteLine(GC.GetGeneration(obj)); // 1 — пережил Gen 0, повышен

GC.Collect(1);
Console.WriteLine(GC.GetGeneration(obj)); // 2 — пережил Gen 1

// Размеры heap по поколениям
var info = GC.GetGCMemoryInfo();
Console.WriteLine($"Gen0 size: {info.GenerationInfo[0].SizeAfterBytes}");
Console.WriteLine($"Gen1 size: {info.GenerationInfo[1].SizeAfterBytes}");
Console.WriteLine($"Gen2 size: {info.GenerationInfo[2].SizeAfterBytes}");

// Антипаттерн — объекты с неожиданно длинным временем жизни попадают в Gen 2:
// Например: кэш в статическом Dictionary который никогда не очищается,
// или событийные подписчики, которых забыли отписать

8.2 Large Object Heap (LOH)

Что это. Объекты размером ≥ 85 000 байт (примерно 83 KB) размещаются не в обычном heap, а в Large Object Heap. LOH никогда не компактируется по умолчанию — GC не перемещает большие объекты, это слишком дорого.

Фрагментация LOH. Поскольку LOH не компактируется, после серии выделений и освобождений больших объектов в нём образуются "дыры". Новый большой объект может не поместиться в дыру подходящего размера — придётся расширять heap. Это приводит к постепенному росту потребления памяти.

Решения. Переиспользование буферов через ArrayPool<T> (см. раздел Memory). Включить компактацию LOH явно — но это дорого. Избегать частых аллокаций больших массивов.

// Объект ≥ 85000 байт → LOH
byte[] smallBuffer = new byte[84_999]; // Gen 0 heap, компактируется
byte[] largeBuffer = new byte[85_000]; // Large Object Heap, НЕ компактируется

// Проверка: в каком heap находится объект
bool isLOH = GC.GetGeneration(largeBuffer) == 2;
// Объекты LOH отображаются как Gen 2 (живут до полной сборки)

// Фрагментация: частое создание и освобождение больших буферов
for (int i = 0; i < 1000; i++)
{
    var buffer = new byte[100_000]; // каждый раз новый, LOH растёт и фрагментируется
    Process(buffer);
    // buffer выходит из scope — GC добавит "дыру" в LOH
}

// Решение: ArrayPool — переиспользование буферов без аллокации
for (int i = 0; i < 1000; i++)
{
    var buffer = ArrayPool<byte>.Shared.Rent(100_000); // взять из пула
    try { Process(buffer); }
    finally { ArrayPool<byte>.Shared.Return(buffer); }  // вернуть в пул
}
// LOH не растёт — один и тот же буфер переиспользуется

// Принудительная компактация LOH (только при диагностике, не в production):
GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;
GC.Collect();

8.3 Dispose Pattern: IDisposable и IAsyncDisposable

Зачем Dispose. GC управляет только управляемой памятью (heap объектов .NET). Unmanaged ресурсы — файловые дескрипторы, сокеты, БД-соединения, нативные хендлы — GC не знает как освобождать. Для них нужен явный Dispose().

Finalizer. Метод ~MyClass() — запасной механизм: GC вызовет его если объект не был задиспожен явно. Но финализаторы дорогие: объект выживает лишнюю сборку (повышается на поколение), финализация происходит в отдельном потоке, непредсказуемо по времени. Поэтому правило: если вы вызвали Dispose() явно, нужно подавить финализацию через GC.SuppressFinalize(this).

Полный паттерн Dispose. Применяется когда класс сам владеет unmanaged ресурсами или содержит IDisposable-поля.

// Полный Dispose pattern с финализатором
public class DatabaseConnection : IDisposable
{
    private IntPtr _nativeHandle; // unmanaged ресурс
    private SqlConnection? _conn; // managed IDisposable ресурс
    private bool _disposed = false;

    // Публичный Dispose — вызывается явно пользователем
    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this); // финализатор больше не нужен
    }

    // Финализатор — запасной выход если Dispose не вызвали
    ~DatabaseConnection()
    {
        Dispose(disposing: false); // только unmanaged ресурсы, не трогать managed!
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return; // идемпотентность — вызов второй раз безопасен

        if (disposing)
        {
            // Managed ресурсы — только когда вызван явно (не из финализатора!)
            // В финализаторе managed объекты могут быть уже собраны GC
            _conn?.Dispose();
            _conn = null;
        }

        // Unmanaged ресурсы — всегда
        if (_nativeHandle != IntPtr.Zero)
        {
            ReleaseNativeHandle(_nativeHandle);
            _nativeHandle = IntPtr.Zero;
        }

        _disposed = true;
    }

    public void Query()
    {
        ObjectDisposedException.ThrowIf(_disposed, this); // проверка в каждом методе
        // ...
    }
}

// IAsyncDisposable — для асинхронного освобождения (закрытие async соединений)
public class AsyncResource : IAsyncDisposable
{
    private bool _disposed = false;

    public async ValueTask DisposeAsync()
    {
        if (_disposed) return;
        await FlushAsync();       // асинхронная очистка буфера перед закрытием
        await CloseAsync();       // асинхронное закрытие соединения
        _disposed = true;
        GC.SuppressFinalize(this);
    }
}

// Использование — using statement автоматически вызывает Dispose/DisposeAsync
using var conn = new DatabaseConnection();
conn.Query(); // после выхода из блока — Dispose() вызван автоматически

await using var res = new AsyncResource();
// DisposeAsync() вызван автоматически

8.4 GC Modes и настройка

Workstation GC. Оптимизирован для интерактивных приложений. Одна heap на процесс, одна нитка GC. Меньшие паузы, но меньшая пропускная способность.

Server GC. По умолчанию в ASP.NET Core. Создаёт отдельный heap и поток GC для каждого логического процессора. Высокая пропускная способность, паузы чуть длиннее. Подходит для серверных приложений с несколькими ядрами.

Background GC. Gen 2 сборка происходит в фоновом потоке, пока приложение продолжает работать (concurrent). Уменьшает stop-the-world паузы.

// runtimeconfig.json — настройка GC режима
{
  "configProperties": {
    "System.GC.Server": true,             // Server GC (default в ASP.NET Core)
    "System.GC.Concurrent": true,         // Background GC (default true)
    "System.GC.HeapHardLimit": 1073741824 // лимит heap 1 GB (для контейнеров)
  }
}

// Программное управление (редко нужно):
GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency;
// Режимы:
// Batch                — максимальная пропускная способность, большие паузы
// Interactive          — баланс (default)
// LowLatency           — минимальные паузы Gen 2 (кратковременно)
// SustainedLowLatency  — долгосрочный low-latency (Server GC required)
// NoGCRegion           — временно отключить GC для критичного кода (опасно!)

// Информация о последней сборке
var info = GC.GetGCMemoryInfo();
Console.WriteLine($"Pause duration: {info.PauseDurations[0].TotalMilliseconds} ms");
Console.WriteLine($"Heap size: {info.HeapSizeBytes / 1024 / 1024} MB");

9. Runtime Fundamentals

9.1 Сборка (Assembly) и манифест

Что такое сборка. Assembly — единица развёртывания и версионирования в .NET. Это файл .dll или .exe, содержащий: IL-код (Intermediate Language), метаданные типов, манифест сборки и опционально ресурсы. Перед исполнением JIT компилирует IL в нативный машинный код.

Манифест. Часть сборки, описывающая её идентичность: имя, версия, культура, публичный ключ (для strong name), список модулей, список внешних зависимостей (referenced assemblies). Именно по манифесту CLR разрешает ссылки между сборками.

Assembly Identity. Сборка идентифицируется четырьмя составляющими: имя + версия + культура + публичный ключ. Это называется "strong name". Без публичного ключа — weak name (только имя+версия).

// WebMessenger состоит из нескольких сборок:
// WebMessenger.Api.dll        — основное приложение
// WebMessenger.Contracts.dll  — DTO, интерфейсы
// WebMessenger.DAL.dll        — репозитории, EF Core

// Каждая .csproj → одна .dll (сборка)
// В .csproj задаётся идентичность сборки:
<PropertyGroup>
  <AssemblyName>WebMessenger.Api</AssemblyName>
  <AssemblyVersion>1.0.0.0</AssemblyVersion>
  <FileVersion>1.0.0.0</FileVersion>
</PropertyGroup>

// Читаем манифест программно:
var assembly = typeof(Program).Assembly;
var name = assembly.GetName();
Console.WriteLine(name.Name);          // "WebMessenger.Api"
Console.WriteLine(name.Version);       // "1.0.0.0"
Console.WriteLine(assembly.Location);  // путь к .dll на диске

// Просмотр зависимостей (referenced assemblies):
foreach (var reference in assembly.GetReferencedAssemblies())
    Console.WriteLine($"{reference.Name} v{reference.Version}");

9.2 Entry Assembly vs Executing Assembly vs Calling Assembly

Entry Assembly. Сборка точки входа процесса — то что запускалось через dotnet WebMessenger.Api.dll. В unit-тестах Assembly.GetEntryAssembly() может вернуть null — нет точки входа.

Executing Assembly. Сборка, в которой находится метод, вызывающий Assembly.GetExecutingAssembly(). Это всегда определённое значение.

Calling Assembly. Сборка непосредственного вызывающего метода (один уровень вверх по стеку). Может меняться в зависимости от того, кто вызвал текущий метод.

// Демонстрация разницы

// В WebMessenger.Api/Program.cs:
var entry     = Assembly.GetEntryAssembly();     // WebMessenger.Api.dll
var executing = Assembly.GetExecutingAssembly(); // WebMessenger.Api.dll (тот же файл)

// В WebMessenger.DAL/Repository.cs — если вызвать там:
var executing = Assembly.GetExecutingAssembly(); // WebMessenger.DAL.dll (другая сборка!)
var entry     = Assembly.GetEntryAssembly();     // WebMessenger.Api.dll (точка входа не меняется)

// Практическое применение — загрузка embedded ресурсов из правильной сборки:
// Assembly.GetExecutingAssembly() — для загрузки ресурсов из ТЕКУЩЕЙ библиотеки
var asm = Assembly.GetExecutingAssembly();
using var stream = asm.GetManifestResourceStream("WebMessenger.DAL.Migrations.seed.sql");

// Assembly.GetEntryAssembly() — для получения версии приложения в целом:
var appVersion = Assembly.GetEntryAssembly()
    ?.GetCustomAttribute<AssemblyInformationalVersionAttribute>()
    ?.InformationalVersion ?? "unknown";

// В unit-тестах GetEntryAssembly() == null — защита:
var entry = Assembly.GetEntryAssembly()
    ?? Assembly.GetExecutingAssembly(); // fallback для тестов

9.3 Assembly Loading: Assembly.Load*

Зачем загружать сборки динамически. Plugin-системы, hot-reload сценарии, dependency injection с автоопределением типов, загрузка типов по имени из конфигурации.

Assembly.Load vs LoadFrom vs LoadFile. Три метода с разной семантикой поиска сборки. Load ищет по имени через стандартные правила CLR (probing). LoadFrom ищет по пути, но регистрирует в общем контексте загрузки. LoadFile загружает по пути в изолированный контекст.

AssemblyLoadContext. .NET Core/.NET 5+ позволяет создавать изолированные контексты загрузки — для плагинов, чтобы разные версии одной библиотеки не конфликтовали.

// Assembly.Load — по имени, поиск через стандартные правила
var asm = Assembly.Load("WebMessenger.Contracts"); // ищет в bin/

// Assembly.LoadFrom — по пути (менее предпочтительно)
var asm = Assembly.LoadFrom("/plugins/MyPlugin.dll");

// Assembly.LoadFile — полная изоляция (нет разделения типов с другими контекстами)
var asm = Assembly.LoadFile("/plugins/MyPlugin.dll");

// Создание экземпляра типа по строковому имени (reflection activation)
var type = asm.GetType("MyPlugin.PluginEntry");
var instance = Activator.CreateInstance(type); // требует публичный конструктор без параметров

// AssemblyLoadContext — изолированная загрузка плагина
public class PluginLoadContext : AssemblyLoadContext
{
    private readonly AssemblyDependencyResolver _resolver;

    public PluginLoadContext(string pluginPath) : base(isCollectible: true)
    // isCollectible: true — контекст можно выгрузить (unload) из памяти
    {
        _resolver = new AssemblyDependencyResolver(pluginPath);
    }

    protected override Assembly? Load(AssemblyName assemblyName)
    {
        var path = _resolver.ResolveAssemblyToPath(assemblyName);
        return path != null ? LoadFromAssemblyPath(path) : null;
        // null — делегировать родительскому контексту (shared BCL)
    }
}

// Загрузка и выгрузка плагина:
var ctx = new PluginLoadContext("/plugins/MyPlugin.dll");
var asm = ctx.LoadFromAssemblyPath("/plugins/MyPlugin.dll");
// ... использование плагина ...
ctx.Unload(); // выгрузить контекст, освободить память плагина

9.4 Tiered Compilation и прогрев (Warmup)

Что такое JIT. .NET использует JIT (Just-In-Time) компиляцию: IL-код компилируется в нативный машинный код при первом вызове метода. Первый вызов медленнее последующих — "холодный старт".

Tiered Compilation (уровневая компиляция). Введена в .NET Core 3.0, включена по умолчанию. Работает в два уровня:
— Tier 0: быстрая компиляция без оптимизаций — метод доступен сразу после первого вызова.
— Tier 1: после нескольких вызовов (~30 раз) JIT перекомпилирует метод с полными оптимизациями в фоне.
Итог: быстрый старт + хорошая производительность в steady state.

ReadyToRun (R2R). Предварительная компиляция при публикации: часть IL сразу компилируется в нативный код. Сокращает время холодного старта, особенно заметно в serverless и контейнерах.

// Tiered Compilation включена по умолчанию.
// Отключить (не рекомендуется, только для диагностики):
<PropertyGroup>
  <TieredCompilation>false</TieredCompilation>
</PropertyGroup>

// ReadyToRun при публикации — сокращает холодный старт:
<PropertyGroup>
  <PublishReadyToRun>true</PublishReadyToRun>
</PropertyGroup>
// dotnet publish -c Release — включит R2R компиляцию

// Profile-guided Optimization (PGO) — .NET 6+:
// Runtime собирает профиль реального использования методов
// и перекомпилирует горячий код с учётом реальных данных
<PropertyGroup>
  <TieredPGO>true</TieredPGO> <!-- включено по умолчанию в .NET 8 -->
</PropertyGroup>

// Принудительный прогрев через RuntimeHelpers (редко нужно):
System.Runtime.CompilerServices.RuntimeHelpers.PrepareMethod(
    typeof(ChatService)
        .GetMethod(nameof(ChatService.GetMessagesAsync))!
        .MethodHandle);
// Компилирует метод сразу, не ждёт первого вызова

// Более практичный прогрев — вызвать критичные пути при старте приложения:
// В Program.cs / hosted service:
public class WarmupService : IHostedService
{
    private readonly IChatService _chat;
    public WarmupService(IChatService chat) => _chat = chat;

    public async Task StartAsync(CancellationToken ct)
    {
        // "пустой" вызов чтобы JIT скомпилировал метод до первого реального запроса
        await _chat.GetUserChatsAsync(Guid.Empty, 1, null);
    }

    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}
В WebMessenger (ASP.NET Core 8) Tiered Compilation включена автоматически. ReadyToRun активируется добавлением <PublishReadyToRun>true</PublishReadyToRun> в .csproj и влияет только на dotnet publish. Для production Docker-образов это рекомендуется.

10. Memory & Spans

10.1 Span<T> и ReadOnlySpan<T>

Что это. Span<T> — ref struct, представляющий непрерывный участок памяти любого происхождения: массив, стек (stackalloc), нативная память. Не аллоцирует heap. ReadOnlySpan<T> — то же самое, но без права записи.

Зачем. Позволяет работать со срезами массивов, строк и буферов без копирования данных. Например, разбить строку на части или обработать кусок байтового буфера — без создания промежуточных подстрок и массивов в heap.

Ограничение — ref struct. Span<T> — ref struct: не может быть полем класса, не может быть захвачен в лямбду, не может быть boxing'нут, не может быть параметром async-метода. Существует только на стеке. Для async API используйте Memory<T>.

// Срез массива — без копирования
byte[] buffer = new byte[1024];
Span<byte> first256  = buffer.AsSpan(0, 256);   // срез первых 256 байт
Span<byte> next256   = buffer.AsSpan(256, 256);  // следующие 256 байт
// first256 и next256 — это просмотровые окна в buffer, не копии!

// Запись в span — записывает в оригинальный массив
first256[0] = 0xFF;
Console.WriteLine(buffer[0]); // 0xFF — оригинал изменён

// Работа со строками без аллокации
ReadOnlySpan<char> text = "Hello, World!".AsSpan();
ReadOnlySpan<char> hello = text[..5];      // "Hello" — не новая строка!
ReadOnlySpan<char> world = text[7..12];    // "World" — не новая строка!

// int.Parse прямо из Span — нет промежуточной строки
ReadOnlySpan<char> digits = "12345".AsSpan();
int value = int.Parse(digits); // API в BCL принимает ReadOnlySpan<char>

// stackalloc — выделение на стеке, нет heap-аллокации вообще
Span<byte> stackBuffer = stackalloc byte[128]; // 128 байт на стеке
// Ограничение: небольшой размер (стек ограничен ~1 MB)
// Не используйте stackalloc для больших буферов!

// Парсинг CSV-строки без аллокации (классический пример)
ReadOnlySpan<char> csv = "alice,30,online".AsSpan();
int comma1 = csv.IndexOf(',');
ReadOnlySpan<char> name   = csv[..comma1];           // "alice"
ReadOnlySpan<char> rest   = csv[(comma1 + 1)..];     // "30,online"
int comma2 = rest.IndexOf(',');
ReadOnlySpan<char> age    = rest[..comma2];           // "30"
ReadOnlySpan<char> status = rest[(comma2 + 1)..];    // "online"
// Нет ни одной промежуточной string аллокации

10.2 Memory<T> и ReadOnlyMemory<T>

Что это. Memory<T> — обычная struct (не ref struct), которая тоже представляет непрерывный участок памяти. Может быть полем класса, параметром async-метода, храниться в Task. Это "async-совместимый Span".

Связь с Span. Memory<T> можно в любой момент преобразовать в Span<T> через свойство .Span — но только в синхронном контексте (не сохраняйте Span между await-точками).

Когда что использовать. Span<T> — для синхронных методов, горячего пути, стековых операций. Memory<T> — когда нужно сохранить буфер через await, в полях класса, в интерфейсах для I/O.

// Memory<T> как параметр async-метода — так нельзя делать со Span
public async Task ProcessBufferAsync(Memory<byte> buffer, CancellationToken ct)
{
    // Можно хранить buffer в поле, передавать в другие методы, использовать между await
    await Task.Delay(100, ct);

    // Получить Span для синхронной работы с данными
    Span<byte> span = buffer.Span; // OK — синхронный контекст
    span[0] = 0xFF;

    await WriteToSocketAsync(buffer, ct); // передаём Memory дальше
    // Span нельзя было бы передать в async-метод
}

// ReadOnlyMemory — для read-only сценариев (сериализация, отправка)
public async Task SendAsync(ReadOnlyMemory<byte> data, CancellationToken ct)
{
    // data.Span — для синхронного чтения
    await _socket.SendAsync(data, ct); // Socket API принимает ReadOnlyMemory
}

// Срез Memory — без копирования, как и у Span
byte[] buffer = new byte[4096];
Memory<byte> mem = buffer.AsMemory();
Memory<byte> header = mem[..16];    // первые 16 байт
Memory<byte> body   = mem[16..];   // остаток

10.3 ArrayPool<T>

Что это. Пул буферов для переиспользования массивов. Вместо создания нового массива каждый раз — берём из пула (Rent) и возвращаем (Return). Устраняет нагрузку на GC и фрагментацию LOH при работе с большими буферами.

Важное. Метод Rent(n) возвращает массив размером не менее n байт — реальный размер может быть больше. Всегда используйте переданный n как рабочий размер, не array.Length. После возврата через Return — данные в массиве могут остаться! Если есть чувствительные данные — передавайте clearArray: true.

// ArrayPool.Shared — общий пул приложения, потокобезопасен
byte[] buffer = ArrayPool<byte>.Shared.Rent(4096); // получаем буфер ≥ 4096 байт
try
{
    // ВАЖНО: реальный размер может быть больше 4096
    // Всегда работаем с запрошенным размером, не buffer.Length
    int bytesRead = await stream.ReadAsync(buffer.AsMemory(0, 4096), ct);
    ProcessData(buffer.AsSpan(0, bytesRead));
}
finally
{
    // ВСЕГДА возвращать в пул! Иначе пул истощается.
    // try/finally гарантирует возврат даже при исключении
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
    // clearArray: true — затирать данные (медленнее, но безопаснее для чувствительных данных)
}

// Кастомный пул с другими параметрами:
var customPool = ArrayPool<byte>.Create(
    maxArrayLength: 1024 * 1024,  // максимальный размер одного буфера
    maxArraysPerBucket: 50);       // количество буферов каждого размера в пуле

// Интеграция с Span/Memory (паттерн из ASP.NET Core internals):
public async Task<int> ReadChunkedAsync(Stream stream, int size, CancellationToken ct)
{
    var buffer = ArrayPool<byte>.Shared.Rent(size);
    try
    {
        int total = 0;
        int read;
        while ((read = await stream.ReadAsync(buffer.AsMemory(total, size - total), ct)) > 0)
            total += read;
        return total;
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer);
    }
}

10.4 ReadOnlySequence<T>

Что это. Представляет потенциально несмежную последовательность памяти — цепочку сегментов (ReadOnlyMemory<T>). Используется в высокопроизводительных I/O API: System.IO.Pipelines (PipeReader/PipeWriter), сетевые протоколы, парсеры.

Зачем. При получении данных по сети буфер может быть физически разбит на несколько несмежных сегментов в памяти. ReadOnlySequence<T> позволяет работать с ними как с единой последовательностью без копирования в один большой буфер.

Уровень применения. Это инфраструктурный тип. Напрямую нужен при написании сетевых протоколов, кастомных парсеров, интеграции с Pipelines. В прикладном коде обычно не встречается.

// ReadOnlySequence — последовательность из нескольких сегментов
// Типичный источник: System.IO.Pipelines
using System.IO.Pipelines;
using System.Buffers;

var pipe = new Pipe();

// Пишем данные в несколько частей:
pipe.Writer.Write(Encoding.UTF8.GetBytes("Hello, "));
pipe.Writer.Write(Encoding.UTF8.GetBytes("World!"));
await pipe.Writer.FlushAsync();

// Читаем как единую ReadOnlySequence:
var result = await pipe.Reader.ReadAsync();
ReadOnlySequence<byte> buffer = result.Buffer;

// Обработка — последовательность может состоять из нескольких сегментов
if (buffer.IsSingleSegment)
{
    // Оптимизация: если один сегмент — работаем напрямую
    ProcessSpan(buffer.FirstSpan);
}
else
{
    // Несколько сегментов — итерируем
    foreach (ReadOnlyMemory<byte> segment in buffer)
        ProcessMemory(segment);
}

// SequenceReader<T> — удобный API поверх ReadOnlySequence для парсинга
var reader = new SequenceReader<byte>(buffer);
while (reader.TryReadTo(out ReadOnlySpan<byte> line, delimiter: (byte)'\n'))
{
    ProcessLine(line); // обрабатываем строку без копирования
}

pipe.Reader.AdvanceTo(buffer.End); // сообщить: потребили до конца
Итог по типам памяти:
  • Span<T> — синхронный код, минимальные аллокации, стек/массив/нативная память
  • Memory<T> — async-код, поля класса, I/O интерфейсы
  • ArrayPool<T> — переиспользование буферов, устранение давления на GC и LOH
  • ReadOnlySequence<T> — несмежная память, Pipelines, сетевые протоколы

11. Async / Await

11.1 Как работает async/await под капотом

Что происходит при await. Ключевое слово await не блокирует поток — оно освобождает его обратно в ThreadPool пока операция ожидает (например, ответ от БД). Когда операция завершается, выполнение продолжается — возможно на другом потоке из ThreadPool. Компилятор преобразует async-метод в конечный автомат (state machine), сохраняющий состояние между await-точками.

ThreadPool. Управляет пулом рабочих потоков. Для CPU-bound задач: Task.Run ставит работу в очередь ThreadPool. Для I/O-bound задач: OS уведомляет .NET об окончании I/O — поток ThreadPool принимает продолжение. Не нужно создавать потоки вручную через new Thread() — ThreadPool управляет их количеством автоматически.

// Синхронный код — поток заблокирован на всё время ожидания:
var result = _repo.GetAll().ToList(); // поток занят, не может обслуживать другие запросы

// Асинхронный код — поток свободен во время ожидания:
var result = await _repo.GetAll().ToListAsync(ct); // поток вернулся в ThreadPool

// Что компилятор делает с async-методом:
public async Task<User?> FindUserAsync(string username)
{
    var user = await _repo.FirstOrDefaultAsync(u => u.Username == username);
    return user;
}
// Компилятор генерирует примерно:
// struct FindUserAsync_StateMachine : IAsyncStateMachine
// {
//     int _state;          // текущая позиция в методе
//     string username;     // захваченные переменные
//     TaskAwaiter awaiter; // awaiter текущей await-точки
//     void MoveNext() { switch(_state) { ... } } // логика продолжения
// }

// Task.Run — для CPU-bound работы (не для I/O!)
var result = await Task.Run(() => HeavyCpuCalculation(data), ct);
// Внутри: ставит делегат в очередь ThreadPool, возвращает Task

// new Thread() — почти никогда не нужно в современном .NET:
// ThreadPool управляет этим лучше. Явный Thread нужен только для
// задач с особыми требованиями (STA для COM, background демоны).

11.2 CancellationToken

Что это. Механизм кооперативной отмены. CancellationTokenSource владеет токеном и может его отменить. CancellationToken — это read-only хендл, который передаётся в методы. Метод периодически проверяет токен и завершается досрочно при отмене.

Кооперативность. Метод не отменяется принудительно снаружи — он сам должен проверять токен и выбрасывать OperationCanceledException. Это предотвращает corrupt state при внезапном прерывании.

Связывание токенов. CancellationTokenSource.CreateLinkedTokenSource объединяет несколько токенов в один — отмена любого из них отменяет объединённый.

// WebMessenger — CancellationToken везде в ChatHub и ChatService
public async Task<SendMessageResponse> SendMessageToUserAsync(
    Guid me, Guid other, string content, CancellationToken ct)
{
    // ct проверяется автоматически во всех async BCL-методах
    await _uow.MessageRepository.InsertAsync(message, ct);
    await _uow.CommitAsync(ct);                           // передаём дальше по цепочке
    await _events.MessageCreatedAsync(chatId.Value, dto, other, ct);
    // Если клиент отключился — ct будет отменён,
    // методы выбросят OperationCanceledException, операция прервётся
}

// В ChatHub: Context.ConnectionAborted — автоматически отменяется при дисконнекте
public async Task JoinChat(Guid chatId)
{
    var ct = Context.ConnectionAborted; // токен жизни подключения
    await Groups.AddToGroupAsync(Context.ConnectionId, SignalRGroups.Chat(chatId), ct);
}

// CancellationTokenSource с таймаутом:
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(30));
await DoLongOperationAsync(cts.Token);

// CancellationTokenSource.CancelAfter — отмена через задержку:
var cts = new CancellationTokenSource();
cts.CancelAfter(TimeSpan.FromSeconds(10)); // отменить через 10 сек
await DoOperationAsync(cts.Token);

// Связывание токенов — отменяется если отменён ЛЮБОЙ из источников:
using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(
    requestCt,      // токен HTTP-запроса
    shutdownCt);    // токен graceful shutdown приложения
await DoWorkAsync(linkedCts.Token);

// Ручная проверка в CPU-bound коде (не awaitable):
for (int i = 0; i < 1_000_000; i++)
{
    ct.ThrowIfCancellationRequested(); // бросает OperationCanceledException
    Process(data[i]);
}

11.3 ConfigureAwait(false)

Проблема SynchronizationContext. В UI-приложениях (WinForms, WPF) и ASP.NET (classic) после await продолжение пытается вернуться на оригинальный поток через SynchronizationContext. Это дорого и может вызвать deadlock, если оригинальный поток заблокирован ожиданием Task.

ConfigureAwait(false). Говорит "не пытайся вернуться на исходный контекст — продолжай на любом потоке ThreadPool". Устраняет deadlock, немного быстрее.

В ASP.NET Core. ASP.NET Core специально не устанавливает SynchronizationContext (в отличие от classic ASP.NET). Поэтому дедлок там не возникнет. Но ConfigureAwait(false) всё равно — хорошая практика в библиотечном коде (библиотека не знает, в каком контексте её вызовут).

// В библиотечном коде — ВСЕГДА ConfigureAwait(false):
// Библиотека не знает будет ли UI-контекст у вызывающего
public async Task<User?> FindUserByUsernameAsync(string username)
{
    return await _repo.GetAll()
        .FirstOrDefaultAsync(u => u.Username == username)
        .ConfigureAwait(false); // не восстанавливать контекст
}

// Deadlock без ConfigureAwait(false) — классическая ловушка в UI/classic ASP.NET:
// UI-поток вызывает .Result (блокирующий вызов)
var user = FindUserByUsernameAsync("alice").Result;
// 1. UI-поток заблокирован на .Result, ждёт завершения Task
// 2. После await продолжение хочет вернуться на UI-поток
// 3. UI-поток занят — DEADLOCK

// Решение 1: никогда не вызывать .Result / .Wait() на async Task в UI
// Решение 2: ConfigureAwait(false) в библиотеке — продолжение не ждёт UI-потока

// В application-коде (ASP.NET Core, console) — ConfigureAwait необязателен,
// но не вреден. Многие команды его не пишут в app-коде для краткости.

// ValueTask vs Task:
// Task — всегда heap-аллокация для объекта Task
// ValueTask — struct, нет аллокации если результат доступен синхронно
// Используйте ValueTask для hot-path методов которые часто завершаются синхронно:
public ValueTask<bool> IsUserCachedAsync(Guid userId)
{
    if (_cache.ContainsKey(userId))
        return ValueTask.FromResult(true); // нет аллокации!
    return new ValueTask<bool>(LoadFromDbAsync(userId));
}

11.4 Task.WhenAll и AggregateException

Task.WhenAll. Запускает несколько задач параллельно и ждёт завершения всех. Эффективен для I/O-bound параллелизма (множественные запросы к БД/API). В отличие от последовательных await — все задачи выполняются одновременно.

AggregateException. Если несколько задач в WhenAll завершились с ошибкой — все исключения оборачиваются в AggregateException. При простом await Task.WhenAll(...) выбрасывается только первое исключение. Чтобы увидеть все — нужно поймать AggregateException явно.

// Последовательно — медленно (ждём каждый по очереди):
var chats    = await _chatRepo.GetUserChatsAsync(userId);    // 50ms
var contacts = await _contactRepo.GetContactsAsync(userId);  // 40ms
var profile  = await _userRepo.GetProfileAsync(userId);      // 30ms
// Итого: ~120ms

// Параллельно через WhenAll — быстрее:
var chatsTask    = _chatRepo.GetUserChatsAsync(userId);
var contactsTask = _contactRepo.GetContactsAsync(userId);
var profileTask  = _userRepo.GetProfileAsync(userId);
await Task.WhenAll(chatsTask, contactsTask, profileTask);
// Итого: ~50ms (самый долгий)

var chats    = chatsTask.Result;    // Task уже завершён — .Result безопасен
var contacts = contactsTask.Result;
var profile  = profileTask.Result;

// Обработка ошибок из нескольких задач:
var tasks = users.Select(u => ProcessUserAsync(u, ct)).ToList();
try
{
    await Task.WhenAll(tasks);
}
catch (Exception)
{
    // await WhenAll выбрасывает только ПЕРВОЕ исключение!
    // Чтобы увидеть все:
    var failed = tasks.Where(t => t.IsFaulted);
    foreach (var t in failed)
    {
        foreach (var ex in t.Exception!.InnerExceptions)
            _logger.LogError(ex, "Task failed");
    }
}

// Task.WhenAny — завершиться когда завершится ЛЮБАЯ задача:
var cts = new CancellationTokenSource();
var workTask    = DoLongWorkAsync(cts.Token);
var timeoutTask = Task.Delay(TimeSpan.FromSeconds(30), cts.Token);

var first = await Task.WhenAny(workTask, timeoutTask);
if (first == timeoutTask)
{
    cts.Cancel();           // отменить работу
    throw new TimeoutException("Operation timed out");
}
// Результат workTask готов:
var result = await workTask;

11.5 IAsyncEnumerable<T> и await using

IAsyncEnumerable<T>. Асинхронная последовательность: элементы появляются по одному асинхронно (например, страницы из БД, события из очереди). Потребляется через await foreach. Поддерживает CancellationToken через [EnumeratorCancellation].

await using. Асинхронное освобождение ресурсов — вызывает DisposeAsync() вместо синхронного Dispose(). Нужно для объектов реализующих IAsyncDisposable: открытые соединения, потоки, транзакции EF Core.

// IAsyncEnumerable — стриминг сообщений без загрузки всего в память
public async IAsyncEnumerable<ChatMessageDto> StreamMessagesAsync(
    Guid chatId,
    [EnumeratorCancellation] CancellationToken ct = default)
{
    DateTime? cursor = null;
    bool hasMore;
    do
    {
        var page = await _uow.GetMessagesPageAsync(chatId, cursor, ct);
        foreach (var msg in page.Items)
            yield return msg;        // каждое сообщение по мере готовности
        hasMore = page.HasMore;
        cursor = page.NextBefore;
    } while (hasMore && !ct.IsCancellationRequested);
}

// Потребление:
await foreach (var msg in StreamMessagesAsync(chatId, ct))
{
    await SendToClientAsync(msg, ct);
    // При отмене ct — итерация прекратится
}

// WithCancellation — передать токен в IAsyncEnumerable:
await foreach (var msg in service.StreamMessagesAsync(chatId)
    .WithCancellation(ct))          // токен отмены
{
    Process(msg);
}

// await using — для IAsyncDisposable (EF Core DbContext, транзакции и т.д.)
await using var transaction = await _context.Database.BeginTransactionAsync(ct);
try
{
    await _context.Messages.AddAsync(message, ct);
    await _context.SaveChangesAsync(ct);
    await transaction.CommitAsync(ct);
}
catch
{
    await transaction.RollbackAsync(ct); // асинхронный откат
    throw;
}
// DisposeAsync() вызывается автоматически при выходе из блока

11.6 Deadlocks и примитивы синхронизации

Deadlock в async. Классический паттерн: синхронный вызов async через .Result или .Wait() при наличии SynchronizationContext. Поток заблокирован, продолжение ждёт этого же потока — взаимная блокировка.

SemaphoreSlim. Async-совместимый семафор. Ограничивает число одновременно выполняющихся async-операций. В отличие от lock — не блокирует поток, а освобождает его через await WaitAsync().

Почему нельзя lock внутри async. lock — синхронный примитив. Захват lock и await в одном блоке — антипаттерн: поток держит lock, уходит на await, другие потоки блокируются не на await а на синхронном lock.

// Deadlock — НИКОГДА не делайте .Result / .Wait() если есть SynchronizationContext:
var user = FindUserAsync("alice").Result; // DEADLOCK в UI / classic ASP.NET!

// Безопасно в ASP.NET Core (нет SynchronizationContext), но всё равно плохая практика:
// Блокирует поток ThreadPool — снижает масштабируемость

// SemaphoreSlim — ограничение параллельных операций без блокировки потока
private readonly SemaphoreSlim _semaphore = new SemaphoreSlim(3); // max 3 параллельно

public async Task ProcessUserAsync(Guid userId, CancellationToken ct)
{
    await _semaphore.WaitAsync(ct); // async-ожидание: поток свободен пока ждём
    try
    {
        await DoHeavyWorkAsync(userId, ct);
    }
    finally
    {
        _semaphore.Release(); // ВСЕГДА в finally!
    }
}

// lock нельзя использовать с await — НЕПРАВИЛЬНО:
lock (_lockObj)
{
    await SomeAsyncMethod(); // ОШИБКА компиляции: нельзя await внутри lock
}

// Правильно: SemaphoreSlim вместо lock для async-кода
await _semaphore.WaitAsync(ct);
try
{
    await SomeAsyncMethod();
}
finally
{
    _semaphore.Release();
}

// Monitor.TryEnter — синхронный, только для синхронного кода
// Mutex — для межпроцессной синхронизации (тяжелее SemaphoreSlim)
В WebMessenger: CancellationToken передаётся по всей цепочке от Hub до репозитория. Context.ConnectionAborted — токен жизни SignalR-соединения, при дисконнекте все async-операции этого соединения отменяются автоматически.

12. Serialization

12.1 System.Text.Json — основные опции

Что это. System.Text.Json — встроенный высокопроизводительный JSON-сериализатор .NET (доступен с .NET Core 3.0). Быстрее Newtonsoft.Json, не требует зависимостей. В ASP.NET Core используется по умолчанию.

JsonSerializerOptions. Центральный объект конфигурации сериализатора. Создание опций — дорогая операция (кэшируется внутри). Никогда не создавайте новый экземпляр JsonSerializerOptions на каждый вызов — используйте статический/singleton.

// Статические опции — один раз, потом переиспользуются
private static readonly JsonSerializerOptions _jsonOptions = new()
{
    PropertyNamingPolicy = JsonNamingPolicy.CamelCase,      // Username → username
    PropertyNameCaseInsensitive = true,                      // десериализация без учёта регистра
    DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull, // не сериализовать null-поля
    WriteIndented = false,                                   // compact JSON (без отступов) в production
    ReferenceHandler = ReferenceHandler.IgnoreCycles,       // игнорировать циклические ссылки
    NumberHandling = JsonNumberHandling.AllowReadingFromString, // "42" → 42
};

// ASP.NET Core настраивает опции глобально через AddControllers():
// В WebMessenger Program.cs — явных JSON-настроек нет, используется дефолт ASP.NET Core
// (camelCase уже включён по умолчанию через AddControllers())
builder.Services.AddControllers()
    .AddJsonOptions(opts =>
    {
        opts.JsonSerializerOptions.PropertyNamingPolicy = JsonNamingPolicy.CamelCase;
        opts.JsonSerializerOptions.DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull;
        opts.JsonSerializerOptions.Converters.Add(new JsonStringEnumConverter());
    });

// Атрибуты на типах/свойствах — переопределяют глобальные настройки:
public class UserDto
{
    [JsonPropertyName("user_name")]       // переопределить имя поля
    public string Username { get; set; }

    [JsonIgnore]                          // не сериализовать это поле
    public string PasswordHash { get; set; }

    [JsonInclude]                         // включить даже если private setter
    public DateTime CreatedAt { get; private set; }
}

// Сериализация и десериализация:
var json = JsonSerializer.Serialize(user, _jsonOptions);
var user = JsonSerializer.Deserialize<UserDto>(json, _jsonOptions);

// Stream-версии — без промежуточной string (меньше аллокаций):
await JsonSerializer.SerializeAsync(stream, user, _jsonOptions, ct);
var user = await JsonSerializer.DeserializeAsync<UserDto>(stream, _jsonOptions, ct);

12.2 Кастомный JsonConverter<T>

Когда нужен. Когда встроенная сериализация не подходит: нестандартный формат даты, кастомное представление перечисления, тип из сторонней библиотеки, который нельзя разметить атрибутами, условная сериализация по значению.

Как работает. Наследуемся от JsonConverter<T>, реализуем Read (десериализация из Utf8JsonReader) и Write (сериализация в Utf8JsonWriter). Регистрируется через опции или атрибут [JsonConverter].

// Пример: DateTime сериализуется как Unix timestamp (число)
// вместо ISO 8601 строки (нужно для взаимодействия с некоторыми клиентами)
public class UnixTimestampConverter : JsonConverter<DateTime>
{
    private static readonly DateTime _epoch = new(1970, 1, 1, 0, 0, 0, DateTimeKind.Utc);

    public override DateTime Read(
        ref Utf8JsonReader reader,
        Type typeToConvert,
        JsonSerializerOptions options)
    {
        // Читаем число из JSON
        var timestamp = reader.GetInt64();
        return _epoch.AddSeconds(timestamp);
    }

    public override void Write(
        Utf8JsonWriter writer,
        DateTime value,
        JsonSerializerOptions options)
    {
        // Пишем число в JSON
        var timestamp = (long)(value.ToUniversalTime() - _epoch).TotalSeconds;
        writer.WriteNumberValue(timestamp);
    }
}

// Регистрация глобально:
options.Converters.Add(new UnixTimestampConverter());

// Или через атрибут на конкретном свойстве:
public class MessageDto
{
    [JsonConverter(typeof(UnixTimestampConverter))]
    public DateTime SentAt { get; init; }  // только это поле как timestamp
    public string Content { get; init; }    // остальные — стандартно
}

// В WebMessenger SentAt сериализуется стандартно как ISO 8601,
// что правильно для взаимодействия с TypeScript-клиентом

12.3 Полиморфная сериализация

Проблема. По умолчанию JsonSerializer сериализует объект по статическому типу переменной. Если переменная типа BaseNotification содержит MessageNotification, в JSON не попадут специфичные поля подтипа, и десериализатор не узнает нужный конкретный тип.

Решение в .NET 7+. Атрибуты [JsonPolymorphic] и [JsonDerivedType] — декларативная настройка полиморфизма. Сериализатор добавляет discriminator-поле (тип) в JSON.

// Иерархия уведомлений
[JsonPolymorphic(TypeDiscriminatorPropertyName = "$type")]
[JsonDerivedType(typeof(MessageNotification), "message")]
[JsonDerivedType(typeof(ReadReceiptNotification), "readReceipt")]
[JsonDerivedType(typeof(TypingNotification), "typing")]
public abstract class BaseNotification
{
    public Guid ChatId { get; init; }
    public DateTime Timestamp { get; init; }
}

public class MessageNotification : BaseNotification
{
    public string Content { get; init; } = "";
    public Guid SenderId { get; init; }
}

public class TypingNotification : BaseNotification
{
    public bool IsTyping { get; init; }
}

// Сериализация BaseNotification автоматически добавит "$type":
BaseNotification n = new MessageNotification { ChatId = id, Content = "hi" };
var json = JsonSerializer.Serialize(n);
// { "$type": "message", "content": "hi", "chatId": "...", "timestamp": "..." }

// Десериализация восстановит правильный подтип:
var deserialized = JsonSerializer.Deserialize<BaseNotification>(json);
// deserialized is MessageNotification — true!

// До .NET 7 — кастомный конвертер или ручной switch по "$type"

// В WebMessenger — SignalR payloads: sealed records (нет полиморфизма),
// каждый тип события — отдельный метод в IChatClient. Это предпочтительный подход.

12.4 Версионирование контрактов сериализации

Проблема. Когда API меняется (добавляются/удаляются/переименовываются поля), старые клиенты могут получить неожиданные данные или не смочь десериализовать ответ. Нужны стратегии безопасной эволюции контрактов.

Правила безопасного изменения.

  • Добавление нового поля — безопасно: старые клиенты игнорируют неизвестные поля (System.Text.Json так делает по умолчанию).
  • Удаление поля — небезопасно: старые клиенты ожидают его. Сначала пометить deprecated, потом убрать в следующей версии.
  • Переименование поля — небезопасно: использовать [JsonPropertyName] для обратной совместимости.
  • Изменение типа — очень опасно: нужна кастомная конверсия.
// Безопасное добавление поля — новые клиенты получат, старые проигнорируют
public sealed record ChatMessageDto
{
    public Guid Id { get; init; }
    public string Content { get; init; } = "";
    public DateTime SentAt { get; init; }
    public string? ReplyToId { get; init; }    // добавили в v2 — nullable, старые клиенты игнорируют
    public bool? IsEdited { get; init; }       // добавили в v3 — nullable, безопасно
}

// Переименование — сохранить старое имя через JsonPropertyName
public sealed record UserDto
{
    // Переименовали "display_name" → "username" — старые клиенты продолжат работать
    [JsonPropertyName("username")]
    [JsonInclude]
    public string Username { get; init; } = "";

    // Или поддержать оба имени через кастомный конвертер / два свойства
    [JsonPropertyName("display_name")] // устаревшее имя для backward compatibility
    public string? DisplayName
    {
        get => null; // не сериализовать значение (WhenWritingNull убьёт это поле)
        init { if (value is not null) Username = value; } // принять старое имя при десериализации
    }
}

// Неизвестные поля — по умолчанию игнорируются в System.Text.Json
// Чтобы получать предупреждение о неизвестных:
var opts = new JsonSerializerOptions
{
    UnmappedMemberHandling = JsonUnmappedMemberHandling.Disallow // бросать исключение
    // или JsonUnmappedMemberHandling.Skip (по умолчанию)
};

12.5 XML: XmlReader / XmlWriter для больших документов

Когда XML. Интеграции с legacy-системами, SOAP-сервисы, форматы вроде DOCX/XLSX (которые внутри XML), конфигурационные файлы. Для новых API предпочтительнее JSON.

Потоковый vs DOM-подход. XDocument/XmlDocument загружают весь документ в память — плохо для больших файлов. XmlReader/XmlWriter — потоковые: читают/пишут по одному элементу за раз без загрузки всего документа.

// XDocument — удобно для маленьких документов (весь DOM в памяти)
var doc = XDocument.Load("config.xml");
var value = doc.Root?.Element("Setting")?.Value;

// XmlReader — потоковое чтение большого XML без загрузки в память
await using var stream = File.OpenRead("large.xml");
using var reader = XmlReader.Create(stream, new XmlReaderSettings
{
    Async = true,
    IgnoreWhitespace = true,
    IgnoreComments = true
});

while (await reader.ReadAsync())
{
    if (reader.NodeType == XmlNodeType.Element && reader.Name == "Message")
    {
        var id = reader.GetAttribute("id");
        await reader.ReadAsync(); // переходим к содержимому
        var content = reader.Value;
        await ProcessMessageAsync(id, content);
        // Обрабатываем по одному — не нужна память для всего файла
    }
}

// XmlWriter — потоковая запись
await using var outStream = File.Create("output.xml");
await using var writer = XmlWriter.Create(outStream, new XmlWriterSettings
{
    Async = true,
    Indent = false,     // compact
    Encoding = Encoding.UTF8
});

await writer.WriteStartDocumentAsync();
await writer.WriteStartElementAsync(null, "Messages", null);
foreach (var msg in messages)
{
    await writer.WriteStartElementAsync(null, "Message", null);
    await writer.WriteAttributeStringAsync(null, "id", null, msg.Id.ToString());
    await writer.WriteStringAsync(msg.Content);
    await writer.WriteEndElementAsync();
}
await writer.WriteEndElementAsync();
await writer.WriteEndDocumentAsync();

13. Reflection & Metadata

13.1 Что такое Reflection и зачем

Что это. Reflection — механизм .NET для инспекции и вызова типов, методов, свойств и полей в runtime через объекты Type, MethodInfo, PropertyInfo и т. д. Позволяет работать с кодом как с данными — читать метаданные, создавать экземпляры, вызывать методы по имени.

Зачем. Используется в фреймворках: DI-контейнеры находят и инициализируют типы, ORM-ы маппят колонки на свойства, сериализаторы читают структуру типа. В прикладном коде — автоматическая регистрация компонентов, валидаторы, mapper-библиотеки.

Стоимость. Reflection значительно медленнее прямых вызовов (на порядки). Каждый GetMethod, GetProperties, Invoke — это runtime-поиск и boxing/unboxing. В hot-path кэшируйте результаты Reflection.

// Получение Type — три способа
Type t1 = typeof(User);                    // compile-time — предпочтительно
Type t2 = user.GetType();                  // runtime — от экземпляра
Type t3 = Type.GetType("WebMessenger.DAL.Entities.User"); // по полному имени строкой

// Инспекция свойств
foreach (var prop in typeof(User).GetProperties())
{
    Console.WriteLine($"{prop.Name}: {prop.PropertyType.Name}");
    // Username: String
    // Email: String
    // IsOnline: Boolean ...
}

// BindingFlags — контроль видимости при поиске
var allProps = typeof(User).GetProperties(
    BindingFlags.Public | BindingFlags.NonPublic |
    BindingFlags.Instance | BindingFlags.Static);
// Без BindingFlags: GetProperties() возвращает только public instance

// Инспекция методов
var method = typeof(UserService).GetMethod(
    nameof(UserService.FindUserByUsernameAsync),
    BindingFlags.Public | BindingFlags.Instance);

Console.WriteLine(method?.ReturnType.Name);          // Task`1
Console.WriteLine(method?.GetParameters().Length);   // 1 (string username)

// Чтение атрибутов через Reflection
var props = typeof(User).GetProperties();
foreach (var prop in props)
{
    var maxLen = prop.GetCustomAttribute<MaxLengthAttribute>();
    if (maxLen is not null)
        Console.WriteLine($"{prop.Name}: MaxLength = {maxLen.Length}");
}
// Username: MaxLength = 50
// Email: MaxLength = 255

13.2 Создание экземпляров через Reflection

Activator.CreateInstance. Самый простой способ создать экземпляр типа по его объекту Type. Подходит для plugin-систем, фабрик по конфигурации, DI-bootstrapping.

Стоимость. Activator.CreateInstance использует Reflection внутри — медленнее чем new. Для hot-path лучше закешировать делегат создания через скомпилированное выражение.

// Создание по объекту Type — без знания конкретного типа на compile-time
Type userType = typeof(User);
var user = (User)Activator.CreateInstance(userType)!;

// С параметрами конструктора:
Type serviceType = typeof(AuthService);
var service = Activator.CreateInstance(
    serviceType,
    optionsArg,  // IOptions<JwtOptions>
    loggerArg);  // ILogger<AuthService>

// Вызов метода через Reflection:
var method = typeof(UserService).GetMethod(nameof(UserService.SearchUsersAsync));
var resultTask = (Task)method!.Invoke(serviceInstance, [userId, "alice", 10])!;
await resultTask; // Invoke возвращает object, нужен каст

// Чтение/запись свойств через PropertyInfo:
var prop = typeof(User).GetProperty(nameof(User.Username));
prop!.SetValue(user, "alice");               // установить значение
var name = (string)prop.GetValue(user)!;    // прочитать значение
// GetValue/SetValue — boxing для value types, медленнее прямого доступа

// Получение значения приватного поля (отладка/тестирование):
var field = typeof(AuthService).GetField(
    "_jwt",
    BindingFlags.NonPublic | BindingFlags.Instance);
var jwt = field?.GetValue(authServiceInstance);

13.3 Кэширование Reflection и Expression.Compile

Проблема. Если вызывать GetMethod, MethodInfo.Invoke в цикле — это катастрофически медленно. Решения: кэшировать MethodInfo в статическом поле, или — ещё лучше — скомпилировать делегат через Expression.Compile().

Expression.Compile. Позволяет построить дерево выражений и скомпилировать его в нативный делегат. Первый вызов дорогой (компиляция), но последующие — такая же скорость как прямой вызов.

// ПЛОХО — GetMethod на каждый вызов:
public string GetUsername(object user)
{
    return (string)user.GetType()         // GetType() — дешёво
        .GetProperty("Username")!         // GetProperty — дорого каждый раз!
        .GetValue(user)!;
}

// ХОРОШО — кэшируем PropertyInfo:
private static readonly PropertyInfo _usernameProp =
    typeof(User).GetProperty(nameof(User.Username))!;

public string GetUsername(User user)
{
    return (string)_usernameProp.GetValue(user)!; // PropertyInfo закеширован
}

// ЛУЧШЕ — Expression.Compile: скорость как у прямого вызова
private static readonly Func<User, string> _getUsernameCompiled = CompileGetter();

private static Func<User, string> CompileGetter()
{
    var param = Expression.Parameter(typeof(User), "u");
    var body  = Expression.Property(param, nameof(User.Username));
    return Expression.Lambda<Func<User, string>>(body, param).Compile();
    // Compile() генерирует нативный код — один раз при старте приложения
}

public string GetUsernameCompiled(User user)
{
    return _getUsernameCompiled(user); // вызов через нативный делегат — O(1)
}

// Обобщённая фабрика через Expression.Compile — создание объектов без Activator
private static readonly Dictionary<Type, Func<object>> _factories = new();

public static object FastCreate(Type type)
{
    if (!_factories.TryGetValue(type, out var factory))
    {
        // Строим Expression: () => new T()
        var body = Expression.New(type);
        factory = Expression.Lambda<Func<object>>(body).Compile();
        _factories[type] = factory;
    }
    return factory();
}
// Первый вызов: медленно (Expression.Compile)
// Последующие: ~как new T() напрямую

13.4 Delegate.CreateDelegate

Что это. Более быстрый способ вызова метода через Reflection чем MethodInfo.Invoke: создаём типизированный делегат один раз, вызываем многократно с нативной скоростью. Промежуточный вариант между Invoke и Expression.Compile.

// Создание делегата из MethodInfo
MethodInfo method = typeof(UserService)
    .GetMethod(nameof(UserService.IsUsernameExistsAsync))!;

// Создать типизированный делегат:
var checker = (Func<string, Task<bool>>)Delegate.CreateDelegate(
    typeof(Func<string, Task<bool>>),
    serviceInstance,   // объект-владелец (для instance методов)
    method);

// Вызов — скорость как у прямого вызова!
bool exists = await checker("alice");

// Для static методов — без объекта-владельца:
MethodInfo staticMethod = typeof(string)
    .GetMethod(nameof(string.IsNullOrWhiteSpace))!;

var isBlank = (Func<string?, bool>)Delegate.CreateDelegate(
    typeof(Func<string?, bool>),
    staticMethod);   // без экземпляра

Console.WriteLine(isBlank("  ")); // true

// Сравнение скоростей (benchmark-ориентир):
// MethodInfo.Invoke:       ~200 нс за вызов
// Delegate.CreateDelegate: ~3 нс за вызов (после создания)
// Expression.Compile:      ~2 нс за вызов (после компиляции)
// Прямой вызов:            ~1 нс за вызов

13.5 Метаданные в runtime: производительность и AOT

Проблема с AOT. Native AOT публикация (.NET 8) компилирует приложение в нативный бинарник без JIT. Reflection работает ограниченно: типы которые не были "видны" компилятору при публикации могут быть обрезаны trimmer'ом — и Reflection их не найдёт.

Атрибуты для сохранения. [DynamicallyAccessedMembers] сообщает trimmer'у: "у этого типа будут использоваться члены через Reflection, не обрезать".

// [DynamicallyAccessedMembers] — подсказка trimmer'у
// Используется в фреймворках (EF Core, ASP.NET Core, DI)
public static void Inspect(
    [DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.PublicProperties)]
    Type type)  // сохранить все публичные свойства этого типа
{
    foreach (var prop in type.GetProperties()) // Reflection безопасен
        Console.WriteLine(prop.Name);
}

// [RequiresUnreferencedCode] — пометить что метод небезопасен для trim
[RequiresUnreferencedCode("Uses Reflection over unknown types")]
public void RegisterAll(Assembly assembly)
{
    // Scan всех типов — trimmer не знает что останется
    var types = assembly.GetTypes()
        .Where(t => t.GetInterface("IService") != null);
    // ...
}

// Source Generators — замена Reflection для AOT-совместимого кода:
// JsonSerializerContext генерирует сериализацию без Reflection
[JsonSerializable(typeof(UserDto))]
[JsonSerializable(typeof(ChatMessageDto))]
public partial class AppJsonContext : JsonSerializerContext { }

// Использование контекста вместо опций:
var json = JsonSerializer.Serialize(user, AppJsonContext.Default.UserDto);
// Нет Reflection в runtime — AOT-безопасно, работает быстрее

// Проверка: будет ли тип доступен в runtime
var type = Type.GetType("WebMessenger.DAL.Entities.User");
if (type is null)
    throw new InvalidOperationException(
        "Type was trimmed. Add [DynamicallyAccessedMembers] or preserve via linker descriptor");
Правило: Reflection — мощный инструмент для инфраструктурного кода (DI, ORM, сериализаторы). В прикладном коде — осторожно. Всегда кэшируйте MethodInfo/PropertyInfo. Для AOT — используйте Source Generators вместо Reflection.

14. Dynamic Types и DLR

14.1 Что такое DLR и зачем

Что такое DLR. Dynamic Language Runtime — слой поверх CLR, добавляющий позднее связывание (late binding): тип и операция разрешаются не при компиляции, а в runtime. В C# доступен через ключевое слово dynamic.

Когда это нужно. Работа с данными неизвестной структуры: JSON без известной схемы, COM-объекты (Excel/Word Automation), результаты из DuckTyping-интерфейсов, скриптинг. В большинстве прикладных задач dynamic не нужен — используйте обобщения и интерфейсы.

// static dispatch — компилятор проверяет типы, быстро
string name = user.Username;     // компилятор знает тип User

// dynamic — всё разрешается в runtime через DLR
dynamic dUser = user;
string name2 = dUser.Username;  // работает, но:
// 1. Компилятор не проверяет — ошибка только в runtime
// 2. DLR кэширует результат после первого вызова (CallSite cache)
// 3. ~10–50x медленнее статического вызова при первом вызове

// Пример реальной пользы — COM Automation (Excel):
// dynamic app = new Application(); // Excel.Application
// app.Visible = true;
// dynamic sheet = app.ActiveSheet;
// sheet.Cells[1, 1].Value = "Hello"; // без dynamic нужны касты каждого шага

// dynamic и перегрузка — выбирается в runtime:
void Print(string s) => Console.WriteLine($"string: {s}");
void Print(int i)    => Console.WriteLine($"int: {i}");

dynamic val = 42;
Print(val); // "int: 42" — перегрузка разрешается в runtime
val = "hi";
Print(val); // "string: hi"

14.2 ExpandoObject — динамические объекты со словарём

Что это. ExpandoObject — встроенный класс, реализующий IDynamicMetaObjectProvider. Позволяет добавлять свойства и методы к объекту в runtime как к словарю.

Когда полезен. Построение динамических DTO без создания класса, конфигурационные объекты, шаблоны данных. Альтернатива: Dictionary<string, object> — более явная, чуть быстрее, без DLR-накладных расходов.

dynamic expando = new ExpandoObject();

// Добавляем свойства динамически:
expando.Username = "alice";
expando.IsOnline  = true;
expando.Greet     = (Action)(() => Console.WriteLine($"Hello, {expando.Username}!"));

expando.Greet(); // Hello, alice!

// ExpandoObject реализует IDictionary<string, object> — можно итерировать:
var dict = (IDictionary<string, object>)expando;
foreach (var kv in dict)
    Console.WriteLine($"{kv.Key} = {kv.Value}");
// Username = alice
// IsOnline = True
// Greet = System.Action

// Проверка наличия свойства:
bool hasEmail = dict.ContainsKey("Email"); // false — не добавляли

// INotifyPropertyChanged поддерживается автоматически:
((INotifyPropertyChanged)expando).PropertyChanged +=
    (_, e) => Console.WriteLine($"Changed: {e.PropertyName}");
expando.Username = "bob"; // Changed: Username

// Сравнение с Dictionary<string, object>:
var plain = new Dictionary<string, object>
{
    ["Username"] = "alice",
    ["IsOnline"] = true
};
// plain["Username"] — явно, быстро, но нет dot-нотации
// expando.Username — удобно, но DLR-накладные расходы

14.3 DynamicObject — кастомное динамическое поведение

Что это. Базовый класс, переопределив методы которого, вы управляете тем, что происходит при обращении к динамическому объекту: что вернуть на obj.SomeProp, что вызвать на obj.SomeMethod(). Используется для прокси, DSL, оберток над внешними API.

// Пример: прокси с логированием обращений
public class LoggingProxy : DynamicObject
{
    private readonly object _inner;

    public LoggingProxy(object inner) => _inner = inner;

    // Вызывается при доступе к любому свойству
    public override bool TryGetMember(GetMemberBinder binder, out object? result)
    {
        Console.WriteLine($"[GET] {binder.Name}");
        var prop = _inner.GetType().GetProperty(binder.Name);
        result = prop?.GetValue(_inner);
        return prop is not null;
    }

    // Вызывается при установке свойства
    public override bool TrySetMember(SetMemberBinder binder, object? value)
    {
        Console.WriteLine($"[SET] {binder.Name} = {value}");
        var prop = _inner.GetType().GetProperty(binder.Name);
        prop?.SetValue(_inner, value);
        return prop is not null;
    }

    // Вызывается при вызове метода
    public override bool TryInvokeMember(
        InvokeMemberBinder binder, object?[]? args, out object? result)
    {
        Console.WriteLine($"[CALL] {binder.Name}({string.Join(", ", args ?? [])})");
        var method = _inner.GetType().GetMethod(binder.Name);
        result = method?.Invoke(_inner, args);
        return method is not null;
    }
}

// Использование:
dynamic proxy = new LoggingProxy(userService);
var task = proxy.FindUserByUsernameAsync("alice");
// [CALL] FindUserByUsernameAsync(alice)

14.5 Подводные камни dynamic

RuntimeBinderException вместо compile-time ошибки. Компилятор не проверяет обращения к dynamic — ошибки типизации обнаруживаются только в runtime. Это главная причина не использовать dynamic без необходимости.

// ОПАСНО — ошибка только в runtime:
dynamic d = GetSomeObject(); // возвращает разные типы в зависимости от условий
var result = d.NonExistentMethod(); // RuntimeBinderException в runtime!

// ОПАСНО — dynamic отключает intellisense и рефакторинг:
dynamic user = userFromDb;
user.Usernam = "alice"; // опечатка — компилятор молчит, ошибка в runtime

// ЛУЧШЕ — явный каст:
var user = (User)userFromDb;
user.Username = "alice"; // compile-time проверка

// ЛУЧШЕ — использовать object с pattern matching:
object raw = GetValue();
if (raw is User u) { /* ... */ }
else if (raw is string s) { /* ... */ }

// Проблема с async/dynamic — нельзя await dynamic:
// await dUser.GetTask(); // не компилируется!
// Нужен явный каст:
Task t = (Task)dUser.GetTask();
await t;

// dynamic и DI — не работает:
// services.AddScoped<dynamic>(...); // бессмысленно
// DI работает через типы — dynamic тип не является реальным типом
Правило: В WebMessenger dynamic не используется и не нужен. Все типы известны на этапе компиляции. dynamic оправдан только при интеграции с COM-объектами, скриптинговыми языками или при парсинге данных без схемы. Во всех остальных случаях — обобщения, интерфейсы, pattern matching.

15. Диагностика и производительность

15.1 Stopwatch — точное измерение времени

Что это. System.Diagnostics.Stopwatch — высокоточный таймер, использующий аппаратные счётчики процессора. Точность — микросекунды. Используйте для предварительных измерений в коде и для логирования медленных операций.

Когда использовать. Быстрые замеры "в полевых условиях" — лог медленных запросов, проверка гипотезы о производительности. Для сравнения алгоритмов — BenchmarkDotNet (см. 15.2): Stopwatch не учитывает прогрев JIT, GC-паузы, variance.

// Базовое использование:
var sw = Stopwatch.StartNew();
var users = await _unitOfWork.Users.GetAllAsync();
sw.Stop();
_logger.LogDebug("GetAllAsync took {ElapsedMs} ms", sw.ElapsedMilliseconds);

// ValueStopwatch — struct, без аллокации на heap:
// (внутри ASP.NET Core используется именно он)
var start = Stopwatch.GetTimestamp();
DoWork();
var elapsed = Stopwatch.GetElapsedTime(start); // TimeSpan
Console.WriteLine(elapsed.TotalMicroseconds);

// Логирование медленных операций — паттерн из WebMessenger-стиля:
async Task<User?> FindUserWithDiagnostics(string username)
{
    var sw = Stopwatch.StartNew();
    try
    {
        var user = await _unitOfWork.Users
            .FindByConditionAsync(u => u.Username == username);
        return user.FirstOrDefault();
    }
    finally
    {
        if (sw.ElapsedMilliseconds > 100)
            _logger.LogWarning(
                "Slow query: FindUser({Username}) took {Ms} ms",
                username, sw.ElapsedMilliseconds);
    }
}

// Stopwatch.Frequency — тиков в секунду (зависит от железа):
Console.WriteLine($"Frequency: {Stopwatch.Frequency} Hz");  // напр. 10_000_000
Console.WriteLine($"IsHighRes: {Stopwatch.IsHighResolution}"); // true на x64

15.2 BenchmarkDotNet — микробенчмарки

Что это. Библиотека для корректного измерения производительности .NET кода. Автоматически учитывает: прогрев JIT (Warmup), GC-паузы, статистическую значимость (Multiple iterations), дисперсию (StdDev). Результат — Mean, StdDev, Min/Max, Allocated (байты).

Зачем нужна отдельная библиотека. Ручное измерение через Stopwatch в loop страдает: первая итерация JIT-компилирует код (аномально долго), GC может сработать случайно, CPU может throttle. BenchmarkDotNet устраняет все эти факторы.

16.1 Roslyn-анализаторы — что это и как работают

Что это. Roslyn-анализаторы — плагины компилятора, которые инспектируют синтаксическое дерево и семантическую модель вашего кода при каждой сборке. Выдают диагностики (ошибки, предупреждения, советы) прямо в IDE и в выводе компилятора. Категории встроенных анализаторов: надёжность (CA1000–CA1999), производительность (CA1800–CA1900), безопасность (CA2100–CA2199), дизайн (CA1000–CA1099), стиль (IDE0xxx). Каждый имеет ID, уровень серьёзности и документацию на docs.microsoft.com.

// Анализаторы работают без настройки — предупреждения видны в IDE
// Пример: CA1862 — используй StringComparison.OrdinalIgnoreCase

//       Причина: ToLower() аллоцирует новую строку + зависит от культуры

// Исправление согласно анализатору:

    => a.Equals(b, StringComparison.OrdinalIgnoreCase);

// Пример: CA2007 — ConfigureAwait(false) в библиотечном коде

17. Source Generators

17.1 Что такое Source Generators и зачем

Что это. Source Generators — компонент компилятора Roslyn, который запускается во время компиляции и добавляет новый C# код в проект. В отличие от T4-шаблонов или PostSharp, это не пост-обработка: генератор участвует в компиляции как равноправный участник.

Зачем. Устранить boilerplate который нельзя обобщить через generics — сериализаторы без Reflection, regex-автоматы, DI-регистрации, маппинг типов, реализации INotifyPropertyChanged. Результат: нулевые аллокации там где раньше был Reflection, AOT-совместимость, IDE видит сгенерированный код.

Два вида: Incremental Source Generators (современный API, .NET 6+) — эффективны, работают инкрементально (только при изменениях). Старый ISourceGenerator — устарел, не использовать в новом коде.

17.2 JsonSerializerContext — сериализация без Reflection

Что это. System.Text.Json Source Generator генерирует код сериализации/десериализации для ваших типов на этапе компиляции. Вместо Reflection в runtime — статически скомпилированные методы. Результат: быстрее, меньше аллокаций, AOT-совместимо.

// 1. Объявить контекст — атрибутами указываем какие типы генерировать:
[JsonSerializable(typeof(UserDto))]
[JsonSerializable(typeof(ChatMessageDto))]
[JsonSerializable(typeof(PagedResult<UserDto>))]
[JsonSerializable(typeof(List<UserDto>))]
[JsonSourceGenerationOptions(
    PropertyNamingPolicy = JsonKnownNamingPolicy.CamelCase,
    WriteIndented = false,
    DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull)]
public partial class AppJsonContext : JsonSerializerContext { }
// Компилятор сгенерирует AppJsonContext.UserDto, AppJsonContext.ChatMessageDto и т.д.

// 2. Регистрация в Program.cs:
builder.Services.ConfigureHttpJsonOptions(options =>
    options.SerializerOptions.TypeInfoResolverChain.Insert(0, AppJsonContext.Default));
// или добавить контекст напрямую:
builder.Services.AddControllers()
    .AddJsonOptions(o => o.JsonSerializerOptions.TypeInfoResolver = AppJsonContext.Default);

// 3. Сериализация через контекст — нет Reflection:
var json = JsonSerializer.Serialize(userDto, AppJsonContext.Default.UserDto);
var dto  = JsonSerializer.Deserialize(json,  AppJsonContext.Default.UserDto);

// 4. Без контекста (старый способ — Reflection в runtime):
var json2 = JsonSerializer.Serialize(userDto); // использует Reflection — медленнее

// Что генерирует компилятор (упрощённо):
// partial class AppJsonContext
// {
//     public static JsonTypeInfo<UserDto> UserDto => /* сгенерированный код */;
//     // Никакого GetProperty(), GetValue() — прямой доступ к полям через il
// }

17.3 GeneratedRegex — регулярные выражения без runtime-компиляции

Проблема. new Regex(...) компилирует паттерн в runtime при первом вызове (или при каждом — если не кэшируется). Regex.CompileToAssembly — устаревший тяжёлый механизм. Source Generator решает это элегантно.

// Атрибут [GeneratedRegex] — генерирует оптимальный автомат на этапе компиляции:
public partial class UserValidator
{
    // Паттерн для имени пользователя: только буквы, цифры, подчёркивание
    [GeneratedRegex(@"^[a-zA-Z0-9_]{3,50}$", RegexOptions.Compiled)]
    private static partial Regex UsernameRegex();

    // Email — упрощённая валидация
    [GeneratedRegex(@"^[^@\s]+@[^@\s]+\.[^@\s]+$", RegexOptions.IgnoreCase)]
    private static partial Regex EmailRegex();

    public bool IsValidUsername(string username)
        => UsernameRegex().IsMatch(username);

    public bool IsValidEmail(string email)
        => EmailRegex().IsMatch(email);
}
// Что генерируется: конечный автомат (DFA) в виде C# кода
// Нет: runtime-компиляции, Reflection, heap-аллокации паттерна
// Есть: полная поддержка отладки, IDE-навигация, AOT-совместимость

// БЫЛО (старый способ — не использовать):
private static readonly Regex _usernameRegex =
    new(@"^[a-zA-Z0-9_]{3,50}$", RegexOptions.Compiled);
// Проблемы: компилируется в runtime, аллоцирует при старте, не AOT-совместимо

17.5 Диагностики Source Generators

Что может пойти не так. Source Generators выдают диагностики как обычные компиляторные ошибки. Главные сценарии: тип не partial, неправильная сигнатура метода, тип не поддерживается генератором.

// SGXXXX — диагностики Source Generators:

// SYSLIB1045: метод не partial — [GeneratedRegex] требует partial:
[GeneratedRegex(@"^\d+$")]
private static Regex DigitsRegex() => ...; // ошибка: не partial
// Исправление: добавить partial к методу и к классу

// SYSLIB1037: тип не поддерживается JsonSerializerContext
// Пример: использование [JsonPolymorphic] с контекстом — требует явного указания типов
[JsonSerializable(typeof(BaseMessage))]  // нужно также перечислить все derived types:
[JsonSerializable(typeof(TextMessage))]
[JsonSerializable(typeof(ImageMessage))]
public partial class AppJsonContext : JsonSerializerContext { }

// SYSLIB0020: JsonSerializerOptions.IgnoreNullValues устарел
// Используйте DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull

// В .csproj:
// <RoslynAdditionalFilePaths>...</RoslynAdditionalFilePaths>
// Или в Visual Studio: Build → Generate → просмотр Output окна

// Форсировать пересборку генераторов (если IDE не подхватил изменения):
// dotnet build --no-incremental

17.6 Когда писать свой Source Generator

Когда оправдано. Вы пишете библиотеку/фреймворк. У вас повторяющийся boilerplate который нельзя устранить generics — например, реализация INotifyPropertyChanged для каждого свойства, автоматическое создание маппингов. Команда сознательно принимает сложность поддержки генератора.

Когда не нужно. В прикладном коде — почти никогда. Используйте существующие генераторы (JsonSerializerContext, GeneratedRegex, AutoMapper Source Gen, Mapster, CommunityToolkit.Mvvm). Написать генератор — нетривиально: отдельный проект, Roslyn API, инкрементальная модель, отладка через второй экземпляр IDE.

Что это. Паттерн для типизированного доступа к конфигурации. Вместо IConfiguration["Jwt:Key"] (строки, без валидации) — строго типизированный класс опций, автоматически заполняемый из конфигурации.

public class JwtOptions

18.4 Валидация опций и ValidateOnStart

Почему ValidateOnStart важен. Без него ошибка конфигурации (пустой JWT key, неверный connection string) обнаружится только при первом обращении к сервису — то есть при первом запросе пользователя после деплоя. С ValidateOnStart() приложение падает сразу при старте с понятным сообщением об ошибке.

// Кастомная валидация — IValidateOptions<T>:
public class JwtOptionsValidator : IValidateOptions<JwtOptions>
{
    public ValidateOptionsResult Validate(string? name, JwtOptions options)
    {
        // Проверки которые нельзя выразить через DataAnnotations:
        if (options.Key.Contains("changeme", StringComparison.OrdinalIgnoreCase))
            return ValidateOptionsResult.Fail(
                "Jwt:Key contains placeholder value 'changeme'. Set a real secret.");

        if (options.Issuer == options.Audience)
            return ValidateOptionsResult.Fail(
                "Jwt:Issuer and Jwt:Audience must be different.");

        return ValidateOptionsResult.Success;
    }
}

// Регистрация кастомного валидатора:
builder.Services.AddSingleton<IValidateOptions<JwtOptions>, JwtOptionsValidator>();
builder.Services
    .AddOptions<JwtOptions>()
    .BindConfiguration(JwtOptions.SectionName)
    .ValidateDataAnnotations()
    .ValidateOnStart(); // оба валидатора выполняются при старте

// FluentValidation-стиль через ValidateOptions (альтернатива):
builder.Services
    .AddOptions<JwtOptions>()
    .BindConfiguration(JwtOptions.SectionName)
    .Validate(opts =>
        opts.Key.Length >= 32,
        "Jwt:Key must be at least 32 characters")
    .ValidateOnStart();

18.5 Кастомный провайдер конфигурации

Когда нужен. Нестандартный источник настроек: база данных, внешний сервис конфигурации, шифрованный файл. Реализуется через IConfigurationSource + IConfigurationProvider.

// Минимальный кастомный провайдер — конфиг из БД:
public class DatabaseConfigurationProvider : ConfigurationProvider
{
    private readonly string _connectionString;

    public DatabaseConfigurationProvider(string connectionString)
        => _connectionString = connectionString;

    // Load вызывается при старте (и при Reload):
    public override void Load()
    {
        using var conn = new MySqlConnection(_connectionString);
        conn.Open();
        using var cmd = conn.CreateCommand();
        cmd.CommandText = "SELECT Key, Value FROM AppConfig WHERE IsActive = 1";
        using var reader = cmd.ExecuteReader();

        var data = new Dictionary<string, string?>(StringComparer.OrdinalIgnoreCase);
        while (reader.Read())
            data[reader.GetString(0)] = reader.GetString(1);

        Data = data; // базовый класс хранит данные в Data
    }
}

// Source — фабрика провайдера:
public class DatabaseConfigurationSource : IConfigurationSource
{
    public string ConnectionString { get; init; } = "";

    public IConfigurationProvider Build(IConfigurationBuilder builder)
        => new DatabaseConfigurationProvider(ConnectionString);
}

// Регистрация в Program.cs:
builder.Configuration.Add(new DatabaseConfigurationSource
{
    ConnectionString = builder.Configuration.GetConnectionString("DefaultConnection")!
});

18.6 IChangeToken — реакция на перезагрузку конфига

Что это. IChangeToken — механизм уведомления об изменении данных. Используется внутри IConfiguration для обнаружения изменений файла appsettings.json (через FileSystemWatcher).

// Реакция на изменение конфига через IOptionsMonitor.OnChange (самый простой способ):
public class DynamicRateLimitService : IHostedService
{
    private readonly IOptionsMonitor<RateLimitOptions> _monitor;
    private IDisposable? _changeSubscription;

    public DynamicRateLimitService(IOptionsMonitor<RateLimitOptions> monitor)
        => _monitor = monitor;

    public Task StartAsync(CancellationToken ct)
    {
        // OnChange возвращает IDisposable — обязательно хранить и Dispose при остановке
        _changeSubscription = _monitor.OnChange((opts, name) =>
        {
            Console.WriteLine($"Rate limit updated: {opts.RequestsPerSecond} req/s");
            UpdateLimits(opts);
        });
        return Task.CompletedTask;
    }

    public Task StopAsync(CancellationToken ct)
    {
        _changeSubscription?.Dispose(); // утечка памяти если не Dispose!
        return Task.CompletedTask;
    }
}

// Прямое использование IChangeToken — для кастомных источников:
IChangeToken changeToken = configuration.GetReloadToken();
changeToken.RegisterChangeCallback(_ =>
{
    Console.WriteLine("Configuration reloaded!");
}, state: null);

// Важно: reloadOnChange в AddJsonFile:
builder.Configuration.AddJsonFile(
    "appsettings.json",
    optional: false,
    reloadOnChange: true); // FileSystemWatcher наблюдает за файлом — true по умолчанию
В WebMessenger используется эталонный паттерн Options: JwtOptions и DropboxOptions с required/init свойствами, DataAnnotations для валидации, ValidateDataAnnotations().ValidateOnStart() — приложение не запустится с невалидной конфигурацией. Секреты в dev — User Secrets, в docker — переменные окружения через docker-compose.yml.

19.4 dotnet publish — параметры публикации

Framework-dependent vs Self-contained. Framework-dependent (по умолчанию) — маленький артефакт, требует установленного .NET на сервере. Self-contained — всё включено в артефакт, работает на чистой машине, но артефакт крупнее.

# Framework-dependent (FDD) — стандарт для Docker/managed hosting:
dotnet publish Server/WebMessenger.Api \
  -c Release \
  -o ./publish/fdd
# Размер: ~5–10 MB (только код приложения)
# Требует: dotnet runtime 8 на сервере/контейнере

# Self-contained (SCD) — для деплоя на сервер без .NET:
dotnet publish Server/WebMessenger.Api \
  -c Release \
  -r linux-x64 \         # Runtime Identifier (RID)
  --self-contained true \
  -o ./publish/scd
# Размер: ~80–150 MB (runtime + код)
# Требует: только glibc на Linux (libc6)

# RIDs — идентификаторы платформы:
# linux-x64   — Linux 64-bit (Ubuntu, Debian, CentOS)
# linux-arm64 — Linux ARM64 (Raspberry Pi 4, AWS Graviton)
# win-x64     — Windows 64-bit
# osx-x64     — macOS Intel
# osx-arm64   — macOS Apple Silicon

19.5 Single-file, Trim и ReadyToRun

Single-file. Упаковывает все DLL в один исполняемый файл. Удобно для CLI-утилит, не меняет производительность — DLL распаковываются в temp при запуске (или в память, если PublishSingleFile + bundled).

PublishTrimmed. Linker удаляет неиспользуемый код из BCL и зависимостей. Уменьшает размер артефакта. Опасно с Reflection — код который используется через Reflection может быть обрезан. Требует тестирования.

ReadyToRun (R2R). Предварительная компиляция IL в нативный код на этапе публикации. Ускоряет cold start (первый запуск), ценой увеличения размера артефакта на 20–40%.

<!-- WebMessenger.Api.csproj — оптимизации публикации: -->
<PropertyGroup>
  <!-- ReadyToRun — ускорить cold start для production: -->
  <PublishReadyToRun>true</PublishReadyToRun>
  <!-- Совместить с --self-contained или FDD на linux-x64 -->

  <!-- Single-file — один бинарник (полезно для CLI/standalone): -->
  <PublishSingleFile>true</PublishSingleFile>

  <!-- Trim — обрезать неиспользуемый код (ТОЛЬКО если нет динамического Reflection): -->
  <PublishTrimmed>true</PublishTrimmed>
  <!-- Trim + ASP.NET Core = безопасно (фреймворк trim-совместим с .NET 8) -->
  <!-- Trim + EF Core = осторожно: EF использует Reflection для маппинга -->
</PropertyGroup>
# Команда публикации для production Docker-образа (оптимальный баланс):
dotnet publish Server/WebMessenger.Api \
  -c Release \
  -r linux-x64 \
  --self-contained false \   # FDD — runtime в базовом образе
  -p:PublishReadyToRun=true \ # ускорить cold start
  -o ./publish
